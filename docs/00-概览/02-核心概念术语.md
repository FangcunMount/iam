# 02-核心概念术语

## 1. 本文定位

本文是 IAM 项目的核心术语表。

它不追求覆盖所有实现细节，而是统一项目文档和源码阅读中的基础语言，尤其用于避免以下混淆：

```text
User、Principal、Subject 混用
LoginIdentity、Credential、Challenge 混用
ProfileLink、Permission、RoleBinding 混用
ResourceKey、ResourcePattern、Scope 混用
IDP、AuthN、Identity 职责混用
container、application、domain、infra 分层混用
```

IAM 领域中，Authentication 通常回答“如何证明身份”，Authorization 通常回答“能访问什么资源”。外部 IAM 基础资料也普遍把 IAM 描述为同时管理身份验证与资源访问控制的体系。本文会采用这个通用边界，但以本项目当前源码和文档为最终事实源。

---

## 2. 术语分层

本文按以下层次组织术语：

```text
系统级术语
认证 AuthN 术语
授权 AuthZ 术语
身份 Identity 术语
外部身份源 IDP 术语
接入与契约术语
运行时与分层架构术语
基础设施术语
易混淆术语对照
```

这些术语不是孤立概念，而是围绕一条主线协作：

```text
外部请求
  -> AuthN 识别并证明调用主体
  -> Principal.UserID 指向 Identity.User
  -> Identity 维护 User/Profile/ProfileLink 身份事实
  -> AuthZ 将 User 映射为 Subject 并判断资源访问权
  -> REST/gRPC/SDK 对外提供接入
```

---

## 3. 系统级术语

### 3.1 IAM

IAM 是 Identity and Access Management，即身份与访问管理。

在本项目中，IAM 是一个面向业务系统接入的身份与访问管理服务。

它聚合以下能力：

```text
身份主体管理
登录认证
Session / Token / JWKS
资源授权
授权版本传播
Profile / ProfileLink 身份事实
第三方身份源适配
REST / gRPC / SDK 接入
```

IAM 不是单纯用户中心，也不是单纯登录系统，也不是 Casbin CRUD 管理后台。

---

### 3.2 Identity

广义上，Identity 表示数字身份。

在本项目中，`Identity` 特指 IAM 内部的身份事实模块。

它负责：

```text
User
Profile
ProfileLink
```

它不负责：

```text
密码校验
短信验证码校验
微信 code2session
Session 创建
Token 签发
资源权限判定
```

这些分别属于 AuthN、IDP、AuthZ 等模块。

---

### 3.3 Access

Access 表示访问能力。

在本项目中，一次访问通常可以描述为：

```text
某个 Subject
在某个 Tenant 下
对某个 Resource
执行某个 Action
并满足某个 Scope
```

也就是：

```text
Subject + Tenant + Resource + Action + Scope -> AuthorizationDecision
```

---

### 3.4 Authentication / AuthN

Authentication，简称 AuthN，表示认证。

它回答：

```text
你是谁？
你如何证明你是这个主体？
认证成功后系统如何表达你？
```

在本项目中，AuthN 围绕以下概念展开：

```text
LoginIdentity
Credential
Challenge
Principal
Session
Access Token
Refresh Token
JWKS
KeyRotation
```

---

### 3.5 Authorization / AuthZ

Authorization，简称 AuthZ，表示授权。

它回答：

```text
你能访问什么资源？
你能执行什么动作？
作用范围是什么？
```

在本项目中，AuthZ 围绕以下概念展开：

```text
Subject
Tenant
Role
Resource
Permission
Scope
RoleBinding
AuthorizationRequest
AuthorizationDecision
PolicyChange
PolicyVersion
Outbox
```

---

### 3.6 IDP

IDP 是 Identity Provider，即身份提供方。

在本项目中，IDP 主要表示外部身份源基础设施，例如：

```text
微信小程序
微信公众号
企业微信
```

IDP 提供外部身份源证明材料，但不直接决定 IAM 内部登录态。

正确边界是：

```text
IDP 负责外部身份源 API 与密钥材料；
AuthN 负责把外部身份源结果映射为 LoginIdentity、Principal、Session、Token；
Identity 负责 User/Profile/ProfileLink；
AuthZ 负责资源访问控制。
```

---

## 4. AuthN 认证术语

### 4.1 User

User 是 IAM 内部稳定身份主体。

它是跨 AuthN、Identity、AuthZ 串联的身份锚点。

在不同模块中的引用方式不同：

```text
AuthN: Principal.UserID 指向 User
Identity: User 是身份事实主体
AuthZ: User 可映射为 Subject user:<userID>
```

User 不是：

```text
登录凭据
微信 openid
OAuth subject
业务 Profile
AuthZ Role
JWT 本身
```

---

### 4.2 LoginIdentity

LoginIdentity 表示 User 绑定的登录身份。

它回答：

```text
系统可以通过什么登录标识找到这个 User？
```

典型例子：

```text
username + realm + username
phone + global + +E164
wechat_minip + appid + openid
wecom + corp_id + userid
```

LoginIdentity 不是 Credential。

它只表示“可用于定位 User 的登录标识”，不一定包含本地可校验的长期认证材料。

例如微信登录身份通常有 LoginIdentity，但没有本地 Credential。

---

### 4.3 Credential

Credential 表示长期认证材料。

它回答：

```text
系统保存了什么长期材料来校验这个登录身份？
```

典型例子：

```text
password hash
passkey public key credential
TOTP encrypted secret
recovery code hash
```

Credential 的特点是：

```text
长期存在
可重复校验
有生命周期
属于认证材料
```

Credential 不等于短信验证码，也不等于微信 session_key。

---

### 4.4 Challenge

Challenge 表示短期认证挑战。

它回答：

```text
系统如何验证一次短期、可过期、可消费的证明？
```

典型例子：

```text
短信验证码登录
手机号绑定验证码
OAuth state
重置密码 code
```

Challenge 的特点是：

```text
短期有效
通常有 TTL
通常只能消费一次
通常按 scene 隔离用途
```

Challenge 不是 Credential。

例如短信验证码是 Challenge，不应该被建模为长期 Credential。

---

### 4.5 Principal

Principal 是认证成功后的运行时主体表达。

它回答：

```text
本次请求认证成功后，系统识别出的主体是谁？
通过哪个 LoginIdentity 认证？
使用了什么认证方式？
```

Principal 通常包含：

```text
UserID
LoginIdentityID
AuthMethod
SessionID
Claims context
```

Principal 不是 User 本身。

User 是身份事实，Principal 是一次认证结果的运行时表达。

---

### 4.6 Session

Session 是服务端认证上下文。

它表示：

```text
某个 Principal 在某个时间、设备、客户端上下文下形成的一段登录态。
```

Session 通常用于支持：

```text
注销
续期
撤销
在线 Verify
设备维度管理
风险控制
```

Session 不是 Access Token。

Access Token 可以是无状态 JWT；Session 是服务端可控的登录态锚点。

---

### 4.7 Access Token

Access Token 是短期访问凭证。

在本项目中，Access Token 当前以 JWT/JWS 方式表达。

它用于让调用方在后续请求中证明：

```text
我已经完成认证，并持有某个短期有效的访问凭证。
```

Access Token 的特点是：

```text
短期有效
适合放在 Authorization: Bearer 中传递
可被资源服务通过 JWKS 本地验签
必要时可通过 Online Verify 校验当前状态
```

Access Token 不是 Session，也不是 Principal 本身。

---

### 4.8 Refresh Token

Refresh Token 是用于换取新 Access Token 的续期凭证。

它通常比 Access Token 生命周期更长，但必须更强服务端可控。

它常用于：

```text
Access Token 过期后续期
Refresh Token 轮换
登出后撤销
异常风险后失效
```

Refresh Token 不应该被资源服务直接当作访问凭证使用。

---

### 4.9 JWT / JWS / JWK / JWKS

JWT 是 JSON Web Token，用于表达 claims。

JWS 是 JSON Web Signature，用于对 JWT claims 做签名保护。

JWK 是 JSON Web Key，用于表达密钥。

JWKS 是 JSON Web Key Set，用于发布一组公钥。

在本项目中：

```text
Token issuer 使用私钥签发 JWT/JWS；
JWKS endpoint 发布公钥；
资源服务通过 kid 找到公钥并本地验签；
在线 Verify 用于检查当前服务端状态。
```

JWKS 只能发布公钥，不应该发布私钥。

---

### 4.10 KeyRotation

KeyRotation 表示签名密钥轮换。

它解决的问题是：

```text
密钥不能长期不变；
新 Token 应使用 active key 签发；
旧 Token 在过渡期仍可用 grace key 验签；
过期密钥应 retired。
```

典型状态可以理解为：

```text
active
    -> grace
    -> retired
```

KeyRotation 是 Token 安全基础设施，不是业务身份模型。

---

## 5. AuthZ 授权术语

### 5.1 Subject

Subject 是授权主体。

它表示：

```text
谁在请求访问资源？
```

本项目当前支持的 Subject 类型可以包括：

```text
user
group
service
```

典型表达：

```text
user:<userID>
group:<groupID>
service:<serviceID>
```

Subject 不是 Principal，也不是 User 本身。

正确关系是：

```text
AuthN Principal.UserID
  -> Identity.User.ID
  -> AuthZ Subject user:<userID>
```

---

### 5.2 Tenant

Tenant 是授权域边界。

它回答：

```text
这条授权事实在哪个授权域内生效？
```

RoleBinding、Permission、PolicyVersion 等授权事实都需要落在 Tenant 边界内理解。

Tenant 不等于业务系统里的所有组织模型，但可以与业务组织、机构、租户等概念建立映射。

---

### 5.3 Role

Role 是权限聚合点。

它表示：

```text
一组 Permission 的业务命名集合。
```

例如：

```text
admin
operator
guardian
viewer
```

Role 不应该直接等同于 User 字段。

错误模型是：

```text
user.role == "admin"
```

正确模型是：

```text
Subject
  -> RoleBinding
  -> Role
  -> Permission
```

---

### 5.4 Resource

Resource 是受保护资源。

它表示：

```text
系统中需要被授权控制的资源类型、资源族或资源目录项。
```

在本项目中，Resource 是领域对象，不是 Casbin obj 字符串的简单别名。

Resource 通常包含：

```text
ResourceKey
DisplayName
AppName
Domain
Type
Actions
ScopeKinds
Description
```

Resource 的职责是作为授权资源目录，约束可授权的动作与 scope 类型。

---

### 5.5 ResourceKey

ResourceKey 是资源目录中的资源标识。

当前采用四段结构：

```text
<app>:<domain>:<type>:<name-or-pattern>
```

例如：

```text
qs:evaluation:report:*
iam:authz:role:*
iam:identity:profile:*
```

当前约束是：

```text
必须是四段；
每段不能为空；
不能包含未 trim 的空白；
作为 ResourceKey 时，前三段不允许 wildcard；
name 段可以表达资源族或目录项。
```

ResourceKey 表达资源类型或资源族，不建议把具体业务对象 ID 强行塞进 ResourceKey。

具体对象范围更适合进入 Scope。

---

### 5.6 ResourcePattern

ResourcePattern 表示授权事实或请求中的资源匹配模式。

它与 ResourceKey 使用同样的四段格式，但语义更偏“匹配”。

例如：

```text
qs:evaluation:report:*
iam:authz:role:admin
```

ResourceKey 更偏资源目录。

ResourcePattern 更偏授权匹配。

---

### 5.7 Action

Action 表示对资源执行的动作。

典型动作包括：

```text
read
create
update
delete
manage
check
```

Action 应该被资源目录约束。

也就是说，不是任何资源都天然支持任何动作。

---

### 5.8 ActionPattern

ActionPattern 表示动作匹配模式。

例如：

```text
read
write
manage
*
```

Action 是请求侧具体动作。

ActionPattern 是授权事实侧可匹配的动作表达。

---

### 5.9 Scope

Scope 表示权限作用范围。

它回答：

```text
这条权限对哪些对象范围有效？
```

常见 Scope 类型：

```text
all
origin:<id>
```

Scope 与 ResourceKey 的边界是：

```text
ResourceKey 表达资源类型或资源族；
Scope 表达对象范围、来源范围或上下文范围。
```

例如：

```text
ResourceKey: qs:evaluation:report:*
Action: read
Scope: origin:profile-123
```

比下面这种方式更清晰：

```text
ResourceKey: qs:evaluation:report:profile-123
```

---

### 5.10 Permission

Permission 是 Role 对 Resource / Action / Scope 的能力声明。

它通常包含：

```text
RoleName
TenantID
ResourcePattern
ActionPattern
Scope
```

Permission 不直接授予给 User。

正确关系是：

```text
Subject
  -> RoleBinding
  -> Role
  -> Permission
```

---

### 5.11 RoleBinding

RoleBinding 是 Subject 在 Tenant 下持有 Role 的授权事实。

它回答：

```text
哪个 Subject 在哪个 Tenant 下拥有哪个 Role？
```

RoleBinding 是 IAM 内部 application/domain 的标准术语。

不要在内部恢复 `assignment` 包。

---

### 5.12 Assignment

Assignment 是对外 wire term。

它主要出现在：

```text
REST API
gRPC proto
SDK public API
```

当前约定：

```text
assignment = REST / proto / SDK 对外术语
rolebinding = application / domain 内部术语
```

不要把 Assignment 和 RoleBinding 写成完全无差别概念。

它们可以表达相近业务含义，但属于不同层次的语言。

---

### 5.13 AuthorizationRequest

AuthorizationRequest 表示一次授权判定请求。

它通常包含：

```text
Subject
TenantID
ResourcePattern / ResourceKey
Action
ObjectScope
```

它是领域层理解的一次 Check 请求，不等同于 REST/gRPC DTO。

---

### 5.14 AuthorizationDecision

AuthorizationDecision 表示授权判定结果。

它回答：

```text
允许还是拒绝？
如果拒绝，原因是什么？
如果允许，匹配到了什么授权事实？
```

AuthorizationDecision 是业务语义结果，不是 HTTP status code。

transport 层可以根据 Decision 映射为协议响应。

---

### 5.15 Check

Check 是权威实时授权判定。

它回答：

```text
这次请求是否允许访问？
```

Check 通常用于：

```text
API 准入
服务间授权判断
资源操作前置校验
```

Check 不等于 Snapshot。

Check 用于安全准入，Snapshot 用于授权事实投影。

---

### 5.16 Snapshot

Snapshot 是授权事实快照。

它回答：

```text
某个 Subject 当前有哪些角色和权限？
```

Snapshot 可以用于：

```text
菜单展示
前端能力提示
SDK 缓存
管理界面
批量判断优化
```

Snapshot 不应该替代权威 Check。

---

### 5.17 PolicyChange

PolicyChange 是授权变更计划。

它表示：

```text
一次授权写入准备改变哪些管理记录、runtime facts、版本和事件？
```

授权写入不是简单 CRUD。

它应该先形成 PolicyChange，再由统一提交链路提交。

---

### 5.18 PolicyChangeCommitter

PolicyChangeCommitter 是授权变更统一提交器。

它负责把 PolicyChange 交给 AuthZ UoW 提交，确保以下内容的一致性：

```text
管理记录
运行时授权 facts
PolicyVersion
Outbox Event
RuntimeReload
```

PolicyChangeCommitter 是 AuthZ 写入链路的关键应用层组件。

---

### 5.19 PolicyVersion

PolicyVersion 是 Tenant 级授权事实版本。

它用于表示：

```text
某个 Tenant 下的授权事实已经发生变化。
```

典型用途：

```text
缓存失效
runtime reload
跨实例授权版本传播
下游系统感知授权变化
```

---

### 5.20 PolicyLinter

PolicyLinter 是授权事实治理工具。

它负责只读诊断授权事实，例如：

```text
孤儿权限
无效资源
无效动作
不支持的 scope kind
潜在过宽授权
```

PolicyLinter 不自动修复权限。

修复应通过未来的 Reconciler 或显式管理命令进入 PolicyChange / PolicyChangeCommitter 链路。

---

## 6. Identity 身份术语

### 6.1 Profile

Profile 是业务身份资料、业务档案或被服务对象。

它可以表示：

```text
本人资料
儿童档案
被测评者档案
业务服务对象
```

Profile 不是登录主体。

Profile 不保存认证凭据，也不直接承载 AuthZ Permission。

---

### 6.2 ProfileLink

ProfileLink 是 User 与 Profile 之间的身份关系事实。

它回答：

```text
哪个 User 和哪个 Profile 有关系？
是什么关系？
关系是否有效？
什么时候建立？
什么时候撤销？
```

ProfileLink 可以表达：

```text
self
owner
guardian
parent
viewer
operator
```

ProfileLink 不是 User 字段，也不是 Permission。

---

### 6.3 RelationType

RelationType 表示 User 与 Profile 的关系类型。

例如：

```text
self
guardian
parent
viewer
operator
```

RelationType 描述身份关系，不直接表示资源权限。

如果某个关系需要带来资源访问权，应通过 AuthZ 写入或 AuthZ Check 明确表达。

---

### 6.4 LinkStatus

LinkStatus 表示 ProfileLink 当前状态。

常见状态可以包括：

```text
active
revoked
pending
```

具体状态以当前代码和数据模型为准。

LinkStatus 用于表达关系生命周期，不用于替代 AuthZ Decision。

---

### 6.5 MyProfiles

MyProfiles 是当前认证用户视角下可见的 Profile 列表。

它是 application/transport 面向当前用户场景的查询能力，不等于无条件查询所有 Profile。

---

### 6.6 MyProfileLinks

MyProfileLinks 是当前认证用户视角下可见的 ProfileLink 列表。

它强调：

```text
当前用户视角
身份关系边界
查询 guard
```

它不等于授权系统中的 Permission 列表。

---

## 7. IDP 外部身份源术语

### 7.1 WeChat / WeCom

WeChat 表示微信身份源。

WeCom 表示企业微信身份源。

在本项目中，它们属于外部身份源，不是 IAM 内部 User 本身。

外部身份源结果需要被 AuthN 映射为 LoginIdentity。

---

### 7.2 ProviderIdentity

ProviderIdentity 表示外部身份源返回的身份结果。

例如：

```text
openid
unionid
corp_id + userid
```

ProviderIdentity 不等于 User。

正确关系是：

```text
ProviderIdentity
  -> LoginIdentity
  -> User
```

---

### 7.3 AppID / CorpID

AppID 表示微信应用标识。

CorpID 表示企业微信企业标识。

它们用于限定外部身份源命名空间。

同一个 openid 在不同 AppID 下不能简单视为同一登录身份。

---

### 7.4 AppSecret

AppSecret 是第三方应用密钥。

它属于敏感配置或密钥材料，应该被加密保存或通过 SecretVault 管理。

AppSecret 不是 Credential。

Credential 是 IAM 保存的用户长期认证材料；AppSecret 是 IAM 调用外部身份源 API 的应用级密钥。

---

### 7.5 session_key / access_token

微信 session_key、企业微信 access_token 等是外部身份源协议中的材料。

它们不等于 IAM 的 Access Token。

边界是：

```text
外部 session_key/access_token：用于调用或验证第三方身份源；
IAM Access Token：IAM 签发给调用方访问业务系统或 IAM API 的短期凭证。
```

---

## 8. 接入与契约术语

### 8.1 REST API

REST API 是 IAM 面向 Web、App、管理后台和普通 HTTP 客户端的接入方式。

REST 层负责：

```text
路由
DTO
参数校验
协议响应
错误码映射
```

REST 层不应该写领域规则，也不应该直接操作数据库。

---

### 8.2 gRPC API

gRPC API 是 IAM 面向可信服务间调用的接入方式。

它适合：

```text
在线 Verify
AuthZ Check
Identity 查询
服务间低延迟调用
```

gRPC service 不应该直接绕过 application 层访问 infra。

---

### 8.3 SDK

SDK 是 IAM 的接入产品层。

它负责封装 IAM 的 REST/gRPC 能力，降低业务服务接入成本。

SDK 不应该成为业务层。

SDK 的职责是：

```text
封装调用
统一错误处理
隐藏协议细节
提供稳定 public API
```

---

### 8.4 OpenAPI

OpenAPI 是 REST 契约事实源。

REST 路径、字段、schema、错误响应应以 OpenAPI 和对应测试为准。

`docs/` 只解释语义和设计取舍，不替代 OpenAPI。

---

### 8.5 Proto

Proto 是 gRPC 契约事实源。

service、message、RPC 方法应以 proto 和生成代码为准。

`docs/` 不应该复制完整 proto 字段清单。

---

## 9. 运行时与分层架构术语

### 9.1 process

process 是生命周期编排层。

它负责：

```text
启动阶段编排
资源准备
后台任务管理
优雅关闭
降级启动
健康诊断
```

process 不负责业务模型。

---

### 9.2 container

container 是组合根。

它负责：

```text
装配 application service
绑定 repository adapter
组装 token/cache/idp/casbin/outbox adapter
生成 REST/gRPC typed deps
提供 runtime tasks
```

container 不应该处理请求，也不应该写业务规则。

---

### 9.3 transport

transport 是协议适配层。

它包括：

```text
REST handler
gRPC service
DTO / proto mapping
错误响应转换
```

transport 的职责是协议转换，不是业务决策。

---

### 9.4 application

application 是用例编排层。

它负责：

```text
Command / Query
Use Case orchestration
事务边界
端口调用
结果组装
```

application 可以调用 domain，也可以依赖 infra adapter 提供的 port 实现。

但 application 不应该泄露 HTTP/gRPC DTO，也不应该写底层 SQL 细节。

---

### 9.5 domain

domain 是领域规则层。

它负责：

```text
Entity
Value Object
Domain Service
Policy
不变量
领域错误
```

domain 不应该依赖：

```text
MySQL
Redis
HTTP
gRPC
Casbin technical API
```

---

### 9.6 infra

infra 是基础设施适配层。

它负责：

```text
MySQL repository
Redis cache/store
JWT signer/verifier
Casbin runtime adapter
IDP API adapter
Outbox repository/relay
SMS adapter
```

infra 可以理解技术细节，但不应该反向污染 domain 语言。

---

### 9.7 port / adapter

port 是 application/domain 期望的能力接口。

adapter 是 infra 对 port 的具体实现。

例如：

```text
TokenSigner port -> JWT adapter
RoleRepository port -> MySQL repository adapter
DecisionEngine port -> Casbin runtime adapter
IDPClient port -> WeChat/WeCom adapter
```

这个模式用于隔离业务核心和外部技术实现。

---

### 9.8 Unit of Work / UoW

Unit of Work 表示一组需要在同一事务边界内提交的操作。

在 IAM 中，UoW 常用于：

```text
AuthN onboarding 创建 User + LoginIdentity + optional Credential
AuthZ 写入管理记录 + runtime facts + PolicyVersion + Outbox Event
Identity 写入 User/Profile/ProfileLink 关系
```

UoW 是 application 层控制事务边界的重要工具。

---

### 9.9 Transactional Outbox

Transactional Outbox 是业务事实和事件记录同事务提交的模式。

它解决：

```text
数据库写入成功，但消息发布失败
消息发布成功，但数据库事务回滚
```

在 IAM 中，AuthZ PolicyVersion 变化可以通过 Outbox 传播。

Outbox 通常是 at-least-once 语义，下游 consumer 必须幂等。

---

## 10. 基础设施术语

### 10.1 MySQL

MySQL 是主要管理事实持久化存储。

它可以保存：

```text
User
LoginIdentity
Credential
Role
Resource
RoleBinding
PolicyVersion
JWKS keys
IDP app config
Outbox records
```

具体表结构以 migration 为准。

---

### 10.2 Redis

Redis 是运行时状态和缓存设施。

它可以用于：

```text
Challenge
Session
Refresh Token
缓存
限流
临时状态
```

具体使用以当前 infra/cache、infra/token、infra/session 等代码为准。

---

### 10.3 Casbin

Casbin 是 AuthZ 的 runtime policy engine。

它负责根据 p/g facts 和 matcher 完成授权判定。

Casbin 不是 IAM 的领域模型。

领域语言是：

```text
Subject
Role
Resource
Permission
RoleBinding
Scope
AuthorizationRequest
AuthorizationDecision
PolicyChange
```

Casbin 技术语言是：

```text
p
g
sub
dom
obj
act
matcher
```

这些技术语言应被限制在 infra/casbin 和相关事实存储边界内。

---

### 10.4 Authorization Facts

Authorization Facts 表示运行时授权事实。

在 Casbin 语境中通常表现为：

```text
p fact：Permission 映射
g fact：RoleBinding 映射
```

Authorization Facts 是 runtime 表达，不是对外业务契约。

---

### 10.5 RuntimeReload

RuntimeReload 表示运行时授权策略刷新。

当授权事实发生变化后，需要让运行时判定引擎感知新版本。

RuntimeReload 通常与以下概念协作：

```text
PolicyChange
PolicyVersion
Outbox Event
Casbin runtime adapter
```

---

## 11. 易混淆术语对照

| 容易混淆 | 正确边界 |
| --- | --- |
| User vs Principal | User 是 Identity 的稳定身份主体；Principal 是 AuthN 认证成功后的运行时主体表达 |
| User vs Subject | User 是身份事实；Subject 是 AuthZ 的授权主体引用 |
| Principal vs Subject | Principal 来自认证结果；Subject 用于授权判定 |
| LoginIdentity vs Credential | LoginIdentity 解决“通过什么标识找到 User”；Credential 解决“用什么长期材料证明控制权” |
| Credential vs Challenge | Credential 是长期认证材料；Challenge 是短期、可过期、可消费的认证挑战 |
| Challenge vs SMS Code | SMS Code 是一种 Challenge secret，不等于 Challenge 领域对象本身 |
| Access Token vs Session | Access Token 是短期访问凭证；Session 是服务端认证上下文 |
| Access Token vs Refresh Token | Access Token 用于访问；Refresh Token 用于续期 |
| JWT vs Principal | JWT 是 claims 的安全表达；Principal 是认证成功后的运行时主体 |
| JWKS vs KeyStore | JWKS 发布公钥；KeyStore 管理签名密钥材料 |
| Profile vs User | User 是稳定身份主体；Profile 是业务身份资料或业务档案 |
| ProfileLink vs Permission | ProfileLink 是身份关系；Permission 是资源访问能力 |
| ProfileLink vs RoleBinding | ProfileLink 连接 User 与 Profile；RoleBinding 连接 Subject 与 Role |
| Role vs Permission | Role 是权限聚合点；Permission 是资源/动作/范围能力声明 |
| RoleBinding vs Assignment | RoleBinding 是内部领域术语；Assignment 是 REST/proto/SDK 对外 wire term |
| ResourceKey vs ResourcePattern | ResourceKey 偏资源目录标识；ResourcePattern 偏授权匹配表达 |
| ResourceKey vs Scope | ResourceKey 表达资源类型或资源族；Scope 表达对象范围 |
| Action vs ActionPattern | Action 是请求侧具体动作；ActionPattern 是授权事实侧匹配表达 |
| Check vs Snapshot | Check 是权威实时判定；Snapshot 是授权事实投影 |
| PolicyChange vs CRUD | PolicyChange 是授权变更计划；CRUD 是简单数据操作模型 |
| PolicyLinter vs Reconciler | PolicyLinter 只读诊断；Reconciler 才可能执行修复 |
| Casbin vs AuthZ Domain | Casbin 是 infra runtime engine；AuthZ Domain 是业务授权模型 |
| container vs application | container 负责装配；application 负责用例编排 |
| transport vs application | transport 负责协议适配；application 负责业务用例 |
| infra vs domain | infra 负责技术适配；domain 负责领域不变量 |
| IDP vs AuthN | IDP 提供外部身份源证明；AuthN 决定如何认证并签发 IAM 登录态 |

---

## 12. 术语使用规则

### 12.1 文档中优先使用领域语言

写 AuthZ 文档时，优先使用：

```text
Subject
Role
Resource
Permission
RoleBinding
Scope
AuthorizationRequest
AuthorizationDecision
PolicyChange
```

不要在领域说明中直接使用：

```text
p
g
sub
dom
obj
act
```

这些属于 Casbin 技术语言。

---

### 12.2 不恢复旧 Account 中心模型

AuthN 文档中不要把业务账号作为核心领域对象。

优先使用：

```text
User
LoginIdentity
Credential
Challenge
Principal
Session
Token
```

---

### 12.3 不把 ProfileLink 写成权限

ProfileLink 是 Identity 关系事实。

资源访问能力必须进入：

```text
AuthZ Resource / Action / Scope / Check
```

---

### 12.4 不把 Assignment 写回内部模型

对外可以保留 Assignment 术语。

内部 application/domain 应统一使用 RoleBinding。

---

### 12.5 不把 ResourceKey 当作对象 ID 容器

ResourceKey 表达资源类型或资源族。

具体对象范围更适合通过 Scope 表达。

---

### 12.6 不把 docs 当作机器契约

字段、路径、RPC、SDK API 以以下事实源为准：

```text
api/rest
api/grpc
pkg/sdk
configs
migrations
```

`docs/` 负责解释语义、边界、架构和设计取舍。

---

## 13. 本文总结

IAM 的术语体系可以压缩成以下主线：

```text
AuthN 通过 LoginIdentity / Credential / Challenge 证明调用者身份，产出 Principal、Session、Token。
Identity 以 User 为稳定身份主体，维护 Profile 与 ProfileLink 身份事实。
AuthZ 将 User 映射为 Subject，通过 RoleBinding、Role、Permission、Resource、Action、Scope 完成授权判定。
IDP 提供外部身份源证明，但不直接决定 IAM 登录态。
REST/gRPC/SDK 是接入形态，不是业务模型本身。
process/container/transport/application/domain/infra 分别承担生命周期、装配、协议、用例、领域和基础设施职责。
```

如果只记一句话：

> User 是身份锚点，Principal 是认证结果，Subject 是授权主体；LoginIdentity 找人，Credential/Challenge 证明控制权，ProfileLink 表达身份关系，Permission 表达资源访问能力。
