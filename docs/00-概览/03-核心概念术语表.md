# 核心概念术语表：名称、来源与可证明的边界

> 状态：已实现 · 定义当前术语和同名字段的实际含义；生命周期、算法及失败处理由各模块主文维护。

## 1. 先辨认名字的所有者，再判断它能证明什么

一个字段叫Subject、Scope或Version，不代表它与另一个包的同名字段有相同语义。阅读代码、接口或日志时，先问：**由谁产生、在哪一阶段成立、保存在哪里、还缺哪一道检查**。本篇提供定义和反例，[模块协作](02-模块划分与协作关系.md)解释跨边界责任，[统一模型](06-跨模块统一模型.md)维护转换关系。

| 分类 | 当前代表 | 分类的实际用处 |
| --- | --- | --- |
| 长期身份/授权事实 | User、ProfileLink、Assignment、PermissionGrant | 确定修改规则和权威来源；已保存不等于本次认证成功 |
| 服务端在线状态 | Challenge、Session、RefreshToken及消费记录 | Redis也保存状态；签名JWT不能替代这些状态的当前检查 |
| 请求材料/声明 | IdentityProof、AccessTokenClaims | 结构合法不等于已验证来源；类型名不能提升信任 |
| 请求内结果 | ExternalIdentity、Principal、Admission/AuthZ Decision | 标明哪一阶段得出的结论；不能跳过后续阶段 |
| 派生投影/读取结果 | runtime Snapshot、SubjectSnapshot、JWKS、Suggest模型 | 标明源事实、过滤规则和时效；不是第二份主数据 |
| 值对象、策略、端口 | Subject.Ref、Assignment Scope、DisclosurePolicy、Verifier | 分别表达引用/约束、判断规则、可调用能力；都不按名字算聚合 |

“聚合根”表达它维护的不变量与写入边界，不等于“有Go struct”或“有数据库表”。核心模型图按Identity 3、AuthN 5、AuthZ 4个小聚合展示的是选定模型，不是IAM全部事实的总数；签名密钥、IDP事实及运行状态另有自己的合同。SignUp跨几个仓储使用同一应用事务，也不会把这些模型变成一个大聚合。下文以实际职责定义术语，不用聚合计数推断独立提交或独立部署。

## 2. 谁被识别：User、Profile、Principal和Subject

| 术语及所有者 | 当前含义 | 不能据此推出 |
| --- | --- | --- |
| Identity User | 内部稳定主体和生命周期事实，当前有active/inactive/blocked；密码和岗位不存于User | 已创建就能登录、是业务员工或具有某动作 |
| Identity Profile | 被管理的自然人档案，可与登录人不同 | 拥有账户、已完成外部认证或自动可搜索 |
| Identity ProfileLink | User与Profile的关系事实，有active/revoked生命周期；参与Identity自助关系门禁 | 是AuthZ岗位或自动生成Suggest可见ID |
| Identity UserStatusReader / UserResolver | 分别读取当前主体状态、校验稳定User锚点存在 | blocked无法Resolve、存在即active，或普通读取锁住生命周期 |
| AuthN Principal | 身份核验成功后的UserID、LoginIdentityID、AuthenticationContext | 已准入、Session已建立、Token已交付或拥有权限；当前Principal没有SessionID字段 |
| AuthZ Subject.Ref | user/group/service类型与非零数字ID的引用；如`user:17` | 主体存在、已认证或允许普通接口给group/service赋权；普通赋权参数当前只接受user |
| 传输ServiceIdentity / management actor | 前者来自证书身份解析，后者由可信adapter构造管理上下文 | RPC目标Subject中的人已认证，或当前服务天然有管理权；ACL还须实际启用/加载 |
| delegated actor、GrantedBy、ChangedBy | 特定入口接收的委派来源/审计声明；验证规则由该入口维护 | 该用户当前存在、有效或已通过用户管理动作验证 |

例如家长User17关联儿童Profile88：家长登录所得Principal指向17，儿童档案仍是88；若业务要判定家长动作，构造`user:17`，不能把Profile88直接当User。另一个mTLS服务替17调用Check时，服务caller与目标`user:17`又是两份输入。`service:123`虽可作为引用格式，并不等于证书中的服务名，也不表示公开Assignment用例支持它。

模型与基数归[Identity模型](../02-业务模块/01-Identity/01-领域模型-User-Profile-ProfileLink.md)，caller/actor准入归[gRPC授权与SDK](../02-业务模块/03-AuthZ/06-关键链路-gRPC服务间授权与SDK.md)。Phone等字段值对象约束格式；跨记录并发唯一性仍依赖数据库guard，不能由单值构造成功推出。

## 3. 什么被核验：入口、秘密、挑战与认证结果

| 术语及所有者 | 当前含义与载体 | 应怎样区分 |
| --- | --- | --- |
| AuthN LoginIdentity | MySQL中的provider+realm+identifier到User映射、验证与状态 | 决定从哪个入口找到User；禁用入口与停用User不同 |
| AuthN Credential | 独立的长期密码校验材料、启用/失败/锁定事实 | 与请求明文、一次性code和IDP AppSecret不同；哈希不是可逆加密 |
| AuthN Challenge（代码名AuthChallenge） | Redis中的短期scene/target、校验hash、payload和期限；没有Attempts/ConsumedAt字段，adapter另维护尝试/消费 | 存储的挑战状态与调用方提交的OTP/state不是同一个对象；一次性来自仓储条件消费 |
| AuthN IdentityProof | PasswordProof、PhoneOTPProof等核验输入，通过CredentialKind选择策略 | 叫Proof仍是待核验材料；有这个kind不要求同种长期Credential行，微信Proof构造不访问provider |
| AuthN AuthDecision / CredentialUpdate | 策略返回OK/拒绝原因、成功Principal及可选凭据记录意图 | Decision本身不保存记录、不创建Session；error与业务拒绝也不同 |
| AuthN AuthenticationContext | Method、Realm、AMR、AuthenticatedAt；描述此次核验事实 | Method是实际策略，AMR是对外手段表达；Kind/Method/AMR的字符串不能直接等同 |
| AuthN admission.Subject / admission.Decision | UserID/LoginIdentityID待准入引用，以及Outcome/Reason结果；无法评估的error与denied分开 | 与AuthZ Subject/Decision不同；准入处理身份状态及归属，不处理资源动作 |
| AuthN Session | Redis中的持续登录状态，持有认证上下文、业务快照和期限 | 不是Principal字段、实时角色集合或当前组织成员证明 |
| AuthN signin.Result | 完整登录应用用例的Principal与TokenPair等交付结果 | 是用例输出，不是持久化聚合或单个AuthDecision |

同一User的密码校验通过，可以产生Principal；随后User inactive导致Admission拒绝，仍没有完整登录结果。反过来，OTP已消费后建Session或签发失败，也不能把“没有收到Token”解释成“一次性证明仍可原样重用”。这里定义各阶段名，顺序、补偿和凭据记录细节归[AuthN模型](../02-业务模块/02-AuthN/01-领域模型与认证策略.md)、[Login](../02-业务模块/02-AuthN/04-关键链路-Login登录认证.md)。

## 4. Token、Claims、密钥和验证不是一个概念

| 术语 | 当前含义 | 成功或构造的边界 |
| --- | --- | --- |
| IAM AccessToken | 与User/LoginIdentity/Session关联的短期已签发访问凭证，当前为JWT | JWT完整性与当前认证状态、资源授权分别检查 |
| AccessTokenClaims | 签发输入/解码结果的声明对象，不含JWT Header/Signature；New先规范化再校验，Validate仅校验声明不变量 | 不是“已经验签”的类型，也不查Session或User；access要求sid、非零身份ID及sub等于UserID字符串 |
| IAM RefreshToken | Redis保存并单次轮换的续期资格与交付值，关联Session；另留ConsumedRefreshToken重放事实 | 不是业务bearer；历史冗余认证字段是兼容读取输入，新签发不写；恢复时间也不能冒充原始持久IssuedAt |
| UserTokenSet / TokenPair | 领域签发集合 / 应用交付DTO | 输出值与在线Refresh记录有不同职责，不是新的聚合 |
| JWS / JWT / JWK / JWKS | 签名封装 / 声明格式 / 单把密钥的JSON表示 / 验证公钥集合 | JWT不是加密的同义词；公钥集合不包含签名私钥，也不证明某bearer现在有效 |
| Signing Key与生命周期元数据 | 当前PEM材料和MySQL密钥元数据共同参与签发/验证公钥发布 | key状态、物理材料、公开缓存分别有恢复责任；不是IDP secret vault中的同一种材料 |
| InitialTokenIssuer / token.Verifier / token.Revoker | 应用初始颁发接口 / 领域验证与在线撤销能力；SDK verifier又是接入实现 | 所属层与调用链不同，不按有状态方法就算新的聚合；本地验证与在线验证不能称等价 |

这里有三种不同的“Subject”：AccessTokenClaims.Subject及JWT `sub`是UserID数字字符串，如`17`；AuthZ Subject是`user:17`；Admission的Subject是两个身份ID的结构。应按明示adapter转换，不能把一个字符串直接复制到另一合同。

本地SDK从Token提取OrgID，或验签通过，只支持各自的解析/密码学合同。IAM在线验证还读撤销/Session/当前User及LoginIdentity，但返回JWT claims并不重查业务组织成员资格。完整宿主身份字段校验和在线策略差异归[Session/Token/JWKS](../02-业务模块/02-AuthN/03-Session-Token与JWKS.md)；JOSE、算法与材料生命周期归[JWT与密钥专题](../06-专题设计/04-JWT-JWS-JWK-JWKS与密钥轮换.md)。

例如Claims字段形状与exp/nbf先后合法，仍可能相对当前时间已经过期；本地验签通过后，User也可能已停用。应写清“声明校验”“本地验证”或“在线认证状态验证”，避免统一称Token有效。

## 5. 授予什么：岗位、能力、配对范围和决策

| AuthZ术语 | 当前定义 | 容易误加的含义 |
| --- | --- | --- |
| Role / ManagementProtection | 全局稳定岗位名称、展示信息、管理保护；Grant通过RoleID关联 | Role字段里没有完整Grant集合；保护规则不自动产生动作或范围 |
| Resource | 资源目录及支持动作；资源键有当前四段语法 | 不是业务对象主表、属性schema或整个路由权限集合 |
| Action | 类型/构造器可表示具体动作及`*`；目录、Check、普通Grant只接受具体动作，可信system Grant另可通配 | 类型可构造不表示所有入口都接受；不支持任意正则/前缀动作 |
| Assignment | Subject直接持有Role的独立分配，可附Scope与授予来源 | 不持有Role继承闭包；受管集合来自服务准入，当前没有managed_by归属字段 |
| PermissionGrant | Role对资源模式/动作的无条件allow；可独立管理和撤销 | 不代表此人已持有Role；UNCONDITIONAL不代表所有业务对象/门店 |
| Assignment Scope（wire名DataScope） | 一个公司内的all_stores或非空stores；内部/协议字段仍为OrgID/org_id | 零值不授予范围；all_stores只限该公司，同公司才可合并，不校验现实门店归属 |
| AuthorizationRequest / Decision | Subject+Resource+Action输入，以及allow/deny和匹配解释；正常未匹配DENY与不可用error分开 | 当前不接受ObjectContext/旧tenant域；一个MatchedGrant不枚举全部范围贡献，ALLOW不是最终对象接受 |
| RoutePermissionChecker | 路由动作判定能力 | 不替业务系统过滤门店、检查关系/对象状态或建立登录态 |
| DirectRoles / EffectiveRoles | 直接Assignment去重后的角色索引 / 当前对外仍叫Effective的直接角色结果 | Effective字段名不证明继承；同一Role跨公司分配不止一条范围 |

例如同一个人通过岗位A得到`read`门店10，通过岗位B得到`retry`门店20。不能先把门店合成10+20，再凭拥有`read`就读门店20；Scope必须与贡献该资源动作的Assignment配对。无Scope的Assignment仍可能使Check ALLOW，却不贡献门店范围。具体模型、通配及配对规则归[AuthZ模型](../02-业务模块/03-AuthZ/01-领域模型设计.md)。

### 同叫Snapshot或PermissionEntry，保留的信息不同

| 名称/载体 | 保留的内容与过滤 | 不能替代 |
| --- | --- | --- |
| runtime Snapshot | 一次不可变发布的角色、Grant、目录、逐Assignment范围、版本与证明时间 | 数据库主事实、所有实例状态或跨调用共同版本 |
| SubjectSnapshot / gRPC Snapshot响应 | 一个Subject在一份快照内的应用过滤角色、PermissionEntry及可选完整assignment facts | Check完全等价展开；全局通配过滤有差异，AppName是投影参数而非caller应用准入 |
| 应用PermissionEntry | 资源/动作/Mode及仅贡献该能力的Scopes | 一个Subject全局门店集合 |
| AssignmentRoleFact / AssignmentScopeFact | 跨应用角色汇总 / 逐Assignment ID、Role及可选Scope | 汇总角色不能代替逐条范围；complete只指该份策略内读取，不代表实时业务/未来版本 |
| REST `/me` permissions | 额外可选展示读取，仅resource/action/mode | 没有Scope/PolicyVersion，不是完整范围合同；读取失败可发生在资料写入之后 |
| SDK GetScopedAuthorizationSnapshot | 同一Snapshot RPC结果后的字段与合同校验封装 | 不是新RPC、自动范围匹配器或能独立发现服务端遗漏的证明 |

读取细节归[授权快照](../02-业务模块/03-AuthZ/02-关键链路-授权判定与不可变快照.md)，传输与SDK映射归[gRPC授权与SDK](../02-业务模块/03-AuthZ/06-关键链路-gRPC服务间授权与SDK.md)。

## 6. Org、Realm、Issuer、时间和Version各自指什么？

| 同名或近似字段 | 来源与语义 | 不应进行的替换 |
| --- | --- | --- |
| Session BusinessContext / Token OrgID | 会话业务快照及其声明投影 | 不从旧数字tenant推导Org；不据此证明当前QS Operator/成员资格 |
| Assignment org_id / DataScope.OrgID | 当前授权合同中的公司ID | 不自动沿用Token组织声明；接入方仍校验真实company/store |
| Suggest Principal.OrgID / OrgIDs | 标准REST将JWT组织声明填入Principal.OrgID，当前不填OrgIDs；OrgIDs为内部多组织输入，非空时策略优先采用。候选模型OrgID默认来自Loader占位配置 | 不等于真实多组织隔离；不与Assignment Scope自动转换 |
| LoginIdentity/ExternalIdentity Realm | provider标识命名空间，影响身份定位与匹配 | 不是旧tenant授权分区或IAM JWT Issuer |
| IAM Issuer / provider来源 | 前者为IAM Token签发来源，后者为外部解析的信任链 | 外部结果不能凭字段名成为IAM签发Token |
| AuthenticatedAt / ExternalIdentity.VerifiedAt / LoginIdentity.VerifiedAt | 原始内部核验时间 / 外部请求级结果的本地时间 / 持久登录身份验证记录 | 刷新不是重新认证，恢复未知的零认证时间不提升为现在；后两者不能互换，非零VerifiedAt不证明provider来源、新鲜度上限或防重放 |
| Token IssuedAt / ExpiresAt / NotBefore | 本次凭证的颁发/到期/生效声明 | 不等于Session实际撤销时刻、岗位撤权传播时限；不同validator的边界判断以其主文为准 |
| PolicyVersion / Snapshot.version / target | 受治理授权事实的提交水位 / 本实例发布版本 / 已观察最高目标 | 不是所有表校验和；数字相同不证明事实相同、全部实例加载或恢复旧库安全 |
| loadedAt / verifiedAt / EvaluatedAt | 快照装配时间 / 充分覆盖目标时绑定该发布的读取或加载开始时间 / 决策求值时间 | 加载成功不必续期；fresh是入口证明预算，不终止已发出的在途结果 |
| scope_contract_version | gRPC配对范围格式版本；当前1表示每项permission携带自己的Scopes | 不是PolicyVersion、新鲜度或主体范围；要求范围的消费方拒绝旧0值 |
| UserVersion / 单行Version / PolicyVersion | 不同实体/任务/全局发布合同中的版本字段 | 不按名字推同一代次、自动递增或生命周期屏障 |

例如Token仍带OrgID1，而新Assignment Scope是公司2：两者没有自动共同修订。又如数据库版本变为42，本实例仍发布41但证明尚在预算内，target=42不等于loaded=42；这些字段应同时显示来源和状态，而不是笼统记“版本42已生效”。时序与恢复合同归[多实例收敛](../02-业务模块/03-AuthZ/04-关键链路-多实例策略收敛.md)、[一致性专题](../06-专题设计/02-事务缓存与事件一致性.md)。

## 7. 外部身份与派生搜索的名字，不能提升为权威主数据

| IDP / Suggest术语 | 实际所有者和用途 | 定义的边界 |
| --- | --- | --- |
| IDP WechatApp / Credentials | 外部应用配置及AppSecret等材料 | 与IAM User、AuthN用户密码Credential不同 |
| IDP AppToken | 调用provider API的凭据及缓存状态 | 不是用户IAM AccessToken，也不赋予业务权限 |
| IDP ExternalIdentity | 标准Resolver的请求级provider/realm/identifier/VerifiedAt结果；没有User/Session或raw secret | 构造/防御复制只保证形状；当前无持久化或transport投影，不自行验provider签名、请求关联或重放 |
| provider/global canonical | LoginIdentity存储中的单个匹配锚点 | 不是完整外部关联图，也不授权自动合并User；各用例匹配合同不同 |
| IDP SecretVault | 当前本地AES-GCM材料保护能力 | 不等同KMS、JWT私钥保管或已支持主密钥平滑rewrap |
| SuggestibleProfile | 内部最小派生模型；默认手机号取关联User，owner取created_by，Org可为占位 | 不是另一份Profile主数据，最小构造合法不证明候选资格/真实号码/当前可见性 |
| Suggest ProjectionChange | Full资料集合、Delta Upsert/Delete的物理投影协议 | 不是Identity业务事件或带提交版本/共同水位的回执 |
| visibility.Principal / AuthorizationFacts | 搜索调用上下文 / 全量与手机号布尔能力读取结果 | OperatorID标准REST取IAM UserID，不是已验证QS Operator；facts没有Scope、版本或持久授权所有权 |
| visibility.Scope | Suggest组合全量能力、组织、owner和服务端ProfileID的范围；普通条件OR | 与Assignment Scope不同；默认creator可见ID不展开ProfileLink，能力缺失不等于其他可见分支必为空 |
| queryprofile.ResultItem | 过滤、排序及按配置披露后的DTO | 非生产可关闭mask；不能统一称已脱敏，也不等于内部含原始号码模型 |
| CandidateBudget / Ranking / Disclosure | 过滤前召回预算配置 / 排序规则 / 敏感输出策略 | 不保证全局TopK；不是三个领域聚合 |

## 8. 记录成功时，必须给成功一个宾语

“验证成功”可能是证明核验、登录准入、Token验签、在线Valid或动作ALLOW；“发布成功”可能是SQL提交、Broker接收或本机快照替换。省略宾语会把多阶段合同混在一起。

| 状态或对象 | 能表达的成功 | 不能省略的后续证据 |
| --- | --- | --- |
| UoW / transaction carrier | 宿主事务协调 / context中携带的事务句柄 | 借用carrier不代表本用例已物理commit、所有库适配器都复用它；提交所有者另记 |
| Outbox / Broker confirm / consumer ACK | 同事务待发意图 / 传输接收 / 某消费者合同的接受 | Policy通知ACK不证明所有实例覆盖目标或业务对象执行成功 |
| SessionRevocation任务 | 独立的持久撤销意图与处理状态 | 不等于通用Outbox消息、当前User代次或已撤销所有新会话 |
| Module / 聚合 / 限界上下文 / 服务 | 代码责任 / 不变量边界 / 语言模型边界 / 部署单元 | 不能从目录名、聚合数或端口数量互相推定 |
| 已实现 / 门禁通过 / 当前runtime / 业务接受 | 源码事实 / 限定检查结果 / 已绑定环境观察 / 指定业务结果 | 文档状态或绿色检查不能代替后三层 |

当前没有RoleInheritance、条件集合或对象属性Check；遗留wire reserved、410 tombstone、迁移记录只表达兼容/退役边界。新概念要明确所有者、性质、字段来源、不变量及调用位置；对外沿用当前契约名称，历史名字只在有日期/版本的说明出现。流程和并发规则回链主文，避免术语表成为第二份实现规格。
