## 1. 本文回答

本文回答 4 个问题：

- 不同读者应该按什么顺序阅读 IAM 文档？
- 当文档、代码、契约、测试、历史材料互相冲突时，应该相信谁？
- 新文档重建过程中，如何避免 `_archive/` 历史事实回流？
- 后续维护文档时，如何判断一篇文档是否可以作为当前事实源？

本文是阅读导航和事实源裁决规则，不展开业务模块内部模型。业务模块细节见 [02-业务模块](../02-业务模块/README.md)。

## 2. 30 秒结论

IAM 文档的阅读顺序应遵循：

```text
先看全局定位；
再看模块协作；
再看核心术语；
再进入业务模块；
最后看专题设计和宣讲材料。
```

事实源优先级应遵循：

```text
源码与运行时行为
  > 机器可读契约与配置
  > 测试
  > 现行 docs
  > _archive 历史材料
```

`_archive/` 只能作为迁移素材或历史追溯，不能直接证明当前事实。

如果只记一句话：

> 阅读 IAM 文档要从 `00-概览` 建立心智模型，从 `02-业务模块` 获取当前事实；裁决事实时永远优先相信代码、契约和测试，不能用 archive 反向覆盖 active docs。

## 3. 事实源优先级

当文档、代码、契约、测试或历史材料冲突时，按下面顺序判断。

| 优先级 | 事实源 | 示例 | 使用规则 |
| --- | --- | --- | --- |
| 1 | 源码与运行时行为 | `internal/apiserver/domain`、`application`、`transport`、`container` | 最终事实来源 |
| 2 | 机器可读契约与配置 | OpenAPI、proto、配置、迁移 | 接口字段、RPC、配置、数据库事实优先看这里 |
| 3 | 测试 | 架构测试、契约测试、模块测试、SDK compile test | 用于证明边界、契约和行为被保护 |
| 4 | 现行 `docs/` | `00-概览` 到 `06-宣讲` | 解释层，必须服从代码、契约和测试 |
| 5 | `_archive/` | 重构前文档、旧专题、历史草稿 | 只能追溯和迁移参考，不能作为当前事实 |

具体规则：

```text
代码和文档冲突：相信代码，更新文档。
契约和文档冲突：相信 OpenAPI/proto/SDK，更新文档。
测试和文档冲突：先核对测试是否仍有效；若测试有效，更新文档。
active docs 和 archive 冲突：相信 active docs，但要回到代码/契约复核。
代码和契约冲突：视为实现或契约漂移，不能靠文档裁决。
```

## 5. `_archive/` 使用规则

`_archive/` 是历史材料，不是当前事实源。

允许使用：

```text
查找旧设计背景；
迁移旧图示；
参考旧表达；
追溯某个概念为什么出现；
寻找待核对的历史线索。
```

禁止使用：

```text
用 _archive 证明当前代码行为；
从 _archive 直接复制结论到 active docs；
把 _archive 的旧目录结构恢复为现行结构；
把 _archive 中的 Account、旧接口、旧模块边界写成当前事实；
在 active docs 正文中引用 _archive 来支撑当前事实。
```

从 `_archive/` 迁移内容时，必须执行：

```text
1. 找到对应当前代码、OpenAPI、proto、配置、迁移或测试；
2. 判断旧内容是否仍然成立；
3. 成立则改写为当前术语；
4. 不确定则标记为“待补证据”；
5. 未实现能力标记为“规划改造”。
```

## 11. 文档维护者阅读路径

文档维护者的目标是填充占位文档、迁移历史内容、保持 active docs 不漂移。

推荐路径：

```text
CONTRIBUTING-DOCS.md
  -> 00-概览/04-阅读路径与事实源优先级.md
  -> 目标目录 README.md
  -> 目标文件
  -> 对应源码 / 契约 / 测试
```

每次写文档前先判断：

```text
这篇文档属于哪个目录？
它应该写当前事实、设计取舍、接入说明，还是宣讲表达？
它引用的事实是否有代码、契约或测试支撑？
是否混入了 _archive 的旧结论？
是否把规划写成已实现？
```

文档维护者必须遵守 3 条硬规则：

```text
不从 _archive 直接搬结论；
不把未核对事实写成已实现；
不把宣讲表达写成事实源。
```

## 13. 事实裁决案例

### 13.1 文档说 Credential 支持 passkey，但代码只实现 password

裁决：

```text
相信代码。
当前事实只能写 password。
passkey 如果是演进方向，标记为“规划改造”。
```

---

### 13.2 archive 里还写 Account，active docs 写 LoginIdentity

裁决：

```text
相信 active docs，但要回到代码核对。
如果代码当前模型是 LoginIdentity，则禁止把 Account 写成当前核心模型。
Account 只能作为历史术语或旧模型说明。
```

---

### 13.3 宣讲材料说 Outbox 保证 exactly-once

裁决：

```text
这是错误表达。
Outbox 只能保证本地事务中业务事实和事件记录的一致性。
事件投递和消费仍需要重试、幂等、去重。
```

---

### 13.4 REST 文档字段和 OpenAPI 不一致

裁决：

```text
相信 OpenAPI。
更新 REST 文档。
必要时补充契约测试或 docs-hygiene 规则。
```

---

### 13.5 模块文档和架构测试冲突

裁决：

```text
先确认架构测试是否仍有效。
如果测试有效，文档更新。
如果测试过期，先修正测试或架构规则，再更新文档。
不能用文档绕过架构测试。
```

## 14. 文档状态标签

当代码和文档成熟度不一致时，使用统一标签。

| 标签 | 含义 | 使用场景 |
| --- | --- | --- |
| `已实现` | 已有代码、契约或测试证据支撑 | 当前稳定能力 |
| `待补证据` | 文档方向可能正确，但还没有完成事实核对 | 占位文件、迁移初稿、待核对表述 |
| `规划改造` | 后续演进方向，不能写成当前事实 | 未落地能力、未来设计 |

规则：

```text
占位文件默认是“待补证据”；
从 archive 迁移的正文默认是“待补证据”；
已落地后才能改为“已实现”；
未落地能力必须标记为“规划改造”；
一篇文档可以部分已实现、部分待补证据，但必须明确分层。
```

修改任何 active docs 前，先检查：

```text
是否属于当前 active docs 范围？
是否需要同步 README 链接？
是否使用了当前术语？

是否需要补充架构测试、契约测试或 docs-hygiene？
```

修改后至少检查：

```text

Mermaid 是否可读；
```

## 17. 本文总结

阅读 IAM 文档时，先按读者角色选择路径：

```text
新读者：00-概览；
后端开发：01-运行时 + 02-业务模块；
模块维护者：目标模块 README -> 领域模型 -> 关键链路 -> 代码索引；
接入方：03-接入与契约 + 机器契约；
文档维护者：CONTRIBUTING-DOCS + 本文 + 事实源；
面试宣讲：06-宣讲 + 05-专题设计 + 02-业务模块。
```

裁决事实时，永远遵守：

```text
源码与运行时行为
  > 机器可读契约与配置
  > 测试
  > 现行 docs
  > _archive 历史材料
```

`_archive/` 只能提供历史线索，不能证明当前事实。任何现行文档中的结论，都应该能够回到代码、契约、测试或当前业务模块事实层。
