# 启动、生命周期与组合根

> 状态：已实现 · 本文追踪 `main` 到模块能力暴露的完整链路，并解释为什么 process、container 和 transport 必须分工。

## 1. 入口只有一条主线

```text
cmd/apiserver/apiserver.go
  -> internal/apiserver.NewApp
  -> config.CreateConfigFromOptions
  -> process.Run
  -> createAPIServer
  -> PrepareRun
  -> preparedAPIServer.Run
```

`cmd` 只声明可执行程序和 Swagger 注解；`app.go` 负责命令/选项、日志和生成 typed Config；`process` 才拥有资源、后台任务、传输服务和 shutdown 的完整生命周期。

将这些职责放进一个 `main.go` 虽然看起来直接，但会让启动失败难分阶段测试、关闭顺序隐藏在 defer 中、业务模块互相 new 具体依赖。当前用明确阶段约束副作用发生顺序。

## 2. PrepareRun 是有顺序的状态机

`prepareRunner` 依次执行：

1. `prepare runtime`：把 server.mode 解析为唯一 RuntimeProfile；
2. `prepare resources`：MySQL、Redis、IDP encryption key、EventBus；
3. `initialize container`：按模块图创建 domain/application/infra；
4. `initialize transports`：创建 HTTP/gRPC server 并注册路由/服务；
5. `start runtime tasks`：key rotation、outbox relay、AuthZ policy sync；
6. `register shutdown callbacks`：组装反向释放顺序。

前一阶段输出作为后一阶段输入，失败时错误携带 stage 名称。它不是数据库事务：早期阶段已打开的资源在 Prepare 失败时如何释放，仍依赖对应组件和进程退出；因此新增阶段必须考虑失败清理，而不能只考虑成功路径。

## 3. Container 是 composition root

Container 的职责是选择具体实现并注入端口，不是执行用例：

```text
DB / Redis / EventBus / configuration
  -> repository / cache / provider adapter
  -> domain service
  -> application service
  -> module capabilities
  -> REST/gRPC/runtime dependency views
```

模块 bootstrap 顺序：

```text
event runtime -> IDP -> AuthN -> AuthZ -> Identity -> Suggest -> cache governance
```

顺序体现当前依赖：

- AuthN 消费 IDP provider 能力；
- Identity 消费 AuthN SessionRevoker 与 AuthZ RoleNameReader；
- Suggest 消费 AuthZ RouteAuthorization；
- Event runtime 先提供 outbox stager/publisher。

Container 用 `moduleGraph` 集中跨模块端口，而不是让模块 import 另一个模块的内部具体类型。`ApplicationCapabilities`、`RuntimeCapabilities`、REST/GRPC deps 是不同视图，防止 handler 获得 DB 或 shutdown collaborator 等过宽权限。

## 4. 为什么跨模块依赖通过 capability

以 Identity 为例，它需要“撤销某 User 的 Session”，并不需要知道 Session 存在 Redis String/ZSet；它依赖 `session.Revoker`。Suggest 需要判断 route permission，并不应操作 CasbinAdapter；它依赖 `RouteAuthorizationRuntime`。

这对应依赖倒置：高层业务依赖语义端口，组合根在最外层选择实现。好处不是为了多写接口，而是：

- 测试可以替换端口；
- 基础设施变化不穿透业务；
- 模块边界可以从构造参数审计；
- 降级时能明确哪个 capability 缺失。

接口如果只是机械复制一个具体类的全部方法，就没有形成边界；当前 capability 仍需持续保持最小化。

## 5. 模块失败怎样记录

Container 会尝试执行 bootstrap plan，记录每个模块的 `ModuleState` 和 failure reason。是否允许带失败继续，不由模块自己偷偷决定，而由 process 的 RuntimeProfile/critical-module validation 控制。

这一区分很重要：

- 初始化错误是事实；
- `ModuleState.Available=false` 是容器状态；
- 是否允许进程继续是运行模式策略；
- REST/gRPC 是否注册能力是传输层结果；
- readiness 是否接流量是运行态结论。

不能只看进程存在或端口监听就判断 IAM 可用。

## 6. HTTP 与 gRPC 并行运行

准备完成后，HTTP 与 gRPC 作为 `processruntime.RunGroup` 服务并行运行。任一 active service 返回错误，wrapper 先把错误送到 process 观察通道，再释放 group，避免底层 RunGroup 在多个短生命周期服务同时退出时随机吞掉真正错误。

这属于生命周期正确性，而不是业务重试：监听端口失败等进程级错误应使整个服务退出并由 supervisor 重启，不能只在 goroutine 里打日志继续。

## 7. 备选结构

| 结构 | 优点 | 代价 | 当前判断 |
| --- | --- | --- | --- |
| main 中直接 new 全部依赖 | 初期直观 | 难测试、难关闭、边界混乱 | 不采用 |
| 全局 service locator | 调用方便 | 隐式依赖、运行期才失败 | 不采用 |
| 编译期 DI 生成 | 大图可自动生成 | 工具链和生成代码成本 | 可选但非必需 |
| 当前显式 composition root | 依赖可读、分阶段可测 | 手工 wiring 较多 | 当前选择 |

## 8. 面试追问

### composition root 为什么应靠近进程边界？

只有最外层知道配置、环境和具体 infra，领域与应用层不应选择 MySQL/Redis/Casbin 实现。把选择集中到 root 能维持依赖方向。

### 启动顺序算业务逻辑吗？

它是运行时不变量：依赖 provider 必须先于 consumer，可服务状态必须晚于注册完成。它不属于领域用例，但同样需要测试和文档。

### 为什么后台任务也要由 process 启动？

因为它们需要统一取消、健康观测和关闭顺序。模块构造函数偷偷启动 goroutine 会造成泄漏、测试不确定和 shutdown 竞态。
