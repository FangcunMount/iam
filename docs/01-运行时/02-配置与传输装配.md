# 配置、运行模式与传输装配

> 状态：已实现 · 本文解释配置怎样成为运行决策，以及 TLS、服务身份、ACL、AuthN、AuthZ 各自保护哪一层。

## 1. 配置是运行输入，不是事实源替代品

命令框架把配置文件与 flags 填入 `options.Options`，`config.CreateConfigFromOptions` 再生成进程使用的 `Config`。
模块最终只接收 `RuntimeOptions` 中与自己有关的 typed 子集。

应区分：

- config：端口、TTL、开关、依赖地址和安全模式；
- database/domain：User、Role、Permission、WechatApp 等业务事实；
- runtime state：模块是否初始化、缓存加载版本、健康状态。

把角色或用户关系写进 YAML 会绕过事务和审计；把纯运行参数写数据库又会引入启动依赖。当前边界总体遵循这一原则。

## 2. 唯一 RuntimeProfile

`server.mode` 只允许：

| mode | environment | production-like |
| --- | --- | --- |
| `debug` | development | false |
| `test` | test | false |
| `release` | production | true |

非法值直接失败，不猜测环境。所有下游模块共享解析后的 Environment，避免某处以 `release` 判断、另一处以自定义 `prod` 判断而产生安全开关分裂。

`allow-degraded-startup` 只有被显式请求且不是 production 时才生效。release 即使配置 true 也不允许降级启动，这是硬门禁。

## 3. 资源与 critical module 门禁

非降级模式下，以下资源失败会阻止 Prepare：MySQL 初始化/获取、Redis、IDP encryption key、Container 初始化和 critical module validation。

EventBus 创建失败目前只记录 warning 并继续，因为基础请求仍可运行；但 durable outbox relay 与 AuthZ 多实例同步会受影响，readiness/告警必须能暴露这类能力缺失。
不能从“进程启动成功”推导事件链健康。

开发降级模式允许空资源进入 Container，模块各自失败并记录 ModuleState；transport 只注册真正可用的能力。它用于诊断，不是可承诺的生产服务形态。

## 4. REST 注册是 capability-driven

REST Router 先注册基础路由，再根据 ModuleState 与能力构造模块路由：

- AuthN `token.Verifier` 能力可用才创建 JWT middleware；
- protected/admin routes 缺少认证/角色保护时不注册，按安全方向关闭；
- Suggest 需要 AuthRequired，并在可用时叠加 profile collection permission；
- debug cache governance 受 environment 和 admin protection 门禁；
- internal seed mock route：生产默认开启，但必须注入 shared secret 才会注册；关闭时不注册。

Handler 的职责是参数/DTO/错误映射，不能直接访问 repository。OpenAPI 是对外机器契约，路由矩阵测试验证已注册 public route 有契约覆盖。

## 5. gRPC 注册与安全分层

gRPC Registry 按模块收集 Registration，注册完成后才把服务标记 SERVING。Suggest 当前没有 gRPC registration。

网络与身份保护分四层：

1. TLS：加密传输、验证服务端；
2. mTLS：额外验证客户端证书 CN/OU/SAN；
3. application auth：Bearer/HMAC/API key，建立调用方服务身份；
4. ACL/业务 AuthZ：限制某身份可调用哪些 RPC 或改变哪些授权事实。

这些层不能互相替代。mTLS 证明持有某 CA 签发证书，不自动证明其有权 BindRole；Bearer 验证也不能替代传输加密。`RequireIdentityMatch` 可要求证书身份与应用凭据身份一致，降低凭据转移使用。

## 6. Insecure 的计算方式

最终 `grpcConfig.Insecure` 只有同时满足以下条件才为 true：

```text
配置 insecure=true
AND mTLS disabled
AND 无 TLS cert/key
```

只要启用 mTLS 或提供证书，process 就不会保持 insecure。生产配置仍需要运维检查证书文件、CA、allowed identities、ACL default deny 和反射服务暴露范围，不能只检查一个 boolean。

当前通用 gRPC config 默认 reflection = true、insecure = true；它是库默认值，不是生产安全基线。生产事实必须以 `configs/apiserver.prod.yaml`、
部署 Secret/文件和进程启动日志共同验证。

## 7. 契约、实现和注册是三个证据面

一个 proto service 存在不等于 runtime 已注册；一个 handler 存在也不等于 OpenAPI 已声明。变更传输能力时至少检查：

```text
REST: OpenAPI path/schema -> Router registration -> handler -> application capability -> tests
gRPC: proto service/method -> generated contract -> Registry registration -> service implementation -> tests
SDK: public method/path -> server contract -> caller/migration tests
```

这也是为什么 Suggest 明确只能称 REST-only：代码没有 Suggest proto、registration 或 SDK。

## 8. 秘密配置

IDP master key、DB/Redis 密码、TLS private key、HMAC/API key 不能写入可提交配置或普通日志。配置结构可以声明路径/引用，真实值应由部署 Secret、
环境文件或 secret manager 注入，并限制文件权限。

配置打印必须使用 allow-list 或 redaction；不能把整个 Options 结构 `%+v` 输出。安全日志细节见后续工程与运维文档。

## 9. 面试追问

### feature flag 与 degraded startup 有什么区别？

feature flag 是预期的能力启停，例如 Suggest enable=false；degraded startup 是依赖故障下的异常运行形态，必须显式、可观测且生产受限。

### mTLS 有了为什么还需要 ACL？

mTLS 解决“连接来自哪个证书身份”，ACL/AuthZ 解决“这个身份能调用什么”。可信员工证书不代表可以调用所有管理 RPC。

### 为什么路由缺 middleware 时选择不注册？

注册后再寄希望 handler 自行检查容易漏保护。对于 admin/protected route，缺安全依赖时从路由表消失是更可靠的 fail-closed。
