# 健康检查、Readiness 与降级启动

> 状态：已实现 · 与 REST router、container readiness、gRPC health、关闭序列和部署检查核对。

## 1. 结论

IAM 明确区分三个端点：

| 入口 | 语义 | 失败状态 | 用途 |
| --- | --- | --- | --- |
| `/healthz` | 进程与 HTTP listener 存活；不访问 MySQL/Redis | 非 `200` | Docker liveness，可触发重启 |
| `/readyz` | 当前实例是否可接收流量 | `503` | 负载均衡、部署 smoke、人工检查 |
| `/health` | 脱敏兼容汇总 | 始终 `200` | 人工概览，不作为部署探针 |

`/readyz` 只返回稳定状态 `ok/degraded/failed/skipped`，不返回底层错误、地址、SQL、Redis key、PEM 路径或配置值。

## 2. Readiness 组件矩阵

组件检查并发执行，单组件默认超时 `500ms`，总超时 `2s`：

| 组件 | 条件 | 硬依赖 |
| --- | --- | --- |
| `mysql` | Ping 成功 | 是 |
| `redis` | Ping 成功 | 是 |
| `authn` | container 已初始化且 TokenService 可用 | 是 |
| `jwks` | 存在 application 可读取的 active key | 是 |
| `authz` | runtime 已加载且 reload health 正常 | 是 |
| `suggest` | 模块按配置初始化成功 | 仅 `suggest.required=true` |
| `session_revocation` | 最老未完成本地安全 Outbox 未超过默认 `5m` | 是 |

可选 Suggest 失败显示 `degraded`，但不把整体切为 not-ready；硬依赖失败或超时使整体返回 `503/not_ready`。Readiness 不主动调用微信、短信等外部 provider。

示例：

```json
{
  "status": "ready",
  "components": {
    "mysql": {"status": "ok"},
    "redis": {"status": "ok"},
    "authn": {"status": "ok"},
    "jwks": {"status": "ok"},
    "authz": {"status": "ok"},
    "suggest": {"status": "ok"},
    "session_revocation": {"status": "ok"}
  },
  "checked_at": "2026-07-24T15:00:00Z"
}
```

## 3. 优雅摘流

收到关闭信号后固定顺序：

```text
MarkDraining
  -> /readyz 立即 503
  -> gRPC overall health = NOT_SERVING
  -> 等待 drain_delay（生产 5s，开发 0s）
  -> 停止后台任务
  -> cleanup Suggest / Identity worker
  -> 关闭数据库
  -> 关闭 HTTP / gRPC listener
```

`drain_delay` 只是给负载均衡传播摘流状态的窗口，不是业务补偿机制。

## 4. 降级启动

进程级降级由 `server.allow-degraded-startup` 请求，并受运行模式约束：

| `server.mode` | 是否可启用 |
| --- | --- |
| `debug` | 可以 |
| `test` | 可以 |
| `release` | 禁止 |

降级启动不等于 ready。即使开发/测试允许进程继续启动，缺少硬依赖时 `/readyz` 仍返回 `503`。

## 5. 部署探针

- Docker `HEALTHCHECK` 保持 `/healthz`，避免依赖短暂故障触发容器重启。
- 负载均衡、部署验证和 smoke 使用 `/readyz`。
- `server-check` 中 `/healthz` 失败是 liveness 故障；`/readyz` 失败只告警并输出稳定组件状态，不自动重启。
- gRPC 独立健康端口继续兼容；draining 时整体状态切到 `NOT_SERVING`。

## 6. 配置

```yaml
health:
  readiness:
    component_timeout: 500ms
    total_timeout: 2s
    outbox_max_pending_age: 5m
    drain_delay: 5s
```

对应环境变量使用 `IAM_APISERVER_HEALTH_READINESS_*`。单组件超时必须小于总超时。

## 7. 指标

- `iam_readiness_component_status{component}`：组件为 `ok` 时为 `1`，其他稳定状态为 `0`。
- `iam_readiness_checks_total{result}`：readiness 的 `ready/not_ready` 结果计数。
- `iam_identity_session_revocation_tasks{status}`：本地安全 Outbox 各持久化状态的任务数。
- `iam_identity_session_revocation_oldest_seconds`：最老未完成撤销任务年龄。

安全边界还提供 `iam_authz_http_authorization_total`、
`iam_grpc_assignment_authorization_total`、`iam_authn_otp_verification_total` 和
`iam_suggest_refresh_total`。标签不得包含用户 ID、手机号、role binding ID、token、
OTP 或其他请求值。
