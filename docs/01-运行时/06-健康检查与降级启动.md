# 健康检查与降级启动

> 状态：已实现 · 当前行为已与 REST router、gRPC server、Suggest module、关闭序列及相关测试核对；未实现的探针分层单独列在“规划改造”。

## 1. 当前结论

IAM 当前没有完整的 liveness、readiness、degraded 三态模型。

现有能力由四类入口组成：

| 入口 | 当前行为 | 是否检查依赖 |
| --- | --- | --- |
| REST `/healthz` | 配置开启后返回 `200` 和 `status=ok` | 否 |
| REST `/health` | AuthN 未启用或 AuthZ runtime reload 不健康时返回 `503/degraded`，否则 `200/healthy` | 只检查有限的 AuthN/AuthZ 状态 |
| `/api/v2/authz/health`、`/api/v2/idp/health` | 返回模块静态 `ok` | 否 |
| gRPC health HTTP 端口 `/healthz` | 独立端口；gRPC health service 为 `SERVING` 时返回 `200` | 检查 gRPC health service 状态 |

因此，当前 `/health = 200` 不能证明 MySQL、Redis、IDP provider、Suggest 索引和所有后台任务都健康。

## 2. REST 健康入口

### 2.1 `/healthz`

通用 HTTP server 在 `server.healthz` 开启时注册 `/healthz`：

```json
{"status":"ok"}
```

这个端点只证明 HTTP 进程能够响应，适合作为轻量存活探针。它不调用数据库、缓存或业务模块。

事实源：

- `internal/pkg/server/genericapiserver.go`
- `internal/pkg/options/server_run_options.go`

### 2.2 `/health`

主 REST router 始终注册 `/health`。当前判断逻辑是：

```text
AuthN enabled && AuthZ runtime reload healthy
  -> 200, status=healthy
otherwise
  -> 503, status=degraded
```

响应还包含 AuthZ 最近一次 reload 时间、错误和 runtime details。这里的 `last_error` 来自内部错误文本，扩展内容前要评估是否适合暴露给未认证调用方。

该端点当前没有调用 `Container.HealthCheck`，也没有检查 MySQL、Redis、Suggest、IDP 或 Outbox relay。

事实源：

- `internal/apiserver/transport/rest/base_routes.go`
- `internal/apiserver/transport/rest/health_routes.go`
- `internal/apiserver/transport/rest/router_test.go`

### 2.3 模块 health 路由

AuthZ 和 IDP 分别注册模块 health 路由：

```text
GET /api/v2/authz/health
GET /api/v2/idp/health
```

它们当前返回静态 `status=ok`，不能用来判断 repository、provider 或 runtime 是否可用。

事实源：

- `internal/apiserver/transport/rest/authz/router.go`
- `internal/apiserver/transport/rest/idp/router.go`
- `internal/apiserver/transport/rest/router_matrix_test.go`

## 3. gRPC 健康入口

gRPC server 可以在 `grpc.healthz-port` 指定的独立 HTTP 端口提供 `/healthz`。端口为 `0` 时不启动该服务。

这个入口调用标准 gRPC health service：

```text
SERVING     -> HTTP 200
其他状态或检查失败 -> HTTP 503
```

它不等同于主 REST `/health`，也不自动汇总所有业务依赖。

事实源：

- `internal/apiserver/process/grpc_server.go`
- `internal/pkg/grpc/server.go`
- `internal/apiserver/process/grpc_server_test.go`
- `internal/apiserver/config/config_contract_test.go`

## 4. 当前降级启动

进程级降级由 `server.allow-degraded-startup` 请求，并受 `server.mode` 的生产安全策略约束：

| `server.mode` | 是否可启用进程级 degraded startup |
| --- | --- |
| `debug` | 可以 |
| `test` | 可以 |
| `release` | 不可以 |

允许进程级降级时，启动链可以记录错误并继续处理数据库初始化、MySQL/Redis 获取、IDP 加密键解析、container 初始化和关键模块缺失。该能力不等于 readiness 健康；主 `/health` 仍没有完整汇总这些依赖。

Suggest 还拥有独立的模块级降级策略：

| 场景 | 行为 |
| --- | --- |
| `suggest.enable=false` | 跳过 Suggest 初始化 |
| 初始化或首次刷新失败且 `required=true` | 返回错误，阻止该模块正常启动 |
| 初始化或首次刷新失败且 `required=false` | 记录 degraded 日志，使用返回空结果的 `DegradedService` |
| 生产环境关闭手机号脱敏 | 初始化失败 |

`SuggestModule.CheckHealth` 只检查模块是否启用以及 service 是否存在，不检查索引版本、最后刷新时间或数据新鲜度；它也没有进入主 `/health` 的判断。

事实源：

- `internal/apiserver/container/suggest/module.go`
- `internal/apiserver/application/suggest/config.go`
- `internal/apiserver/application/suggest/degraded.go`

其他模块是否允许降级，必须分别以 process/container 初始化代码为准，不能从 Suggest 的 `required` 语义类推。

## 5. 当前关闭行为

收到关闭信号后，当前关闭序列依次执行：

```text
lifecycle hooks
  -> cleanup Suggest module
  -> close database connections
  -> close HTTP server
  -> close gRPC server
```

代码没有维护独立的 `draining` readiness 状态，因此不能宣称收到信号后探针会先切换为 not-ready。

事实源：

- `internal/apiserver/process/shutdown_lifecycle.go`
- `internal/apiserver/process/shutdown_lifecycle_test.go`

## 6. 已存在但未接入主探针的检查

`Container.HealthCheck` 可以 ping MySQL 和 Redis，但当前主 `/health` 没有调用它。`DatabaseManager.HealthCheck` 也存在，但不能据此推断部署探针已经覆盖数据库健康。

这些函数是可复用能力，不是已完成的 readiness 聚合。

## 7. 规划改造

如果部署需要区分存活和接流量，最小演进方向是：

1. 保留轻量 `/healthz` 作为 liveness；
2. 新增或明确一个 readiness 入口，汇总真正的硬依赖；
3. 明确 optional 依赖的 degraded 表达，不把它们全部升级为 `503`；
4. shutdown 开始时先切换 readiness，再停止接收新流量；
5. 为每个进入 readiness 的组件增加测试，并避免在响应中泄露内部错误和配置。

在这些代码和测试落地前，下列内容都不是当前事实：

```text
完整三态健康模型；
MySQL/Redis/Suggest/IDP/Outbox 的统一组件矩阵；
draining 探针；
Suggest 进程内索引 freshness；
所有后台任务的健康聚合。
```
