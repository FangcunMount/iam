# 安全日志与凭据处置

> 状态：已实现 · 维护命令、生产日志契约和交付探针的运维入口。

## 1. 边界

IAM 生产日志不得包含 Refresh Token、Token hint、Redis 凭据 key、GORM
原始 SQL 或底层 gRPC Internal 错误。生产使用 GORM silent 和结构化 JSON
日志。`/app/iam-maintenance` 是镜像内离线工具，不提供网络 API，也不会在
apiserver 启动时自动运行。

维护工具默认 dry-run；任何删除都需要 `--apply` 和对应的精确确认短语。

本轮保持 Redis key 格式 `refresh_token:<value>` 兼容；安全边界是该 key
和 Token 值完全不进入日志。清理 Refresh Token 只会使长期刷新凭据失效，
不会立即撤销现有 Access Token 或全部 Session。

## 2. 上线前检查

1. 公告认证维护窗口，记录发布 SHA、active JWKS kid、Redis DB 编号和
   Token TTL；不得读取或复制 Token/SQL 日志行。
2. 确认 Redis 是单实例而非 cluster。
3. 先部署安全日志版本，确认 `/healthz`、`/readyz` 和新登录。
4. 所有处置都先 dry-run，只保存不含内容的 JSON 统计摘要。

## 3. Refresh Token 全量失效

在与 apiserver 相同 env/network 的容器上下文中执行：

```text
/app/iam-maintenance purge-refresh-tokens
```

dry-run 只输出 `scanned/matched/deleted` 数量。确认维护窗口后停止
`iam-apiserver`，避免清理期间产生新 Token，再执行：

```text
/app/iam-maintenance purge-refresh-tokens \
  --apply --confirm=PURGE_REFRESH_TOKENS
```

完成后再次 dry-run，`matched` 必须为 `0`。工具使用
`SCAN MATCH refresh_token:*` 与分批 `UNLINK`，不使用 `KEYS` 或
`FLUSHDB`；Session、Challenge、OTP 和 IDP cache 不在处理范围内。

## 4. 修复前日志处置

宿主机真实日志目录可以挂载到容器 `/var/log/iam`，工具只接受这一规范化
容器路径，只处理第一层 `app/warn/error` 当前文件和轮转文件：

```text
/app/iam-maintenance dispose-sensitive-logs
```

摘要只包含文件数量、总字节、最早/最晚修改时间、Refresh Token 和 GORM
SQL 命中数；gzip 文件只做计数读取，不输出日志行、Token、SQL 或文件名。
确认摘要后执行：

```text
/app/iam-maintenance dispose-sensitive-logs \
  --apply --confirm=DELETE_PRE_5_4_IAM_LOGS
```

工具不递归删除目录，不处理非白名单文件，拒绝符号链接和越界路径。删除
不可恢复；外部日志平台及失败部署日志中的修复前副本需按平台能力另行
删除，只保留 run ID、时间范围和删除结果。

## 5. 恢复与观察

重启 IAM 后必须确认：

- `/healthz=200` 且 `/readyz=200`；
- 新登录和新 Refresh Token 轮换成功；
- 旧 Refresh Token 返回既有 `401`；
- 新日志没有 Token、SQL 或底层 gRPC 错误文本。

至少观察一个 Access Token TTL（当前生产基线为 60 分钟），关注 Refresh
401、重新登录量、Redis 错误和 readiness。历史 Token 和日志不得在回滚时
恢复；安全问题优先向前修复。
