# AuthZ 领域模型设计

> 状态：已实现 · 本文以当前领域对象、数据库约束与运行时校验为依据。

## 结论

AuthZ v3 的最小事实模型由 `Role`、`Assignment`、`RoleInheritance`、`PermissionGrant`、`Resource` 和 `ConstraintSet` 组成。角色负责聚合，
Grant 负责表达能力，ConstraintSet 负责对象属性条件；三者不可互相替代。

![AuthZ v3 领域模型与运行时编译图](../../_images/architecture/authz-domain-model-v2.png)

[SVG 图源](../../_images/architecture/authz-domain-model-v2.svg)

图中的 `Assignment` 已经是统一的领域与代码术语，对应 `domain/authz/assignment.Assignment`。
Snapshot 内部的自有不可变角色图只负责 Subject/Role 与 Role/Role 的闭包，不保存 PermissionGrant，也不直接产生最终 Decision。

围绕这些事实，AuthZ 的职责主链分成三段：Assignment、RoleInheritance、PermissionGrant 等命令服务负责建权与赋权；
`DecisionService` 与领域 `AuthorizationEvaluator` 负责验权和产生 Decision；AuthZ middleware 或业务服务在访问边界施权，不拥有授权事实或判定规则。
`PolicyVersion + Outbox + reload` 属于第一段事实变更后的发布收敛机制，不单独构成第四个子域。

写模型另有一层 **Policy / Plan / Outcome**语义，用于跨聚合规则与原子写动作，不替代上述事实：

| 类型 | 代表 | 位置 |
| --- | --- | --- |
| Policy | `ResourceChangePolicy`、`RoleRemovalPolicy`、`ReplacementPolicy`、Assignment/Object admission | `domain/authz/policy`、`domain/authz/assignment`、application admission |
| Plan | `ReplacementPlan`（受管 Assignment 的 Grant/Revoke 集合） | `domain/authz/assignment` |
| Outcome | `RevokeOutcome` + `AtomicRevoke`（Grant/Inheritance 原子撤销结果） | `domain/authz/permissiongrant`、`roleinheritance` |

Application 只负责加载事实、执行 Plan/Outcome 映射、递增 `PolicyVersion` 与写 Outbox；immutable runtime 仍是可重建投影。

## 统一术语

| 术语 | 含义 | 不是 |
| --- | --- | --- |
| Subject | 被授权主体，通常是 User 或服务身份 | 登录名、角色名 |
| Tenant | 权限事实与判定的授权域 | 仅展示用组织字段 |
| Role | Grant 的聚合容器 | 直接可执行的权限字符串 |
| Assignment | 同一 Tenant 内 Subject→Role 的直接关系 | 继承后角色集合 |
| Direct Role | 从 Assignment 直接得到的 Role | 父角色 |
| Effective Role | Direct Role 加全部可达父角色 | 仅直接角色 |
| RoleInheritance | 同一 Tenant 内 Child Role→Parent Role | Subject→Role |
| PermissionGrant | Role 对 Resource/Action 的允许规则 | 第三方 policy 行或字符串 tuple |
| Resource | 受保护资源及其对象属性 schema | 具体业务对象实例 |
| ConstraintSet | Grant 上的对象属性条件集合 | 客户端自由表达式 |
| ObjectAttributes | 业务服务加载并提交的受信对象属性 | 客户端自报 JSON |

## 模型为什么要拆成六类事实

AuthZ 当前的关键设计决定是把不同变化原因分开：

| 变化 | 应修改的对象 | 不应被连带改写的事实 |
| --- | --- | --- |
| 用户换岗位 | Assignment | RoleInheritance、PermissionGrant |
| 岗位继承基础能力 | RoleInheritance | 每个用户的 Assignment |
| 某角色增加能力 | PermissionGrant | Role 名、用户事实 |
| 资源新增可用动作 | Resource catalog | 已有主体关系 |
| 对象状态变化 | 业务模块事实 | IAM 权限表 |
| 对象级规则变化 | ConstraintSet | 客户端提交格式 |

如果把六类事实压成一条字符串 policy，短期省掉了显式对象，长期却会让用户生命周期、角色组织、资源治理和对象状态共用一个变更边界。当前模型接受更多表和更多校验，换取责任可审计、数据可收敛和运行时可重建。

## Subject 与 Tenant

`subject.Ref` 只保留 `Type` 和 `ID`。值对象当前接受 `user`、`group`、`service` 三类，但“语法上支持”不等于“写链路已经全部可用”。

当前组合根只注册 User resolver，Assignment 写入会校验主体存在性。所以当前可证明的边界是：

- 领域值对象为 group/service 预留了形状；
- 完整的可写 Assignment 验证链主要是 User；
- 开放 group/service 不能只改 proto，还需 resolver、生命周期、删除约束与服务身份语义。

AuthZ 不复制用户姓名、登录标识、组成员或服务凭据。它只持有授权引用，主体真实性由事实拥有模块与 resolver 保证。

Tenant 则是决策域，同时约束 Role、Assignment、RoleInheritance、PermissionGrant 和 PolicyVersion。同名 Role 在两个 Tenant 中不是同一个事实；
任何 Assignment、继承边或 Grant 跨 Tenant 引用都应在写入或 reload 时失败。

## Role：稳定标识与能力聚合

Role 保留稳定 `Name`、可更新 `DisplayName`、Tenant 和描述。当前 `Name` 的领域校验是 trim 后非空；如果名称呈 `app:name` 形状，
冒号前缀还会被快照作为可选 app namespace 过滤。

因此：

1. Role name 会被 SDK、Assignment constraints 和 bootstrap 引用，不应当作展示文案随意改名。
2. `admin`、`tenant_admin` 等名称本身不带权限；真正的 allow 必须来自 PermissionGrant。
3. Role 删除前必须确认没有活跃 Assignment、Grant 或继承边引用，否则会让快照不可重建。

## Assignment：直接关系

Assignment 只表示 Subject 被直接授予哪个 Role。比如：

```text
user:42 --Assignment--> school_teacher
school_teacher --RoleInheritance--> basic_user
```

则：

- `direct_roles = [school_teacher]`
- `roles/effective_roles = [school_teacher, basic_user]`

因此 `GetAuthorizationSnapshotResponse.roles` 与 `direct_roles` 不能混用；前者包含继承结果，后者只反映直接 Assignment。

把 effective role 回写为 Assignment 会把可派生关系变成新事实：之后即使撤销 `school_teacher -> basic_user` 继承边，
用户仍然会因为被误写的 direct Assignment 保留 `basic_user`。这正是 proto 同时返回 `roles` 与 `direct_roles` 的原因。

数据层通过 active generated guard 约束同一 `subject_type + subject_id + role_id + tenant_id` 只有一条活跃 Assignment。记录软删除后可再次授予，
因此该设计同时保护并发唯一性与历史可追溯性。

## RoleInheritance：有向无环角色图

`child -> parent` 表示子角色继承父角色的 Grant。领域规则包括：

- child 和 parent 必须属于同一 Tenant；
- 不能自继承；
- 写入时拒绝形成环；
- 删除父子关系后，后续快照不再包含由该边带来的有效角色；
- 多层继承由角色图闭包计算，不复制 Grant。

不可变角色图同时装载 Assignment 与 RoleInheritance，负责得到有效角色集合。它不装载 PermissionGrant。

写入和 reload 两道防线共同维持无环图：

- 变更前校验 child/parent 存在、同 Tenant 且不相同；
- MySQL 仓储锁定 Tenant 内相关角色和现有继承边，再检查成环；
- 快照构建对全部历史数据重做交叉 Tenant、自环和 DFS 环检测；
- 有效角色解析保持 32 层边界，并用 visited set 对菱形路径去重。

继承边使用 `revoked_at` 表达撤销，active unique guard 允许历史边撤销后重新授予。Grant 不复制到 child role，所以修改 parent 能力只需更新一份事实。

## PermissionGrant：能力事实

PermissionGrant 的核心维度是：

```text
Tenant + Role + Resource + Action + optional ConstraintSet
```

Resource 和 Action 使用分段匹配，当前最多四段；通配符只能按既定匹配规则出现。Grant 的存在表示允许，未匹配到允许规则时默认拒绝。当前模型没有独立的 deny Grant。

应区分逻辑维度与运行时物理结构：运行时首先按 Tenant 和有效角色取得候选 Grant，再匹配 Resource/Action，并不是数据库或内存中的固定“四维数组”。

当前 PermissionGrant 是 allow-only，没有独立 deny Grant。这避免了 allow/deny 优先级、继承 deny 和通配 deny 的组合歧义，代价是“局部例外拒绝”需要重新设计角色或条件。

Grant 建立有两条路径：

| 路径 | 用途 | Resource ID | Action | Constraint |
| --- | --- | --- | --- | --- |
| managed `New` | REST 管理和常规 Grant | 必填 | catalog 中的具体 Action | 可有，必须符合 schema |
| trusted `NewSystem` | bootstrap/migration 系统 Grant | 可为 0 | 可为 `*` | 必须无条件 |

系统通配 Grant 不是普通 REST 写入的捷径。有条件 Grant 也不能授权 `list`、`search`、`batch` 或 `batch_*`，因为这些动作发生在具体对象加载前，没有安全的属性可供求值。

Grant 的 canonical key 使用 SHA-256，输入为版本、Tenant、Role ID、Resource ID、Resource Pattern、Action 和 canonical Constraint JSON。
因此逻辑相同但 JSON 顺序不同的条件会得到同一标识，为去重、幂等与审计提供稳定基础。

## Resource 与 ObjectAttributes

Resource 定义资源名称和允许参与条件授权的 `attribute_schema`。对象实例及其属性仍归业务模块所有。

对象级授权链为：

```text
客户端请求对象 ID
  -> 业务服务加载对象
  -> 业务服务提取 schema 允许的属性
  -> AuthZ Check 校验并求值 ConstraintSet
```

客户端不能直接提交所有者、组织、状态等字段来影响授权结果。未注册属性、类型不匹配或缺少条件所需属性时，判定失败或拒绝，不能静默放宽。

Resource key 必须精确为四段：

```text
<app>:<domain>:<type>:<name-or-pattern>
```

非通配分段必须是小写字母开头的 `a-z / 0-9 / _ / -` 字符串。`Resource.Key` 只允许最后 name 段为 `*`，`Resource.Pattern` 允许任意分段为 `*`。匹配是四段逐段覆盖，
不是 glob 或正则表达式。

`attribute_schema` 版本当前为 1，最多 32 个属性；key 必须是 `object.<name>`，类型只能为 `string`、`int64`、`bool`。
只有 string 属性可声明 `allowed_string_values`。schema 规范化会去重枚举值并按 key 排序。

更新 Resource schema/action catalog 时，应用层会重新校验依赖的活跃 Grant；全局 Resource 变更会递增所有受影响 Tenant 的 PolicyVersion。
Resource 被活跃 Grant 引用时不能删除。

## ConstraintSet v1

ConstraintSet 是结构化、版本化的条件集合，绑定在 PermissionGrant 上。其职责是表达诸如“对象所属组织等于 Principal 所属组织”之类的对象条件，而不是承载任意脚本。

约束求值遵循：

- 仅使用受信 Principal 上下文与受信 ObjectAttributes；
- 属性名必须被 Resource schema 接受；
- 所有必需条件满足才允许；
- 无条件 Grant 可用于列表、搜索和批量 capability；
- 需要对象属性的 Grant 只能在对象已加载的链路上检查。

v1 的硬边界是：

- 只有 `all_of`，最多 8 个 predicate；
- 同一 key 不可重复，key 必须是 `object.*`；
- operator 当前只有 `eq`；
- value 只能是 string/int64/bool，且类型字段与实值字段必须一一对应；
- predicate 必须被 Resource schema 接受，类型与可选枚举值一致；
- 规范化后按 key 排序，以 canonical JSON 参与 GrantKey 计算。

当前没有 `any_of`、不等于、大小比较、主体属性表达式或任意脚本。如果需要扩展，应先升级条件语言版本和威胁模型，不应直接放宽 parser。

## ObjectAttributes 的当前信任白名单

领域模型可表达多种 `object.*` 属性，但当前 gRPC 传输层实际放行的窗口很窄：

```text
caller:   qs-apiserver.svc
resource: qs:evaluation:collection:assessments
key:      object.origin_type
type:     string
```

这个白名单把“某个属性在 schema 中合法”与“某个调用方有权声明它”分开。新增对象属性时，只更新 Resource schema 不足以完成接入；还必须确定事实拥有者、gRPC caller 白名单、类型映射和伪造属性测试。

## 判定与失败语义

| 情况 | 结果 |
| --- | --- |
| 无匹配 Grant | `DENY` |
| 有无条件匹配 Grant | `ALLOW` |
| 有条件 Grant 且条件满足 | `ALLOW` |
| 条件所需属性缺失或不可信 | `DENY` 或输入错误，不能放行 |
| Resource/Action 输入非法 | 参数错误 |
| 运行时快照不可用 | 服务错误，不应 fail-open |

## 代码不变量与数据基线

必须明确二者差别：

- 代码不变量：同 Tenant 关系、禁止继承环、默认拒绝、对象属性 schema 校验。
- 当前数据基线：平台域目前通过通配 PermissionGrant 提供全局管理能力。

`RequirePermissionOrGlobal` 的代码会检查平台域中任何匹配的 PermissionGrant，并不强制它必须是通配 Grant。因此“只有平台通配才能全局放行”需要由 bootstrap、数据审计和运维校验维持，
不能只靠代码注释假定。

## 不变量的多层落点

| 不变量 | 领域/应用层 | 仓储/数据层 | reload 防线 |
| --- | --- | --- | --- |
| 同 Tenant 关系 | 构造与 command 校验 | 按 Tenant 查询和唯一约束 | 交叉 Tenant 引用拒绝建照 |
| 无重复活跃 Assignment | command 幂等处理 | active generated guard | 同一关系只建一条边 |
| 继承无环 | 变更前检查 | 锁定相关角色/边 | 全图 DFS 再校验 |
| Grant 符合 Resource | `ValidateAgainst` | ID/活跃状态约束 | 未知 Resource 或错误 Action 拒绝建照 |
| Constraint 类型安全 | normalize/schema validate | canonical JSON | 求值前再验请求属性 |
| 默认拒绝 | Grant 只表达 allow | 无 deny 事实 | 无匹配返回 deny |

没有任何单层可以独立代表整个不变量。领域校验阻止新脏数据，数据层承受并发，reload 校验阻止历史脏数据变成活策略。

## 为什么不采用其他模型

### 把权限写在 Role 上

这会让 Role 的组织语义与 Resource catalog 的发布节奏捆绑，也很难为单条能力增加 ConstraintSet 和审计字段。独立 PermissionGrant 让角色稳定、能力可变。

### 把继承展开成 Assignment

这会丢失直接关系与派生关系的区别，撤销继承边时还要识别并删除大量派生记录。当前模型保留边与图闭包，不物化 effective roles。

### 把业务对象同步到 IAM

这会引入延迟投影、双写和删除一致性，而 IAM 仍不是业务事实的拥有者。当前只让业务服务提交最小受信属性，避免把整个对象模型拖入 IAM。

### 允许任意条件脚本

任意脚本会扩大 CPU/内存消耗、注入、非确定性和无法解释的风险。ConstraintSet v1 故意小，能够在写入前完全校验，并在请求期稳定求值。

## 变更模型前的评审问题

1. 新事实的真正拥有者是 AuthZ 还是业务模块？
2. 它是直接事实，还是可从其他事实重建的投影？
3. Tenant 边界如何验证，数据层如何防并发冲突？
4. 设计是否会让客户端自报授权所依赖的事实？
5. 历史脏数据使新快照构建失败时，是保留旧快照还是部分发布？
6. proto、OpenAPI、SDK、bootstrap、维护工具和文档门禁哪些需要同步？

只有这些问题有可验证答案，模型变更才算完整。
