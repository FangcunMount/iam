# AuthZ 安全加固与发布验收

> 状态：已实现 · 本文记录代码合同、隔离环境验证和后续生产操作步骤。生产部署与数据治理尚未执行。

本次保留 Role、Assignment、RoleInheritance、PermissionGrant、Resource、Subject/Tenant、ConstraintSet、Evaluator 与 DecisionService。REST v3 路径、gRPC 方法和字段、SDK 方法、GrantKey 算法、事件载荷及数据库表结构保持不变。

## 发布前只读审计

维护命令通过 `MYSQL_HOST`、`MYSQL_PORT`、`MYSQL_USER`、`MYSQL_PASSWORD`、`MYSQL_DATABASE` 连接指定数据库。凭据由部署环境注入，不放入命令行或报告。

```sh
iam-maintenance authz-hardening preflight \
  --attribute-providers=/app/configs/authz_attribute_providers.yaml > authz-preflight.json
```

报告包含：

- `fingerprint`：按确定顺序读取的全部授权事实（含撤销历史）、策略版本、相关用户存在/状态事实及提供者配置指纹。
- `blockers`：非法或跨租户引用、超深或成环继承、不满足 schema 的 Grant、缺少可信提供者，以及 platform 写主体证明失败。每项记录种类、对象和原因。
- `changes`：拟撤销的 Grant 完整前像，以及精确目录 `*` 的只读替代动作。
- `platform_writers`：由实际匹配 Grant 求值证明能在 platform 执行目录 create/update/delete 的既有活跃 User；不依赖角色名。
- `policy_versions`：各租户当前版本。

preflight 使用只读一致事务，不补建版本、不删关系、不新增管理员、不扩大提供者信任。发现阻断项时先修复明确的事实或部署配置，然后重新审计；不自动截断继承。

## 发布与数据收敛顺序

1. 保存 preflight 输出和受影响记录；确认至少一个既有主体具备完整 platform 目录写权限。
2. 先部署提供者配置和新代码。文件路径、格式和条件覆盖必须可用。
3. 枚举全部实例，核对部署 SHA、每租户版本、新鲜度和 readiness。混合版本期间不宣称新边界已全面生效。
4. 全部实例启用 platform 专属目录边界后，再执行 apply。使用紧邻执行的 preflight 指纹，数据或配置变化后重新审阅报告。

```sh
iam-maintenance authz-hardening apply \
  --attribute-providers=/app/configs/authz_attribute_providers.yaml \
  --expected-fingerprint='<reviewed-fingerprint>' \
  --confirm=APPLY_AUTHZ_HARDENING > authz-apply.json
```

apply 使用维护命名锁和同事务行/范围锁，复核完整指纹后执行。它撤销非 platform 下精确针对目录的 create/update/delete；目录独立 `*` 创建缺失的 read/list/validate_action 后撤销原记录。已有只读 Grant 按 GrantKey 去重。覆盖其他资源的广泛通配 Grant 保留，目录实际写入口仍只接受 platform 授权。

每受影响租户递增一次 PolicyVersion 并写一次 Outbox；任何失败整体回滚。重复执行在使用当前指纹且无待治理记录时不递增版本和事件。报告的 `applied_changes` 保存前像，`before_fingerprint` 与最终 `fingerprint` 形成审计关联。必须同时检查命令退出状态和 `succeeded`，不能把失败事务的中间报告当成已提交证据。

5. 等待各实例重新确认版本，执行原允许/现在应拒绝的目录写样例，验证普通读取仍成功。
6. 输出最终数据证据，并归档实例证明和业务请求结果。

```sh
iam-maintenance authz-hardening evidence \
  --attribute-providers=/app/configs/authz_attribute_providers.yaml \
  --build-sha='<deployed-commit-sha>' > authz-evidence.json
```

evidence 为只读操作，要求无阻断项和无待治理 Grant。它证明指定数据库和配置的数据状态，不能单独证明该 SHA 已部署到全部实例。

## 观察和恢复

持续观察版本回退拒绝、新鲜度年龄、同步失败、过期拒绝、503 和授权延迟。短暂失败允许消耗既有确认预算；达到上限后停止服务。实例只有重新证明一致并满足订阅/循环状态后才恢复就绪。

结构整理可以独立回退。租户隔离、platform 写边界与新鲜度修复不作为普通回退目标；故障优先修复前进。不得降低 PolicyVersion、自动恢复历史撤销 Grant 或通过清空版本记录恢复旧权限。恢复历史权限必须走显式授权变更，形成新事实、新版本和新事件。

IAM 的时间保证覆盖本次授权查询。外部业务缓存、调用方自行保留的 SubjectSnapshot 和已开始执行的业务操作，必须由其自身失效与请求控制机制负责。
