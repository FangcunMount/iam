# 外部身份信任模型与方案演化

> 状态：已实现 · 本文以当前微信/企微适配、WechatApp、AuthN provider key 与 signup/linking 流程为依据；未来 OIDC/多 provider 方案仅作设计分析。

## 1. IDP 真正解决的不是“调微信接口”

第三方登录表面上是一条 code exchange，实质上是一次信任翻译：

```text
客户端声称“这是 provider 给我的 code”
  -> IAM 服务端向受信 provider 验证
  -> provider 返回其命名空间内的主体标识
  -> IDP 标准化为 ExternalIdentity
  -> AuthN 在 provider/realm/app 作用域内查 LoginIdentity
  -> Identity User 成为内部稳定锚点
```

每一步回答的问题不同：

| 层 | 能证明什么 | 不能证明什么 |
| --- | --- | --- |
| client code | 客户端持有一个短期材料 | code 真伪、归属、是否重放 |
| provider response | provider 在某 app/realm 识别到某标识 | IAM 中对应哪个 User |
| ExternalIdentity | IAM 已标准化外部声明 | 账号已绑定、User 当前可登录 |
| LoginIdentity | 外部键与内部 User 的绑定事实 | 本次 proof 是否仍新鲜 |
| User | IAM 内部主体连续性与状态 | 当前资源动作是否授权 |

因此 IDP 的边界不是 SDK 封装，而是 anti-corruption layer：它阻止 provider 的标识、错误和 token 语义直接污染 AuthN/Identity。

## 2. 外部标识必须带命名空间

只存一个 `openid` 字符串不构成全局身份键。稳定键至少需要：

```text
provider + realm/app scope + external identifier
```

原因：

- openid 通常在 app 作用域内唯一，不同应用可能给同一人不同 openid；
- 企微 userid 属于企业/组织语境，不能与普通微信 openid 混用；
- provider 可能存在 sandbox/production、开放平台/小程序等不同 realm；
- 相同字符串在不同 provider 下没有身份等价含义。

当前 AuthN 的 ProviderKey/realm 语义就是为了让 uniqueness 在正确命名空间内成立。若只对 identifier 建全局唯一索引，可能误合并两个无关主体；若完全不约束，
又可能让同一外部身份绑定多个 User。

## 3. openid、unionid 与 UserID 的关系

### 3.1 openid

openid 适合作为某个 provider app 内的登录键。它不应泄漏为所有业务表的主体外键，因为 app 迁移或 provider 解绑会改变其可用性。

### 3.2 unionid

unionid 在满足 provider 配置和平台条件时，可帮助识别关联应用中的同一外部主体。但它不是无条件存在，也不自动授予账户合并权限。

安全合并至少要处理：

```text
unionid 缺失怎么办？
两个既有 IAM User 出现同一 unionid 怎么办？
由哪个受信流程证明可以合并？
合并后 ProfileLink、Session、Assignment 和审计历史如何处理？
provider 绑定被撤销后内部 User 是否继续存在？
```

当前实现把外部标识用于 LoginIdentity 映射，没有把 unionid 直接升级成 UserID 或自动合并账户。自动合并是独立高风险用例，不应作为登录查询的副作用。

### 3.3 UserID

UserID 是 IAM 内部稳定引用。它隔离 provider 变化，并让 password、phone、wechat、wecom 等多种 LoginIdentity 共同指向同一主体。

```text
Wechat openid ─┐
WeCom userid ──┼─> LoginIdentity bindings -> UserID
Phone/username ┘
```

UserID 的稳定性是跨模块协作基础：Identity、AuthN Session、AuthZ Subject 映射都不需要理解 provider 字符串。

## 4. Provider App、Credential 与 AppToken

IDP 内部也有三种容易混淆的生命周期：

| 对象 | 性质 | 生命周期 | 主要风险 |
| --- | --- | --- | --- |
| WechatApp | provider 应用配置事实 | 管理员创建/启停/修改 | 选错 app/realm |
| AppSecret/API key | 可恢复的长期敏感凭据 | 轮换、泄漏响应 | 数据库+master key 同时泄漏 |
| AppToken | provider 签发的短期调用凭证 | 获取、缓存、过期/刷新 | 缓存旧值、并发击穿 |

它们都不是 AuthN 用户 Credential：

- AppSecret 证明 IAM 服务有权代表 provider app 调 API；
- 用户 password/OTP/provider code 证明某个最终用户；
- AppToken 只服务 provider API，不应被业务 API 接受为 IAM Bearer Token。

分层能避免一类严重错误：把 provider access token 透传给业务系统，或把 IAM refresh token 用来刷新 provider app token。

## 5. 信任提升必须发生在服务端

错误方案：客户端提交 `{openid: "victim"}`，服务端据此登录。

这没有任何所有权证明。正确方案必须由服务端执行下列之一：

- 用短期 code 调 provider endpoint 交换并校验结果；
- 验证 provider 签名、issuer、audience、nonce/state 和时间声明；
- 对需要解密的 payload 同时验证签名、会话绑定和重放条件。

当前微信/企微路径由 provider adapter 完成服务端交换，再只返回最小标准化标识。第三方 SDK response 不直接进入 domain/application，避免把 SDK 某个字段的存在误当成 IAM 信任规则。

## 6. Prepare/Commit 为什么分开

provider 网络调用可能慢、超时、限流或重试。若把它放进 MySQL transaction：

- 事务连接和锁被网络尾延迟占用；
- provider 故障可耗尽本地连接池；
- 重试语义与数据库回滚混在一起；
- 事务超时不代表 provider code 一定未消费。

当前 signup/linking 把流程拆为：

```text
Prepare:
  读取 WechatApp + 解密 secret + 调 provider + 标准化 proof

Commit:
  在本地短事务中检查冲突并写 User/LoginIdentity/Credential 等事实
```

Prepare 结果只在请求内使用，不是可长期复用的认证票据。这个结构接受“外部 proof 完成后，本地事务仍可能失败”，但失败不会留下部分本地事实；客户端重试时应重新遵循 proof 时效和幂等规则。

## 7. 绑定冲突是业务决策，不是 repository error

当一个外部标识已绑定另一个 User，不能简单执行 upsert 覆盖。需要区分：

- 同一 User 重复绑定：可以按幂等语义返回既有关系；
- 已绑定其他 User：必须拒绝或进入受控账户合并/恢复流程；
- provider 声明变化：不能仅凭新 unionid 改写旧归属；
- 用户解绑最后一个 active identity：当前由 AuthN 原子保护阻止账户失联。

唯一索引负责并发裁决，但“冲突后怎么处理”属于 application/domain 语义。数据库 duplicate key 不能自动等价于幂等成功。

## 8. Secret 轮换为什么比更新一列复杂

理想轮换通常需要：

```text
new secret staged
  -> provider/new credential 验证
  -> 切换 active version
  -> 使相关 AppToken cache 失效或隔离
  -> 保留短期 previous version（若协议允许）
  -> 观察并最终 retire old
```

当前实现是单槽 AuthSecret 覆盖：

- 没有 previous-secret grace；
- 密文没有独立 master-key version；
- 轮换不会自动删除 appID 对应的 AppToken cache；
- API symmetric/asymmetric key rotation 方法仍是未实现占位。

这不表示算法错误，而表示轮换协议尚不完整。文档必须把“能更新 secret”与“支持零停机、可回滚轮换”分开。

## 9. AppToken 缓存的一致性选择

每次 provider API 请求都取新 AppToken，状态简单但延迟高且容易触发 provider 限额。单进程内存 cache 不能协调多实例。当前选择 Redis 共享 cache + 短 lease：

```text
read usable token
  -> miss/near expiry: try lease
  -> winner fetches provider and stores TTL
  -> loser waits/re-reads
```

这个方案的核心不是“用了 Redis”，而是避免多实例同时回源。当前残余窗口：锁竞争后的 reread 只检查 token 非空，没有再次按 `ExpiresAt` 判定 usable；
minimum Redis TTL 还可能让业务已过期的 token 留在 key 中。

安全修复方向应是让缓存值携带并校验业务过期时间，而不是仅调整 Redis TTL。secret 轮换是否应立即失效 AppToken，还要依据 provider 协议明确；不能用一条全局缓存规则猜测。

## 10. 故障时为什么不能“降级信任”

| 故障 | 错误降级 | 正确方向 |
| --- | --- | --- |
| provider timeout | 信任客户端 openid | 本次 proof 失败 |
| secret 解密失败 | 使用空/旧配置继续 | fail closed，告警并修复 key |
| app disabled | 仍允许既有 code 登录 | 拒绝该 provider proof |
| Redis AppToken cache 失败 | 所有实例无协调直打 provider | 当前 lease 失败显式返回，避免惊群 |
| provider 返回缺关键 ID | 创建匿名 LoginIdentity | adapter 报错，不落本地事实 |

认证系统的可用性降级不能扩大信任。可以依赖已经建立且仍有效的本地 Session，但不能把未经验证的外部声明转换成新 Session。

## 11. 替代架构

### 11.1 IDP 直接创建/维护 User

优点是少一个映射层；代价是 provider 生命周期绑死业务主体，多 provider 合并、解绑和内部封禁都困难。当前由 AuthN/Identity 拥有内部事实。

### 11.2 每个 provider 一套业务模型

微信表、企微表、OIDC 表分别直连 User，初期直观，但会复制唯一性、状态、link/unlink、审计和恢复逻辑。当前用共同 provider key/LoginIdentity 抽象，adapter 保留协议差异。

### 11.3 标准 OIDC broker

把微信/企微先接入外部 identity broker，IAM 只验证 OIDC，可统一协议、MFA 和 federation；代价是新增高可用安全核心、claim mapping 和迁移依赖。
当前 provider 数量和既有 SDK 使内置 adapter 更直接，未来扩大 federation 时可重新评估。

### 11.4 长期缓存用户 ExternalIdentity proof

可在 provider 不可用时登录，但会把一次性证明变成长效可重放凭据，无法感知 provider 侧撤销。当前持久化的是 LoginIdentity 绑定，持续登录由 IAM Session 负责；新登录仍需新 proof。

## 12. 跨模块不变量

1. IDP 不创建 User、Session、Assignment；
2. AuthN 不读取第三方 SDK struct，只消费标准化 proof；
3. Provider identifier 必须与 provider/realm/app scope 一起判重；
4. 外部声明不能绕过 LoginIdentity 冲突和 User 当前状态；
5. provider AppToken、IAM AccessToken、IAM RefreshToken 三者绝不互换；
6. provider 故障不降级为信任客户端自报身份；
7. 密钥更新、缓存失效和回滚是同一轮换协议的不同步骤。

## 13. 面试追问

### 为什么 unionid 不直接作为 User 主键？

它受 provider 能力与应用关联条件约束，可能缺失，也无法表达 password/phone/其他 provider。内部 UserID 隔离外部标识变化，unionid 只是可能的关联证据。

### OAuth code 已经由 provider 生成，为什么还需要 state/nonce？

code 证明 provider 颁发了材料，不自动证明响应属于当前发起的客户端会话。state/nonce 绑定请求上下文，降低 login CSRF、响应替换和重放。

### AppToken 为什么需要分布式锁而用户登录 code 不需要共享缓存？

AppToken 是多实例共享的 provider 调用凭证，高并发回源会击穿限额；用户 code 是一次性 proof，缓存复用会扩大重放风险。二者生命周期和共享语义不同。
