# IDP 模块边界与代码索引

> 状态：已实现 · 本文给出 IDP 的依赖方向、协议暴露面和典型修改路径，防止 provider 配置、用户认证与 IAM Token 再次混为一层。

## 1. 边界表

| 能力 | IDP | AuthN | Identity | AuthZ |
| --- | --- | --- | --- | --- |
| 管理 AppID/AppSecret | owner | consumer | 无 | 保护管理接口 |
| code 换 openid/userid | adapter owner | 发起并消费结果 | 无 | 无 |
| 外部 ID 到 LoginIdentity | 提供 proof 结果 | owner | 只接收 User 关联 | 无 |
| 创建 User | 无 | SignUp 编排 | domain owner | 无 |
| Session/IAM Token | 无 | owner | 状态联动 | 消费主体 |
| provider AppToken | owner | 通常不消费 | 无 | 无 |
| 资源授权 | 无 | 提供 Principal | 提供 User 事实 | owner |

## 2. 允许的依赖方向

```text
domain/idp ports
  <- application/idp use cases
  <- infra adapters (MySQL/Redis/AES-GCM/WeChat SDK)
  <- container/idp

AuthN application/domain ports
  <- IDP module capabilities / WeChat adapter
```

IDP domain 不 import AuthN；AuthN 通过 `authentication.IdentityProvider` 和 IDP repository/vault 端口消费能力。容器负责跨模块连接。

不允许：

- IDP handler 直接创建 LoginIdentity/User/Session；
- AuthN 直接读取 `idp_wechat_apps` 表或解析密文字节；
- 把 provider SDK object 传到 domain/application；
- 下游服务通过获取 AppSecret 自己实现 code exchange；
- 把 provider access token 填入 IAM JWT claims。

## 3. 分层代码地图

### Domain：`internal/apiserver/domain/idp/wechatapp`

| 文件/概念 | 责任 |
| --- | --- |
| `wechatapp.go`, `types.go` | App、Type、Status |
| `credential.go` | Auth/Msg/API credential model 与 fingerprint |
| `rotater.go` | 加密轮换、version、幂等；API key 方法仍未实现 |
| `accesstoken.go` | token expiry/skew |
| `accesstoken-cacher.go` | locked read-through 策略 |
| `interfaces.go`, `external.go` | Creator/Rotater/Cacher 与 repo/vault/provider/cache ports |

当前包名是历史具体化结果。若抽象多 provider，应该先识别稳定接口，再迁移命名；不能简单把 `WechatApp` 全局替换成 `ProviderApp` 却保留微信专有 Type 和字段。

### Application：`internal/apiserver/application/idp`

| 子包 | 责任 |
| --- | --- |
| `wechatapp/service_metadata.go` | create/get/list/update/enable/disable |
| `wechatapp/service_credentials.go` | AppSecret/MsgSecret rotation |
| `wechatapp/service_token.go` | get/force-refresh provider token |
| `prepare/resolve.go` | AuthN proof/linking 共用的 app 查询、type/status/secret 解析和错误映射 |

`prepare.ResolveAppSecret` 是跨认证 surface 的统一安全检查：依赖可用、app 存在、type 匹配、enabled、credential 存在、decrypt 成功。

- `rest.go`、`grpc.go` 暴露 capabilities；
- `module.go` 向 AuthN 暴露 repository、vault、WechatAuthProvider。

## 4. Transport 与契约

### REST

`/api/v2/idp/health` 可独立注册；wechat-app 管理路由只有 AdminMiddlewares 非空才注册。REST 支持 metadata 管理、凭据轮换和 access token 获取/刷新。

契约事实源：`api/rest/idp.v2.yaml` 与 `transport/rest/idp`。路由实现存在不代表契约已同步，反之亦然。

### gRPC

`IDPService` 注册 `GetWechatApp`、`GetWechatAccessToken`、`RefreshWechatAccessToken`。当前 `GetWechatApp` 返回解密后的 AppSecret，是显式高敏感接口。修改它时必须同步：

- proto 与生成代码；
- service mapper/tests；
- SDK client；
- 调用方迁移；
- transport authentication/authorization；
- 日志与 tracing payload 规则。

## 5. 典型修改路径

### 新增 provider

1. 识别 provider app/credential/identity/token 的专有语义；
2. 定义 domain port，不把 SDK 类型上提；
3. 实现 credential storage/vault 使用；
4. 实现 proof exchange adapter；
5. 在 AuthN 新增 ProviderKey 与 proof/strategy；
6. 组合根注入；
7. 定义 REST/gRPC 管理契约；
8. 增加 realm/global identifier 冲突与重放测试。

### 修改 AppSecret 轮换

同时处理 repo schema、domain lifecycle、vault key version、provider 激活顺序、AppToken 两层缓存失效、审计与回滚。当前单槽字段无法自然支持宽限窗口，需要 migration 而非仅改 rotater。

### 修改 AppToken 缓存

同时检查：

- cache key 是否包含 provider/app/credential version；
- validity 与 TTL 是否一致；
- lock loser reread 是否重新校验；
- force refresh 是否也争 lease；
- provider SDK 第二层 cache；
- Redis 不可用策略；
- 是否允许返回刚 fetch 但 cache set 失败的 token。

### 收缩 secret 暴露

优先新增不返回 secret 的 metadata RPC，并迁移调用方；确认没有消费者后再从 proto 移除敏感字段。不要只在 mapper 中留空而不更新契约语义，否则调用方会把空值误判为配置损坏。

## 7. 当前风险

1. 本地 AES-GCM master key 没有 version/托管审计与在线轮换。
2. AppSecret 单槽覆盖，没有双凭据宽限。
3. secret rotation 不会自动失效 domain/SDK 两层 AppToken cache。
4. lock loser reread 只检查非空，可能返回不满足 skew 的 token。
5. force refresh 不参与同一 lease 协议。
6. API 对称/非对称 key rotation 是空实现。
7. gRPC 查询暴露明文 AppSecret 和 provider token，依赖外围强保护。
