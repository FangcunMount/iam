# Suggest 模块边界与代码索引

> 状态：已实现 · 本文解释 Suggest 从哪些权威事实派生、哪些能力只属于本模块，以及修改搜索/权限/刷新时应落在哪一层。

## 1. 数据所有权

| 数据 | Owner | Suggest 中的形态 |
| --- | --- | --- |
| User/Profile/ProfileLink | Identity | Loader 输入，不可回写 |
| Principal/JWT context | AuthN | `OperatingPrincipal` 最小快照 |
| Role/route permission | AuthZ | `ProfileAccessScope` 的输入 |
| ProfileSearchTerm/Trie/Hash | Suggest | 可丢弃的进程内派生状态 |
| 原始手机号 | Identity | 仅为获准精确搜索进入内存索引 |

Suggest 的 Store 不是 repository。任何“修复名称/手机号”的需求都必须修改 Identity 事实，再由刷新传播；直接改 Store 只在本进程、下次刷新前暂时生效。

## 2. 与 Identity 的边界

默认 Loader 从三类表派生 eligibility：Profile、ProfileLink、User。ProfileLink 的 active 状态决定 User 的手机号是否可作为某 Profile 的搜索键。

Suggest 不拥有：

- User/Profile 的创建、禁用、删除；
- ProfileLink 的建立/撤销；
- 手机号规范化和唯一性；
- Profile 的完整详情与最终读取授权。

Delta 监听三类事实变化，是为了维护读模型，不代表 Suggest 可以定义这些事实的生命周期。

## 3. 与 AuthN 的边界

REST middleware 完成 JWT 验证并写 request context；Suggest 只取 UserID、tenant domain 和 business org。它不重复验签、不加载 Session、不接触 Credential。

本地/在线验签语义由 AuthN 接入层决定。Suggest 不能因为拿到了 UserID 就假设 token 尚未撤销；需要即时撤销时应确保所用 middleware 具有相应在线检查语义。

## 4. 与 AuthZ 的边界

Suggest 不逐候选调用 AuthZ。它只调用粗粒度能力：平台角色、tenant role 和手机号搜索 action，然后与业务 visibility 组合成 scope。

这是一种 query-time policy compilation：

```text
AuthZ coarse capability
+ business Org/Profile visibility
-> local ProfileAccessScope
-> high-frequency in-memory filter
```

收益是延迟稳定；代价是 scope 解析和索引项必须拥有足够一致的维度。详情读取仍应在权威接口再次授权。

## 5. 分层代码地图

### Domain：`internal/apiserver/domain/suggest`

| 文件 | 责任 |
| --- | --- |
| `profile.go` | Term、Keyword、Query、默认上限 |
| `principal.go` | 最小 operating identity |
| `scope.go` | access scope 编译与本地 allow policy |
| `ranking.go`, `match_kind.go` | 去重与 deterministic ranking |
| `mobile.go` | 手机号形态识别和 mask |

Domain 不知道 Trie、Redis、Gin、GORM 或 Casbin。

### Application：`internal/apiserver/application/suggest`

| 文件 | 责任 |
| --- | --- |
| `ports.go` | Suggestor、Runtime、Index、Source、ScopeProvider、Limiter |
| `service.go` | 查询编排、limit、strategy、DTO mask |
| `search_strategy.go` | mobile denied / numeric exact / prefix text |
| `refresher.go` | Full/Delta lock、游标、runtime mutation |
| `config.go` | 行为配置与默认值 |
| `degraded.go` | 非 required 启动失败后的空服务 |

### Infrastructure

| 能力 | 路径 |
| --- | --- |
| Full/Delta SQL | `infra/mysql/suggest/loader.go` |
| created_by visibility | `infra/mysql/suggest/profile_visibility_resolver.go` |
| scope provider/cache | `infra/suggest/access` |
| Store/Runtime/Trie/Hash | `infra/suggest/search` |
| memory/Redis rate limit | `infra/suggest/ratelimit` |
| Prometheus metrics | `infra/suggest/metrics` |

### Transport / Container

- REST handler/principal/DTO：`transport/rest/suggest`；
- route contract：`api/rest/suggest.v2.yaml`；
- module/startup/cron/health：`container/suggest/module.go`；
- REST capability wiring：`container/suggest/rest.go`。

当前没有 gRPC registration 或 `pkg/sdk/suggest`，所以代码中存在 service 不等于其他进程可直接调用。

## 6. 典型修改路径

### 增加新的搜索字段

1. 判断它是否允许进入派生索引、是否敏感；
2. 扩展 ProfileSearchTerm；
3. Full/Delta 都投影该字段；
4. Store 记录每 Profile 的旧 keys，Delta 时可撤销；
5. 定义查询策略、排序和 limit；
6. 定义输出是否可暴露/脱敏；
7. 增加 Full/Delta 等价与删除测试。

只增加 Trie/Hash 写入而不记录旧 key，会导致更新后旧值仍可命中。

### 修改可见范围

1. 先确认权威业务语义属于 AuthZ、组织系统还是 Identity；
2. 扩展 Principal/scope 的最小字段；
3. 更新 scope provider 和 compiled set；
4. 确保 Loader term 提供同一维度；
5. 定义 AuthZ/visibility 失败时 fail-closed 还是降级；
6. 覆盖无 scope、跨 org、owner、admin 和错误路径。

不要把授权查询放进 `Store.SuggestProfile` 的候选循环。

### 修改 Delta SQL

必须验证：

- affected set 覆盖源表所有变更；
- since 参数数量/顺序正确；
- upsert 是完整 term，不是局部字段；
- 失去 eligibility 时输出 tombstone；
- 多条关系聚合不产生重复/脏手机号；
- query start watermark 不丢边界变更。

### 更换集中式索引

保留 application 的 Index/Runtime/Source 端口，把 Elasticsearch/Redis adapter 放 infra。重新定义 scope filter 是服务端 query 过滤还是查询后过滤；敏感手机号不能先大范围返回到应用再过滤。

## 7. 运维与观测

当前应关注：

- refresh 结果（success/failed/refresh_in_progress）；
- full/delta duration；
- upsert/tombstone 数；
- current index terms；
- recall candidates 与 visible candidates；
- query strategy/result count；
- rate limited 次数；
- 最后一次成功刷新时间。

缺失但有价值的信号：source watermark、runtime generation、index age、各实例 term count 分布、visibility error rate 和缓存命中率。增加它们时不要使用姓名/手机号作为 label。
