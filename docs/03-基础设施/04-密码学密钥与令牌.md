# 密码学边界、密钥存储与 JWT/JWKS 生命周期

> 状态：已实现 · 已与 Argon2id、AES-GCM SecretVault、JWT generator、keyset lifecycle、MySQL JWKS repository 和配置核对。

## 1. 本文回答

- 密码、IDP secret、JWT 私钥为什么采用不同的保护方式？
- JWS、JWT、JWK、JWKS 分别是什么，不能混成什么？
- 为什么 JWT 密钥元数据在 MySQL、私钥材料在 PEM 文件、公钥在 JWKS？
- active → grace → retired 的轮换状态机如何避免新旧 Token 断档？
- 多实例轮换、自动初始化、私钥和公钥不匹配时如何失败？
- 还有哪些方案，为什么当前选择这套实现？

## 2. 30 秒结论

IAM 把“凭据保护”和“Token 签名”拆成三条不同安全链：

| 对象 | 当前算法/存储 | 目的 |
| --- | --- | --- |
| 用户密码 | Argon2id hash + server-side pepper | 单向验证；数据库泄露时提高破解成本 |
| 微信 AppSecret/消息密钥 | AES-GCM + 32-byte master key | 需要调用 provider，必须可逆解密并保证完整性 |
| JWT 签名私钥 | RSA PEM file；MySQL 保存 public JWK 和生命周期元数据 | 私钥签名、公钥发布、可轮换 |

JWT/JWKS 核心状态机：

```text
new key becomes active (唯一签名 key)
old active -> grace (继续发布，只验签)
grace expires -> retired (不发布、不验签)
```

迁移 000016 和 atomic activator 保证数据库层最多一个 active key；启动时还会验证 active PEM 私钥与 MySQL public JWK 的模数/指数匹配。
缺失或错配在 release 环境 fail closed。

## 3. 先分清密码学对象

### 3.1 JWT 不是加密

当前 Access Token 是 JWS 签名的 JWT。payload 可被持有者解码，机密信息不能因为“放进 JWT”就视为隐藏。

- JWT：claims 的结构化载体；
- JWS：签名和完整性保护；
- JWK：一把公钥的 JSON 表示；
- JWKS：多把可用于验证的 public JWK 集合；
- `kid`：Token header 指向具体验证 key 的标识。

JWKS 绝不能包含 private key 参数。

### 3.2 Hash 与 Encryption 不是替代关系

密码只需验证，不需还原，所以使用慢 hash。IDP AppSecret 必须在调用微信 API 时取回明文，所以需要 authenticated encryption。

如果把 AppSecret hash，provider 调用无法进行；如果把用户密码可逆加密，master key 泄露会暴露全部密码。

## 4. 密码：Argon2id + Pepper

`internal/apiserver/infra/crypto/argon2_hasher.go` 实现 `authentication.PasswordHasher`：

- 每个密码 hash 包含独立 salt；
- Argon2id 提供 memory-hard 计算；
- pepper 由服务配置/秘密注入，不随 hash 一起保存在数据库；
- `Verify` 使用 constant-time comparison；
- `NeedRehash` 支持参数演进；
- 登录成功时可把旧参数 material 旋转为新 hash。

Salt 防彩虹表和相同密码 hash 相同；pepper 在数据库单独泄露时增加一道服务端秘密。Pepper 不是 salt 的替代品，也不能弥补弱密码策略。

当前 Credential 还保存失败次数、锁定时间、状态和算法标识；密码验证结果由 application recorder 更新锁定策略，而不是让 hasher 自己修改数据库。

## 5. IDP SecretVault：AES-GCM

`SecretVault` 使用 32-byte master key 创建 AES-256-GCM：

1. 生成随机 nonce；
2. `Seal` 产生 ciphertext + authentication tag；
3. 将 nonce 与 ciphertext 一起保存；
4. `Open` 同时验证完整性并解密。

为什么选 GCM：

- 同时提供机密性和完整性；
- 随机 nonce 让同一明文不会得到同一 ciphertext；
- API 简洁，减少“加密了但未认证”的误用。

master key 不应进入数据库或代码仓库。生产启动缺少/无效 `idp.encryption-key` 会失败；仅受控 degraded 模式允许模块不可用。

当前 `SecretVault.Sign` 也提供基于 key reference 的签名端口，但主要 IDP 流程是 AppSecret/消息密钥加解密。文档不能把端口能力写成已接入 KMS。

## 6. JWT Profile、claims 与签名

Token Profile 固定为 `RS256 + kid + JWS Compact`。`JWSKeySource` 同时返回 `kid + algorithm + RSA key`，签发/验证要求
`header.alg == JWK.alg == RS256`；none/HS/RS384/RS512 与 active-key 非 RS256 一律 fail closed。

`jwt.JWSCompactTokenCodec` 负责 compact/header/key binding/signature/time/canonical issuer，并只解析已登记 `token_type`。
audience 与 accepted token type 由 application verification policy 决定；domain verifier 继续负责 revocation、active Session、Admission。

Access Token claims 是显式投影，不是任意 Principal.Claims 透传。当前对外合同包括：

- registered：`iss/sub/aud/exp/nbf/iat/jti`
- 类型化：`token_type/sid/user_id/login_identity_id/tenant_id`（及盘点确认需要的 `org_id`）
- 认证合同：`amr`；`auth_time` 顶层 unix + 过渡期 `attributes.auth_time` 双写
- 不再签发 `auth_method`/`realm` 到新 access JWT；Realm 不参与授权域（授权域只来自显式 `tenant_id`/`tenant_domain`）

Claims 是签发时快照，不会随数据库自动变化。因此在线验证还要检查：

- JWS/issuer/audience/expiry；
- revoked access token marker；
- Session 是否 active；
- 当前 User/LoginIdentity 是否允许访问。

这就是当前 IAM 选择“有状态 JWT 验证”，而不是只验证签名。

## 7. 为什么拆分 key metadata 与 private material

MySQL `jwks_keys` 保存：

- `kid`；
- public JWK；
- status；
- NotBefore/NotAfter；
- 创建/更新时间。

PEM storage 保存 private key。JWKS endpoint 只从 publishable metadata 构建公钥集合。

优点：

- 数据库查询和生命周期事务不需要读取私钥；
- public metadata 可安全用于 JWKS；
- private material 可使用更严格文件权限/挂载；
- 未来可把 private resolver 替换为 KMS/HSM，而不重写 domain/application 端口。

代价是出现“双介质一致性”：MySQL row 与 PEM 文件必须配对。当前启动 `ValidateActiveKey` 会解析 private key，并比较 RSA `N/E` 与 public JWK；不匹配直接失败。

## 8. 原子激活与轮换

### 8.1 创建候选

KeyManager：

1. 生成 UUID `kid`；
2. 生成 RSA key pair；
3. 构造 public JWK；
4. 先保存 PEM candidate；
5. 调用 repository atomic activator；
6. 激活失败或无需轮换时删除 candidate PEM。

### 8.2 激活事务

Atomic activator 在数据库事务/锁下：

- 判断 bootstrap/if-due/force 条件；
- 将旧 active 转为 grace，并设置覆盖验证窗口的 NotAfter；
- 插入新 active；
- 数据库 unique guard 阻止两个 active 提交。

多实例同时 `RotateIfDue` 时最多一个成功激活；其他实例读取最终 active 并清理未使用 PEM candidate。

### 8.3 Grace 为什么必要

旧 Token 在新 key 激活前已经签发。若立刻停止发布旧公钥，所有未过期旧 Token 会突然无法本地验签。

Grace key：

- 不再签发新 Token；
- 仍出现在 JWKS；
- 在 NotAfter 前可验签；
- 宽限结束后退役。

GracePeriod 至少应覆盖所有可能使用旧 key 的 Token 验证窗口；配置验证要求它小于 RotationInterval，但这不自动证明它大于实际 Access Token TTL，运维仍要联动核对。

## 9. JWKS 发布快照

`KeySetBuilder` 查询 active/grace keys，过滤不可发布/无效 key，构建并验证 JWKS，然后生成：

- JSON body；
- ETag（SHA-256 content hash）；
- Last-Modified；
- 进程内 snapshot。

短时间内复用快照减少数据库和序列化成本。激活/退役后 lifecycle application 会刷新发布快照；启动也会预热。

快照是派生状态，MySQL metadata 才是事实源。多实例各自持有快照，因此每个实例必须在自己的生命周期操作/重启中刷新；当前没有共享 JWKS snapshot cache。

## 10. 启动与环境策略

启动 `ensureJWKSReady`：

1. 查询 active keys，必须 0 或 1；
2. development 或显式 `jwks.auto_init` 可在 0 key 时 bootstrap；
3. production 默认不凭空生成首把 key；
4. active key 过期时只在允许条件下替换；
5. 验证 PEM 与 public JWK 匹配；
6. 构建 JWKS snapshot；
7. 更新状态指标。

production 不自动初始化的理由：新建密钥会改变所有消费者的信任材料，需要明确发布/备份/多实例挂载流程，不能由任意新 Pod 静默决定。

## 11. 为什么不采用其他方案

### 11.1 对称 HMAC 签 JWT

未采用。HS256 要把同一 secret 分发给所有验证方，任何验证方都能伪造 Token；RS256 只分发公钥，签名权限集中在 IAM。

### 11.2 所有 key 都存在数据库，包括 private key

未采用。实现简单但扩大数据库泄露影响面。当前把 private material 与 metadata 分离。

### 11.3 只在文件系统保存 key，不存 metadata

未采用。难以原子管理 active/grace 状态、并发轮换、查询和审计。

### 11.4 直接使用 KMS/HSM

是更强的生产方案，但当前未实现。它可以消除本地 PEM 暴露并提供审计/不可导出 key；代价是外部依赖、签名延迟、成本和离线开发复杂度。现有 `PrivateKeyResolver/Storage` 端口为未来替换保留边界。

### 11.5 轮换时立即删除旧 key

未采用。会让仍有效的旧 Token 集体失效，造成验证中断。

## 12. 当前代价与风险

- PEM 文件的备份、挂载、权限和多实例一致性是部署责任；
- 保存 PEM 后数据库激活失败需要补偿删除，补偿失败有指标但仍可能留 orphan file；
- 删除 retired DB row 后再删 PEM，PEM 删除失败同样可能留 orphan；
- 当前只实现并强制 RSA/RS256 Profile；创建、轮换、签发与 SDK 均不接受其他算法；
- 类型字段即使能表达 EC/OKP，也不代表相应 generator 已接入；
- JWKS snapshot 是进程内的，多实例刷新需要各实例自己的生命周期/重启保证；
- private key 没有 KMS/HSM 的不可导出和集中审计能力；
- pepper/master key 的轮换流程需要额外运维设计，不能仅修改配置值。

## 15. 面试追问

### 为什么有了 JWT 还需要 Session？

JWT 负责可验证声明，Session 负责服务端生命周期和撤销。需要 logout、封禁和 refresh rotation 时，纯无状态 Token 不够。

### 为什么旧 key 要留在 JWKS？

它仍要验证轮换前签发但尚未过期的 Token。留在 JWKS 不代表还能签名，grace key 只验不签。

### 数据库和 PEM 谁是真相源？

生命周期和 public metadata 以 MySQL 为真相，签名能力还必须有匹配 PEM。二者任一缺失都不能安全签名，因此启动做交叉验证。
