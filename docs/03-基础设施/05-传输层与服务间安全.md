# REST/gRPC 传输层与服务间安全

> 状态：已实现 · 已与 HTTP/gRPC server、路由/服务注册、JWT middleware、mTLS/Auth/ACL/Audit 拦截器和错误映射核对。

## 1. 本文回答

- REST 和 gRPC 在同一进程中如何装配、启动和关闭？
- TLS、mTLS、应用凭据、ACL、AuthZ 分别保护哪一层？
- 为什么认证成功不等于授权通过？
- 为什么 transport 只依赖 application capabilities？
- 错误如何映射而不泄露内部细节？
- 还有哪些接入方案，为什么当前保留 REST + gRPC + Go SDK？

## 2. 30 秒结论

IAM 同一进程并行运行 HTTP REST 与 gRPC。两者共享业务 application service，但拥有独立 transport adapter、安全链和机器契约。

```text
REST: TLS/reverse proxy -> Gin middleware -> module handler -> application port
gRPC: TLS/mTLS -> interceptors -> registered service -> application port
```

安全层次不能互相替代：

| 层 | 回答的问题 |
| --- | --- |
| TLS | 链路是否加密，服务端是谁 |
| mTLS | 客户端持有什么受信证书 |
| application credential | 请求是否持有 Bearer/HMAC/API key |
| gRPC ACL | 这个服务身份能否调用这个 RPC method |
| AuthN JWT middleware | 业务用户是谁、Session 是否有效 |
| AuthZ | 该主体能否对该业务资源执行动作 |

## 3. 进程装配

`process.prepareTransports`：

1. 构建 Generic HTTP server；
2. 构建 gRPC server；
3. 从 Container 构建窄化的 REST deps；
4. 注册可用模块的 REST route；
5. 收集 Identity/AuthN/AuthZ/IDP gRPC registrations；
6. 启动阶段由 `processruntime.RunGroup` 并发运行两种 server；
7. 任一 server 返回错误，group 结束并把错误交给进程生命周期。

Suggest 当前只有 REST，没有 proto、gRPC registration 或 Go SDK API。文档不能为了目录对称虚构 Suggest gRPC。

## 4. 为什么 transport 不直接访问 repository

Container 模块对外暴露 `ApplicationCapabilities`，REST/gRPC registrar 再把端口交给 handler/service。

```text
transport -> application driving port -> domain/infra ports
```

禁止路径：

```text
handler -> GORM repository
gRPC service -> Casbin concrete adapter
router -> Container 内部字段
```

原因：

- transport 只负责协议解析、鉴权入口、DTO 映射和错误转换；
- 事务与业务不变量在 application/domain 统一执行；
- REST/gRPC 共用同一用例，避免两个协议行为分叉；
- 架构测试可以静态防止依赖反转。

## 5. REST 安全链

Generic server 创建 Gin engine，基础路由包括 liveness/readiness/metrics/docs 等。模块路由按 ModuleState 和依赖完整性条件注册。

受保护业务路由典型链：

```text
request
 -> logging/recovery/request context
 -> JWTAuthMiddleware.AuthRequired
      -> TokenService.VerifyToken
      -> requestctx 写入 User/Principal/tenant
 -> RequirePermission or admin policy
 -> handler DTO mapping
 -> application service
```

AuthN 登录/JWKS public endpoint、管理员 endpoint、当前用户 endpoint 的 middleware 组合不同，必须以 router 和 OpenAPI security 声明逐路由核对。

Token 验签成功只产生 Principal；是否允许访问资源仍要执行 AuthZ。把 `AuthRequired` 当成 permission check 会造成越权。

## 6. gRPC 拦截器链

Unary 当前顺序：

1. Recovery；
2. Request ID；
3. request-scoped logging；
4. mTLS identity extraction（启用时）；
5. application credential validation（启用时）；
6. service ACL（启用时）；
7. audit（启用时）。

顺序有语义：Recovery 在最外层；日志需要 request ID；ACL 需要之前提取的服务身份；audit 记录前面认证/授权后的调用结果。

Stream interceptor 有对应链，但 stream 和 unary 能力不应自动视为完全相同；新增 stream RPC 时需单独验证 identity propagation、logging 和 cancellation。

## 7. TLS 与 mTLS

### 7.1 单向 TLS

客户端验证 IAM 服务端证书，链路加密，但服务端仅凭 TLS 不知道具体客户端服务身份。

### 7.2 mTLS

服务端同时验证客户端证书，并提取 CN/OU/SAN。配置可限制 allowed CN/OU/SAN，支持 CA file/dir、最低 TLS 版本和证书自动重载。

mTLS 适合服务间身份，但证书身份必须再映射到 method ACL；“证书有效”不等于“可调用所有 IAM RPC”。

gRPC 另有独立 HTTP health port，便于基础设施探针在无需客户端证书的情况下检查进程；它不能暴露业务 RPC。

## 8. Application credential 与 identity match

gRPC credential interceptor 支持配置 Bearer、HMAC、API key。它解决证书之外的应用层凭据问题。

当 `require_identity_match` 启用时，TLS identity 与应用凭据 identity 应一致，减少“拿 A 服务证书配 B 服务 token”的混用。关闭该约束会扩大信任组合，必须是显式部署决策。

HMAC 还需要 timestamp validity 防重放；API key 简单但长期静态 secret 风险更高。配置文件只应保存 key reference/公开标识，真实 secret 通过环境或 secret manager 注入。

## 9. gRPC ACL 与业务 AuthZ

`configs/grpc_acl.yaml` 是服务身份到 RPC method 的 allowlist，default policy 是 deny。它适合回答：

> `qs-server` 这个服务能不能调用 `IdentityRead/GetUser`？

业务 AuthZ 回答：

> 已认证 User/Service Subject 能不能对某个 resource/action/scope 执行操作？

两者维度不同：

- ACL 发生在 method 入口，粒度是调用方服务和 RPC method；
- AuthZ 发生在用例/路由，粒度是 subject、tenant、resource、action、scope。

高风险 assignment mutation 还有 `configs/grpc_assignment_constraints.yaml`，限制可分配域、subject type、role 和 delegated actor，不能只靠 method ACL。

## 10. 注册与降级

Container 收集 gRPC registration 时按 ModuleState 判断：

- AuthN、Identity、IDP、AuthZ 可用才注册；
- registration 描述列出真实 service；
- Registry 注册后设置 health serving status；
- Suggest 不参与 gRPC registration。

REST 同样按模块和 auth middleware 可用性注册。模块存在但 JWT middleware 缺失时，受保护路由不会以无保护方式降级注册，而是跳过并告警。这是 fail closed。

## 11. 错误映射与信息泄露

Domain/application 使用稳定 IAM error code；transport 将其映射为 HTTP/gRPC status。

gRPC `PublicStatusMessage` 对 Internal/Unavailable 返回固定公开消息，而不是把数据库、Redis、SQL、文件路径或 provider response 原样返回。详细 error 只进入安全日志。

批量接口尤其不能把每项 `err.Error()` 无筛选回传。错误映射需要同时保持：

- 客户端可分类；
- REST/gRPC 语义一致；
- 内部细节不泄露；
- 日志保留 request ID 和内部 root cause。

## 12. 为什么保留两种协议

### REST

适合浏览器、管理平台、开放接入和 OpenAPI 工具链；调试成本低。

### gRPC

适合内部服务间强类型调用、低开销、mTLS/服务 ACL 和 Go SDK 封装。

代价是维护两套协议映射和契约防漂移。IAM 用共享 application service + OpenAPI/proto + route/compile tests 降低分叉，而不是让两个 handler 各自实现业务。

## 13. 为什么不采用其他方案

### 13.1 只提供 REST

可降低契约数量，但内部服务失去 proto 强类型、标准 gRPC health/interceptor 和现有 SDK 通路。

### 13.2 只提供 gRPC

浏览器/第三方接入成本上升，管理 API 和可视化调试不便。

### 13.3 REST handler 直接复用 gRPC client/service

未采用。会让内部协议成为进程内业务层，并引入序列化/错误双重映射。两种 transport 应并列依赖 application port。

### 13.4 只靠网络边界和 mTLS，不做 ACL/AuthZ

未采用。网络和证书只能证明来源，无法表达 least privilege 的 method 和业务资源权限。

### 13.5 把详细内部错误返回客户端便于排障

未采用。它泄露实现和敏感上下文；正确做法是公开稳定 code/message，内部日志用 request ID 关联 root cause。

## 14. 当前代价与风险

- REST/OpenAPI、gRPC/proto、Go SDK 三个公共面需要持续契约校验；
- gRPC ACL 是配置型 allowlist，新增/重命名 RPC 必须同步更新，否则 fail closed；
- 配置中存在 HMAC/API key 示例，生产 secret 注入和轮换属于部署责任；
- stream interceptor 与 unary interceptor 需要分别验证；
- gRPC health serving 不自动等于业务 readiness，需结合 `/readyz` 和组件健康；
- reverse proxy 后的 client IP、TLS termination 和 forwarded headers 必须有明确可信边界。

## 17. 面试追问

**mTLS 和 JWT 有什么区别？**

mTLS 主要证明连接对端服务身份并保护通道；JWT 承载用户/服务主体声明和认证上下文。两者可叠加，不能简单互相替代。

**ACL 和 RBAC 为什么都要有？**

ACL 限制服务能调用哪些 RPC；RBAC/AuthZ 决定业务主体能操作哪些资源。前者是接口面最小权限，后者是业务面访问控制。

**为什么错误映射属于安全设计？**

未经处理的内部错误可能暴露 SQL、路径、secret hint 或基础设施拓扑；稳定公开错误同时也是客户端兼容契约。
