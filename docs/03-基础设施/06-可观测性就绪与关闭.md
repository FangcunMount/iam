# 可观测性、Readiness 与优雅关闭

> 状态：已实现 · 已与 readiness checker、health routes、runtime lifecycle、shutdown sequence、低基数指标和发布探针核对。

## 1. 本文回答

- liveness、readiness、module health 为什么不能混成一个 `/health`？
- release 与 degraded startup 的边界是什么？
- 关闭时为什么要先 draining，再停后台任务和 server？
- 日志、指标和探针各自提供什么证据？
- 当前哪些故障仍无法靠现有可观测性完全判断？

## 2. 30 秒结论

IAM 明确区分三层健康事实：

| 信号 | 问题 | 当前语义 |
| --- | --- | --- |
| `/healthz` | 进程是否活着 | liveness-only，不访问 MySQL/Redis |
| `/readyz` | 是否应该接新流量 | 并行检查 required/optional components，有总超时 |
| 模块/运行时详情 | 哪个依赖或后台机制异常 | readiness snapshot、metrics、安全日志 |

优雅关闭顺序：

```text
收到 signal
 -> MarkDraining + gRPC NOT_SERVING
 -> 等待 drain delay 让负载均衡停止派流
 -> 停后台任务/订阅
 -> cleanup Suggest/Identity worker
 -> 关闭 DB/Redis
 -> 关闭 HTTP
 -> 关闭 gRPC
```

顺序的目标是避免“资源先关了，请求和 worker 仍在跑”。

## 3. 启动模式与 fail closed

`RuntimeProfile` 统一解析 server mode/environment/production-like。正常 release/production 要求关键资源和模块可用；`allow_degraded_startup`
只有在 profile 允许且显式请求时生效。

准备阶段是有序 stage runner：

1. runtime profile；
2. MySQL/Redis/IDP key/EventBus；
3. Container modules；
4. REST/gRPC transports；
5. background tasks；
6. shutdown hooks。

stage 失败会停止后续准备，避免启动一个注册了一半路由、缺少关键依赖却仍被视为健康的进程。

Degraded 模式的意义是受控诊断，不是生产默认可用性策略。路由注册仍按 ModuleState fail closed；模块不可用不会变成未鉴权路由。

## 4. Liveness 为什么必须简单

如果 `/healthz` 每次访问数据库，当数据库抖动时 orchestrator 会重启所有 IAM 实例，放大故障并造成重连风暴。

当前 `/healthz` 只证明 HTTP 进程可响应。它不证明：

- 数据库可用；
- Redis 可用；
- active JWKS key 存在；
- AuthZ 原生不可变快照已成功加载且版本新鲜度满足要求；
- Suggest 已完成首次 full refresh。

因此容器 liveness 使用 `/healthz`，发布 gate 还需要单独检查 `/readyz`。

## 5. Readiness Checker

Checker 对每个 component 设置 `Required` 和 CheckFunc，并发执行：

- 单组件 timeout；
- 总 timeout；
- required error => `failed`，整体 not_ready；
- optional error => `degraded`，整体仍可 ready；
- nil check => `skipped`；
- draining => 立即 not_ready。

响应只暴露稳定状态，不把原始 DB/Redis error 返回客户端，避免健康接口成为信息泄露面。

## 6. 当前 readiness components

| Component | Required | 检查内容 |
| --- | --- | --- |
| `mysql` | 是 | `PingContext` |
| `redis` | 是 | `PING` |
| `authn` | 是 | module available 且 AuthenticationGrantIssuer / Refresher / Revoker / Verifier / ServiceTokenIssuer 均已装配 |
| `jwks` | 是 | 可读取唯一 active key |
| `authz` | 是 | runtime available，最近 reload health 成功 |
| `suggest` | 取决于 `suggest.required` | enabled 时 service + 至少一次成功 refresh |
| `session_revocation` | 是 | store 可读，最老未完成任务年龄不超阈值 |

注意：

- AuthN check 是装配检查，不会执行真实登录；
- JWKS check 验 active metadata，启动阶段已额外验证 PEM 匹配；
- AuthZ check 依赖 runtime reload health，不会为每次 probe 做完整权限判定；
- Suggest 关闭时返回 OK，不表示提供 Suggest API；
- session revocation 检查 backlog age，而不是只看 worker goroutine 是否存在。

## 7. 为什么有 optional component

Suggest 是辅助读模型，可根据部署把它设为 optional；核心 Identity/AuthN/AuthZ 仍可工作。是否 optional 不是代码作者随意决定，而是部署对产品可用性的定义。

如果业务前端把 Suggest 当成关键注册入口，就应设置 `required=true`。文档只能说明机制，不能替平台替业务决定可用性目标。

## 8. Draining 与优雅关闭

### 8.1 先拒绝新流量

`MarkDraining` 让 `/readyz` 返回 not_ready；gRPC health overall status 设置为 `NOT_SERVING`。等待 `drain_delay` 给 load
balancer/endpoints controller 时间摘除实例。

### 8.2 再停后台任务

Lifecycle hooks 停止：

- Outbox relay context；
- AuthZ policy sync subscriber；
- JWKS rotation scheduler。

之后模块 cleanup 停止：

- Suggest cron/refresher；
- Identity session revocation worker。

### 8.3 最后关资源和 listener

关闭 DB/Redis 后再继续处理请求会产生大量伪故障，因此资源关闭放在 drain 和 worker stop 之后。HTTP/gRPC listener 最后关闭。

各步骤错误被记录并继续执行，避免一个 cleanup error 阻止其余资源释放。代价是 shutdown 返回值不会聚合所有失败给 orchestrator，运维必须观察日志。

## 9. 后台任务的生命周期归属

| 任务 | Owner | 启动 | 停止 |
| --- | --- | --- | --- |
| JWKS rotation | AuthN runtime capability | `startRuntimeTasks` | lifecycle hook |
| domain event outbox relay | platform/container | `runOutboxRelay` goroutine | cancel context |
| AuthZ policy sync | AuthZ runtime | subscriber Start | subscriber Stop |
| Suggest refresh cron | Suggest module | module initialize | module Cleanup |
| Identity session revocation | Identity module | module initialize | module Cleanup |

Owner 必须同时暴露启动/停止或 cleanup；只启动 goroutine 不注册停止路径会造成测试泄漏、关闭竞态和重复消费。

## 10. 指标设计

当前指标遵循低基数原则，label 使用稳定枚举，如 component、result、scene、method，而不是 UserID、token、phone、resource instance。

已覆盖的高信号面包括：

- readiness component status/check result；
- AuthN OTP 和 refresh；
- AuthZ HTTP/gRPC assignment；
- Identity session revocation backlog/处理；
- Suggest refresh/query；
- JWKS rotation/material validation；
- Outbox relay 主要通过结构化日志和 status snapshot。

高基数业务标识应进入受控日志/trace，不应成为 Prometheus label，否则会造成时序爆炸。

## 11. 日志与敏感信息

生产配置使用 JSON、关闭颜色和 development 模式，MySQL log level 受约束。日志应记录：

- request ID/correlation；
- 稳定 action/resource/result；
- error category 和 retryable；
- duration/count；
- 必要的非敏感 ID。

禁止记录：

- 原始 Access/Refresh Token；
- password/OTP；
- IDP AppSecret/master key/private PEM；
- 完整手机号或未经评估的 provider response；
- 原始 SQL 参数中的秘密。

Public response 与内部日志分离：客户端拿稳定 code/message，服务日志持有受控 root cause。

## 12. 发布探针语义

生产 image/container liveness 使用 `/healthz`。远程发布脚本同时获取 health/readiness，并按 gate 规则判断：当前 `/readyz` 失败只告警而非自动回滚的事实必须明确保留。

这意味着“发布脚本成功”不等于“所有 required component ready”。生产验收必须单独保存 readiness 结果和观察窗口；不能从进程仍在运行反推上线健康。

## 13. 为什么不采用其他方案

### 13.1 一个 `/health` 检查所有东西

未采用。无法区分该重启进程还是停止派流，容易放大依赖故障。

### 13.2 readiness 直接返回底层 error

未采用。虽然排障方便，但会泄露拓扑和内部错误；详细信息应进入日志/metrics。

### 13.3 关闭时先关 listener，再随意 cleanup

未采用。没有 drain window，长请求和 worker 可能被硬切；资源顺序也不可控。

### 13.4 后台任务各自监听 OS signal

未采用。多个独立 signal handler 会竞争顺序。统一 process lifecycle 使停止顺序可测试。

### 13.5 所有组件都 required

未采用。辅助读模型可按产品目标降级；但 required/optional 必须显式配置，不能在失败时临时改口。

## 14. 当前代价与风险

- readiness 是瞬时采样，不代表一段时间内稳定；
- AuthN/JWKS/AuthZ 检查是窄化探针，不是完整 E2E；
- general domain outbox 已是 required readiness component；任何 unfinished bucket 的最老记录超过
  `health.readiness.outbox_max_pending_age` 时，实例退出 ready；
- shutdown step error 主要记录日志，不汇总为最终失败；
- 部分后台 goroutine 的首次失败只记录日志，需要指标/告警确保可见；
- 发布 gate 当前对 readiness 失败只告警，生产闭环依赖外部验收记录；
- `/healthz` 简单是设计选择，不能用它证明依赖健康。

## 17. 面试追问

**Liveness 和 readiness 的根本区别？**

Liveness 决定进程是否应被重启；readiness 决定实例是否应接新流量。依赖故障通常应先摘流，而不是重启所有进程。

**为什么 shutdown 要先 not-ready 再 sleep？**

负载均衡摘除不是瞬时完成。先公布 not-ready，等待传播，再停资源，可以减少新请求落到正在关闭的实例。

**指标为什么不能用 UserID 做 label？**

用户数会形成无界时序数量，导致 Prometheus 内存和查询成本爆炸；用户级排障应使用日志/trace，并做好敏感信息治理。
