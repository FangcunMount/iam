## 1. 本文回答

本文回答 10 个问题：

- IAM 哪些内容属于机器契约事实源？
- REST、gRPC、SDK、架构边界、文档链接分别以什么为准？
- 为什么不能从 prose docs 反推机器契约？
- 什么叫契约漂移？
- OpenAPI、proto、SDK、transport、application、docs 之间如何同步？
- 改 REST 契约时如何防漂移？
- 改 gRPC 契约时如何防漂移？
- 改 SDK public API 时如何防漂移？
- active docs 与 archive docs 如何区分？
- 修改后应该执行哪些 Verify？

本文是 `03-接入与契约/` 的契约治理文档，负责定义事实源、同步规则和防漂移检查。

## 2. 30 秒结论

IAM 接入契约的事实源分为五类：

| 契约 | 事实源 | 验证 |
| --- | --- | --- |
| REST | `../../api/rest` | `make api-validate` |
| gRPC | `../../api/grpc` | `make proto-gen` + `go test ./internal/apiserver/transport/grpc/...` |
| SDK | `../../pkg/sdk` | `go test ./pkg/sdk/...` |
| 架构边界 | `../../internal/pkg/architecture` | `go test ./internal/pkg/architecture` |
| 文档链接 | `../../scripts/check-docs-links.py` | `make docs-hygiene` |

最重要的规则：

```text
OpenAPI 是 REST 机器事实源；
proto 是 gRPC 机器事实源；
pkg/sdk 是 Go SDK public API 事实源；
architecture tests 是分层依赖事实源；
active docs 只能解释当前事实，不能反向定义机器契约；
archive docs 不能作为当前事实源引用。
```

如果只记一句话：

> 机器契约看代码和生成源，文档只解释语义和边界；任何契约变更都必须同步 transport、application、SDK、测试和文档。

## 4. 什么是契约漂移

契约漂移是指：

```text
机器契约、运行时实现、SDK、测试、文档之间不再一致。
```

常见漂移：

| 漂移类型 | 例子 | 风险 |
| --- | --- | --- |
| OpenAPI 与 handler 漂移 | OpenAPI 新增字段，handler 没读 | 调用方按文档调用失败 |
| handler 与 application 漂移 | handler 参数名改了，use case 仍按旧语义 | 业务行为错误 |
| proto 与 service 漂移 | proto 新增 RPC，server 未实现 | 生成成功但运行不可用 |
| proto 与 mapper 漂移 | field 改名，mapper 未同步 | 数据丢失或零值错误 |
| SDK 与 OpenAPI/proto 漂移 | SDK public API 还按旧字段 | 业务服务编译或运行失败 |
| 文档与机器契约漂移 | 文档写了 endpoint，但 OpenAPI 没有 | 误导调用方 |
| docs active/archive 漂移 | active docs 引用 archive 旧事实 | 当前事实被旧设计污染 |
| 架构边界漂移 | transport 直接访问 repository | 分层被破坏，安全链路绕过 |

## 5. 防漂移基本原则

### 5.1 机器契约优先

```text
REST path/schema/status/security 以 OpenAPI 为准；
gRPC service/message/field/enum 以 proto 为准；
SDK public type/method/options 以 pkg/sdk 为准；
运行时行为以 transport + application + domain 测试为准；
文档只解释语义、边界、阅读路径和修改检查清单。
```

禁止：

```text
从 prose docs 反推 REST 字段；
从 README 反推 proto message；
从示例代码反推 SDK public API；
从 archive 文档反推当前实现；
把未实现接口写成已实现事实。
```

---

### 5.2 契约变更必须联动

任何契约变更至少影响：

```text
机器契约；
transport mapper；
application command/query/result；
业务模块文档；
SDK；
测试；
示例；
接入文档。
```

不要只改其中一个点。

---

### 5.3 文档只解释事实，不制造事实

文档可以写：

```text
模块定位；
业务语义；
对象边界；
错误模型；
接入路径；
修改检查清单；
Verify 命令；
待核对状态。
```

文档不应该写：

```text
OpenAPI 中不存在的 endpoint；
proto 中不存在的 RPC；
SDK 中不存在的 public API；
当前代码未实现的能力，除非明确标注为规划；
archive 中的旧模型作为当前事实。
```

## 6. REST 防漂移

REST 契约事实源：

```text
../../api/rest/*.yaml
```

运行时事实源：

```text
../../internal/apiserver/transport/rest
```

修改 REST API 时必须同步检查：

```text
1. OpenAPI path/method 是否正确；
2. request schema 是否与 handler DTO 对齐；
3. response schema 是否与 handler response 对齐；
4. status code 是否与错误映射一致；
5. security scheme 是否正确；
6. handler 是否实现；
7. DTO mapper 是否更新；
8. application use case 是否匹配；
9. SDK 是否需要调整；
10. 文档是否需要同步。
```

Verify：

```bash
make api-validate
go test ./internal/apiserver/transport/rest/...
go test ./pkg/sdk/...
make docs-hygiene
```

REST 详细规则见 [01-REST接入契约.md](01-REST接入契约.md)。

## 7. gRPC 防漂移

gRPC 契约事实源：

```text
../../api/grpc/**/*.proto
```

运行时事实源：

```text
../../internal/apiserver/transport/grpc
```

修改 gRPC API 时必须同步检查：

```text
1. proto package/service/rpc 是否正确；
2. message field number 是否稳定；
3. 删除字段是否 reserved；
4. enum 新值是否兼容老客户端；
5. generated code 是否更新；
6. service method 是否实现；
7. proto mapper 是否更新；
8. status code 是否与错误模型一致；
9. application use case 是否匹配；
10. SDK 或 generated client 是否同步；
11. 文档是否需要同步。
```

Verify：

```bash
make proto-gen
go test ./internal/apiserver/transport/grpc/...
go test ./pkg/sdk/...
make docs-hygiene
```

gRPC 详细规则见 [02-gRPC接入契约.md](02-gRPC接入契约.md)。

## 8. SDK 防漂移

SDK public API 事实源：

```text
../../pkg/sdk
```

修改 SDK 时必须同步检查：

```text
1. public type/method/options 是否变化；
2. compile test 是否覆盖；
3. 是否 import internal 包；
4. REST OpenAPI 或 gRPC proto 是否同步；
5. generated code 是否同步；
6. 错误模型是否与 REST/gRPC 一致；
7. TokenSource / timeout / retry 是否符合安全策略；
8. 日志是否脱敏；
9. README / docs / examples 是否同步；
10. 业务模块语义是否需要补充。
```

Verify：

```bash
go test ./pkg/sdk/...
make api-validate
make proto-gen
make docs-hygiene
```

SDK 详细规则见 [03-Go-SDK接入模型.md](03-Go-SDK接入模型.md)。

## 9. 业务模块文档防漂移

业务模块文档事实源：

```text
../02-业务模块
```

业务模块文档负责解释：

```text
领域模型；
关键链路；
对象边界；
模块协作；
代码事实源；
Verify。
```

业务模块文档不负责定义：

```text
REST path；
REST request/response schema；
gRPC service/rpc/message；
SDK public API；
数据库 schema；
运行时配置。
```

修改业务模块文档时要检查：

```text
是否引用了不存在的契约；
是否把规划写成已实现事实；
是否把 archive 旧事实当当前事实；
是否与 REST/gRPC/SDK 接入文档冲突；
是否与模块 README 的文件名和阅读路径一致；
是否需要同步代码事实源路径。
```

Verify：

```bash
make docs-hygiene
```

涉及代码语义时补充对应模块测试。

## 10. active docs 与 archive docs

文档分为：

```text
active docs：当前事实和当前推荐路径；
archive docs：历史设计、旧方案、废弃模型、讨论记录。
```

规则：

```text
active docs 不应引用 archive 作为当前事实；
archive docs 可以保留历史背景，但必须标注非当前事实；
如果旧文档内容被合并，应删除旧入口或改为跳转说明；
README 只能指向 active docs；
接入文档只能引用当前机器契约和当前业务模块文档。
```

禁止：

```text
从 archive 复制旧字段到 OpenAPI；
从 archive 复制旧模型到 README；
active docs 链接 archive 表示“当前实现”；
使用旧文件名继续作为推荐阅读入口。
```

## 11. 架构边界防漂移

架构边界事实源：

```text
../../internal/pkg/architecture
```

重点防止：

```text
domain import transport；
domain import infra concrete；
domain import generated proto；
transport 直接访问 repository；
handler/service method 直接写业务规则；
infra store 直接调用 AuthZ；
SDK import internal；
IDP 直接创建 User；
Suggest 直接写 RoleBinding；
AuthN 直接做资源授权。
```

Verify：

```bash
go test ./internal/pkg/architecture
```

## 12. 修改类型与联动矩阵

| 修改类型 | 必改 | 可能需要改 | Verify |
| --- | --- | --- | --- |
| 新增 REST endpoint | OpenAPI、REST handler、application、docs | SDK、AuthZ route policy | `make api-validate` + REST tests |
| 修改 REST response 字段 | OpenAPI、handler mapper、tests | SDK、docs、examples | `make api-validate` + SDK tests |
| 新增 gRPC RPC | proto、generated、service、application、docs | SDK、AuthZ method policy | `make proto-gen` + gRPC tests |
| 修改 proto message field | proto、generated、mapper、tests | SDK、REST 对齐文档 | `make proto-gen` + SDK tests |
| 修改 SDK public API | SDK code、compile tests、SDK docs | OpenAPI/proto、examples | `go test ./pkg/sdk/...` |
| 修改业务模型名称 | 业务模块 docs、domain/application | REST/gRPC/SDK 字段命名 | module tests + docs hygiene |
| 修改错误模型 | OpenAPI/proto、transport mapper、SDK | 接入文档、示例 | transport tests + SDK tests |
| 修改授权策略 | AuthZ docs/code、middleware/interceptor | REST/gRPC route policy、SDK examples | AuthZ tests + architecture tests |
| 修改 Suggest 脱敏字段 | Suggest docs/code、OpenAPI/proto、SDK | 业务系统接入文档 | Suggest tests + API validate |
| 移动/删除文档 | README、链接、docs hygiene | 目录索引 | `make docs-hygiene` |

## 13. CI 建议

契约防漂移建议进入 CI：

```text
make docs-hygiene；
make api-validate；
make proto-gen；
go test ./pkg/sdk/...；
go test ./internal/apiserver/transport/rest/...；
go test ./internal/apiserver/transport/grpc/...；
go test ./internal/pkg/architecture；
```

如果 `proto-gen` 会修改生成文件，CI 应能检测工作区是否有未提交变更。

如果 OpenAPI 生成 SDK，CI 应能检测 SDK 是否与 OpenAPI 同步。

如果文档链接检查失败，应阻断合并，避免 README 指向不存在文件。

## 14. 常见反模式

| 反模式 | 问题 | 推荐做法 |
| --- | --- | --- |
| 从 prose docs 反推接口字段 | 文档不是机器契约 | 字段以 OpenAPI/proto 为准 |
| 改 OpenAPI 不改 handler | REST 契约漂移 | OpenAPI、handler、test 同步 |
| 改 proto 不跑生成 | gRPC 生成物漂移 | 执行 `make proto-gen` |
| 改 SDK public API 不改 compile test | 兼容性不可控 | compile test 保护 public API |
| active docs 引用 archive | 当前事实被旧方案污染 | active 只引用 active |
| handler/service method 写业务规则 | transport 吞并 application | transport 只做协议适配 |
| SDK import internal | 接入层穿透服务内部 | SDK 只依赖 public contract |
| domain import generated proto | 领域层污染 | mapper 留在 transport/application 边界 |
| Store / Index 直接调用 AuthZ | infra 吞并授权决策 | application 编排授权 |
| 错误模型各协议不一致 | 调用方处理困难 | REST/gRPC/SDK 错误语义映射一致 |

## 16. 本文总结

契约事实源可以压缩成：

```text
REST：api/rest + api-validate；
gRPC：api/grpc + proto-gen；
SDK：pkg/sdk + go test ./pkg/sdk/...；
架构边界：internal/pkg/architecture；
文档链接：docs-hygiene。
```

防漂移的核心规则是：

```text
不从 prose docs 反推机器契约；
改 OpenAPI 或 proto 后同步 transport、application、SDK、测试和接入文档；
改 SDK public API 后同步 SDK 文档、示例和 compile test；
active docs 不引用 archive 作为当前事实；
handler/service method 不承载业务规则；
SDK 不 import internal；
domain 不 import transport、infra concrete 或 generated proto；
CI 应覆盖契约、生成物、SDK、架构边界和文档链接。
```
