# 架构护栏与分层验证

> 状态：已实现 · 架构测试保护依赖方向和安全边界，不证明业务功能本身正确。

## 1. 分层目标

```text
transport -> application -> domain
                   ^          ^
                   | ports    |
                container -> infra implementations
```

更准确地说，container 位于最外层同时看见 application/domain/infra/transport，用于装配；domain 不认识 DB/Redis/Gin/gRPC；application 不认识 transport 或 concrete infra；transport 只消费 capabilities，不获取 container 或全局 Viper。

六边形架构的价值不是目录名，而是变化隔离：业务规则可在没有网络和数据库时测试，外部技术通过端口替换，协议变更不要求修改领域对象。

## 2. 当前 architecture test 保护什么

`internal/pkg/architecture/architecture_test.go` 解析 Go AST/import，主要约束：

- domain 不新增 infra、database、transport 等依赖；
- application 不 import transport/concrete infra，测试支持只能走受控 testutil；
- REST Router 不 import Container 或全局 Viper；
- application/container 只接收 typed config，不直接读 Viper；
- 模块 composition、capability 与退役 facade 不回流；
- AuthN JWT/Keyset 技术类型不重新进入 domain；
- transport logger 不读 body、Authorization、Cookie、RawQuery；
- gRPC internal error 不直接暴露底层 err；
- 生产 logging 与 maintenance binary 交付契约存在。

这已经超过普通“禁止反向 import”：它把重构后最容易复发的安全和兼容边界固化成可执行规则。

## 3. allowlist 为什么危险

临时架构例外如果只写 package 名，会永久化。当前 test 要求 allowlist 带原因，并检查 retired reason；当例外代码消失后，未使用 allowlist 也应失败，迫使维护者删除债务记录。

正确流程：

1. 优先增加 port/factory seam；
2. 确实无法一次迁移时，写最窄 file:import 例外；
3. 原因包含具体清理阶段/条件；
4. 新增 issue/计划但不能把计划当完成；
5. 重构完成时删除例外，并让 guard 验证没有回流。

## 4. 为什么只靠 code review 不够

依赖方向违规往往编译正常、测试正常，reviewer 也容易把一个方便 import 当成小事。随着代码增长，application 逐渐直接查 GORM、handler 直接取全局配置，最终模块无法独立测试。

AST guard 便宜、确定、在 CI 早失败，适合保护结构不变量。它不适合判断“这个领域服务拆得是否合理”等需要语义理解的问题；架构评审仍不可替代。

## 5. 端口设计的判断标准

好的端口使用业务语言：

```text
SessionRevoker.RevokeByUser
AtomicIdentityUnlinker.UnlinkOwnedUnlessLastActive
RuntimePolicyReloader.LoadPolicy
```

差的端口机械复制技术 API：

```text
Redis.Do
DB.Raw
Casbin.GetEnforcer
```

前者把业务原子性和责任说清楚，后者只是隐藏具体类型，仍把技术决策泄漏给高层。

## 6. 架构测试的盲区

它不能证明：

- port 实现符合业务语义；
- 事务覆盖了所有写入；
- Redis Lua 没有并发 bug；
- module bootstrap 顺序正确（需要 composition tests）；
- OpenAPI 与 runtime 对齐（需要 contract gates）；
- 生产配置/数据与仓库一致（需要部署证据）。

因此 architecture test 是必要护栏，不是“架构验收通过”的全部证据。

## 7. 面试追问

### Clean Architecture 的依赖倒置和 Go interface 有什么关系？

interface 只是工具。关键是端口由高层语义定义，低层实现它；若 application import infra interface 或暴露 GORM 类型，形式上有 interface 也没有倒置。

### container 可以依赖所有层，是否破坏规则？

Composition root 就是允许知道具体选择的最外层。它应只 wiring，不包含业务流程；否则会变成无法测试的上帝对象。

### 静态架构测试何时比 linter 更合适？

当规则是项目特有的包边界、退役路径和安全 token 时，AST 测试可直接表达并随仓库演进；通用 lint 适合语言级风格和常见 bug。
