# 测试、契约与验收证据

> 状态：已实现 · 依据 `95141ea2` 及当前独立工作区复核。既有用例、门禁和工作流有明确选择范围；本篇区分源码发现、实际执行、目标环境与业务接受。

IAM的一项检查应回答一个具体问题。例如“请求已取消后，应用仍调用补偿并给它独立deadline”，与“Redis中的Session已经撤销”需要不同证据。测试名、package路径、MySQL service、覆盖率或命令exit 0都不能替代这个判断。

本篇维护**怎样选择验证、怎样报告结果以及怎样识别缺口**。各模块维护规则、失败窗口和专项用例，阶段执行次数/日志摘要由[复核台账](../_data/reviews/2026-10-06-docs-refactor.md)维护；不把各篇的“本轮通过多少项”累积成一份当前全系统验收证明。

## 1. 先写要证明的结论，再检查证据是否匹配

审阅一份验证报告，依次检查六个要素：结论、源码/checkout、选择、后端与输入、断言、执行结果。以下是IAM中的不同证据责任。

| 要证明的结论 | 适用证据 | 还需要独立证明什么 |
| --- | --- | --- |
| 准入拒绝不建Session、不签Token | SignIn应用替身记录副作用并断言没有调用 | 真实用户状态与登录入口、持久化故障、完整公开认证链 |
| “最后一条active入口不能解绑” | 仓储结果与最终状态；目标MySQL的锁/竞争用例 | SQLite单连接结果不能代替MySQL行锁或多个进程 |
| 顶层事务rollback、Required复用与hook顺序 | UoW真实事务句柄和持久化断言，注明后端 | 借用宿主吞错、跨DB carrier、commit未知、取消后的hook |
| 服务证书/method/caller/AppID准入 | 使用当前server与真实loopback mTLS的正反用例 | 替身业务不证明Assignment、对象Scope、生产证书或用户接受 |
| REST/proto/SDK兼容 | 所选注册、字段、错误和消费者调用断言；生成/编译分别记录 | 规范比较不证明handler语义，嵌入Unimplemented可使未实现RPC仍编译 |
| 模块启动、drain和资源关闭 | 指定故障点、实际资源owner与结束状态 | closure顺序或单runner错误不证明完整Prepare abort/SIGTERM链 |
| 镜像已部署且业务可用 | 实际部署SHA/配置与环境窗口，真实业务正反用例 | 构建、推送、liveness或gRPC SERVING不能单独证明业务接受 |

这些证据互补，不构成“做了低层测试便自动到达高层”的阶梯。真实MySQL也不能检测未执行的Go内存race；race检测只观察本次执行的内存访问，不验证数据库事务竞争。架构护栏的直接import、路径和原文范围由[架构正文](01-架构护栏与分层验证.md)维护。

## 2. 测试名相同，后端、输入和断言可能不同

### 2.1 取消补偿：证明应用调用合同，不宣称真实撤销完成

`internal/apiserver/application/authn/signin/completion_test.go`的取消用例在调用前取消请求，Session、mint、保存与revoker都为替身。它分别注入mint/save/incomplete失败，检查SID、撤销reason、补偿context未取消且带deadline；mint/save分支用ErrorIs检查原注入错误仍可追溯，补偿失败时各分支检查补偿错误。incomplete分支没有断言自身错误码或消息。

这个结果支持“应用为失败补偿提供独立context”，没有观察真实Redis状态、五秒实际超时或I/O中途取消。若要证明失效Session不能再次刷新，需要另结合Redis状态、在线Token应用与完整入口。详见[Token主文](../02-业务模块/02-AuthN/05-关键链路-Token签发刷新吊销.md)。

### 2.2 AfterCommit：先看是否真的存在commit观察

`internal/apiserver/application/authn/signingkey/key_lifecycle_test.go`中`TestCreateAndActivateRefreshesOnlyAfterCommit`使用预置lifecycle结果；成功后检查刷新一次，mutation失败后不再刷新。“CommittedMutationSurvives…”检查刷新失败不改变应用返回，仍未运行数据库事务。

因此可报告“mutation能力成功/失败后的应用刷新策略通过”，不能报告“真实数据库提交后才发布”。若adapter借用宿主事务，还要观察宿主commit与发布时点；实际窗口由[密码材料与密钥主文](../03-基础设施/04-密码学密钥与令牌.md)维护。接口注释、测试名字和fake成功值都不构成提交回执。

### 2.3 Concurrent：并发goroutine并不等于真实行锁竞争

`internal/apiserver/infra/mysql/loginidentity/repo_unlink_concurrent_test.go`启动两个goroutine，断言一次Unlinked、一次LastActive，最终剩一条active。这是明确的结果断言，但后端由Identity testutil选择：

| helper / fixture | 缺环境或默认情况下 | 设置环境后的责任 |
| --- | --- | --- |
| `application/identity/testutil/mysql_helper.go` | 三个host入口均空时使用临时SQLite文件，连接池限制为1 | host非空时连接MySQL并AutoMigrate；必须使用明确的隔离fixture |
| `application/identity/testutil/db.go`的`SetupTestDB`；`testhelpers/db.go`的`SetupTempSQLiteDB` | 固定SQLite | 启动MySQL service不会自动把它换成MySQL |
| `testfixtures/authzdb/database.go`要求MySQL的入口 | 缺专用DSN时Skip | 有DSN才执行相应MySQL路径，仍需检查选测与结果 |
| migration的`openMigrationMySQL` | 缺`MYSQL_HOST`时Skip，不做连接 | 接入隔离MySQL；部分用例有独立required约定 |
| 显式可靠消息proof | 特定环境缺失直接失败，部分tag用例另有Skip | 必须满足各用例的MySQL/NSQ/旧binary等前提 |

表中简写都位于`internal/apiserver`下，migration helper位于`internal/pkg/migration/jwks_single_active_mysql_test.go`。三个Identity host入口为`MYSQL_HOST`、`IAM_APISERVER_MYSQL_HOST`、`MYSQL_HOSTNAME`；不同`REQUIRED=1`与`REQUIRE_MYSQL=true`是各helper独立约定，没有统一开关。

本篇清除外部后端环境后执行LoginIdentity仓储包，得到SQLite单连接结果。MySQL适配器中的锁和真实跨连接竞争需要MySQL证据，详见[身份绑定](../02-业务模块/02-AuthN/03-关键链路-Linking登录身份绑定.md)与[MySQL事务](../03-基础设施/01-MySQL事务与迁移.md)。目录名有mysql、测试名有Concurrent都不足以确定实际后端。

### 2.4 指标调用与实际断言分开

`internal/apiserver/infra/suggest/metrics/recorder_test.go`调用`ObserveSelection(10,4)`后只断言`index_terms=42`；刷新测试调用duration/items/timestamp，但检查的是部分Counter标签与正值。metric名称存在也不证明样本、时间和计数正确。

这不能扩大为“Suggest所有指标都无断言”：QueryProfile用例确实检查matched/visible，Refresher也检查upsert/tombstone。判断必须定位测试体。真实exporter、采集窗口和告警另取证，见[观测主文](../03-基础设施/06-可观测性就绪与关闭.md)。

## 3. exit 0、package pass、test pass与Skip分别统计

本篇对旧独立角色迁移测试做了一个明确选择：在移除MySQL环境的子进程中执行`TestFreshDatabaseMigratesToIndependentRolesMySQL`。它在helper中Skip，命令exit 0；以下摘取真实JSON事件，仅保留判断所需字段：

```json
{"Action":"run","Package":"github.com/FangcunMount/iam/v5/internal/pkg/migration","Test":"TestFreshDatabaseMigratesToIndependentRolesMySQL"}
{"Action":"skip","Package":"github.com/FangcunMount/iam/v5/internal/pkg/migration","Test":"TestFreshDatabaseMigratesToIndependentRolesMySQL"}
{"Action":"pass","Package":"github.com/FangcunMount/iam/v5/internal/pkg/migration"}
```

这里是**1项已选择但跳过、0项测试pass、1个package pass**。它证明缺环境分支被观察到，没有执行迁移。未选择的测试也不能记为Skip；`go build`或`go test -c`登记为编译。`-run '^$'`只表示没有匹配的普通用例：存在测试程序时仍会执行包初始化及可能的TestMain，不能只凭flag记为“仅编译”；无测试文件的包应按实际输出另记。

当前旧测试仍断言版本35，`migrate.go`的Run在FreshStages后继续Up，当前完整链测试要求40。MySQL工作流选择完整链，未选择旧35用例。因此它的专项绿色也不能证明旧断言通过；本篇没有为了变绿修改测试或执行真实迁移。

汇总JSON时以`Package+Test`标识记录run/pass/skip/fail，package结束事件另计；父测试和子测试都会产生事件，pass事件数量不是独立业务场景数。要补充有无缓存、选择表达式、标签和超时。`-count=1`用于明确本次重跑；`-short`只向测试提供短运行标志，不自动隔离后端，`-list`也只是枚举顶层名字。

## 4. CI声明、实际执行与已发布门禁

### 4.1 普通CI

`.github/workflows/ci.yml`声明三类job，lint/test成功后才build：

| job | 当前步骤 | 支持的结论与限制 |
| --- | --- | --- |
| lint | docs-hygiene、docs-facts、历史分类、api-validate、依赖下载、make lint；工作区另加docs-validation-tests | 每步成功才支持该步范围；make lint有golangci-lint或go vet后备，二者不能被概括成同一检查器 |
| test | 依赖下载/verify、service-token退役检查、reviewer脚本用例、`go test -v -race -coverprofile=coverage.out -covermode=atomic ./...`、报告/上传 | 默认构建条件、下划线目录、用例条件仍限制覆盖；没有消息tag/真实MySQL/NSQ服务 |
| build | `make build`，上传`bin/apiserver`，保留7天 | 构建和短期artifact，不证明maintenance镜像内容、启动、迁移或部署 |

普通CI未显式设置`-coverpkg`、`-count=1`或消息tag，也无仓库内覆盖率阈值与proto/Swagger再生成diff门禁。`atomic`指并发安全的覆盖计数，并不表示业务写入原子性。覆盖报告依赖被编译/执行的代码与计数范围；语句被执行也不证明返回值、副作用、失败或恢复被断言。不能仅提高百分比代替关键不变量用例。

**工作区与main必须分别报告。**本篇撰写阶段，比对确认main `95141ea2`已经有docs-hygiene/docs-facts等步骤；独立重构工作区新增文档validator回归步骤与target，同时增强同名链接/事实脚本的锚点、历史分类和SVG/PNG摘要等能力。主CI已有同名命令不代表这些增强已发布。当时只读核对声明，没有触发新远程CI，第40–46篇新稿尚未发布；本批正文发布范围见[阶段台账](../_data/reviews/2026-10-06-docs-refactor.md#6-第三批第四十至四十六篇2026-10-07)。

### 4.2 MySQL专项：触发、选中和实际后端是三件事

`.github/workflows/concurrency-tests.yml`支持手动触发及固定路径push/PR触发，启动MySQL 8。它还有迁移、维护与合成备份/恢复fixture步骤，并非只跑一个仓储并发命令。

首条命令只选`internal/apiserver/infra/mysql/...`，名字匹配Concurrent/Concurrency及几个指定用例。仅AuthZ application/domain/runtime变化不在自动触发路径内；`infra/authz/integration/hardening_mysql_test.go`的Role删除/Grant创建、Resource缩动作/Grant创建不在该package选择中。就算专项启动，Assignment等固定SQLite fixture也不会自动变成MySQL。

工作流保存文本并检查退出码，没有统一校验预期用例集合和零Skip；日志artifact仅失败时上传。审阅一次运行时应取到选测表达式、实际测试名、Skip和后端证据，而不是只看job标题。备份/恢复合成fixture证明该fixture流程，不是线上数据、完整schema或生产恢复窗口。

### 4.3 可靠消息专项：不同链路各自拥有证据

| 入口 | 当前可观察范围 | 不应扩大为 |
| --- | --- | --- |
| `reliable-messaging-m6-subscriber.yml` | 两项container AuthZ选测与一项PlatformWiring；父测试另执行冷启动子测试、检查receipt及无Skip输出 | 全部Original/Standard UoW、维护handoff或业务端到端 |
| `reliable-messaging-m6-image-handoff.yml`与对应script | 独立probe经IAM UoW写Grant/撤销/恢复，走镜像真实mTLS/ACL Check并核FIN | 公开Assignment写接口、QS对象Scope或用户业务接受 |
| `reliable-messaging-primary-image.yml` | 构建、资产/候选身份及显式候选发布步骤 | 已部署生产、完成consumer切换或业务接受 |
| `scripts/testing/reliable-messaging-business-proof.sh` | 独立IAM/QS测试binary与隔离环境；设置`RM_BUSINESS_REQUIRED=1` | 当前普通/M6工作流已执行该业务proof |

前三份文件位于`.github/workflows`。exact-image自动触发路径只列部分fixture目录，没有涵盖实际构建的另外三个probe目录；只改它们不会自动触发该专项。工作流声明和历史证明可作为导航，新的运行仍要绑定具体SHA、镜像和receipt。发布状态、业务ACK与Broker确认的责任见[事件主文](../03-基础设施/03-事件与Transactional-Outbox.md)，本篇未运行这些外部专项。

## 5. 契约和生成验证不能相互替代

`make api-validate`实际顺序是Spectral、warning基线、已提交Swagger/OAS schema比较、静态路径双向比较、一个Gin注册用例。Docker可用时使用镜像，否则npx后备固定CLI；只有整条执行成功才报告api-validate通过，单独Python或Go子步骤只支持对应结论。

当前通用schema比较按短名匹配完整OAS key，70个候选全部跳过，Suggest另有精确响应/schema专项；Gin用例只纳入JWKS及v2，v3 AuthN/v4 AuthZ未进入这道动态门。两个静态路径集合相同也不能证明路由真实注册、security/default/error或handler行为正确。生成链、比较范围和兼容矩阵由[契约治理](../04-接口与SDK/01-REST-gRPC与契约治理.md)拥有，不在本篇复制全部DTO细节。

proto注册文本、descriptor/Registry、SDK公开符号编译、实际RPC各证明不同责任。`pkg/sdk/public_api_compile_test.go`不编译Markdown或下划线程序；旧AuthZ例子两处API失配由[SDK主文](../04-接口与SDK/02-Go-SDK与业务系统接入.md)登记。生成文件存在、注册成功和Unimplemented嵌入都不能证明每个方法可调用且被正确授权。

## 6. 从变更选最小充分验证，再写可复核结果

先识别改变了哪个合同，再补对应证据；不要按目录名机械运行一组“全部验证”。已有用例可以复用，但要读它的输入和断言，必要时才增加新的故障/并发场景。

| 变更 | 验证选择 | 新证据应观察的结果 |
| --- | --- | --- |
| SignIn完成/补偿 | 应用用例；若改变Redis动作，再选adapter和在线Token链 | 原失败保留、未授权无状态、补偿失败可恢复；真实状态另观察 |
| 登录入口/Assignment事务 | 领域/应用与UoW；目标DB的锁/约束专项 | 最终不变量、rollback、借用提交者和未知结果，不能只断言NoError |
| mTLS/ACL/内容准入 | 所选证书/方法正反例；对应RPC的拒绝无副作用 | transport身份与业务目标分别检查，不能以Allow替身证明对象访问 |
| DTO/proto/SDK | 实际生成与diff、受影响consumer编译、字段/错误/默认值行为 | 旧请求/源码/binary各自的兼容合同，不仅符号数量 |
| 启动/后台/关闭 | 模块可用性、故障点、在途请求和资源结束 | abort/join/仍可重试的关闭结果；liveness与readiness分开 |
| 文档或门禁 | 链接/锚点、事实、validator回归；必要的局部源码用例 | 文档事实与检测范围，不能由文档绿色反推业务接受 |

本篇实际的离线选择为五个全量包：UoW、SignIn、signingkey、LoginIdentity仓储、Suggest metrics；另选一个迁移测试观察Skip。选择前核对了helper，并在子进程移除外部数据库/消息和专项环境，关闭依赖下载。以下是其中一个命令，不是完整系统验收入口：

```bash
go test -race -count=1 -json -timeout=90s ./pkg/uow/gorm
```

不要把`go test ./internal/apiserver/...`或`-short ./...`当作自动安全离线模板：helper可能读取现有环境、AutoMigrate或启动外部proof。广覆盖入口仍有价值，但前提是明确后端、隔离边界和适用tag；执行时不能为了获得绿色结果静默排除本来必须验收的场景。

报告至少保留checkout/未提交范围、命令/选择/tag、工具链/环境类别、后端、预期与实际事件、断言定位、原始输出/摘要、结论与未执行项。本篇44个pass事件与1个Skip分别登记；如果结论要求真实MySQL，替身通过只能作为局部进展，该结论仍未完成。

## 7. 发布、运行与业务接受的证明继续分开

提交SHA不充分：dirty工作区需要记录实际相关文件摘要与归属；源码分析、基线失败、修改后验证和历史执行是不同记录。旧日志可复核或复用，但应写明原日期/选择，并确认输入无偏移，不能把源码推论写成新复现实验。

| 状态 | 最少要绑定的证据 | IAM中的边界 |
| --- | --- | --- |
| 已构建/推送 | 镜像digest、构建输入和asset身份 | 不代表部署job执行 |
| 已部署 | 目标环境、实际运行SHA/digest/配置、部署结果和时间 | 不代表所有迁移/数据/证书与消费者已验收 |
| 运行检查通过 | 指定health/ready、版本/任务信号及明确窗口 | 聚合采样、历史liveness或固定SERVING不代表永久正确 |
| 业务接受 | 可信用户/caller、动作和对象范围、提交与消费结果、正反场景 | Check允许、Broker确认、业务ACK分别观察，不能互相替代 |

生产证据还要按变更补迁移version/dirty、active JWKS、worker freshness、积压/错误窗口或备份恢复，不能机械以一份列表替代验收。当前未取得的部署配置/数据/消费者事实写unknown。报告只保留可审计来源、时间与操作者，不复制token、secret或敏感日志正文。

## 8. 待实施的治理设计

**选择与预期结果清单。**由用例owner维护必跑测试名、tag、后端和必需环境；CI核对实际run与pass/skip，并常态保留成功日志。可先覆盖跨聚合锁、迁移与M6，避免一开始自动解析全仓所有动态子测试。成本是清单随重命名维护；验收包括必需用例消失、未选择或Skip时失败，允许的条件跳过仍能解释。这是候选，现有工作流没有统一清单门禁。

**从覆盖百分比转向风险合同。**为最后入口、CAS、结果未知、旧key保留、Prepare失败资源等维护输入/故障/断言表，并追踪source-only、stub、目标后端、部署和业务证据的缺口。owner是对应模块，领域与适配器应共同定义可观察结果。成本是fixture和故障点设计；增加覆盖计数不能替代这些断言。

**可追溯验证回执。**将checkout加相关dirty摘要、选择、工具链、环境类别、断言与原始日志链接保存到统一回执；脚本不保存凭据。相同SHA但配置/生成物/fixture不同不能合并成同一接受结果。先复用现有台账与receipt，新增机器校验需明确版本、保留期和失败政策，不能把目前临时摘要清单当作已经部署的证据服务。
