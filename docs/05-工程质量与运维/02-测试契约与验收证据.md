# 测试、契约与验收证据

> 状态：已实现 · 本文定义各验证门能支持的结论，避免用一个绿色命令替代完整验收。

## 1. 证据金字塔不是互相替代

| 证据 | 能证明 | 不能证明 |
| --- | --- | --- |
| domain/application unit | 规则与编排在替身下成立 | 真实 DB/Redis/provider |
| repository/integration | SQL、约束、事务在目标数据库成立 | 全进程 wiring、生产数据 |
| concurrency | 特定并发不变量 | 所有时序/负载 |
| architecture | import/安全结构边界 | 业务语义 |
| contract | schema/path/proto/注册对齐 | handler 业务正确 |
| SDK compile | public symbol 可编译 | runtime 兼容与网络安全 |
| full `go test -race ./...` | 当前 checkout 广覆盖、race detector 命中 | 未覆盖路径、外部环境 |
| build/image | 可编译/打包 | 可启动、可迁移、可服务 |
| migration test | 指定旧状态可升级 | 线上真实数据分布 |
| staging smoke/load | 近真实环境行为 | 生产全量与长期窗口 |
| production observation | 该环境该窗口结果 | 永久正确 |

报告必须写清命令、checkout、环境和结果，不能只写“测试通过”。

## 2. 当前 CI 门

`ci.yml` 分三 job：

- lint：docs hygiene、docs facts、OpenAPI validate、依赖下载、make lint；
- test：依赖校验、`go test -race -cover ./...`；
- build：在前两者成功后 `make build` 并上传短期 artifact。

并行的 `concurrency-tests.yml` 只在相关路径或手动触发时启动 MySQL 8，运行仓储并发、JWKS/Identity migration integration，以及 backup/restore 合成演练。

因此普通 CI 绿色不能推出 MySQL concurrency workflow 本次也运行；验收时要检查 path trigger 和实际 run。

## 3. 契约 gates 的边界

`make api-validate` 包含 Spectral、canonical OpenAPI/Swagger 比对与 route contract check，需要 Docker daemon。若本地 Docker 不可用，
应明确写“未执行”，不能用 Go transport test 替代。

`proto_contract_test` 保护 proto 与 runtime registration，`public_api_compile_test` 保护 SDK symbol。
它们分别不覆盖 REST schema lint 和真实 server-client E2E。

## 4. 并发不变量要在真实存储验证

SQLite/内存 stub 无法准确模拟 MySQL row lock、unique index、isolation 和 affected rows。以下事实需要 MySQL-backed test：

- active phone 唯一；
- 最后一个 LoginIdentity 原子解绑保护；
- Role/PolicyVersion 并发写；
- JWKS single active guard；
- ProfileLink self/active uniqueness；
- migration 对真实 DDL/data 的行为。

Race detector 发现 Go 内存数据竞争，不会发现两个独立进程的 SQL lost update；MySQL integration 也不会发现未同步 map 的 Go race。两者都要有。

## 5. 原始 checkout 与修复后验证

代码审查/验收要区分：

```text
baseline evidence：修改前就通过/失败什么
post-change evidence：本轮修改后通过/失败什么
```

修复后测试通过不能反推原始实现无缺陷。Dirty worktree 还要注明哪些改动属于用户、哪些属于本轮，避免把未提交外部修改算作本轮产出。

## 6. 生产证据边界

没有 production connector、凭据或可审计结果时，只能写“无法访问/未验证”，不能写“生产无错误”。Production acceptance 至少需要：

- image SHA/config fingerprint；
- migration version/dirty；
- `/healthz` 与 `/readyz`；
- active JWKS 与关键 worker freshness；
- 关键业务 smoke；
- 指标/错误率/积压在明确窗口内；
- 备份存在且恢复演练有独立证据。

人工台账应记录证据链接/时间/操作者，不复制 token、SQL 或敏感日志正文。

## 7. 推荐验证顺序

```bash
# 1. 快速结构/文档/契约
make docs-hygiene docs-facts
go test ./internal/pkg/architecture ./pkg/sdk

# 2. 受影响模块
go test ./internal/apiserver/...

# 3. 全量 race
go test -race ./...

# 4. OpenAPI（Docker 可用时）
make api-validate

# 5. MySQL workflow / staging / production evidence
# 必须按环境单独记录
```

实际执行应按变更风险裁剪，但跳过项要列出原因与残余风险。

## 8. 面试追问

### 100% coverage 是否等于正确？

不等于。Coverage 只说明语句被执行，不说明断言充分、并发/故障/生产数据覆盖。关键是不变量、边界和失败语义是否被针对性测试。

### Mock 越多测试越快，为什么还要 integration？

Mock 证明高层按约定调用端口；真实存储才证明端口实现的 SQL、事务和原子性满足约定。两者验证不同责任。

### 验收为什么要记录未执行项？

绿色结果只在已执行范围内有效。隐藏未执行的 migration/load/production 检查会制造错误确定性，无法做风险决策。
