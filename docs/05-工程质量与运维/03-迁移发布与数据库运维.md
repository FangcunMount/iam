# 迁移、发布与数据库运维

> 状态：已实现 · Schema 迁移嵌入 apiserver 二进制并可在启动时执行；生产备份/恢复由独立受控脚本完成。

## 1. 当前迁移机制

`internal/pkg/migration/migrations/*.sql` 通过 `embed.FS` 编入二进制，golang-migrate 使用 `schema_migrations(version, dirty)` 追踪状态。当前文件序列到 000023，中间缺号不影响版本引擎。

启动时 `DatabaseManager.Initialize` 建立连接后根据 `migration.enabled` 调 `Migrator.Run()`：

- clean 且落后：依序 Up 到最新；
- 已最新：`ErrNoChange`，正常继续；
- dirty：明确失败，阻止非降级启动；
- migration SQL 失败：返回错误；
- MySQL 根本不可用时 `runMigrations` 会 warning 并返回 nil，但后续 `prepareResources` 在非降级模式仍因 MySQL unavailable 失败。

应用业务连接与迁移 `sql.DB` 分开，避免 migrator Close 影响业务 pool。

`internal/pkg/migration/migrations/*.sql` 是 schema 的唯一事实源。仓库不再保留可误执行的静态 `schema.sql`；`configs/mysql/bootstrap.sql` 只在迁移完成后写入幂等系统基线数据，`scripts/check-docs-facts.py` 会阻止静态 schema 副本回归或 bootstrap 混入 DDL。

## 2. 不要修改已发布迁移

迁移版本只执行一次。修改已经在线上执行过的 `000001` 不会改变已有库，还会让新库与旧库通过不同历史到达不同 schema。

规则：

- 已发布 migration 视为不可变；
- 修复用新版本 forward migration；
- up/down 成对，但 destructive down 不应被假定安全；
- DDL、数据回填、约束建立分阶段设计；
- 先清理冲突数据，再加 unique/not-null guard；
- 大表变更评估锁、磁盘、复制延迟和执行时间。

`internal/pkg/migration/MIGRATION_GUIDE.md` 已收敛为当前入口和权威文档索引，不再保留旧 `iam_*` 表名、失效 Make target 或可误执行的数据迁移 SQL；实际 migration SQL、process wiring 和 integration tests 仍是实现证据。

## 3. Expand/Contract 发布

需要无停机兼容时：

```text
Release A: expand schema（新列/表可选，旧代码仍可运行）
Release B: dual read/write 或 backfill，观测完成
Release C: 切 canonical read，停止旧写
Release D: contract（删除旧列/约束）
```

一次 migration 同时 rename/drop 并部署只认新 schema 的代码，会让滚动发布期间旧实例崩溃。当前自动启动迁移适合小规模单序部署；多实例大 DDL 更适合独立 migration job 和显式发布 gate。

## 4. Dirty state 不是把 flag 改回去

Dirty 表示某版本执行中断，MySQL DDL 可能已经部分生效。正确处置：

1. 停止继续自动重试；
2. 保存 schema/version/错误证据并确认备份；
3. 逐条核对该 up SQL 哪些已生效；
4. 决定 forward-complete 或恢复备份；
5. 只有物理状态与目标版本一致时才 force version；
6. 在 staging 复现并记录处置脚本。

仅 `UPDATE schema_migrations SET dirty=0` 会让迁移器跳过未完成 SQL，是最危险的“修复”。

## 5. 生产发布探针

生产容器 liveness 访问容器内 `127.0.0.1:9080/healthz`；部署脚本还检查 `/readyz`。两者均 200 才宣布发布成功。

`/readyz` 失败只让发布 gate 失败并输出稳定组件状态，不自动 rollback/restart。原因是自动回滚可能恢复与已升级 schema 不兼容的旧镜像，或在外部依赖故障时形成重启循环。操作者应先判断 migration、依赖和 runtime state 再选择动作。

## 6. 备份与恢复

`db-ops.yml` 的 backup/restore/status 全部调用 `scripts/dbops/database-operation.sh`：

- 只接受 MySQL 8 client；
- 凭据写入临时 0600 defaults file，不进入命令行；
- backup 使用 `--single-transaction --quick` 流式 gzip；
- 先写 `.partial`，非空且 `gzip -t` 成功后原子 rename；
- 最终文件 0600，目录 0700；
- 当前只保留最近 3 份；
- restore 只接受精确文件名、拒绝路径/符号链接/损坏 gzip；
- 原始 mysql stderr 不进入 workflow 日志。

备份成功不等于可恢复。Concurrency workflow 在 MySQL 8 fixture 中执行 backup -> drop -> restore -> data assertion，证明脚本链可用；生产仍需要按 RPO/RTO 定期做隔离恢复演练。

## 7. 当前生产边界

`db-ops.yml` 已没有 migrate 操作；生产迁移依赖应用启动或未来独立机制。自动启动迁移与多实例同时启动的并发、DDL 锁和权限分离需要部署层控制。

生产应用账号与迁移账号目前是否实际分离不能从仓库确认；这是部署证据，不应由文档宣称已完成。用户维护的验收记录用于补充此类当前环境事实。

历史表退役只读预检使用 `scripts/dbops/legacy-retirement-preflight.sh` 或 `make db-retirement-preflight`。format v5 要求显式环境标签和数据库名，凭据通过 0600 临时 defaults file 或绝对路径 defaults file 传给 MySQL；输出 server/migration 元数据、估算和精确行数、schema 指纹、读取前即时 I/O、数据库对象依赖、AuthN 分类 parity 及逐表 eligibility。AuthN 只以不可变身份冲突、无 canonical 权威的歧义和待补缺失作为 blocker；canonical 密码材料、状态和锁定事实的可变差异只作聚合观测，旧 JOIN 无法到达的孤儿凭据单独计数。表 I/O 依次读取 Performance Schema、`sys.schema_table_statistics` 和启用 `opt_tablestat` 的阿里云 RDS `information_schema.TABLE_STATISTICS`；任何零计数都只能按对应计数器生命周期和证据窗口解释。2026-08-07 目标库账号无法读取前两条路径，业务所有者已分别授权 `platform_tables` 和 `audit_tables` I/O waiver，并接受无法排除低频外部查询的剩余风险。完整字段和执行示例见[遗留资产、兼容层与数据库退役审计](06-遗留资产兼容层与数据库退役审计.md)。

`000019_retire_legacy_tables` 只退役 Identity 的 `children/guardianships`。它会先补齐 `profiles/profile_links`，再做数据一致性和数据库对象依赖断言，最后执行单条 DROP；任何冲突或依赖都会让 migration 失败并保留旧表。该版本不包含 `auth_accounts`、`auth_credentials_legacy`、tenant、字典或审计表。

`000020_retire_schema_version` 只处理被 `schema_migrations` 替代的冗余元数据表，生产已验收 `version=20, dirty=0` 且 `schema_version` 不存在。`000021_retire_unused_platform_tables` 只处理已从当前 bootstrap 移除的 `tenants/data_dictionary`，生产已通过独立发布验收 `version=21, dirty=0` 且两表不存在。两版都在唯一最终 DROP 前检查 FK、trigger、view、routine、event 和不可见定义，down 明确不可逆。

`000022_retire_unused_audit_tables` 只处理 `operation_logs/audit_logs/auth_token_audit`；三表在发布前精确行数和数据库对象依赖均为 0，业务所有者已确认 IAM MySQL 不承担这三类日志真相源，并接受当前结构化日志本地保留 30 天的能力边界。生产已通过独立发布验收 `version=22, dirty=0` 且三表不存在。AuthN 已取得 format v3 目标库 dry-run 基线，确认 230,093 个旧账号全部已有 canonical 身份；format v4 在目标库分批提交 180,000 条旧 OAuth 登录键，format v5 已补齐最后 49,029 条并由独立新快照复验证明 remaining 0、hard conflict 0、eligible。当前运行镜像、数据库对象依赖和健康证据已闭合；Performance Schema、`sys` 与阿里云 Object statistics 均未提供表级 I/O 观察窗。2026-08-12 业务所有者明确接受无法排除低频外部访问的剩余风险，并授权 `authn_tables` I/O waiver 与 `000023` 发布。

`000023_retire_legacy_authn_tables` 只处理 `auth_accounts/auth_credentials_legacy`。迁移不写 canonical 数据；它要求两张旧表成对存在或成对缺失、`auth_login_identities/auth_credentials` 的关键 schema 完整、所有可达账号/密码/手机号/OAuth 已有 canonical 映射且无 hard conflict，并检查 FK、trigger、view、routine、event 及不可见定义，最后才用一条 DROP 同时删除旧表。缺少旧账号的 3 条密码和 5 条 OAuth 因历史查询本就不可达，由发布前完整备份承接取证与恢复。down 明确不可逆。

AuthN 准备批通过 `iam-maintenance reconcile-authn-legacy` 统一执行。dry-run 只输出聚合计划；`reconcile-authn-verify` 只读且仅在 `retirement_eligible=true` 时返回成功，用于 apply 后和发布前机器门禁；`status` 的 AuthN scope 会在同一任务中先执行 v5 verify，再把短期、私有且一次性消费的证据交给通用预检，避免重复运行旧 v4 AuthN parity。apply 必须经 `Database Operations` 的 production environment 审批、指定两小时内的完整备份并输入 `BACKFILL_AUTHN_LEGACY_MISSING`。format v5 按默认 5,000、最大 50,000 行分批提交；apply（包括零写入重跑）始终返回 `verification_required=true`，必须由新快照 verify 收口。整个生命周期持有 MySQL server-side named lock。旧 OAuth 键迁移为 marker-scoped LoginIdentity，已有 canonical owner 优先且不覆盖，无 canonical 权威的跨 owner 歧义 fail closed。该准备批本身不删除旧表；本次 `000023` 仍须以发布前 fresh verify、owner waiver、零数据库对象依赖和完整备份为执行前提。

`000019` 生产执行前后至少保留以下 gate：

1. 执行 secret-safe 只读预检并保存环境、运行镜像 SHA、migration version/dirty、对账和依赖摘要；
2. 完成可恢复备份和隔离恢复断言，评估 metadata lock 与单序发布窗口；
3. 仅由一个 migration runner/实例执行 000019；
4. 执行后确认 `version=19, dirty=0`、`profiles/profile_links` 数据完整且 `children/guardianships` 不存在；
5. 若失败，保留现场并选择 forward-complete 或恢复备份，不手改 dirty flag。

`000020–000022` 的历史发布 gate 是：运行当时的 format v2 只读预检且对应 eligibility 为 `eligible`，保存 I/O 状态、采集时间和剩余风险说明，完成可恢复备份，确保单 migration runner，并逐版验收 version/dirty 和旧表不存在。`000023` 使用 format v5。`platform_tables`、`audit_tables`、`authn_tables` waiver 只能用于各自获批表组；它们不能覆盖非零 I/O、dirty、版本、数据对账或数据库对象依赖，也不适用于 Identity。

## 8. 面试追问

### `--single-transaction` 是否保证所有备份一致？

对 InnoDB 事务表提供一致快照，但 DDL、非事务表和外部对象仍有边界；还要带 routines/triggers/events 并做恢复演练。

### 为什么 rollback 不一定比 forward fix 安全？

Down migration 可能删新数据，旧代码也可能不兼容已写入的新格式。生产通常优先可验证的 forward fix，恢复备份则意味着明确的数据回退/RPO 决策。

### 自动迁移为什么在多实例下危险？

多个实例可能竞争 DDL/metadata lock，且应用启动超时与 migration 生命周期耦合。独立 job 能保证单执行者、显式权限和更清晰的发布 gate。
