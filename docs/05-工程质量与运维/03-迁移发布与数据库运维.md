# 迁移、发布与数据库运维

> 状态：已实现 · Schema 迁移嵌入 apiserver 二进制并可在启动时执行；生产备份/恢复由独立受控脚本完成。

## 1. 当前迁移机制

`internal/pkg/migration/migrations/*.sql` 通过 `embed.FS` 编入二进制，golang-migrate 使用 `schema_migrations(version, dirty)` 追踪状态。当前文件序列到 000018，中间缺号不影响版本引擎。

启动时 `DatabaseManager.Initialize` 建立连接后根据 `migration.enabled` 调 `Migrator.Run()`：

- clean 且落后：依序 Up 到最新；
- 已最新：`ErrNoChange`，正常继续；
- dirty：明确失败，阻止非降级启动；
- migration SQL 失败：返回错误；
- MySQL 根本不可用时 `runMigrations` 会 warning 并返回 nil，但后续 `prepareResources` 在非降级模式仍因 MySQL unavailable 失败。

应用业务连接与迁移 `sql.DB` 分开，避免 migrator Close 影响业务 pool。

`internal/pkg/migration/migrations/*.sql` 是 schema 的唯一事实源。仓库不再保留可误执行的静态 `schema.sql`；`configs/mysql/bootstrap.sql` 只在迁移完成后写入幂等系统基线数据，`scripts/check-docs-facts.py` 会阻止静态 schema 副本回归或 bootstrap 混入 DDL。

## 2. 不要修改已发布迁移

迁移版本只执行一次。修改已经在线上执行过的 `000001` 不会改变已有库，还会让新库与旧库通过不同历史到达不同 schema。

规则：

- 已发布 migration 视为不可变；
- 修复用新版本 forward migration；
- up/down 成对，但 destructive down 不应被假定安全；
- DDL、数据回填、约束建立分阶段设计；
- 先清理冲突数据，再加 unique/not-null guard；
- 大表变更评估锁、磁盘、复制延迟和执行时间。

仓库中的旧 `internal/pkg/migration/MIGRATION_GUIDE.md` 含历史表名/命令，不能作为当前 schema 事实；以实际 SQL、process wiring 和 integration tests 为准。

## 3. Expand/Contract 发布

需要无停机兼容时：

```text
Release A: expand schema（新列/表可选，旧代码仍可运行）
Release B: dual read/write 或 backfill，观测完成
Release C: 切 canonical read，停止旧写
Release D: contract（删除旧列/约束）
```

一次 migration 同时 rename/drop 并部署只认新 schema 的代码，会让滚动发布期间旧实例崩溃。当前自动启动迁移适合小规模单序部署；多实例大 DDL 更适合独立 migration job 和显式发布 gate。

## 4. Dirty state 不是把 flag 改回去

Dirty 表示某版本执行中断，MySQL DDL 可能已经部分生效。正确处置：

1. 停止继续自动重试；
2. 保存 schema/version/错误证据并确认备份；
3. 逐条核对该 up SQL 哪些已生效；
4. 决定 forward-complete 或恢复备份；
5. 只有物理状态与目标版本一致时才 force version；
6. 在 staging 复现并记录处置脚本。

仅 `UPDATE schema_migrations SET dirty=0` 会让迁移器跳过未完成 SQL，是最危险的“修复”。

## 5. 生产发布探针

生产容器 liveness 访问容器内 `127.0.0.1:9080/healthz`；部署脚本还检查 `/readyz`。两者均 200 才宣布发布成功。

`/readyz` 失败只让发布 gate 失败并输出稳定组件状态，不自动 rollback/restart。原因是自动回滚可能恢复与已升级 schema 不兼容的旧镜像，或在外部依赖故障时形成重启循环。操作者应先判断 migration、依赖和 runtime state 再选择动作。

## 6. 备份与恢复

`db-ops.yml` 的 backup/restore/status 全部调用 `scripts/dbops/database-operation.sh`：

- 只接受 MySQL 8 client；
- 凭据写入临时 0600 defaults file，不进入命令行；
- backup 使用 `--single-transaction --quick` 流式 gzip；
- 先写 `.partial`，非空且 `gzip -t` 成功后原子 rename；
- 最终文件 0600，目录 0700；
- 当前只保留最近 3 份；
- restore 只接受精确文件名、拒绝路径/符号链接/损坏 gzip；
- 原始 mysql stderr 不进入 workflow 日志。

备份成功不等于可恢复。Concurrency workflow 在 MySQL 8 fixture 中执行 backup -> drop -> restore -> data assertion，证明脚本链可用；生产仍需要按 RPO/RTO 定期做隔离恢复演练。

## 7. 当前生产边界

`db-ops.yml` 已没有 migrate 操作；生产迁移依赖应用启动或未来独立机制。自动启动迁移与多实例同时启动的并发、DDL 锁和权限分离需要部署层控制。

生产应用账号与迁移账号目前是否实际分离不能从仓库确认；这是部署证据，不应由文档宣称已完成。用户维护的验收记录用于补充此类当前环境事实。

历史表退役只读预检使用 `scripts/dbops/legacy-retirement-preflight.sh` 或 `make db-retirement-preflight`。入口要求显式环境标签和数据库名，凭据通过 0600 临时 defaults file 或绝对路径 defaults file 传给 MySQL；输出只有 server/migration 元数据、表级聚合、依赖计数和对账计数。Performance Schema 的零 I/O 只覆盖 server 启动或 summary 最近清零后的窗口，不能单独批准删表。完整字段和执行示例见[遗留资产、兼容层与数据库退役审计](06-遗留资产兼容层与数据库退役审计.md)。

## 8. 面试追问

### `--single-transaction` 是否保证所有备份一致？

对 InnoDB 事务表提供一致快照，但 DDL、非事务表和外部对象仍有边界；还要带 routines/triggers/events 并做恢复演练。

### 为什么 rollback 不一定比 forward fix 安全？

Down migration 可能删新数据，旧代码也可能不兼容已写入的新格式。生产通常优先可验证的 forward fix，恢复备份则意味着明确的数据回退/RPO 决策。

### 自动迁移为什么在多实例下危险？

多个实例可能竞争 DDL/metadata lock，且应用启动超时与 migration 生命周期耦合。独立 job 能保证单执行者、显式权限和更清晰的发布 gate。
