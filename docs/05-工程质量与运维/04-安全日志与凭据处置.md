# 安全日志与凭据处置

> 状态：已实现 · 按当前材料出口和三个处置命令核对范围；真实凭据失效、日志删除及外部副本处置未在本轮执行。

## 1. 先分别回答材料、出口和处置效力

一次“日志安全修复”至少包含三件事：停止继续产生不该输出的材料，限制既有材料的读取和复制，使已暴露凭据按其验证合同失效。只关闭一个logger、删除一个目录或清理一个Redis族，都不能替代另外两件事。

本篇拥有日志材料约束、处置目标/回执和恢复接受；[观测](../03-基础设施/06-可观测性就绪与关闭.md)拥有信号、sink和保留的实现细节，[传输](../03-基础设施/05-传输层与服务间安全.md)拥有拒绝/panic控制流，[Redis](../03-基础设施/02-Redis与缓存一致性.md)拥有扫描/状态合同，[密码学](../03-基础设施/04-密码学密钥与令牌.md)与[IDP凭据](../02-业务模块/04-IDP/01-应用凭据与AppToken缓存.md)拥有材料和代次变化。这里将这些合同组合成可判断的处置步骤，不再复制全部业务链路。

| 材料 | 用途与约束 | 不能混同 |
| --- | --- | --- |
| Access/Refresh Token、密码/OTP、AppSecret、私钥和含凭据的Redis key | 为认证、交换或签名使用；禁止作为普通日志、指标标签和任意公共error的排障正文 | 现有业务API有秘密导出路径，实际caller/归属准入由IDP等主文维护；不代表可以让logger再次复制 |
| User/Session/LoginIdentity/App ID、IP、request/trace ID | 可按具体用途关联事实；仍要控制来源、读取范围、长度及保留 | “不是token”不等于匿名、可信或可无限记录 |
| 错误分类、稳定code、阶段、计数、耗时 | 普通诊断优先使用这些有界信息 | 分类丢弃cause，不代表另有完整安全审计 |
| SQL、请求/响应、失败消息、heap/core及部署artifact | 可能混合上述材料，各有独立owner和访问/副本政策 | JSON、压缩或数据库存储不是材料脱敏 |

“不得包含凭据”是材料约束；下文的源码和测试只证明特定出口遵守哪些部分。仓库没有一个覆盖所有logger、依赖hook、指标、消息及外部平台的通用脱敏层。

## 2. 当前保护落实在哪些出口

### 2.1 省略原值、分类错误与静态检查分别看

[APILogger](../../internal/pkg/middleware/api_logger.go)不展开headers/query/body/响应正文或handler error：开始记录实际URL.Path、解析后的ClientIP和关联ID，结束记录route模板、状态/大小/耗时；health/ready/metrics等固定路径跳过。ClientIP可按代理配置读取forwarded headers；实际Path和传入ID仍可能带调用方提供的内容，不能把metadata统一视为经过验证的常量。

[gRPC logger](../../internal/pkg/middleware/grpc_server_logger.go)记录method、peer/metadata关联信息、耗时与code，不展开请求或status message。它不为每个业务字段做过滤，也不证明外层拒绝、panic及stream的记录完全相同；完整控制流回链传输正文。

[BaseHandler](../../pkg/core/handler.go)与[safelog](../../internal/pkg/safelog/error.go)只记录code、HTTPStatus、category、retryable，不返回err.Error；Core公共错误取coder.String。gRPC mapper将Internal/Unknown/DataLoss及若干服务器失败改成稳定文案，但已存在的InvalidArgument等status仍保留message。因此“所有gRPC错误都已脱敏”过强，生产者仍须保证这些message可以公开。

AuthN/IDP的Login解析日志省略provider code/secret/token/raw response；既有sentinel测试只证明这条映射路径。IDP[凭据](../../internal/apiserver/application/idp/wechatapp/service_credentials.go)/[管理](../../internal/apiserver/application/idp/wechatapp/service_metadata.go)错误日志仍有err.Error()，不能据专用Login日志证明它们安全，也不能仅由err.Error()认定某次生产错误已包含秘密。

[日志护栏](../../internal/pkg/architecture/architecture_test.go)检查两个固定transport logger的禁用片段、指定安全文件、gRPC service正则、mapper片段与生产配置/Dockerfile文本；不是全文数据流分析。换写法、跨函数/helper、依赖模块、未扫描出口和目标部署配置需要对应证据。

### 2.2 生产准入与依赖旁路

[Options.Validate](../../internal/apiserver/options/validation.go)在production-like标准装配中要求MySQL log-level=1、JSON、关color/development；这是准入要求，不只是一份YAML建议。直接构造组件或改变装配路径要另核对。现有GORM测试在silent模式不求值/输出SQL callback；另一用例组合GORM LogLevel=4与应用logger debug，确认普通SQL走SQLDebug并输出。不能把GORM info与应用info当成同一级别，不覆盖所有数据库调用或其他日志出口。

Redis适配器自身省略Refresh原值和key，但[DatabaseManager](../../internal/apiserver/process/database.go)可安装锁定component-base v0.8.0的RedisHook。该hook只遮盖AUTH/HELLO参数；GET/SET/DEL等参数按长度截断后仍可输出，错误/慢命令分支在普通info配置下也能进入日志。Refresh key含原token，截断不等于省略。生产模板enable-logging=false只描述这一配置选择，当前Validate和固定logger护栏没有统一阻止这个旁路。本篇未做hook泄露实验。

LogSender记录phone/code，release校验拒绝显式sms.provider=log；但若解码后SMS组非nil且Provider为空白，Complete只补nil组，Validate未拒绝空值，[sender factory](../../internal/apiserver/container/authn/application.go)再回退log。这是带前提的源码分支，未运行完整配置解码/启动或认定生产已发生。不要把“显式log被拒绝”扩大为全部有效配置均禁止这个出口。

### 2.3 其他出口不能用access logger代替检查

| 出口 | 当前边界 | 处置需要的责任 |
| --- | --- | --- |
| HTTP指标 | 锁定prometheus middleware使用完整URL.String和Host；query可能进入标签，/metrics未挂JWT/AuthZ | 指标生产者、采集与存储副本分别确认范围；删除日志不删除series |
| 可选dump、Recovery、net/http及gRPC Recovery | 可输出headers/body/response、panic或stack；内层mapper/Audit不覆盖全部分支 | 按实际装配检查错误和异常出口；不能只调低常规log level |
| SMS MQ wire | 包含phone/code，LogSender也明文输出 | 消息/provider用途与权限独立；不是禁止业务投递，而是避免追加诊断副本 |
| IAM policy失败审计 | 保存收到的raw payload/metadata/cause，不承担Direct SMS失败审计 | 数据库/消息owner裁定保留、读取和清理；本篇日志工具不清审计表 |
| 配置、CLI与部署诊断 | 不应靠输出完整Options/env、SQL或Docker logs定位目标 | 配置和交付owner使用非秘密目标回执；脚本的有限过滤不证明所有artifact安全 |

失败审计同时承担重复handoff的message identity与内容核对；删行或脱敏会改变后续去重/对账依据，不能直接套用普通日志的年龄策略。候选保留/加密方案必须同时决定调查材料和重复交接的寿命，本篇不删除这些记录。

这些是当前出口和条件窗口，不是本轮生产泄露报告。具体query、panic和失败消息的源码条件分别由观测、传输及[事件正文](../03-基础设施/03-事件与Transactional-Outbox.md#9-direct-sms-的成功与补偿边界)维护。

## 3. 同一条日志可能留下哪些副本

生产配置的duplicate输出将error送入all/app与error文件及stdout/stderr；warn进入all/app与warn文件及stdout，特定sink使用精确level匹配，error不会因此再进入warn文件。[Compose](../../build/docker/docker-compose.prod.yml)又用json-file保留容器输出，并将宿主/data/logs/iam挂到容器/var/log/iam；[部署脚本](../../scripts/cd/remote-deploy.sh)还可能打包configs和logs，失败诊断输出docker logs。文件、容器日志、发布备份、流水线artifact、代理/采集平台及人工导出不是同一份资产。

时间轮转按首次写入生成日期文件。锁定writer请求目录0755、文件0644，实际权限还受umask、已有文件与挂载影响，不能由“生产JSON日志”推导0600。该分支也没有实现配置注释暗示的100MB/10备份/自动压缩合同；详细保留/Flush限制归观测正文。IAM目录处置既不处理Docker管理的日志，也不清外部平台或发布备份。

处置记录应按副本owner列目标、时间范围、访问限制、处置状态和验证方式；未查看的副本标为unknown。保留run ID、源码/部署SHA、数量及批准依据，不把秘密正文重新贴到工单、聊天或公开artifact。若取证确需原材料，应另定受限取证范围及保存期限，不能以“审计需要”为由自动再复制一份。

## 4. 三个命令的准入、目标和回执

镜像提供/app/iam-maintenance命令行入口，三个命令不会随apiserver自动运行，也不提供网络API；两种Redis清理会主动访问Redis。它们**默认 dry-run**，不是默认不访问目标。

| 命令 | apply确认短语与范围 | 目标/成功输出 |
| --- | --- | --- |
| purge-refresh-tokens | PURGE_REFRESH_TOKENS；仅refresh_token:* | 独立Redis env；mode及scanned/matched/deleted |
| purge-login-state | PURGE_IAM_LOGIN_STATE；Session、两个索引、Refresh、ConsumedRefresh、RevokedAccess六族 | 同一env读取器；mode及六族聚合计数 |
| dispose-sensitive-logs | DELETE_PRE_5_4_IAM_LOGS；分析选中的第一层文件 | CLI先限制规范化/var/log/iam；apply有预览及completed两条JSON |

确认短语防误触，不验证操作者权限、目标身份、停写状态、备份或前次dry-run结果。三个命令都没有本批operation ID/目标指纹绑定；不能拿上次预览或别的范围给本次请求授权。

Redis读取IAM_APISERVER_REDIS_CACHE_*，不加载apiserver YAML；未提供时可落到127.0.0.1:6379/DB0，cluster或非空ADDRS拒绝。HOST/PORT/DB/账号/TLS必须同实际目标核对，不能因为“进入同一个容器”就认为配置一致。TLS允许显式insecure skip；目标验证与连接加密仍是不同决定。连接凭据不应打印进回执。

参数合同也有差别：Refresh/日志解析错误归一化，未检查剩余位置参数；login-state检查NArg并可直接返回解析错误。Refresh/日志dry-run接受空白confirm，login-state要求严格空串。publicMaintenanceError只是返回err.Error，不是所有维护命令的通用过滤器；本篇只能按这些入口的具体包装说明公共输出。

## 5. Redis清理：先限定失效目标

### 5.1 两种范围不能互换

Refresh清理不删除Session、索引、ConsumedRefresh、RevokedAccess、Challenge、OTP或IDP cache；它阻断相应旧Refresh继续查到记录，不自动阻止已有Access使用、登录或其他来源续期。

六族清理还删除撤销marker，本质上是登录状态重置，不是“再增加一层撤销”。当前在线Session验证、JWT声明资格与SDK本地验签有不同感知边界；尤其SDK本地验签不查询Redis Session/denylist，清理不能提供全部在途请求的同步拒绝。细节归[Token](../02-业务模块/02-AuthN/05-关键链路-Token签发刷新吊销.md#4-在线verify检查当前状态返回的仍是jwt声明)及[Session](../02-业务模块/02-AuthN/03-Session-Token与JWKS.md)，不得自行承诺“全量即时登出”。

| 暴露材料 | 本篇命令可做到 | 仍需对应owner决定 |
| --- | --- | --- |
| 一批Refresh值 | 删除整个匹配族的记录，影响范围可能远大于这批 | 只撤销特定Session/入口是否更合适；旧Access和已交付请求怎么接受 |
| 六族在线登录状态 | 逐族删除选中key | Session/本地验签/在途、重新登录及denylist移除的结果 |
| 密码材料或入口锁定状态 | purge不修改Credential | 当前在线Token检查不读Credential；改密/锁定不等于撤销既有Session，User/入口状态与准入另按AuthN合同判断 |
| OTP/Challenge、IDP AppToken/Secret | 两种purge均不清这些族或provider凭据 | 一次性证明、provider失效及两层缓存/在途交换的合同 |
| JWT签名私钥、IDP主密钥 | purge不轮换、不rewrap、不修复PEM/元数据 | 签名资格、旧SDK缓存及主密钥/密文的同批迁移与恢复 |

IDP有具体的秘密交付路径：gRPC GetWechatApp可解密返回AppSecret，REST/gRPC Token出口交付AppToken，接收方另承担存储与日志责任。当前Token读取/刷新未检查IsEnabled，Secret轮换只更新仓储、不清两层缓存或执行provider撤销；停用/轮换不能直接当成全部Token出口与微信侧材料已失效。

更换IDP Secret也不自动使已有IAM Session失效；仅更换主密钥会令旧密文失去读取路径，相同Secret的fingerprint no-op不能承担rewrap。判断依据由IDP/密码学主文维护，不能通过扩大Redis删除范围“修好”另一种材料。

### 5.2 预览、扫描及失败后的事实

helper使用SCAN MATCH和整批UNLINK，不使用KEYS/FLUSHDB；COUNT是工作量提示，遍历可重复、变化中的key可能被返回或遗漏，见[SCAN合同](https://redis.io/docs/latest/commands/scan/)。当前对返回数量求和而不去重，也没有将返回数组再切成严格batch-size小批；matched不是全库唯一快照，deleted是UNLINK回执求和。

[UNLINK合同](https://redis.io/docs/latest/commands/unlink/)将key移出keyspace与后台内存回收分开；它不证明副本、持久化文件或备份中的秘密被擦除。CLI成功只证明当次遍历/回执完成，不是全系统材料处置。

Refresh默认timeout=2分钟，login-state=5分钟。它们传递context，但Options未开启ContextTimeoutEnabled；锁定go-redis v9.16.0的socket I/O默认取Background并有命令重试，不能承诺严格墙钟总上限或在途UNLINK被撤销。现有cancel测试只在调用前取消，未注入丢回包或真实执行中超时。

例如第一批删除成功，第二批失败，或者Redis已执行UNLINK但回包丢失：错误不能证明零删除。helper有部分结果，两个CLI错误路径不输出这些计数；成功后的JSON写入失败也可表现为非零。保持停写、记录“已执行但结果需对账”、重新预览当前状态，不按旧计数盲目继续；六族之间没有共同事务。

### 5.3 经目标与停写核对后的模板

操作者应先绑定实际源码/部署、目标Redis实例与DB、影响族、旧Access/JWKS资格、签发/会话writer和接受清单。停写由实际writer owner取证，工具不检测，也不自动停止apiserver。仅关闭migration、API入口或某个runner不能自动证明所有writer已停。

以下是选择范围后的模板，只运行已批准的对应命令；本篇没有执行它们：

```text
/app/iam-maintenance purge-refresh-tokens
/app/iam-maintenance purge-refresh-tokens --apply --confirm=PURGE_REFRESH_TOKENS
```

六族清理必须另做对应预览，不能复用Refresh清理的批准与数量：

```text
/app/iam-maintenance purge-login-state
/app/iam-maintenance purge-login-state --apply --confirm=PURGE_IAM_LOGIN_STATE
```

## 6. 日志处置：选择全部文件，不是只删命中行

### 6.1 CLI路径、文件集合与统计意义

[CLI](../../cmd/iam-maintenance/main.go)先ValidateProductionLogDirectory：Clean后只接受/var/log/iam，Lstat实目录并EvalSymlinks核对；库函数AnalyzeLogDirectory本身允许其他实目录，临时目录测试不等于生产canonical入口已执行。

只选择第一层app/warn/error家族：精确family.log，或family.前缀且以.log结尾、含.log.或以.log.gz结尾。它不是严格日期/版本文件名校验；非白名单文件与nested目录跳过，命中白名单却是symlink/非普通文件则拒绝。压缩候选按.gz后缀解读gzip。

marker只统计每行的Refresh相关片段和GORM相关片段，大小写无关，同行可各增加一个分类命中；不解析token、SQL语义或全部秘密。total_bytes是文件大小（gzip为压缩体积），earliest/latest是文件mtime而非事件时间。Scanner限制单行4MiB，无全扫描字节/耗时上限；坏gzip/超长行可使分析失败。

确认短语DELETE_PRE_5_4_IAM_LOGS没有日期、5.4版本或marker筛选能力。**分析选中的白名单文件全部删除，即使marker=0或文件包含修复后新日志。** 因此需要绑定本批完整集合和保留/取证要求，不能凭短语解释删除时间范围。

### 6.2 路径身份复核和两条回执

Dispose逐文件重新Lstat、检查regular/non-symlink及SameFile，再os.Remove。它检查文件身份，没有比较内容SHA、大小/mtime变化；同一文件继续追加仍可能通过。校验、打开和删除之间也没有共同原子绑定；路径竞争、日志轮转、hardlink/打开句柄、外部副本和底层持久化另有边界。删除目录项不是安全擦除证明。

apply先输出mode=apply的分析摘要，此时deleted_files仍为0；随后删除，成功才输出第二条result=completed。库层部分失败保留DeletedFiles，CLI却归一化错误而丢弃部分结果。第一条JSON不能作为完成回执；最后输出失败也不能推出文件未删。

既有测试先在调用Dispose前将error.log替换为symlink；Dispose随后删除app.log，再在error.log复核时失败，最后重新分析剩余文件并重试。它证明这一受控顺序，不证明真实目录竞争已封闭或原集合可无条件恢复。应停止/协调日志writer、轮转和采集，确认取证副本及保留边界，再按当前集合处置；这些协调没有由CLI自动提供。

```text
/app/iam-maintenance dispose-sensitive-logs
/app/iam-maintenance dispose-sensitive-logs --apply --confirm=DELETE_PRE_5_4_IAM_LOGS
```

仅在目标容器挂载与实际权限吻合时使用模板。不可恢复删除需要对应范围批准；Docker日志、发布备份、指标和外部平台由各自owner另行处置，不能给本工具换一个path去越界清理。

## 7. 恢复接受与证据如何组织

一个可审阅的处置批次至少要分别保存：目标/源码与非秘密有效配置、暴露出口及副本清单、writer/采集协调证据、选定族/文件集合的批准、各阶段回执或结果未知、恢复后的接受。CLI当前没有生成这样的完整批次账本，以下是操作约定及候选输入，不是自动实现。

恢复检查应按本次动作选择断言：新登录/Refresh轮换是否成功；受影响旧Refresh是否拒绝；在线Session和实际SDK调用方式是否达到约定拒绝；新日志/指标/错误出口是否还产生该材料；外部副本是否按owner完成处置。/healthz、/readyz只是进程/组件信号，不证明这些断言。

至少观察一个 Access Token TTL，并按本批旧令牌真实到期、签名资格/SDK缓存、Runtime/在途与采集延迟延长；未知窗口不能写成已关闭。若泄露私钥对应的旧公钥仍被消费者接受，还可能产生新的签名材料；其接受仍取决于声明/在线状态等，不能只等原来一批Token到期。单个TTL、401数量或一次新登录成功都不能证明全体凭据失效，拒绝摘要也不是完整业务接受。

安全恢复不能把已处置的旧token、已退役私钥或敏感日志随数据库/镜像回退重新引入。镜像、数据库、Redis、Broker及密钥恢复分别核对兼容和材料资格，完整资产合同回链[迁移发布](03-迁移发布与数据库运维.md)。本篇没有进行真实失效、删除、主密钥迁移或生产恢复。

## 8. 候选设计：针对哪种失败补合同

以下均未实施，应分别由对应owner选择；没有用文档改写替代业务修复。

| 候选与owner | 具体变化 | 收益、成本及验收 |
| --- | --- | --- |
| 材料出口owner：有界字段协议 | 普通日志按用途白名单收code/阶段/非秘密ID；Redis hook只收命令名/族/耗时，禁参数；显式公共message与受限细节分开 | 避免安全适配器被依赖旁路抵消；会减少排障细节，需受限诊断协议。以GET/SET失败、provider错误及异常出口的虚构sentinel逐sink验证 |
| 配置owner：校验与factory共同选择 | production-like拒绝raw Redis command logging/dump与空SMS provider；Complete、Validate、复制及factory使用同一有效模式 | 封闭“校验未选、构造补选”窗口；兼容旧空值配置需迁移。跑解码→完成→校验→装配矩阵，不能只测validator字符串 |
| 处置owner：批次与结果状态 | operation ID绑定目标实例/DB/族或受限文件manifest、源码、停写证据；区分planned、partial、outcome_unknown、verified并持久回执 | 可对账输出/回包失败；增加秘密最小化、回执存储及权限。注入第二批失败/提交后输出失败，不能自动认定零修改或完成 |
| 文件/sink owner：批准集合与生命周期 | 明确截止/版本或完整集合，内容变化及轮转政策；协调writer/采集，采用目录/文件身份绑定删除；限定权限与副本保留 | 防止新文件、同inode追加和路径变化超出批准；需平台机制与取证成本。并发替换/追加/轮转及外部副本按明确接受测试 |
| 凭据owner：按验证方式定义效力 | 分开Refresh、在线Session、离线JWT、provider缓存、OTP和密钥代次；需要即时拒绝时选择在线准入/代次或业务屏障 | 避免扩大删除却未覆盖消费者；增加可用性/缓存/兼容代价。分别验旧Access、在途刷新、旧provider cache及业务已接受请求 |

对token输出hash/mask不是当前统一方案：它仍引入关联标识，不能用“不是原值”跳过用途、读取范围和保留设计。默认排障不需要时省略；确需关联时另定作用域/期限和访问合同，不让它成为新的持久秘密索引。
