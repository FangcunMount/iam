# 安全日志与凭据处置

> 状态：已实现 · 维护二进制只提供离线命令，不提供网络 API，也不会随 apiserver 自动执行。

## 1. 日志边界

IAM 日志不得包含 Refresh Token、access token hint、Authorization/Cookie、密码/OTP、Redis credential key、完整请求体、GORM 原始 SQL或底层 gRPC Internal 错误。

生产配置使用 GORM silent 和结构化 JSON；transport logger 只记录 request/service metadata。architecture test 扫描危险 API/字符串，gRPC mapper 收敛公共错误文案。

Hash/Mask token 仍可能成为跨日志关联标识并被误用，因此当前选择完全省略 credential，而不是“脱敏后记录”。

## 2. 维护工具安全模型

镜像内 `/app/iam-maintenance` 支持：

```text
purge-refresh-tokens
dispose-sensitive-logs
reconcile-authn-legacy
```

三个命令均默认 dry-run；删除或补缺写入必须同时传 `--apply` 和各自的精确确认短语。输出只有聚合计数、字节、时间范围和稳定结果，不输出 token、密码材料、SQL、文件名或底层依赖错误。AuthN reconciliation 的数据语义和发布门禁见[迁移发布与数据库运维](03-迁移发布与数据库运维.md)。

## 3. Refresh Token 全量失效

预检：记录发布 SHA、active JWKS kid、Redis DB 和 Token TTL；确认 Redis 不是 cluster；先部署安全日志版本并验证 `/healthz`、`/readyz`、新登录。

```text
/app/iam-maintenance purge-refresh-tokens
```

dry-run 确认范围后停止 apiserver，避免清理中产生新 token，再执行：

```text
/app/iam-maintenance purge-refresh-tokens \
  --apply --confirm=PURGE_REFRESH_TOKENS
```

工具以 `SCAN MATCH refresh_token:*` + 分批 `UNLINK` 工作，不使用 `KEYS`/`FLUSHDB`。它不删除 Session、Challenge、OTP 或 IDP cache。

清除 refresh token 只阻止长期续期，不立即使既有 access token 或全部 Session 失效。如需紧急全面下线，还要按 User/LoginIdentity/Session 撤销，并等待/评估 access token 在线验证语义。

## 4. 修复前日志处置

工具只接受规范化 `/var/log/iam`，只处理第一层白名单日志与轮转文件，拒绝 symlink、递归目录和越界路径。

```text
/app/iam-maintenance dispose-sensitive-logs

/app/iam-maintenance dispose-sensitive-logs \
  --apply --confirm=DELETE_PRE_5_4_IAM_LOGS
```

删除不可恢复；外部日志平台、备份和失败部署 artifact 的副本需在各平台单独处置。只保留 run ID、时间范围、批准人和删除结果，不复制敏感正文作为证据。

## 5. 恢复与观察

重启后验证：

- `/healthz=200`、`/readyz=200`；
- 新登录与 refresh rotation 成功；
- 旧 refresh token 返回既有 401；
- 新日志不出现 credential、SQL 或底层 Internal 文本。

至少观察一个 Access Token TTL，关注 refresh 401、重新登录量、Redis 错误和 readiness。历史 token/log 不应在回滚时恢复；安全修复应向前兼容。

## 6. 为什么默认 dry-run 仍不够

Dry-run 与 apply 之间状态会变化，所以还需要停写窗口或可重复的范围校验。确认短语只能防误触，不能代替授权审批、审计、备份和目标环境核对。

工具对 Refresh Token 采用宽 prefix scope，属于高影响动作。必须在与 apiserver 同 env/network 的容器上下文运行，先确认 Redis DB，不得靠默认 host/db 猜测生产目标。

## 7. 面试追问

### 日志里记录 token hash 安全吗？

它不泄露原 token 的前提取决于 token 熵，但仍形成稳定关联标识并扩大处理范围。若排障并不需要，最小化原则是完全不记录。

### 为什么不用 FLUSHDB？

Redis 同 DB 还有 Session、OTP、Challenge、IDP cache 等不同族。FLUSHDB 破坏范围过大；SCAN+UNLINK 能精确处理目标族并减少阻塞。

### 删除日志为什么也需要证据？

需要证明删除范围与授权一致、外部副本已处理且新版本不再产生泄漏，但证据本身不能再次复制敏感内容。
