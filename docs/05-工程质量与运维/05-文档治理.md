# 文档治理：事实归属、更新闭环与验证边界

> 状态：已实现 · 2026-10-07 对照main `6f73026d`与撰写阶段独立重构工作区复核。本文解释现有文档组织和检查器；当时尚未发布的工作区增强、人工维护约定与未实施候选分别说明，阶段发布结果另见台账。

文档治理要使读者能找到一个问题的完整答案，并判断答案依据哪个实现、合同和执行证据。IAM中“撤销后不能再访问”至少涉及Session在线验证、SDK本地验签、结果缓存与在途业务请求；将这句话复制到四篇正文，不能消除四种效力的差别。

当前做法是按责任划分完整正文，用摘要和链接连接不同视角，保留带日期的历史证据，并用脚本检查有限的事实与引用。**内容归属是维护约定，自动检查没有证明全部语义一致。**具体提交规则统一归[维护约定](../CONTRIBUTING-DOCS.md)；本篇说明怎样处理冲突、选择更新范围和识别绿色结果的边界。

## 1. 一个完整答案归谁，取决于它维护哪个合同

“同一主题一个主文”不能解释成一个词只能出现一次。AuthN和Redis都谈Session：前者维护状态、准入与撤销效力，后者维护key、TTL、原子操作和恢复机制。它们应回答不同问题，并相互回链；复制同一份完整撤销时序会造成两个更新点。

| 读者要回答的问题 | 完整正文 | 相邻材料保留什么 |
| --- | --- | --- |
| Refresh在哪一步改变Session，轮换失败后是什么状态？ | [Token主链路](../02-业务模块/02-AuthN/05-关键链路-Token签发刷新吊销.md) | Session模型定义对象；Redis解释存储动作；SDK解释消费与重放 |
| User停用事实如何提交，如何交接撤销任务？ | [Identity边界](../02-业务模块/01-Identity/04-模块边界-Identity与AuthN-AuthZ-Suggest.md) | AuthN维护准入、在线Session与在途接受窗口；安全专题只串联风险 |
| 身份解绑与既有Session是什么关系？ | [Linking](../02-业务模块/02-AuthN/03-关键链路-Linking登录身份绑定.md) | Session模型定义状态；AuthN边界解释跨模块接受效力 |
| 授权写入已提交，哪个实例和哪个读取入口能观察到？ | [AuthZ收敛](../02-业务模块/03-AuthZ/04-关键链路-多实例策略收敛.md) | Outbox维护交接；运行时维护组件与探针；发布页维护该批观察 |
| 客户端请求字段可省略吗，描述与handler为何不一致？ | [AuthZ REST](../02-业务模块/03-AuthZ/05-关键链路-REST管理与路由授权.md)维护行为；[契约治理](../04-接口与SDK/01-REST-gRPC与契约治理.md)维护描述差异和演进 | API README指向机器文件和生成入口；SDK页解释调用方影响 |

目录owner不自动等于个人审批者，也不证明CI强制了所有权。现有[AuthN owner表](../02-业务模块/02-AuthN/README.md)和[AuthZ owner表](../02-业务模块/03-AuthZ/README.md)帮助按问题定位；跨文更新仍由作者和reviewer检查。当前Identity与[AuthN边界](../02-业务模块/02-AuthN/07-模块边界-AuthN与Identity-IDP-AuthZ.md)仍有撤销任务去重/完成状态的复述，需要按Stage/Worker协议与准入/接受窗口核对并收敛，不能由owner表存在推断重复已全部消除。新增正文的判断是“现有owner是否无法完整承载这个问题”，不是补齐对称目录。

概览解释对象和边界，专题解释跨模块约束与方案取舍，表达材料组织讲述顺序。它们可以保留理解所需的结论，例如“本地验签没有在线Session撤销语义”，但不再维护一份全量规则、代码索引和失败矩阵。减少重复的代价是读者需要跳转，因此摘要必须给出适用边界和明确问题链接，不能只写“详见代码”。

## 2. 发生冲突时，先拆命题，再决定修文档还是改合同

[事实优先级](../CONTRIBUTING-DOCS.md#2-事实与状态)用于重新核对当前实现，不能让代码自动废止公开合同。代码说明选定checkout执行什么，OpenAPI/proto说明发布描述承诺什么，部署证据说明特定环境观察到什么；三者冲突是需要记录和处理的偏移。

以Role PUT为例：`internal/apiserver/transport/rest/authz/dto/role.go`使用普通string，`internal/apiserver/transport/rest/authz/handler/role.go`总把两字段地址交给应用；`NewUpdateRoleCommand`拒绝空display_name。省略名称实际拒绝，但`api/rest/authz.v4.yaml`的更新schema没有名称必填声明。这是当前行为与公开描述的差异，不能用“代码优先”把旧调用方的省略预期视为已迁移。

提供名称而省略description还有更深一层：应用将返回对象的描述置空，但标准Role仓储经`internal/pkg/database/mysql/base.go`调用GORM `Updates(struct)`；锁定v1.30.0的更新callback跳过未显式选中的零值字段，RolePO也没有强制写description的hook。因此当前响应可为空，数据库旧描述仍可保留，后续读取可与该响应不同。核对需要追到mapper、仓储和依赖，不能从赋值直接推导持久化结果。本篇据此窄校准REST和契约正文；这是源码结论，没有在本轮执行数据库复现实验。

处理这种偏移时分别写清以下事实：

| 命题 | 应核对的证据 | 更新责任 |
| --- | --- | --- |
| 当前请求怎样解析、校验及写入？ | DTO、handler、应用/领域和实际相关断言；注明源码版本 | 行为owner修正正文、表与例子，不据YAML推断运行行为 |
| 发布描述宣称什么？ | 当前机器源、生成物、注册与消费者；注明不一致处 | 契约owner登记差异，不将两份描述相同当作实现一致 |
| 接下来采用哪种合同？ | 兼容决策、受影响消费者与验证方案 | 选择保留当前行为或修改省略语义后，再协调实现、描述及迁移 |
| 目标环境执行的是哪个版本？ | 实际部署SHA/配置、时间窗和行为回执 | 新运行记录；源码和文档修正不能补出部署结论 |

本轮记录偏移并修正文档，没有改Role行为或机器契约。[契约主文](../04-接口与SDK/01-REST-gRPC与契约治理.md)拥有完整生成和兼容矩阵，本篇不建立另一份修复清单。历史注释、测试名和多篇一致说法只能提供线索，不能按出现次数“投票”。

同样，“已提交”“已交接”“实例已加载”“公开请求生效”应拆开核对，而不是统一改成成功。原因无法从代码或决策记录确认时，写成“基于当前约束的设计分析”；合理推理不等于原作者当时的选择理由。

## 3. 写具体设计，要把场景、取舍与证据连起来

“采用Redis提升性能并保证一致性”没有说明IAM的实际问题。一个可复核的段落应从可观察场景开始，例如Refresh新令牌已生成，Session延长成功，但Rotate返回错误：调用方拿不到新pair，Session却可能已经改变。

`internal/apiserver/domain/authn/token/refresher.go`中`ExtendToRefreshExpiry`先于`RotateRefreshToken`，足以支持这个源码条件推论；它不能证明生产发生过该故障。完整并发、CASfalse和撤销窗口由[Token主文](../02-业务模块/02-AuthN/05-关键链路-Token签发刷新吊销.md)维护。若建议合并Redis操作，还须说明Session与token key布局、adapter责任、兼容存量及响应丢失后的结果核对；不能只写“加事务解决”，也不能把建议时序画成当前实现。

设计深度由这些关系判断：问题为何重要，谁拥有不变量，当前顺序如何成立，失败留下什么状态，候选方案解决哪条合同，又增加什么成本。对一个局部问题写透，通常比列十个模式名更有信息。章节长短、术语数量和覆盖率都不直接度量这种深度。

图、表和正文也有不同证明义务。对象图标出实体、值对象和投影，不能由struct或表名推导聚合；成功时序须注明成功路径，未显示的失败分支不能被读者理解为无失败；业务动作不应冒充真实状态枚举。图源语法、渲染布局、代码时序和环境行为分别验证。

## 4. 更新闭环按影响传播，不按文件数量结案

以发现“Session已撤销仍有本地JWT接受窗口”为例，在线Token verifier与`pkg/sdk/auth/verifier/local_strategy.go`承担不同合同。治理步骤应先确定是遗漏限制、源码发生变化，还是准备增加新的在线检查；三者需要不同交付物。

1. **绑定输入和变化。**记录checkout及未提交相关文件，定位调用者、规则和出口；把源码推论与已执行用例分开。已有日志若被复用，保留原日期/选择并确认输入仍适用。
2. **先更新完整owner。**核对状态、时序、失败矩阵和验证入口；随后同步模型定义、Redis机制、SDK消费、安全专题与导航的必要摘要。只改文首一句新结论而保留旧表/图，会继续误导读者。
3. **找相邻复述和引用。**搜索关键概念、函数/路径、旧标题和链接目标，而不只搜索被改文件名。代码路径存在不证明符号/调用仍有效；重新命名章节也可能破坏既有深链。
4. **按结论验证。**文字修正运行文档门禁与必要的局部核对；行为变化另选择真实后端/消费者/运行证据。文档检查不负责替代Session、JWT、缓存或在途请求的验收。
5. **交付范围明确。**reviewer能看到许可文件、保留材料、已执行结果与未执行项；合并、镜像构建/推送、部署与业务接受分别登记。

重命名或收敛章节时，优先改仓库内调用入口；对已存在的有效深链，可以在现行对应章节保留有明确用途的HTML锚点。例如[迁移失败章节](03-迁移发布与数据库运维.md#3-dirty-处置)保留旧dirty锚点但维护现行内容。不要制造大量无内容跳转稿；对无法穷举的外部引用，要说明兼容范围，不能因仓库内链接通过而宣称外部全覆盖。

更新闭环是一项人工工作约定。当前检查器没有自动建立概念/符号到owner的依赖图，也没有阻止所有“只改其中一页”的变更。完成一篇深化和同步相邻摘要，是不同粒度的成果；[逐篇台账](../_data/reviews/2026-10-06-docs-refactor.md)分别记录，不能用所有页面标为“已实现”推导本轮质量验收完成。

## 5. 历史材料保存原批次，当前纠正另写来源

历史发布日期、SHA、人数、fingerprint、环境和观察窗属于原批次。今天补上锚点检查，不能回填为旧CI当时已经检查锚点；今天观察流水线completed，可以追加新观察，不把旧in_progress截图改成新状态。若发现历史结论错误，应保留原记录，另写带日期的纠正、依据和影响，再从当前入口指向纠正。

| 材料 | 维护方式 | 读者如何使用 |
| --- | --- | --- |
| 现行设计或操作手册 | 随实现/合同变化更新；历史执行数字放到可追溯记录 | 回答当前规则与下一次操作边界，不复用旧审批/指纹作为新授权 |
| 带日期的执行/验收记录 | 保留原输入、结果和缺口；后续观察单独追加并区分日期/版本 | 支持原批次结论，不能仅凭页名“最终验收”推断今日状态 |
| 有推理/审计价值的旧稿 | `_archive`组入口写来源、原因与用途；必要时保持原相对路径语境 | 用于演进追溯；当前正文须独立解释现行规则 |
| 无持续参考价值的重复稿 | 核对引用后删除，由Git恢复历史 | 不为历史留存把重复事实继续挂在active入口 |

文首“已实现”表达所述源码能力核对，不能代替逐篇质量复核、main发布或环境验收。当前facts还禁止根页为“已实现”而子页含“规划改造”；这是分类规则的限制，不能据此把未实施候选改写为当前能力。现状正文中的候选段应明确标注，若整篇是规划则同步解释目录入口状态，不为通过门禁消除真实状态差异。

`docs/_data`及旧`docs/archive`不自动获得历史身份。工作区`HISTORICAL_DOCS`明确登记六项；`validate_documentation_status`要求恰好一个合法状态、登记项为“历史记录”且正文含日期形状。未登记的现行设计不能仅换标签跳过部分现行检查。这个状态登记仍没有证明日期有效、SHA真实或记录未被改写。

历史身份只跳过`check_active_docs`中部分现行文本规则，其他定点检查仍可能读历史字段；hygiene默认仍遍历`_data`与旧`archive`，也扫退役词原文。`_archive`原稿则退出当前正文检查；main默认仅选择根索引，撰写阶段独立工作区还检查维护的组及登记嵌套索引。不要为变绿把现行设计整篇藏入归档，也不要修归档原链接来假装它描述今天。

[归档总索引](../_archive/README.md)登记用途，[重构快照](../_archive/2026-10-06-docs-refactor/README.md)登记来源。实际原稿保全需另有文件摘要/快照与差异核对；归档索引存在不是逐字节保存证明。门禁打印的当前库存与旧记录中的原统计可以不同，状态数也不等于技术正文完成数。

现行手册允许包含历史段，但须明确日期起止，将本次前置条件/命令与原批次执行结果分开。例如[Scope迁移手册](../operations/assignment-scope-migration.md)同时保留旧批次人数/证据和当前实现限制，其整理必须按段落处理，不能把整页标为历史来退出当前操作维护。临时日志路径与摘要也不是长期可取证位置；摘要标识所选字节，不保证文件仍可读取，需要材料owner另定受限保存位置与期限。

## 6. 同名门禁不等于同版本检查能力

以下记录撰写阶段main `6f73026d`和2026-10-07独立工作区两个输入；本批只发布正文，未提交的脚本、Make和CI增强不能被称为main已发布能力。检查器入口为`scripts/check-docs-links.py`和`scripts/check-docs-facts.py`。

| 检查 | main已提交范围 | 独立工作区增强与共同限制 |
| --- | --- | --- |
| hygiene选文 | 默认root README、docs、api、SDK README/docs；排除.git/node_modules/vendor；`_archive`只选根README | 增加归档组README和三个登记嵌套索引；两版都不遍历所有仓库Markdown，例如Docker说明不在默认输入中 |
| 链接/路径 | 本地目标存在，不验证章节fragment；纯页内锚点跳过 | 增加Markdown/HTML锚点、重复标题和代码块排除；代码路径和退役词仍有特定选择规则，不是完整Markdown解析/符号检查 |
| facts | 定点配置/迁移/事件/wiring/公开描述与文本断言；main历史登记仅阶段台账一项 | 登记六项历史、顶层归档索引完整性、架构SVG/PNG摘要；其他定点和两份Python契约比较仍有限 |
| validator回归 | 已有3项历史状态helper回归及CI步骤 | 增加`docs-validation-tests`的10项回归与CI步骤；回归检查检测机制，不验证全部文档语义 |

### 6.1 先看选择集合，再看绿色结果

hygiene显式传入路径会替换默认输入；不存在的路径被静默跳过，零文件也可成功。链接校验不联网访问HTTP等外链，绝对路径直接视为存在；路径正则会忽略空白、通配符和未纳入的前缀/后缀。源码路径的后缀筛选还先于剥离行号，带行号的repo前缀路径可能未入选；行号内容与Go符号均不验证。代码块排除用于可点击链接，不代表路径/退役词扫描也全部排除字面示例。

因此“hygiene检查了所有引用”过强；报告需要保留实际文件集合与检查版本。新增归档嵌套索引若不属于现有层级或登记集合，也不会自动进入链接检查；新增业务owner表仍须人工复核。

facts不是将代码完整推导为自然语言规则。它对特定文本、YAML值、迁移编号/片段、服务/RPC和装配路径做断言，随后调用`scripts/check-openapi-contracts.py`和`scripts/check-route-contracts.py`。没有再生成Swagger/proto，也没有运行handler或消费者。通用schema比较当前因短名匹配规则零命中仍成功，两份同样陈旧的描述也能有相同路径集合；完整范围由[契约主文](../04-接口与SDK/01-REST-gRPC与契约治理.md)维护。退出码必须结合候选/命中/跳过集合解释。

### 6.2 摘要一致不是生成或视觉证明

工作区facts匹配`docs/_images/architecture`一级SVG集合与manifest键集，再检查同名SVG/PNG字节摘要，并查部分禁用概念。它不重渲染、不验证renderer字段，也不验证其他目录、Mermaid或额外PNG的完整集合。

修改SVG但不更新对应记录会失败；同时手工改PNG和manifest也可能通过，不能由此证明PNG来自该SVG。撰写阶段独立工作区中的`render-docs-diagrams.js`用sharp重新生成全部一级SVG的同名PNG，再写manifest；该辅助脚本尚未随本批正文发布，需要已有Node/sharp依赖。变更后仍须查看渲染文字/关系/裁切，并将查看结果与当前图源绑定。没有图变更时，不为文档通过重新渲染全部图。

### 6.3 回归与CI证明哪个机制

撰写阶段独立工作区中尚未发布的`test-docs-validation.py`有10项回归，分别覆盖5项链接/锚点与归档选择、2项历史分类、3项图源/PNG变化及未登记SVG拒绝；图例使用临时复制并patch ROOT。`scripts/test-docs-release-validation.py`的3项检查覆盖历史登记、日期形状、缺失/重复状态，其中部分与前两项重叠，不能相加为13项独立文档风险均已封闭。

这些用例未覆盖零文件、绝对链接或全部解析语法，也未证明hash可建立生成出处。main的CI lint已有两文档门禁和3项历史helper；工作区才新增10项validator步骤。两版`make ci`均没有直接编入文档门禁，不能与`.github/workflows/ci.yml`视为相同入口。触发声明、检查版本和某次实际job结果分别报告，完整验证选择由[测试与验收正文](02-测试契约与验收证据.md)维护。

## 7. 候选改进应封闭具体缺口，并支付维护成本

以下是基于现有检查与正文分析的候选，本轮均未实施；书面owner规则已经存在，不能将这些自动化能力一起标为已实现。

| 候选合同 | 谁负责、解决什么 | 成本与验收 |
| --- | --- | --- |
| 显式检查范围及命中回执 | checker维护者输出输入、实际文件、候选/命中/跳过；缺输入/应有集合为空拒绝 | 维护合理的预期集合及豁免；以拼错路径、新目录、零schema匹配和普通增文正反例验证 |
| 主题影响表 | 各模块owner记录受影响主文、摘要、图和合同，reviewer按变化查遗漏 | 依赖表本身会陈旧；先覆盖撤销、策略版本、密钥等高风险主题，再检验只改一页的漏同步是否可发现 |
| 冲突与兼容决策回链 | 契约/行为owner记录现源差异、选定合同、消费者和未完成验证 | 需要明确谁接受兼容代价，避免台账无限堆积；解决后归入主文，保留原决策批次 |
| 生成与保全证据 | 图示维护者记录可复核渲染；历史记录owner绑定来源/输出摘要，后续纠正另记，并确定受限保存位置/期限 | 工具链差异、存储保留和证据访问需要管理；图摘要只作一致性，历史摘要只作所选材料身份 |

是否增加自动门禁，取决于能否给出稳定、有效的正反样本；把一句复杂业务承诺编码为必须出现的字符串，只会验证措辞。人工语义复核应定位责任、调用和断言，机器检查承担可重复的小范围约束，环境验收承担真实效果，三者各有明确输入。
