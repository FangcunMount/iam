# 遗留资产、兼容层与数据库退役审计

> 状态：已实现 · 2026-10-07按main `3a12cd4b`核对当前读写、拒绝和恢复合同；新治理方案均为候选，目标数据库与外部消费者未在本轮核验。

退役要回答两个问题：旧能力还能否被使用，留下的代码、字段或表现在为谁服务。IAM已经停止Casbin、继承、条件求值、tenant授权分区和服务JWT运行路径，但旧Outbox表仍被当前空库准备写入、被启动门禁和状态读取查询。由“旧Relay已删”推导“旧表可删”，会破坏现役合同。

本篇维护资产分类、兼容退出和新退役批次的证据要求。[AuthZ模型](../02-业务模块/03-AuthZ/01-领域模型设计.md)拥有当前授权规则，[Session合同](../02-业务模块/02-AuthN/03-Session-Token与JWKS.md)拥有旧声明解释，[Outbox](../03-基础设施/03-事件与Transactional-Outbox.md)拥有发送/失败交接，[迁移发布](03-迁移发布与数据库运维.md)拥有执行、备份与部分恢复；这里解释这些合同怎样约束删除决策。

## 1. 先按现有责任分类，再判断是否退出

| 分类 | 当前例子 | 能得出的结论与退出成本 |
| --- | --- | --- |
| 现役能力/存储 | 直接Assignment、PermissionGrant、公司/门店Scope、标准Outbox、NSQ失败审计 | 维护当前业务事实或durable交接；旧名字、低访问量不改变其责任 |
| 存量解释与源兼容 | 标识元数据、旧Refresh/JWT解释、SDK公开字段 | 仍可能影响登录、通知或调用方编译；退出须处理存量与消费者 |
| 显式拒绝路径 | REST继承410、非空ObjectContext拒绝、旧TokenType拒绝、旧CLI退役错误 | 防止旧请求被误当成功；删除拒绝入口也会改变可观察合同 |
| 历史/恢复资产 | 嵌入迁移、版本表、role/condition/scope回执、继承归档 | 保留起点、结果和恢复依据；不等于旧能力可在当前二进制重新开启 |
| 待独立设计的治理候选 | 清除旧标记、移除fallback、拆除旧Outbox依赖 | 要先替换现役责任、取新证据并验收；本篇没有实施这些变更 |

静态“零引用”只覆盖被选仓库、语言和调用形态，不能排除动态SQL、外部运维脚本、低频消费者、旧二进制或备份恢复后的访问。一个资产可能同时属于多个分类：旧Outbox表既是历史数据载体，也是当前启动依赖，必须逐项解除责任。

## 2. 授权能力退役，不代表所有旧字段都即时拒绝

### 2.1 拒绝、忽略与防复用是三种合同

[REST router](../../internal/apiserver/transport/rest/authz/router.go)保留继承三路由的410 tombstone，所选测试在无业务依赖下检查GET/POST/DELETE的拒绝。它没有证明所有历史路径都注册，也没有替代完整认证/授权中间件验收。

[AuthZ proto](../../api/grpc/iam/authz/v4/authz.proto)将旧domain字段号和名称reserved，防止新协议重新赋予它们其他含义；这不是输入验证器。[Check handler](../../internal/apiserver/transport/grpc/service/authz/service.go)显式拒绝有ObjectID、属性或内部unknown的ObjectContext，随后只用Subject/Resource/Action创建请求；没有检查请求顶层unknown。

锁定gRPC v1.80.0默认codec调用`proto.Unmarshal`，protobuf v1.36.11默认保留unknown。因此旧domain wire字段可能被保留并忽略，不恢复旧授权分区，也不必然产生InvalidArgument。这是依赖和handler源码推论，本轮没有构造旧binary wire实验。不能将REST410、非空兼容字段拒绝和proto reserved合写为“旧输入全部拒绝”。

### 2.2 条件残留阻断的是特定数据集加载

[MySQLSource](../../internal/apiserver/infra/authz/runtime/mysql_source.go)只加载未软删且未撤销Grant，却加载全部未软删Resource。mapper在恢复领域对象前拒绝含条件/属性项或非法兼容表示；空白、null、{}以及合法对象中的空all_of/attributes数组仍可接受，不能按JSON字符串非空判断。一个没有Grant引用的活跃Resource，也可能阻断加载。已撤销条件Grant可以保留为历史行；[FindRoleID](../../internal/apiserver/infra/mysql/permissiongrant/repo.go)故意绕过条件恢复，供保护判断和撤销使用。

[LoadPolicy](../../internal/apiserver/infra/authz/runtime/runtime.go)失败不发布新快照，也不清除旧快照。首次加载失败没有可用Runtime；已有快照则仍受[证明预算](../../internal/apiserver/infra/authz/runtime/freshness.go)约束，预算内可能继续判定，过期Check才Unavailable。不能由“mapper fail closed”推导“发现任意历史条件行立即全实例拒绝”。完整版本/通知与预算合同归[策略收敛](../02-业务模块/03-AuthZ/04-关键链路-多实例策略收敛.md)。

### 2.3 留下的名字需要按含义消歧

当前`EffectiveRoles`直接返回DirectRoles，不计算继承闭包；Resource.Domain是资源键第二段，例如`iam:authz:collection:roles`中的authz、`qs:evaluation:collection:assessments`中的evaluation，iam/qs则是第一段App。该业务域不是旧授权分区。Assignment Scope表示同公司的all_stores或指定门店，运行时不核验门店存在和对象归属，Check也没有Scope参数。消费者须将匹配permission与同公司范围配对，再检查业务对象，不能把Scope当成条件求值器。

无条件[GrantKey](../../internal/apiserver/domain/authz/permissiongrant/grant.go)仍纳入旧规范的空constraints字符串，以保持已有键合同。只因字符串或方法名来自旧模型而改写，可能改变标识或公开调用，却没有实现新的业务能力。

`tenant-retirement`仍在main命令分派中，但[最终handler](../../cmd/iam-maintenance/tenant_retirement.go)无条件返回退役错误；旧提示也不代表可执行迁移。现行role-model、condition、assignment-scope工具各有版本与数据准入，不能用一个命令名推断完整操作链仍存在。

## 3. AuthN兼容会改变实际解释，退出须处理存量

### 3.1 删除标识标记，可能同时破坏登录与通知

微信身份按AppID/OpenID、同provider/global UnionID、带指定标记的历史行顺序查找；登录回退要求`legacy_identifier_semantics=openid_or_unionid`，通知查询反而排除该值的行，避免将含义不明的Identifier当OpenID。仅存在元数据键不等于命中此谓词。入口分别见[身份选择](../../internal/apiserver/domain/authn/authentication/wechat-identity.go)、[仓储](../../internal/apiserver/infra/mysql/loginidentity/repo.go)与[通知查询](../../internal/apiserver/application/authn/notificationrecipient/query.go)。

假设历史Identifier实际存UnionID：直接删标记，可能失去登录回退，又使通知返回错误OpenID。修复须核实provider/App/Realm归属和真实OpenID，保存旧值及关系映射，验新登录与通知后才能退出；不能猜测改列或由本仓未见新写者推断目标库已经零行。去除歧义的收益，需要支付数据查证、消费者协调和恢复成本。

Realm仍是当前唯一键的一部分；000030只把username身份归一到default realm，遇到同名冲突先阻断。OrgID由org_id建立，SDK不会从tenant_id推导；typed v2 Session.BusinessContext.Attributes仍可保留旧键，这不恢复tenant授权语义。不得把“旧tenant退役”扩大为Realm/OrgID也退役或全部旧键自动清理。

### 3.2 解释成功不是已完成存储迁移

[Refresh](../../internal/apiserver/domain/authn/token/refresher.go)在Session副本中恢复旧Refresh上下文，Extender按SID重新读取并延期；新Refresh不再写旧上下文字段。若上下文仅在旧Refresh、实际Session缺失它，后续刷新可能失去这份补充事实。此为源码条件推论，helper通过没有证明两轮真实存储链。完整恢复和写入责任由[Token主文](../02-业务模块/02-AuthN/05-关键链路-Token签发刷新吊销.md)维护。

服务端与SDK拒绝显式service/unknown/refresh TokenType；缺失或空token_type仍解释为access，并继续原签名、声明等验证，不能将该兼容称为接受任意类型。新JWT仍双写数字auth_time与attributes.auth_time，因此“新写入全部无legacy”也不成立。SDK Roles/Scopes可解析旧声明，不代表当前IAM继续签发角色或让JWT成为授权事实源。

[LegacyFallbackRetirementPolicy](../../internal/apiserver/domain/authn/token/legacy_fallback_retirement.go)取Access、Refresh和Session配置寿命最大值，并从“全实例升级”和“fallback持续为零”两时间中较晚者计算窗口。当前仅定义和纯测试调用，没有生产采集、自动重置或关闭fallback的接线。它验证调用者提供的时间，不验证时间事实。

候选退出至少要确认全部旧写入者停止、存量实际最长寿命、各入口与外部SDK消费观察、备份恢复不会重引旧对象。一次服务器指标静默不覆盖SDK本地解析；默认TTL不覆盖历史长寿命。应先建立有范围的观察回执，再删除解释分支并验证旧/新存量，不能让纯policy的true替代这些证据。

## 4. 旧Outbox运行路径已退役，旧表仍有当前责任

### 4.1 正常运行、空库准备和检查分别追踪

正常producer与维护操作使用标准Stager；关闭标准模式会在[InitEventing](../../internal/apiserver/container/platform/eventing.go)拒绝启动，没有自动legacy fallback。当前[FreshStages](../../internal/apiserver/process/database.go)31只准备历史租户起点，33/35需要发布时使用仅insert的[BootstrapStager](../../internal/apiserver/infra/mysql/eventoutbox/bootstrap_stager.go)写入旧表pending。该adapter不提供投递或恢复方法，不能说每个stage或每次准备都必然新增事件。

[启动](../../internal/apiserver/container/platform/reliable_eventing.go)调用CheckLegacyDrained，[状态reader](../../internal/apiserver/infra/mysql/eventoutbox/standard_status.go)同时查询旧/标准表。旧表缺失可能使查询报错，非published旧行阻断启动；“旧Relay不用”不能支持“当前没有旧表读写”。Fresh仅适用于version0且信息库tables除schema_migrations外无其他表/视图的数据库，不是普通存量库的修复入口，也不盘点全部routine等对象。

| 结果/旗标 | 实际谓词 | 不能据此推导 |
| --- | --- | --- |
| Legacy drained | 旧表所有BINARY status均为published；unknown也拒绝 | 无旧writer、表可删、标准表已排空 |
| readiness成功 | legacy残留、标准quarantined/unknown失败；正常标准积压按年龄阈值判断 | 标准pending为零或消息已被业务接受 |
| SDKDataReady | 完整无截断、元数据一致、未完成标准intent有效、无标准unknown/quarantine且旧unfinished为零 | 标准pending/retry_wait/publishing为零；PublishedContentIssues不纳入该旗标，另由RecoveryRequired提示积压 |
| LegacyRollbackDataReady | 数据检查通过、标准行全published、旧unknown为零 | 旧二进制兼容当前schema，或已获得切换授权 |
| UnusedSchemaCanBeRemoved | 仅未截断且标准表全表为空 | 旧表排空、failure audit为空、当前资产可DROP |

[只读预检](../../internal/apiserver/infra/mysql/eventoutbox/reliable_preflight.go)的WriterExclusionVerified/CutoverAuthorized保持false；schema-down命令返回成功也只是其数据条件。published意味着相应发送结算，不等于消费者业务接受。删除时必须先替换Fresh写入、启动检查和双表reader的责任，并解决历史数据交接。

### 4.2 当前发送和失败审计不能当普通历史日志删除

000038创建rm_outbox，000039增加重试字段，000040创建iam_nsq_failure_audit。38/39 Down要求标准表全部行数零，published也阻止回退；40 Down另要求失败审计全表零，前述预检没有读取它。

失败审计承担NSQ失败交接的durable事实与人工恢复，可能保留payload等敏感材料；归属、去重、确认和恢复由[Outbox失败交接](../03-基础设施/03-事件与Transactional-Outbox.md#8-failed-handoff-保留的是失败事实)维护，材料访问由[安全日志](04-安全日志与凭据处置.md)维护。删除旧audit_logs表的历史结论，不能授权清掉现役失败审计。

## 5. 数据库退役按实际起点和恢复能力判断

### 5.1 迁移版本、允许对象与运行准入各有证明范围

嵌入目录有38组up/down，版本范围1–40，4/10缺号。旧SQL仍服务于空库完整链和已有库历史，不能因领域模型退役删除。schema_migrations的version/dirty说明迁移状态，不记录SQL文件摘要，也不证明当前所有列、索引和数据等于原发布版本。

[dbops status](../../scripts/dbops/database-operation.sh)接受clean38/39/40、恰一条迁移记录，检查固定名称集合、退役对象与可见表权限。40要求21个必需对象；38/39主要要求必需计数20、总数20或21，没有逐版本证明缺的恰是failure audit，替代组合可能同计数通过。它不核验全部物理定义、账号权限或外部访问，首个success输出也早于后置guard，应看完整输出与退出码。

当前producer要求clean>=39并能解析标准列；subscriber另检查失败审计id列。status成功不能代替当前应用启动准入，列可解析也不是精确物理schema证明。历史“15运行表+1迁移表”或“17张”不作为今日目标库库存；本轮未观察目标version、dirty、对象或数据，均为unknown。

### 5.2 各SQL不是同一种“安全删除”

000019先补建/复制Profile及ProfileLink、做parity和依赖检查，再DROP children/guardianships；此前复制与DDL不形成整批可回滚事务。000020–22主要做各自依赖断言，不能概括为历史行都完成内容对账；000023有自身数据门禁。

000024允许四份清理复制表全部不存在，或四表整组存在；两分支都检查两个canonical表及id结构、数据库依赖和可见表权限。四表存在时另要求精确结构/1359行、双向内容及无canonical ID重叠，然后退役。不向canonical合并，这个固定历史表组的准入不能复用为新候选的通用证明。019–24 Down拒绝恢复空壳，数据恢复另依赖备份和适配版本。

另有未复现的源码组合风险：已有profiles与children，且000009已删profiles.height/weight时，019的CREATE TABLE IF NOT EXISTS不补列，后续拷贝/parity仍引用它们，可能在最终删除前失败。legacy-only直接执行19和空库全链均未覆盖该组合。[Identity迁移地图](../02-业务模块/01-Identity/05-分层架构与代码索引.md#5-迁移地图版本起点与物理结构一起看)拥有起点/fixture详情；本篇保留缺口，不改旧SQL或声称已复现。

### 5.3 Schema Down、数据补偿和旧版本恢复分别选择

| 合同 | 当前边界 | 恢复前要解决什么 |

## 6. 新批次要建立可判定的退出合同

以“移除旧Outbox表”或“删除微信标记”为候选，先写出替换后的责任，再决定删什么。前者须处理Fresh、启动与reader，后者须处理真实标识、登录与通知；只记录表/字段名称和owner同意，没有解释新系统怎样成立。

| 要宣称的结果 | 本批最低输入与后置证据 | 剩余限制 |
| --- | --- | --- |
| 某资产当前无人使用 | 实际二进制/配置/维护工具SHA，正常/初始化/恢复读写链，外部仓/脚本与观察范围 | 单仓零引用或静默窗口不覆盖未知消费者 |
| 目标表不存在 | 指定实例/库/账号与元数据权限，精确对象名称/类型库存 | 可见范围以外仍需证明；版本和SQL不能代替现场 |
| Outbox已排空 | 指定旧/标准表、完整无截断查询，明确所有非published状态及失败处理 | 不证明停写、业务接受、数据安全销毁或可恢复 |
| 可执行本批变更 | 精确候选manifest、关系/内容/依赖对账与fingerprint覆盖，读写冻结的实际观察、排他runner、新批授权 | 布尔声明、旧waiver及PolicyVersion锁不是全系统排他证明 |
| 可以恢复 | 受限备份、DDL/回执/逐行映射及摘要，恢复工具版本、实际演练与授权/登录/消息等结果核对 | 数据库恢复不原子恢复Redis、Broker、密钥和外部副本 |
| 已完成且可以退出兼容 | 提交后重读/回执、实例与消费者观察、失败/结果未知处置，明确窗口和业务范围验收 | 命令零退出、某实例已加载或一次新登录不覆盖全体接受 |

当前role/scope Apply检查调用者传入的writes-stopped布尔值，IAM锁住全局policy行；QS读取来自另一连接，没有IAM+QS跨库原子事务。fingerprint证明所选投影未漂移，不证明所有访问者都冻结；Role后续after_hash与Scope包含QS投影的范围也不同。恢复幂等性须按各自receipt状态判断，不能统一承诺重复rollback都完整核验后成功。

以下治理方案尚未实施，须由资产owner选择并承担代价：

## 8. 本篇验证按命题选择

本轮三个精确选择批均使用race/count=1：11个包、33个顶层及7个子测试，共40run/pass，0skip/fail；11个package pass另计。静态SQL8项、BootstrapStager3项、readiness stub3项合计14pass；兼容policy/SDK声明10顶层含5子例为15pass；AuthZ mapper/入口/Runtime9顶层含2子例为11pass。文件或父子事件数量不表示独立生产场景全部覆盖。

| 证据 | 可支持 | 不能支持 |
| --- | --- | --- |
| embedded SQL/本仓bootstrap文本断言 | 所选语句、准入片段、顺序和Down拒绝存在 | MySQL真实DDL/行锁、全部历史起点、019组合复现 |
| BootstrapStager内存SQLite | 所选事务插入/回滚与插入型职责 | 真实MySQL旧表排空、外部writer或NSQ投递 |
| mapper、REST/gRPC/SDK纯替身 | 所选输入返回error或旧ObjectContext/继承入口拒绝；原因/顺序须另追源码 | 顶层reserved旧wire、全部拒绝原因、完整中间件和全实例即时拒绝 |
| Runtime fake source/clock、readiness stub | 加载失败/证明预算；三个readiness仅验标准pending过龄、空snapshot和未注入outboxStore时required组件失败 | 目标MySQL残留、其他legacy/quarantine/unknown分支和实际路由可用性 |
| 本地签名/static JWKS、旧类型/OrgID与纯policy | 所选声明解释和窗口计算规则 | 真实旧对象寿命、采集接线、外部消费者或退出授权 |

其中Grant mapper用例只构造ConstraintSet、RoleID仍为零，并仅断言error；即使移除条件检查，领域也会拒绝零RoleID，故该测试不能独立证明条件错误来源或“恢复之前”的顺序。顺序由当前mapper先ValidateEmpty再Restore的源码支持，本轮没有补新测试。gRPC用例直接注入服务身份，不证明握手/ACL；三个readiness用例也未穷尽legacy/unknown/quarantine分支。
