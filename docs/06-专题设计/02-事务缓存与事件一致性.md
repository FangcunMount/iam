# 事务、缓存与事件的一致性谱系

> 状态：已实现 · 本文统一解释当前 MySQL、Redis、Outbox 和进程内投影的一致性选择与失败语义。

## 1. IAM 不是一种“一致性模型”

不同数据承担不同风险：

| 数据 | 真相 | 派生/协调 | 当前一致性 |
| --- | --- | --- | --- |
| User/Profile/ProfileLink | MySQL | Suggest index | 写强一致，搜索最终一致 |
| LoginIdentity/Credential | MySQL | Session/Token | 注册本地事务，登录跨 MySQL/Redis 有窗口 |
| Authorization facts | MySQL Assignment/Inheritance/PermissionGrant/Resource Schema | per-instance immutable authorization snapshot | 写事务，加载最终一致 |
| AuthZ version event | MySQL outbox | broker/subscriber | 至少一次倾向 |
| Session | Redis | User/LoginIdentity indexes | WATCH/Lua 协调 |
| JWKS key state | MySQL | in-memory publish snapshot | 激活事务，发布需刷新 |

因此问“系统是强一致还是最终一致”过于粗糙。应问某条不变量在哪个事实源、跨越哪些边界、故障时风险朝哪个方向。

## 2. 能放进一个数据库事务的就不要先用 Saga

SignUp 的 User/LoginIdentity/Credential、Identity 的 Profile/ProfileLink、AuthZ 的 fact/version/outbox 都在单 MySQL UoW 中原子提交。
只要资源属于同一数据库，本地事务最容易推理和恢复。

外部 provider 和 Redis 不进入 MySQL 事务：外部调用先 Prepare，Redis 派生状态通过补偿、Outbox或在线 guard 收敛。

## 3. Outbox 关闭哪一个窗口

错误双写：

```text
commit DB
  -> process crash
  -> event never published
```

Outbox 把“业务事实 + 待发事件”写在同一事务，再由 relay 重试发布。它不把 broker、consumer 和所有缓存变成一个分布式事务；重复、延迟、积压和 shutdown 仍要治理。

详见 [事件与 Transactional Outbox](../03-基础设施/03-事件与Transactional-Outbox.md)。

## 4. 缓存旧值的风险方向

- Profile Suggest 旧索引：通常遗漏/展示旧候选，若可见性旧则可能泄漏；
- AuthZ 旧策略：grant 延迟影响可用性，revoke 延迟影响安全；
- JWKS 旧集合：缺新 key 会误拒绝，保留过期旧 key 可能扩大信任窗口；
- subject access 旧缓存：可能继续允许被封禁用户，风险最高；
- IDP AppToken 旧值：provider 调用失败，主要是可用性，但 token 泄漏仍是安全问题。

TTL 不是一个中性数字，应由允许的风险窗口反推。

## 5. 数据库 truth 与缓存 version

可靠缓存治理至少需要：

```text
source version
loaded version
last successful refresh time
last error
backlog/lag
```

当前 AuthZ 有 DB PolicyVersion 和 reload health，但没有严格 per-tenant loaded version barrier；
Suggest 有 last successful refresh 指标/健康，但没有跨实例 generation；Redis family governance 主要 inspect，不是自动修复。

文档应诚实写这些边界，而不是用“有 version/event”推导强一致。

## 6. 原子操作优先表达业务不变量

典型例子：

- Challenge `ConsumeIfSecretMatches`；
- Refresh token CAS rotation；
- LoginIdentity `UnlinkOwnedUnlessLastActive`；
- JWKS single active DB guard；
- AuthZ PolicyVersion increment。

“先查再改”在单线程测试里正确，在并发下会失效。仓储端口应把原子业务动作作为一个方法，让实现选择行锁、unique constraint、Lua 或 WATCH。

## 7. 五个不能混用的一致性维度

工程讨论中的“一致性”至少包含五个问题：

| 维度 | 问题 | IAM 例子 |
| --- | --- | --- |
| atomicity | 一组修改是否全成或全败 | User/LoginIdentity/Credential 同一 UoW |
| durability | 成功返回后事实能否跨崩溃保留 | MySQL commit、Redis AOF/部署策略 |
| ordering | 并发或重复消息以什么顺序生效 | Refresh CAS、PolicyVersion event |
| freshness | 读到的投影落后事实多久 | AuthZ 不可变快照 reload、Suggest refresh |
| idempotence | 重试/重复消费是否改变最终结果 | Outbox relay、Session revoke |

Transactional Outbox 主要解决 durability 和跨边界“不漏掉传播意图”，不会自动解决消费者顺序、投影新鲜度或业务幂等。Redis Lua 主要解决指定键上的 atomicity，
不会把 MySQL 也拉进同一个事务。

只有先明确要保护哪个维度，技术选择才有意义。

## 8. 一致性机制的选择顺序

当前 IAM 可以归纳出一条选择规则：

```text
1. 对象能否由一个实体方法保护？
   -> entity/value object
2. 是否都在同一个数据库事务资源？
   -> local transaction/UoW
3. 是否是数据库中的并发唯一性？
   -> unique constraint / row lock / conditional update
4. 是否都在 Redis 的有限键集合？
   -> Lua / WATCH
5. 是否是 DB 事实到异步消费者？
   -> transactional outbox + idempotent consumer
6. 是否只是可重建查询投影？
   -> version/full refresh/delta + freshness health
7. 是否跨独立系统且必须作为一个长业务流程？
   -> 再评估 Saga/补偿，而不是默认上 Saga
```

这条顺序体现“选择最小的正确一致性边界”。过早引入分布式协调会增加状态机；边界过小又会留下双写窗口。

## 9. 典型失败窗口逐项推导

### 9.1 Session 创建与 Refresh Token 保存

当前登录签发先创建 Session，再保存 refresh token。若 refresh store 失败，请求不会得到完整 TokenPair，但已创建 Session 可能保留到 TTL。

风险方向：没有新 refresh credential 泄露，但产生暂时不可达的孤儿 Session 和索引占用。

候选方案：

- 失败时补偿 revoke/delete Session：实现简单，但补偿自身也可能失败；
- 用同一 Redis Lua 同时创建两类记录：原子性强，但脚本耦合 Session、索引和 refresh schema；
- 先存 refresh 再建 Session：可能产生可持有 refresh 却无有效 Session 的更危险窗口。

当前选择没有伪装成原子事务；文档把它列为可治理残余窗口。

### 9.2 Refresh 时先延长 Session 再 CAS 轮换

当前顺序优先避免“新 refresh 已生效但 Session 延长失败”。并发输家或 Redis 错误时，Session TTL 可能已延长，但调用方拿不到新 Token。

这是安全风险较小、状态精确性不完美的折中。若改成单 Lua，应同时验证 Session ownership、absolute max TTL、旧 refresh ID、写新 refresh 和删旧 refresh，脚本测试成本会明显上升。

### 9.3 Identity 状态与 Session 撤销

User block/deactivate 落 MySQL，Session 在 Redis，无法用一个本地事务覆盖。当前做法：

```text
MySQL transaction:
  update User status
  insert identity_session_revocation_outbox
commit
  -> worker retry revoke Redis sessions
```

在 worker 收敛前，IAM 在线 verify 还会重查 User/LoginIdentity 状态并拒绝，因此异步撤销不是唯一安全屏障。Outbox 负责最终清理，在线 guard 关闭安全窗口。

### 9.4 AuthZ committed 到 loaded

Policy fact/version/outbox 可以同事务提交，但每个实例 reload 发生在事务外。grant 延迟造成暂时拒绝，revoke 延迟可能暂时越权。

当前通过每实例广播、reload health 和 readiness 降低风险；由于尚无 per-tenant loaded-version barrier，不能宣称写响应与全实例生效线性一致。

### 9.5 Suggest Full/Delta

Full 在新 Store 中构建完再原子替换，避免查询读到半个索引；Delta 在当前 Store 锁内处理 upsert/tombstone。它保证单实例内的结构完整性，不保证多实例同时切换，
也不保证 Identity commit 后立即可搜。

这里选择 availability-first 的旧快照读取，但可见性过滤必须使用当前可信 scope；若过滤事实也陈旧，风险从“搜不到”升级为“可能泄漏”。

## 10. 事件语义的完整链路

可靠事件需要区分六步：

```text
business fact created
  -> event staged in same DB transaction
  -> outbox row claimed
  -> broker publish acknowledged
  -> consumer receives (possibly duplicate/out of order)
  -> consumer side effect converges
```

每一步对应不同证据：事务测试、outbox 状态、relay 指标、broker 观测、consumer 日志、最终业务状态。把“publish 成功”当成“缓存已刷新”会跳过最后两步。

当前事件目录还区分：

- `durable_outbox`：丢失会破坏传播语义，需要落库重试；
- `best_effort`：只用于不承担业务不变量的信号；
- `Signal`：进程内通知，不能被描述为跨实例可靠消息。

选择 durable 与否取决于丢失后果，不取决于事件名字听起来是否重要。

## 11. 幂等、去重与 exactly-once

“业务只发生一次”不能只靠 broker 投递次数。至少要区分：

```text
delivery once       broker 是否重复交付
processing once     consumer handler 是否重复运行
effect once         最终业务副作用是否只生效一次
```

Outbox relay 在 crash 边界上可能重复 publish；consumer 必须让重复事件收敛。AuthZ reload 是天然可重复的全量加载，Session revoke 也应幂等。若副作用是转账、发送不可撤回通知，
则需要业务幂等键/ processed-event 记录，而不是声称消息系统 exactly-once。

PolicyVersion 还可用于合并过时通知：事件携带的 version 是“至少发生到这里”的提示，consumer 应加载数据库最新事实，而不是假定必须逐个应用每条事件 diff。当前实现仍以全量 reload 为主，
重复正确但有性能成本。

## 12. 方案演化与替代设计

### 12.1 同步双写 MySQL + Redis/MQ

代码短，但任一顺序都存在一边成功一边失败；把网络调用放事务内还会延长锁、耗尽连接。当前只在本资源内同步提交，跨资源传播显式建模。

### 12.2 XA/两阶段提交

理论上提供跨资源原子提交，代价是参与者支持、协调器、长时间锁和可用性降低。Redis、外部 provider 和当前消息链并不适合统一加入 XA，且多数派生状态可通过重试/重建收敛。

### 12.3 Saga

适合跨服务、长时、每步都有明确补偿的业务流程。当前 Signup 的本地事实集中在同一 MySQL，外部 proof 在提交前完成，没有必要把它升级成 Saga。未来若注册必须同步创建多个独立系统账户，才需要重新评估。

### 12.4 CDC

从 binlog 捕获变化可以减少应用显式 stage，但要从低层行变化恢复领域语义，schema 演进和事件版本更复杂。当前事件产生时机属于应用语义，显式 catalog + outbox 更可审计。

### 12.5 只用短 TTL

TTL 是兜底上限，不是传播协议。它不能保证何时刷新、不能解释积压，也无法处理“旧值在 TTL 内会越权”的场景。当前 TTL 与主动撤销/version/reload 配合使用。

## 13. 如何定义新鲜度 SLA

对任一投影至少记录：

```text
truth version/time
loaded version or last-success time
current lag/oldest pending age
last error
required/optional policy
lag exceeds threshold 时的行为
```

SLA 应从风险反推：

- AuthZ revoke：安全敏感，阈值短，超限应让实例 not ready 或高风险请求 fail closed；
- Session revocation：必须有 backlog age 和在线状态兜底；
- Suggest：可容忍更长刷新，但敏感可见性不能放宽；
- JWKS：grace 必须覆盖 Access Token TTL，不能为发布数量上限提前丢弃仍需验签的 key。

## 14. 面试追问

### 为什么不使用分布式事务统一 MySQL/Redis/broker？

2PC 需要所有资源支持协调，增加可用性、锁和运维成本。当前通过本地事务守真相、Outbox 传播、幂等消费和在线 guard收敛，更符合这些状态的风险与规模。

### 最终一致多久才算正确？

必须有 SLA。授权 revoke 可能要求秒级且超时 fail closed；搜索索引可能允许分钟级。没有最大延迟、监控和超限行为的“最终一致”只是未定义。

### unique constraint 和分布式锁怎么选？

能由数据库唯一性表达的不变量优先 unique constraint，它与事实提交同事务且崩溃后仍有效。锁适合跨资源协调或降低击穿，但锁 TTL/ownership/释放都有额外失败模式。
