# 事务、缓存与事件：提交边界、传播水位与失败恢复

> 状态：已实现 · 2026-10-07按main `3a12cd4b`核对现行提交、读取与恢复路径；本文中的改造方案为候选，目标数据库、Redis、Broker及生产收敛未在本轮验证。

IAM没有一份覆盖MySQL、Redis、消息与全部投影的共同事务。一次操作的成功，要分别说明**事实是否提交、传播意图是否保存、某次读取能否使用它、失败后能否安全重试**。授权写入已提交，不等于本机或其他实例已加载；Redis交换成功，不等于调用方拿到结果；投影结构完整，也不等于资格最新。

本篇回答这些跨模块关系与设计取舍。连接/事务传播归[MySQL](../03-基础设施/01-MySQL事务与迁移.md)，在线状态与竞争归[Redis](../03-基础设施/02-Redis与缓存一致性.md)，消息身份、结算与失败交接归[Outbox](../03-基础设施/03-事件与Transactional-Outbox.md)。这里以具体时序解释它们怎样共同保护业务，以及尚未覆盖的窗口。

## 1. 先分清事实、投影与协调记录

| 链路 | 当前事实源与本地边界 | 边界外还要完成什么 | 风险方向 |
| --- | --- | --- | --- |
| SignUp、Profile/ProfileLink | 实际使用同一MySQL transaction的组合写入 | 需要provider换码/一次性证明的入口先完成该步骤；搜索另刷 | SQL失败不回滚已发生的换码/Challenge消费；关系提交不保证立即可搜 |
| AuthZ管理写入 | fact、全局PolicyVersion、标准Outbox意图同事务 | 每实例从数据库重建快照并确认新鲜度 | 新grant迟到可能误拒；revoke迟到可能继续放行 |
| User停用/封禁 | User状态与Session撤销任务按标准UoW同事务 | Redis批量撤销；在线准入读取用户/身份状态 | guard观察到停用才拒绝，不是所有在途请求屏障 |
| Session、Refresh、Challenge | Redis中的在线事实，分别有主键/索引、CAS或消费条件 | 初始颁发补偿、结果交付、数据持久策略 | 丢失后没有MySQL镜像自动恢复；不能统一称可重建缓存 |
| Suggest | MySQL源事实；进程内Store是查询投影 | Full/Delta、能力与visibility组合 | 旧结果既可能遗漏，也可能借旧owner分支继续可见 |
| JWKS | 数据库密钥状态；私钥材料和各级发布/验签缓存另有责任 | 本机发布刷新、HTTP/SDK刷新与重叠窗口 | 缺新key误拒，旧信任保留与紧急退役另取证 |
| IDP AppToken | provider颁发，IAM与SDK两层缓存 | 刷新lease、凭据轮换与provider失效 | 外层刷新不证明内层回源，更不证明旧凭据即时停止使用 |

原子性、持久性、顺序、新鲜度、幂等性是不同命题。MySQL事务能保护选定SQL的全成全败；Redis Lua/WATCH能裁决选定竞争；版本核对能给读取提供有期限的证明。任何一种成功都不自动补齐另外四种，也不等于目标部署已采用相同持久化配置。

## 2. 事务的边界由提交者与真实连接决定

### 2.1 顶层成功、借用回调成功和传播成功分别报告

[共享UoW](../../pkg/uow/gorm/uow.go)的根DB分支在GORM Transaction成功后返回；已有共享txCtx时直接调用回调，不新增提交、保存点或rollback-only标记。仓储须绑定同一tx，或确实读取carrier；把同库仓储放在同一函数里，不证明它们使用同一连接。

具体误用：内层先写Assignment和version，再Stage失败。宿主若传播error，正常顶层回滚；宿主若吞错后返回nil，前面SQL仍可能提交，留下事实与意图不配对。这里是当前传播合同的源码推演，不是已复现的生产事故。方法内填入Go对象的ID/时间也不随SQL回滚恢复，调用者须等待整笔结果后交付。

AfterCommit可把本机通知放到标准根DB提交后，但当前生产应用没有注册它。hook普通错误只记录并继续，执行用原ctx，进程退出、取消或panic各有窗口，没有持久重试。把裸GORM外层tx当UoW基座又未携carrier时，底层可仅完成保存点，本UoW却开始跑hook；名称本身不证明宿主已提交。精确前提与选项合同见[事务主文](../03-基础设施/01-MySQL事务与迁移.md#2-共享-uow-有两条执行分支)。

因此本机reload与AfterCommit适合作为加速，不能承担不可丢失的传播义务。必须恢复的意图要进入同一事实库事务；append失败交回提交者，宿主继续拥有commit/rollback与连接生命周期。

### 2.2 外部证明、DDL与补偿不由该事务兜底

[SignUp](../../internal/apiserver/application/authn/signup/service.go)先Prepare，再进入自身WithinTx。涉及外部code或一次性证明的分支，普通入口先处理该步骤，避免在这笔本地事务里等待provider；若调用者已持有外层tx，Prepare仍可能发生在宿主事务期间。username/mock及可信legacy输入不要求同样的外部交换。SQL失败不撤销已发生的换码/证明消费，重试须重新判断材料可用性，不能盲重放整个注册。

迁移DDL也不是这份业务事务合同：journal、SQL body、Fresh准备分别有边界，失败可保留部分物理效果。恢复依赖准确起点与回执，不是统一执行Down。完整恢复归[迁移发布](../05-工程质量与运维/03-迁移发布与数据库运维.md)和[退役审计](../05-工程质量与运维/06-遗留资产兼容层与数据库退役审计.md)。

## 3. AuthZ用四个状态解释“撤权何时生效”

| 状态 | 当前含义 | 不能代替什么 |
| --- | --- | --- |
| committed version | 数据库中已提交的管理事实/全局版本 | 内层WithinTx返回值不能证明宿主提交 |
| target | 实例已获知应覆盖的最高目标 | 不是已加载事实，也不是立即禁用旧结果的开关 |
| loaded | 当前不可变快照水位 | 不单独证明新鲜，也不包括其他实例或外部缓存 |
| confirmed / fresh | 最近一次充分版本确认及读取预算 | 不要求所有实例同水位，不从撤权提交时刻起算全局SLA |

宿主借用事务的条件时序，数字只用于说明：

```text
宿主SQL事务中：事实由v41改为v42，同时Stage意图
  → 内层Required返回；即时本机reload从另一个根DB事务读到v41
  → 宿主此后才决定：rollback则没有本次已提交意图
  → 若commit v42，Relay传播，其他实例仍需独立加载与确认
```

普通顶层写入的即时reload在自身commit后；借用宿主时则可能过早。这两类成功不能合写。写服务reload错误不回滚已提交事实；[MySQLSource](../../internal/apiserver/infra/authz/runtime/mysql_source.go)从其根DB开启独立只读事务，不能把txCtx当作读己写屏障。

[通知应用服务](../../internal/apiserver/application/authz/policypublication/service.go)先记target，已覆盖时跳过，否则调用LoadPolicy；成功返回没有再次要求loaded≥事件目标。另一个接口条件是：若Source成功返回未覆盖target42的v41数据，Load可返回nil，但不续证明。它不证明标准同主库在已提交事件之后仍返回v41，不能与上面的提交前reload合为普通时序。

因此消息ACK/FIN不独立证明目标覆盖。核对读数据库最新版本，足够覆盖才续证明；重复旧通知不会替过期快照续期，绕过全局version的直接事实修改也不能靠同版本核对发现。

加载失败保留完整旧快照。当前Check、Snapshot、EffectiveRoles在读取入口检查确认年龄，默认60秒；证明起点是充分版本读取或加载的开始时刻，不是完成时刻。已知target领先仍可在预算内读取旧结果。证明年龄不是自撤权commit起的群体延迟，也不撤销已过入口的在途求值。readiness还检查同步注册与其他依赖，探针摘流另依赖接入方。准确配置、CAS竞争与未覆盖时序归[多实例收敛](../02-业务模块/03-AuthZ/04-关键链路-多实例策略收敛.md)。

若业务要求“撤权提交之后所有新业务请求必须拒绝”，需定义请求所需版本、哪些实例/缓存参与、过时怎样拒绝及在途动作怎样处理。当前的有预算快照方案没有提供该屏障。新增版本barrier会增加读库/等待或拒绝成本，还必须让版本比较与实际求值绑定同一快照；单独多读一次health不能实现它。

## 4. AuthN在线状态用竞争和补偿保护不同阶段

### 4.1 初始颁发不交付失败pair，仍有补偿窗口

[SignIn完成链](../../internal/apiserver/application/authn/signin/completion.go)依次准入、创建Session、校验对齐、mint/校验pair、保存Refresh，再交付。Session成功返回后发生后续错误，才使用WithoutCancel与独立五秒超时尝试Revoke。

撤销成功可使后续观察到该已撤销Session的在线路径拒绝；它不覆盖已过guard的请求、纯本地验签或后续覆盖写。Revoke保留带撤销状态的主记录到剩余TTL，SignIn补偿也不删除Refresh，所以成功不保证物理清理。补偿失败还可能留下在线有效状态，须区分可用性与占用空间。

Create自身报错却已写入的情况可能没有返回SID，不能说所有初始失败都已补偿或无残留。相反，先存Refresh也不能无条件称“更危险”：是否能用仍取决于Session、准入和交付合同。

### 4.2 Refresh先延期再交换，CAS成功与交付成功不同

[Refresher](../../internal/apiserver/domain/authn/token/refresher.go)先校验Session/准入并mint候选pair，再Extend，最后Rotate，没有另外先保存候选的步骤。Lua比较旧记录ID与PTTL后写新Refresh、consumed marker并删旧记录。并发输家、交换失败或返回丢失不撤回此前延期；延期后又发生Revoke，也可能得到在线已不可用的pair。Extend发现主对象missing时返回nil，故nil也不是一份持续存在证明。

Rotate=false还可能表示旧记录缺失、ID不符或PTTL非正，不独立证明重放；当前按replay处理撤SID。A/B共同读到旧Refresh与活跃Session，A成功交换，B随后CAS=false并撤同一SID，A拿到的pair也可能在下一次在线读取失败。

锁定go-redis对普通脚本命令的部分网络错误会自动重发，首次已交换但回复丢失、重发返回false，可能使同一次请求走撤销。这两种完整时序都是源码条件推论，本轮没有并发赢家持续可用或网络丢回复实验。原子竞争不等于请求恰好执行一次。

候选有两类：把Session状态/寿命与交换条件纳入单脚本，缩小本资源内窗口；或设计有期限的请求/结果回执，处理交换后交付未知。前者增加跨键、索引与版本耦合，也不能保证调用方收到结果；后者涉及秘密留存、重放资格和恢复权限。只有末尾重读Session不能保证之后不被撤销。细节归[Token主文](../02-业务模块/02-AuthN/05-关键链路-Token签发刷新吊销.md)。

### 4.3 Redis原子动作与在线guard各有边界

| 机制 | 当前裁决对象 | 留下的窗口 |
| --- | --- | --- |
| Session MULTI/EXEC、Extend/Revoke WATCH | 主对象与所写命令；WATCH不监控User/LoginIdentity索引 | 索引不等于精确资格集合；EXEC执行期错误不是全命令回滚 |
| Challenge ConsumeIfSecretMatches | 当前序列化SecretHash匹配才消费 | 不独立证明调用者读到的代次；Lua错误/回复丢失需核对 |
| OTP逐维限额、Challenge与发送 | 单维计数原子，失败逐段补偿 | 没有配额+Challenge+provider共同提交，退款不撤回已发短信 |
| 在线Token verifier | 签名/声明、撤销marker、Session、LoginIdentity与User状态 | 多次Redis/MySQL读没有共同瞬间；不冻结后续业务动作 |

当前标准组合根的User状态来自MySQL仓储，AuthN LoginIdentity也直接读MySQL，没有“subject access旧缓存”这条现役标准路径。但读己看到的状态仍有时点/隔离边界；[SDK本地策略](../../pkg/sdk/auth/verifier/local_strategy.go)成功不调用在线Session/Admission，fallback主策略成功也不remote。短Access TTL与在线撤销是不同的信任合同，不能把本地验签成功报告为在线可用。

## 5. Identity停用：提交清理意图，在线拒绝另行发生

标准UoW把User状态与identity_session_revocation_outbox任务同tx提交，worker再按User撤Redis Session。任务在SQL里持久存在，避免进程在status commit后退出就永久丢失清理意图；它不是标准rm_outbox的MQ投递链，也没有把Redis加入SQL事务。

当前状态应用用例在SessionRevocations缺失时允许状态成功而不stage；真实Identity UoW注入Store。已inactive/blocked重试直接成功，不自动补丢失任务。Store.Stage也不自行RequireTx，责任在正确绑定仓储和错误传播；“有Outbox类名”不能独立证明所有调用都原子。

在线Admission观察到停用/封禁或失效LoginIdentity会拒绝，即使worker尚未清完；这是另一个安全检查。UserVersion用于任务身份/去重，不是Redis撤销时的fencing。源码允许停用提交、worker延迟、重新激活并新登录、旧任务才执行的交错；worker只传UserID/Reason，Redis按执行时索引遍历，因此可能撤掉新Session。这是未专项复现的条件推论。

Complete/Fail只按task_id/processing写回，也不检查RowsAffected，nil不证明本次确实转换了任务状态；它没有标准Outbox的token/version结算合同。若希望旧任务只清旧代Session，候选须定义截止/代次、执行资格与任务接管，验重新激活和并发worker；只加去重键不够。完整准入/重试与恢复归[Identity协作合同](../02-业务模块/01-Identity/04-模块边界-Identity与AuthN-AuthZ-Suggest.md)，不承诺后台任务恰好一次或用户状态/Session瞬时切换。

## 6. Outbox保护传播意图，消费水位仍独立

### 6.1 六个阶段逐段取证

```text
业务事实与意图同事务commit → claim/lease准入 → 发送
  ├ producer观察发送结果 → Outbox条件结算
  └ Broker可能投递 → consumer加载/副作用或失败交接 → FIN动作
```

这里列的是独立证据与两个推进分支，不是六步全局顺序：consumer可在producer观察确认或SQL结算前运行，AuthZ加载也在handler返回/FIN前。实例投影/业务效果是否达到所需状态，仍须取自己的水位与结果。

[StandardStager](../../internal/apiserver/infra/mysql/eventoutbox/standard_stager.go)借用宿主SQL transaction，事件身份及完整指纹用于识别同意图与冲突。lease/条件写回防止过时worker覆盖数据库状态，不撤回已发生的远端发送，也不保证每个身份只publish一次。

Broker Confirmed、published持久状态、consumer FIN和业务接受分别记录。Unknown表示不能安全推断未发送；当前Relay重试可重复发送。publish已完成而结算SQL报错，也需查询实际持久状态，不能从错误反推没有发布或没有写回。标准unknown持久状态与transport.Unknown不是同一概念。

AuthZ消费全量读取当前事实，版本提示不是逐事件diff，重复旧通知可跳过或重复加载；可重复执行不证明这次已经覆盖target。毒消息先经失败handoff Confirmed才FIN原消息，失败消息另在Audit.Record成功后FIN。go-nsq Finish首先提交本地响应与发送队列，不证明nsqd已收到；两个FIN都不等于策略完成收敛，也不授权任意不可撤回的通知副作用重复执行。

### 6.2 best_effort与进程内Signal承担较小责任

[事件目录](../../configs/events.yaml)把AuthZ version标为durable_outbox、OTP SMS标为best_effort。SMS mq sender走DirectPublisher，没有同事务意图或持久直发去重回执；Confirm也不证明下游provider/手机接受。发送可能已发生时删除Challenge、回退限额不撤回它，重发可能产生新消息身份。provider为log/aliyun时也不是这条MQ链。

Signal只通知本进程，不能替代跨实例可靠传播。是否持久化由丢失后果决定，但“持久化意图”仍只保护这一层：Broker存储、consumer副作用和恢复owner继续独立。关闭也须停止新准入、join已接纳publish/写回，再Drain真实driver；超时返回不证明driver已经停止。Store借用sql.DB不关闭它，ManagedPublisher拥有专用NSQ连接，consumer与借用Publisher另有关闭责任。完整join/资源保留、失败审计与首次空库旧意图交接由[事件主文](../03-基础设施/03-事件与Transactional-Outbox.md)维护。

## 7. 查询投影完整，不代表跨事实资格一致

### 7.1 Suggest有三个不同的旧窗口

标准Full用一次SQL拉取，在新Store构建后替换；Delta在当前Store整批加锁，保证所选内存写入与查询不交错。它们没有把授权能力、visibility和投影绑定同一版本，也没有多实例generation。标准Loader先完成映射再调用writer；writer error时Refresher只不推进cursor，不给任意可替换writer恢复此前内容。锁不是通用错误回滚。

一是**源变化捕获**：Delta按查询开始时间推进cursor，默认SQL用严格timestamp>since，没有提交序号/上界。事务timestamp早于cursor却稍后commit，可能持续漏Delta，需后续成功Full兜底；本轮未做真实MySQL并发复现。成功空Delta也推进lastSuccess，不能据此证明源变化已全覆盖。

二是**范围许可**：MySQL visibility只查操作者创建且未删的Profile；Scope还允许旧Store owner或同Org等OR分支。Profile42已在MySQL删除，即便实时visibility不再有42，Store旧owner17仍可能让操作者17看到它。visibility TTL设零没有移除所有旧许可；默认投影Org是占位配置，JWT Org也不是本次查询的新成员事实。

三是**多版本能力**：search、list_all与对应手机号动作分别Check，FactsReader只消费bool。v41有list_all而无search_by_mobile_all、v42撤前者授后者，两次调用可能组合出任何单一版本都没有的all+全量手机号能力；search_by_mobile属于另一分支。批量能力读可缩小该窗口，却不能自动把JWT、visibility和Store绑定同一时刻。上述均是源码条件推演，不能写成已完成并发验收。

如果要求删除/关系撤销后即刻不可见，须让所有许可分支共同依赖可信资格，明确共同版本或撤销事实及超限行为；只刷新一份ProfileIDs仍会留下owner兜底。完整刷新/资格/限流合同分别归[刷新](../02-业务模块/05-Suggest/02-关键链路-索引刷新Full-Delta.md)与[查询](../02-业务模块/05-Suggest/03-关键链路-SuggestProfile查询.md)。

### 7.2 健康、缓存TTL与事实证明分别使用

Suggest健康只要求至少一次成功刷新，不按年龄拒绝；后续错误可继续绿，optional调度失败还可能留下DegradedQuerier的空结果。不能写成当前已实现 freshness SLA。AuthZ则有读取证明预算；两者不能复用一个“health=true就最新”的解释。

JWKS状态变更后刷新失败不回滚已提交状态；数据库active唯一guard只保护数据库谓词，不保证各实例签名/发布、SDK缓存同步。重叠窗口须结合实际令牌寿命、时钟和消费缓存验收，数量上限不能直接授权提前丢仍需验签的key。IDP则有外层AppID lease与SDK内层token缓存，Refresh可能仍命中内层；lease过期不禁止旧holder继续写回，SecretVersion变化也不自动使两层缓存失效。具体时效与风险分别归[JWKS](../02-业务模块/02-AuthN/06-关键链路-JWKS与本地验签.md)和[AppToken](../02-业务模块/04-IDP/01-应用凭据与AppToken缓存.md)。

TTL可限制某个缓存条目的使用，不证明刷新成功、源版本覆盖或紧急撤销完成。Session物理TTL、逻辑ExpiresAt，AuthZ证明年龄，SuggestlastSuccess和IDP估计寿命分别有起算点；不能设同一数字就宣称全系统拥有相同最大旧窗口。

## 8. 改造先选具体不变量，再支付协调成本

以下均为候选，没有在本轮实现。

| 要解决的命题 | 可评估设计 | 需要承担的成本与验收 |
| --- | --- | --- |
| 借用宿主授权写入不提前reload | 正确提交者登记本机加速hook，保留同事务Outbox；内层错误始终传播 | 根DB/carrier前提、取消/commit后退出、宿主rollback；hook仍不能替代持久传播 |
| 撤权后的读取满足指定版本 | 快照与水位一起读取/求值，定义落后拒绝或等待、实例集合与在途边界 | 增加读/等待或拒绝成本；正反例含丢通知、错误加载、跨预算在途和外部缓存 |
| Refresh交换后结果可恢复 | 有限结果回执或受限重试政策；单脚本联合Session条件另行评估 | 交付未知、秘密留存、并发/撤销、跨键与兼容协议；不只验证CAS赢家 |
| Suggest撤销与能力组合一致 | 同快照批量能力读取、所有OR分支的资格事实、提交水位或可靠变更捕获 | 源/资格/Store多重成本；验晚提交、删除旧owner、跨能力版本与刷新超龄 |
| key/provider轮换后旧缓存停止使用 | 明确各消费者失效、版本key/有ownership的写回及观察窗口 | 验历史长寿命对象、缓存失效/新材料不可用、晚归旧holder及回滚引入 |
| 结果未知时不盲重放 | 用业务身份绑定提交前后事实、错误阶段、有限恢复材料与人工owner | 回执访问/生命周期和partial/outcome_unknown分类；注入提交后丢回复再对账 |

数据库unique/行锁、实体方法与仓储原子动作优先保护能在本资源内表达的不变量。例如最后一个active LoginIdentity的解绑锁住身份集合，JWKS guard保证至多一个active；它们各有精确范围，不代替User准入、材料可用或全局传播。业务幂等要比较完整身份/内容和实际终态，不能由delivery一次推出effect一次。

若新增跨独立系统的长流程，再评估有明确失败/补偿合同的Saga；当前SignUp本地事实本来同库，外部proof消费又未提供通用返还，直接套Saga名称不会补齐恢复。以CDC替代Stage也须为本系统定义领域事件、全局版本、schema演进和消费者恢复；它不是自动生成正确资格事实。XA/事务消息若进入候选，必须重新列参与者、宿主与Broker时序；现有Redis/provider/SDK链没有这套共同提交接线。

独立Relay可以借用业务库、权限与生命周期，Outbox继续与事实同事务；把意图搬入中央独立库反而要重新解决事实/意图双写。同步MySQL+Redis/MQ也不因代码更短消除窗口。比较方案应围绕上述不变量、实际可恢复事实与代价，而不是只比较模式名称。
