## 2. 一句话定位

IAM 是一个面向业务系统接入的身份与访问管理服务，统一管理用户、档案与登录身份，通过认证确认“你是谁”，通过授权判断“你能做什么”，并为外部登录、服务间访问和 Profile 联想搜索提供可复用的基础能力。

---

## 3. 更短版本

如果只能说 15 秒：

```text
IAM 是业务系统的统一身份与权限底座，负责把用户、档案、登录身份、访问控制和外部身份源统一起来，让业务系统不用各自重复实现登录、验权和用户关系管理。
```

---

## 4. 面试开场版本

如果用于面试开场，可以这样说：

```text
这个 IAM 项目本质上是一个身份与访问管理中心。我把它拆成 Identity、AuthN、AuthZ、IDP、Suggest 五个核心模块：Identity 维护用户和档案关系，AuthN 负责登录认证和 Token，AuthZ 负责角色权限和访问决策，IDP 负责微信等外部身份源接入，Suggest 负责在安全范围内做 Profile 联想搜索。整体目标是让业务系统通过 REST、gRPC 或 Go SDK 接入统一的认证、授权和身份事实能力。
```

## 5. 金字塔结构

### 5.1 顶层结论

```text
IAM 是业务系统的统一身份与访问管理底座。
```

---

### 5.2 三个核心价值

| 价值 | 说明 |
| --- | --- |
| 统一身份事实 | 把 User、Profile、ProfileLink、LoginIdentity 等身份事实集中建模 |
| 统一认证授权 | 用 AuthN 证明调用者身份，用 AuthZ 判断资源访问权 |
| 统一接入能力 | 通过 REST、gRPC、Go SDK 给业务系统提供标准接入方式 |

---

### 5.3 五个核心模块

| 模块 | 一句话 | 负责回答 |
| --- | --- | --- |
| Identity | 身份事实中心 | 用户是谁？档案是什么？用户和档案是什么关系？ |
| AuthN | 认证中心 | 当前请求者如何证明自己是谁？ |
| AuthZ | 授权中心 | 某个主体能不能访问某个资源？ |
| IDP | 外部身份源接入 | 外部 provider 说了什么？如何转换成 IAM 可用身份事实？ |
| Suggest | Profile 联想搜索读模型 | 当前请求者在允许范围内能搜索到哪些 Profile 候选项？ |

---

### 5.4 三类接入方式

| 接入方式 | 适合场景 |
| --- | --- |
| REST | Web、App、管理端、跨语言 HTTP 调用 |
| gRPC | 可信服务间调用、内部强类型接口 |
| Go SDK | Go 业务服务快速接入 IAM 能力 |

---

### 5.5 一条主链路

```text
外部登录 / 用户请求
  -> IDP 解析外部身份，若需要
  -> AuthN 完成认证并签发 Token
  -> Identity 提供用户与档案事实
  -> AuthZ 判断资源访问权
  -> Suggest 在允许范围内提供 Profile 候选搜索
  -> 业务系统基于决策继续业务流程
```

## 6. 30 秒版本

```text
IAM 是一个统一身份与访问管理服务。它把业务系统里分散的用户、儿童档案、登录身份、外部身份源和权限判断集中起来，拆成 Identity、AuthN、AuthZ、IDP、Suggest 五个模块。业务系统接入后，不需要各自重复实现登录、Token、权限判断、微信身份解析和 Profile 搜索，而是通过 REST、gRPC 或 Go SDK 调用 IAM 的标准能力。
```

---

## 7. 1 分钟版本

```text
这个 IAM 项目主要解决业务系统身份与权限能力分散的问题。它的核心是五个模块：Identity 负责 User、Profile、ProfileLink 等身份事实；AuthN 负责登录认证、Session、AccessToken、RefreshToken 和 JWKS；AuthZ 负责 Subject、Role、Permission、RoleBinding 和 Check；IDP 负责微信等外部身份源的 app、credential、access token 和 external identity 解析；Suggest 是一个读模型，用来在安全范围内做 Profile 联想搜索。

业务系统可以通过 REST、gRPC 或 Go SDK 接入 IAM。请求进入后，先由 AuthN 证明调用者是谁，再由 AuthZ 判断这个主体能不能对某个资源执行某个动作，必要时读取 Identity 的身份事实，或者通过 Suggest 搜索可见范围内的 Profile 候选。整体目标是把身份事实、认证、授权和外部身份源接入从业务系统中抽出来，形成统一、可复用、可治理的身份权限底座。
```

## 8. 3 分钟版本

```text
IAM 是一个面向业务系统接入的身份与访问管理服务。这个项目的出发点是：业务系统通常会重复实现用户管理、微信登录、Token 校验、角色权限、用户与档案关系、Profile 搜索等能力，时间久了会出现身份事实不统一、认证授权混杂、权限规则分散、外部身份源难治理、搜索与隐私边界不清等问题。

所以我把 IAM 拆成五个核心模块。

第一是 Identity，它是身份事实中心，负责 User、Profile、ProfileLink 这些对象，回答“用户是谁、档案是什么、用户和档案是什么关系”。这里的重点是身份关系建模，比如 ProfileLink 只是身份关系事实，不等于权限。

第二是 AuthN，它是认证中心，负责 LoginIdentity、Credential、Challenge、Principal、Session、AccessToken、RefreshToken 和 JWKS。它回答“当前请求者如何证明自己是谁”。这里我把 Session、AccessToken、RefreshToken 分开建模，AccessToken 用于短期 API 访问，RefreshToken 只用于续期，JWKS 用于业务系统本地验签。

第三是 AuthZ，它是授权中心，负责 Subject、Role、Permission、RoleBinding、Resource、Action、Scope 和 AuthorizationDecision。它回答“某个主体能不能对某个资源执行某个动作”。这里我把 AuthZ 领域模型和 Casbin runtime 分开，Casbin 只是 infra 层的策略判定引擎，不进入领域模型。

第四是 IDP，它负责外部身份源，比如微信小程序、公众号、企业微信等 provider 的 app、credential、access token 和 external identity 解析。它只负责把外部身份事实解析出来，不直接创建内部用户，也不签发 IAM Token。

第五是 Suggest，它是 Profile 联想搜索读模型。它不是 Identity 主数据，而是从 Profile 事实中派生搜索索引和 Snapshot，在查询时结合可见性过滤、排序、截断、脱敏，返回安全的候选项。

接入层上，IAM 提供 REST、gRPC 和 Go SDK。REST 适合 Web/App/管理端和跨语言调用，gRPC 适合内部服务间调用，Go SDK 用于 Go 业务服务快速集成。架构上通过分层依赖、架构测试、契约测试、SDK compile test、docs hygiene 来防止代码边界和文档事实漂移。

所以这个项目不是简单的登录服务，而是一个围绕身份事实、认证、授权、外部身份源和安全搜索建立的统一 IAM 底座。
```

## 9. 项目不是什么

为了避免误解，可以明确说：

```text
IAM 不是单纯的 JWT 登录 demo；
IAM 不是只管理用户表的 CRUD；
IAM 不是把微信 openid 直接当内部用户；
IAM 不是把 Token claims 当完整权限系统；
IAM 不是把 Casbin 当领域模型；
IAM 不是把 ProfileLink 当 Permission；
IAM 不是让业务系统直接访问 IAM 数据库；
IAM 不是把搜索索引当身份主数据。
```

## 10. 项目最值得讲的点

如果面试或评审时间有限，优先讲这些：

| 亮点 | 为什么值得讲 |
| --- | --- |
| Identity / AuthN / AuthZ 分离 | 体现领域边界，不把登录、用户、权限混在一起 |
| Session / AccessToken / RefreshToken 边界 | 体现认证安全设计，而不是简单发一个 token |
| JWKS 与本地验签 | 体现服务间接入、性能和密钥治理能力 |
| AuthZ 领域模型与 Casbin runtime 分离 | 体现领域建模能力，不被框架牵着走 |
| Transactional Outbox + PolicyVersion | 体现授权事实和 runtime reload 的一致性设计 |
| ProfileLink 不是 Permission | 体现身份关系和授权关系的清晰边界 |
| Suggest 作为读模型 | 体现读写分离、搜索安全、脱敏和最终一致设计 |
| 架构护栏与契约防漂移 | 体现工程治理能力，不只是写业务代码 |

## 11. 推荐表达顺序

讲项目时不要一上来堆技术栈，建议按这个顺序：

```text
1. 项目一句话定位；
2. 业务系统为什么需要 IAM；
3. 五个核心模块；
4. 一条主链路；
5. 两三个关键设计取舍；
6. 接入方式；
7. 架构护栏和测试治理；
8. 回到项目价值。
```

不推荐：

```text
一上来讲 Casbin；
一上来讲 JWT；
一上来讲目录结构；
一上来讲数据库表；
把所有模块平铺介绍，没有主线；
把未实现能力说成已实现。
```

## 14. 本文总结

IAM 的一句话定位是：

```text
面向业务系统接入的统一身份与访问管理服务。
```

展开后是：

```text
Identity 管身份事实；
AuthN 管认证；
AuthZ 管授权；
IDP 管外部身份源；
Suggest 管可见范围内的 Profile 联想搜索；
REST/gRPC/Go SDK 提供接入；
架构护栏和契约测试保证边界不漂移。
```

宣讲时最重要的是：

```text
先讲项目解决什么问题；
再讲模块如何拆；
再讲关键边界和设计取舍；
最后讲工程治理和事实源。
```
