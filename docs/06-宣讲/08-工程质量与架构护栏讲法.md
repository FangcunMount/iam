# 工程质量与架构护栏讲法

> 状态：规划改造 · 已完成当前事实盘点；正文仍含待实现或尚未收敛的设计内容，不得作为现有能力承诺。

---

## 1. 本文目标

本文用于回答：

```text
IAM 如何保证工程质量和架构长期不漂移？
```

它是宣讲稿，不是完整测试方案文档，适用于：

```text
面试讲工程质量；
解释为什么需要架构护栏；
解释分层依赖如何被测试固化；
解释契约如何防漂移；
解释 SDK public API 如何保持稳定；
解释文档体系如何避免旧事实回流。
```

本文采用金字塔表达：

```text
先一句话定位；
再讲四类护栏；
再讲每类护栏保护什么；
再讲 CI 和 Verify；
最后讲常见追问。
```

---

## 2. 一句话定位

IAM 的工程质量不是只靠单元测试，而是通过架构测试、契约测试、SDK compile test 和 docs hygiene，把分层边界、接口契约、外部调用面和文档事实源固化成可验证的工程护栏。

更短一点：

```text
工程质量不是靠自觉，而是靠自动化护栏防止边界和契约漂移。
```

---

## 3. 30 秒版本

```text
IAM 的工程质量我不是只靠单元测试，而是设计了多层护栏。第一层是 architecture tests，用来保护 domain、application、infra、transport、container、SDK 之间的依赖方向，防止 handler 直接访问 repository、domain import proto、SDK import internal。第二层是 contract tests，用来保护 OpenAPI、proto、SDK 和 transport 实现不漂移。第三层是 SDK compile test，用来保护 Go SDK public API 和示例代码可编译。第四层是 docs hygiene，用来保护 README 链接、active/archive 边界和文档事实源不漂移。
```

---

## 4. 1 分钟版本

```text
IAM 的工程质量核心不是“多写几个单元测试”，而是把长期演进中最容易坏掉的边界固化下来。

我把护栏分成四类。第一类是架构测试，主要检查 import 依赖方向，比如 domain 不能依赖 infra、transport 不能绕过 application、SDK 不能 import internal。第二类是契约测试，主要检查 REST OpenAPI、gRPC proto、Go SDK 和 transport 实现之间是否一致，防止接口定义和运行时实现漂移。第三类是 SDK compile test，用来保护 Go SDK 的 public API，避免外部业务服务升级 SDK 后编译失败。第四类是 docs hygiene，用来检查文档链接、README 入口、active docs 和 archive docs 的边界，防止旧事实回流到当前文档。

这些护栏的目标是：代码规模变大后，不依赖口头约定维护架构，而是用测试、CI 和文档入口让边界可验证。
```

---

## 5. 3 分钟版本

```text
我在 IAM 项目里对工程质量的理解，不只是业务测试能不能通过，而是系统在持续迭代后，分层边界、接口契约、SDK 调用面和文档事实源是否还能保持一致。

所以我把工程护栏设计成四层。

第一层是 architecture tests，也就是架构测试。它主要保护代码依赖方向。比如 domain 不能 import infra、transport、generated proto；application 不应该依赖 transport 或具体 infra；transport 不应该绕过 application 直接访问 repository、transaction manager 或 Casbin；infra 不应该反向调用 application；SDK 不能 import internal。这样可以防止项目写着写着变成 handler 里堆业务逻辑、domain 里混数据库和 proto 的结构。

第二层是 contract tests，也就是契约测试。IAM 对外有 REST、gRPC 和 Go SDK 三类接入方式。REST 的事实源是 OpenAPI，gRPC 的事实源是 proto，SDK 的事实源是 pkg/sdk public API。契约测试要保证 OpenAPI 和 REST handler 对齐、proto 和 gRPC service/mapper 对齐、SDK 和公开契约对齐，错误模型、认证授权语义和敏感字段脱敏也要跨协议一致。

第三层是 SDK compile test。Go SDK 是业务系统接入 IAM 的外部调用面，它必须稳定。如果 public API 随便改，外部服务升级 SDK 就会编译失败。所以 SDK 的主要 public client、request/response、TokenSource、错误模型和示例代码，都应该通过 compile test 或 mock server test 保护起来，同时架构测试还要保证 SDK 不 import IAM internal 包。

第四层是 docs hygiene。这个项目文档很多，如果没有文档卫生检查，很容易出现 README 指向不存在文件、active docs 引用 archive 旧事实、文档写了代码里不存在的接口、Verify 命令指向错误路径等问题。所以 docs hygiene 用来检查链接、入口、active/archive 边界和事实源引用，保证文档不是新的漂移源。

这四类护栏组合起来，解决的是不同层面的质量问题：单元测试保护局部业务逻辑，架构测试保护分层边界，契约测试保护接口事实源，SDK compile test 保护外部接入面，docs hygiene 保护文档体系。它们共同保证 IAM 在长期演进中不会因为模块增多、接口增多、文档增多而失控。
```

## 6. 金字塔结构

### 6.1 顶层结论

```text
IAM 用多层工程护栏保证长期演进质量。
```

---

### 6.2 四类核心护栏

| 护栏 | 保护什么 | 核心 Verify |
| --- | --- | --- |
| architecture tests | 分层依赖边界和模块职责 | `go test ./internal/pkg/architecture` |
| contract tests | REST/gRPC/SDK 与运行时实现一致 | `make api-validate` / `make proto-gen` / transport tests |
| SDK compile test | Go SDK public API 和示例可编译 | `go test ./pkg/sdk/...` |
| docs hygiene | 文档链接、入口、active/archive 边界 | `make docs-hygiene` |

---

### 6.3 五个质量维度

| 维度 | 说明 |
| --- | --- |
| 分层质量 | domain、application、infra、transport、container 不互相污染 |
| 契约质量 | OpenAPI、proto、SDK 和 runtime 实现一致 |
| 接入质量 | 业务系统通过稳定 REST/gRPC/SDK 接入，不穿透 internal |
| 安全质量 | Token、secret、手机号、权限判断、脱敏规则不被绕过 |
| 文档质量 | README、事实源、Verify、active/archive 不漂移 |

---

### 6.4 一条质量主线

```text
设计边界
  -> 写入文档
  -> 固化为测试
  -> 接入 CI
  -> 失败阻断合并
  -> 反向约束代码演进
```

## 7. 架构测试讲法

一句话：

```text
架构测试负责把分层依赖边界变成可执行的 import 规则。
```

它保护：

```text
domain 不依赖 infra / transport / api / proto / SDK；
application 不依赖 transport / container / 具体 infra；
transport 不绕过 application 直接访问 repository / tx / Casbin / container；
infra 不反向依赖 application / transport；
container 只做 wiring，不被业务层反向调用；
SDK 不 import internal；
Casbin 不进入 domain；
Suggest index/store 不直接吞并 AuthZ 决策。
```

讲解重点：

```text
架构测试不是测业务逻辑；
它测的是代码结构有没有越界；
失败时优先修正依赖方向，不要第一反应加白名单；
白名单必须有文档说明和退出条件。
```

典型例子：

```text
如果 domain/authz import 了 Casbin，架构测试应该失败；
如果 transport/rest 直接 import infra repository，架构测试应该失败；
如果 pkg/sdk import internal/apiserver，架构测试应该失败。
```

---

## 8. 契约测试讲法

一句话：

```text
契约测试负责保证公开接口契约和运行时实现一致。
```

它保护：

```text
OpenAPI 与 REST handler 不漂移；
proto 与 gRPC service / mapper 不漂移；
SDK public API 与 OpenAPI/proto 不漂移；
错误模型在 REST/gRPC/SDK 之间语义一致；
认证、授权、限流、脱敏等接入语义不被绕过；
文档不制造机器契约之外的接口事实。
```

核心事实源：

| 契约 | 事实源 |
| --- | --- |
| REST | `api/rest` |
| gRPC | `api/grpc` |
| Go SDK | `pkg/sdk` |
| REST runtime | `internal/apiserver/transport/rest` |
| gRPC runtime | `internal/apiserver/transport/grpc` |

讲解重点：

```text
REST 看 OpenAPI；
gRPC 看 proto；
SDK 看 pkg/sdk public API；
文档只解释语义，不反向定义接口字段；
契约变更必须同步 transport、application、SDK、测试和文档。
```

---

## 9. SDK Compile Test 讲法

一句话：

```text
SDK compile test 负责保护外部 Go 调用面的稳定性。
```

它保护：

```text
public client 能编译；
request / response 主要类型能编译；
TokenSource 用法能编译；
错误类型或错误码用法稳定；
示例代码能编译；
SDK 不 import IAM internal；
删除或破坏 public API 能被测试发现。
```

讲解重点：

```text
SDK 是业务系统接入 IAM 的产品化调用面；
SDK 不是 IAM 服务端内部代码；
SDK 不应该穿透 internal；
compile test 是保护外部调用方的最低成本手段。
```

典型例子：

```text
如果把 client.AuthN().Login(ctx, req) 的 public API 改坏，compile test 应该失败；
如果示例里的 TokenSource 用法不再编译，compile test 应该失败；
如果 SDK import internal/apiserver，architecture test 应该失败。
```

## 10. Docs Hygiene 讲法

一句话：

```text
Docs hygiene 负责防止文档链接、阅读路径和事实源漂移。
```

它保护：

```text
README 链接存在；
目录入口与实际文件一致；
active docs 不引用 archive 作为当前事实；
删除或合并旧文档后 README 同步；
Verify 命令不指向不存在路径；
文档不把未实现能力写成已实现事实；
接入文档不手写完整机器契约 schema。
```

讲解重点：

```text
文档不是附属品；
文档也会漂移；
文档漂移会误导后续开发和面试讲解；
docs hygiene 是把文档体系当工程资产治理。
```

典型例子：

```text
README 指向已删除文件，docs hygiene 应该失败；
active docs 引用 archive 旧模型当当前事实，应该被识别和修正；
文档里写了 OpenAPI 不存在的 endpoint，要标注规划或删除。
```

## 11. 四类护栏如何配合

| 场景 | 需要哪些护栏 |
| --- | --- |
| 新增 REST endpoint | contract tests + docs hygiene + transport tests |
| 新增 gRPC RPC | proto-gen + gRPC tests + SDK tests + docs hygiene |
| 修改 AuthZ domain | domain/application tests + architecture tests |
| 引入 Casbin adapter | architecture tests + AuthZ runtime tests |
| 修改 Go SDK public API | SDK compile test + contract tests + docs hygiene |
| 移动文档或合并文档 | docs hygiene |
| 新增 Suggest 手机号搜索 | contract tests + privacy tests + architecture tests + docs hygiene |
| 调整分层依赖 | architecture tests |

## 12. CI 讲法

可以这样讲：

```text
这些护栏最终要进入 CI，而不是只在本地手工跑。PR 阶段至少应该跑 docs-hygiene、api-validate、proto-gen、architecture tests、transport tests 和 SDK tests。这样只要有人改坏分层、改坏契约、改坏 SDK public API 或改坏文档链接，CI 就会阻断合并。
```

建议流水线：

```bash
make docs-hygiene
make api-validate
make proto-gen
go test ./internal/pkg/architecture
go test ./internal/apiserver/domain/...
go test ./internal/apiserver/application/...
go test ./internal/apiserver/transport/rest/...
go test ./internal/apiserver/transport/grpc/...
go test ./pkg/sdk/...
```

讲解重点：

```text
CI 不是为了形式；
CI 是把设计边界变成团队约束；
越核心的边界，越应该自动化检查；
失败时应该修正结构或契约，而不是跳过测试。
```

## 13. 与单元测试的关系

单元测试仍然重要，但它覆盖的是局部行为。

| 测试类型 | 保护对象 |
| --- | --- |
| 单元测试 | 单个函数、领域规则、use case 分支 |
| 集成测试 | 多组件协作行为 |
| 架构测试 | import 方向、分层边界、模块职责 |
| 契约测试 | OpenAPI/proto/SDK 与 runtime 一致 |
| SDK compile test | 外部 Go 调用面可编译 |
| docs hygiene | 文档链接和事实源不漂移 |

讲解句：

```text
单元测试保证功能局部正确，架构护栏保证系统长期不变形。
```

## 14. 典型业务场景讲法

### 14.1 防止 handler 越写越重

```text
如果 REST handler 直接访问 repository、开启事务、调用 Casbin，短期看是快，但长期会绕过 application 的用例编排和权限边界。架构测试可以把 transport -> infra 这类依赖直接挡住。
```

---

### 14.2 防止接口定义和实现漂移

```text
如果 OpenAPI 新增了字段，但 handler 没有解析，业务系统会按文档调用却得不到效果。契约测试和 api-validate 可以把 OpenAPI、handler、SDK 的同步作为检查项。
```

---

### 14.3 防止 SDK 破坏外部调用方

```text
Go SDK 是业务服务接入 IAM 的外部调用面。如果 public API 随便变，业务服务升级 SDK 时会编译失败。compile test 可以用示例代码提前发现这种破坏性变化。
```

---

### 14.4 防止文档旧事实回流

```text
IAM 文档分 active 和 archive。如果 active README 引用了 archive 里的旧模型，后续开发就可能按旧事实实现。docs hygiene 的作用就是让文档入口、链接和事实源保持一致。
```

## 15. 面试追问展开点

| 追问 | 回答要点 |
| --- | --- |
| 你说的架构测试测什么？ | 测 import 依赖方向和禁止依赖，例如 domain 不依赖 infra、SDK 不 import internal |
| 契约测试和单元测试有什么区别？ | 契约测试关注 OpenAPI/proto/SDK 与运行时实现一致，单元测试关注局部业务逻辑 |
| 为什么 SDK 要 compile test？ | SDK 是外部调用面，compile test 能低成本保护 public API 兼容性 |
| docs hygiene 有必要吗？ | 文档会漂移，尤其是 README 链接、active/archive 和 Verify 命令，漂移后会误导实现和宣讲 |
| CI 里最核心跑哪些？ | docs-hygiene、api-validate、proto-gen、architecture tests、transport tests、SDK tests |
| 如果架构测试失败怎么办？ | 优先调整依赖方向，谨慎加白名单；白名单必须有原因和退出条件 |
| 为什么不只靠 code review？ | code review 容易漏，自动化测试可以把核心边界变成稳定门禁 |

## 16. 常见反模式

| 反模式 | 问题 | 推荐做法 |
| --- | --- | --- |
| 只靠单元测试 | 覆盖不了架构边界和契约漂移 | 增加 architecture / contract / docs 护栏 |
| 只靠 code review 管边界 | 人工容易漏 | 用架构测试固化禁止依赖 |
| handler 直接访问 repository | 绕过 application | transport -> application -> port -> infra |
| domain import proto | 协议污染领域 | mapper 留在 transport/application 边界 |
| SDK import internal | 外部调用面穿透服务内部 | SDK 只依赖公开契约 |
| OpenAPI 改了 handler 不改 | 契约漂移 | contract tests 和 api-validate |
| proto 改了不跑生成 | 生成物漂移 | `make proto-gen` 进入 CI |
| SDK public API 无 compile test | 外部调用方易被破坏 | 示例和 public API compile test |
| README 指向旧文件 | 文档入口失效 | docs hygiene |
| active docs 引用 archive 旧事实 | 旧模型回流 | active 只引用 active 当前事实 |

## 17. 推荐表达顺序

讲工程质量与架构护栏时建议按这个顺序：

```text
1. 先说工程质量不是只靠单元测试；
2. 说明长期演进最容易漂移的是分层、契约、SDK、文档；
3. 讲 architecture tests 保护分层依赖；
4. 讲 contract tests 保护 REST/gRPC/SDK 契约；
5. 讲 SDK compile test 保护外部调用面；
6. 讲 docs hygiene 保护文档事实源；
7. 讲这些护栏进入 CI；
8. 用一两个具体反模式举例。
```

不推荐：

```text
只说“我写了单元测试”；
只列工具名，不讲保护对象；
把架构测试讲成普通业务测试；
把契约测试讲成接口冒烟测试；
忽略文档漂移；
说有 CI 但讲不清 CI 阻断什么问题。
```

## 20. 本文总结

工程质量与架构护栏讲法可以压缩成：

```text
architecture tests 保护分层依赖；
contract tests 保护 OpenAPI/proto/SDK 与实现一致；
SDK compile test 保护外部 Go 调用面；
docs hygiene 保护文档链接和事实源；
CI 把这些护栏变成合并门禁。
```

宣讲时最重要的是：

```text
不要只说“写了测试”；
要说清楚每类测试保护什么边界；
要说清楚这些边界为什么容易漂移；
要说清楚失败时如何反向约束代码结构和契约演进。
```
