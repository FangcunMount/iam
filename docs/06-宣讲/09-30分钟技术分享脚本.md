## 4. 0-3 分钟：项目定位与问题背景

### 4.1 目标

这一段要让听众先明白：

```text
IAM 不是一个登录 demo；
IAM 是业务系统的统一身份与访问管理底座；
它解决的是身份事实分散、认证授权混杂、外部身份源接入混乱、权限边界不清的问题。
```

---

### 4.2 可直接讲

```text
这个项目我把它定位成一个面向业务系统接入的 IAM，也就是身份与访问管理服务。

它不是单纯的用户表 CRUD，也不是简单发一个 JWT。它要解决的是业务系统中经常重复出现的几类能力：用户和档案关系管理、登录认证、Token 管理、资源访问授权、微信或企业微信等外部身份源接入，以及在安全范围内做 Profile 联想搜索。

所以我对这个项目的一句话定位是：IAM 是业务系统的统一身份与访问管理底座，负责统一管理身份事实、认证、授权、外部身份源和安全搜索能力。
```

---

### 4.3 继续补一句业务背景

```text
在真实业务里，如果每个业务系统都自己维护用户表、自己接微信登录、自己判断权限、自己做搜索，很容易出现几个问题：身份事实不统一、openid 和内部 User 混用、认证和授权混在一起、权限规则散落在业务代码里、搜索结果缺少可见性和脱敏控制。

IAM 的价值就是把这些公共能力抽出来，形成统一模型和统一接入方式。
```

## 6. 7-10 分钟：Identity 讲法

### 6.1 目标

Identity 这一段只讲清一件事：

```text
Identity 是身份事实中心，不是登录模块，也不是权限模块。
```

---

### 6.2 可直接讲

```text
第一个核心模块是 Identity，它是身份事实中心。

我把 Identity 的核心对象拆成三个：User、Profile、ProfileLink。

User 是内部稳定身份主体，不能简单等同于手机号、openid 或 unionid。

Profile 是业务档案或被服务对象，比如儿童档案、患者档案。很多业务数据其实是围绕 Profile 展开的。

ProfileLink 表示 User 和 Profile 之间的关系，比如监护关系、档案归属关系或服务关系。

这里最重要的边界是：ProfileLink 不是 Permission。它只能说明“这个用户和这个档案有什么关系”，不能直接推出“这个用户能读取、修改、删除或导出哪些资源”。真正的访问决策要交给 AuthZ。
```

---

### 6.3 本段可以强调的反模式

```text
openid 不是 UserID；
Profile 不是登录账号；
ProfileLink 不是 Permission；
Identity 不处理 password / otp 校验；
Identity 不直接做资源授权。
```

## 7. 10-13 分钟：AuthN 讲法

### 7.1 目标

AuthN 这一段要讲清：

```text
AuthN 负责证明“你是谁”，不负责判断“你能做什么”。
```

---

### 7.2 可直接讲

```text
第二个核心模块是 AuthN，也就是认证中心。

AuthN 的核心问题是：当前请求者如何证明自己是谁。

这里我把几个概念分开建模：LoginIdentity 表示登录身份，比如手机号、微信小程序、企业微信或后台账号；Credential 表示长期认证材料，比如密码哈希或 OAuth provider 标识；Challenge 表示短期认证挑战，比如验证码或扫码状态；认证成功后产出 Principal，表示这次请求的认证主体上下文。

在会话和 Token 上，AuthN 会创建 Session，并签发 AccessToken 和 RefreshToken。AccessToken 是短期访问凭证，可以通过 JWKS 本地验签；RefreshToken 是续期凭证，只能用于 refresh/logout/revoke，不能进入普通业务 API。

这里最重要的边界是：Token 验签成功只代表认证通过，不代表授权通过。后续资源访问仍然要进入 AuthZ Check。
```

---

### 7.3 本段可以强调的反模式

```text
AuthN 不是简单发 JWT；
LoginIdentity 不是 User；
Principal 不是完整 User entity；
AccessToken 不等于 RefreshToken；
RefreshToken 不进普通业务 API；
验签不等于授权。
```

## 8. 13-15 分钟：AuthZ 讲法

### 8.1 目标

AuthZ 这一段要讲清：

```text
AuthZ 负责“能不能做”，并且必须有 Resource / Action / Scope 维度。
```

---

### 8.2 可直接讲

```text
第三个核心模块是 AuthZ，也就是授权中心。

AuthZ 的核心问题是：某个 Subject 在某个 Scope 下，能不能对某个 Resource 执行某个 Action。

这里我没有把权限简化成 user.role == admin，而是拆成 Subject、Resource、Action、Scope、Role、Permission、RoleBinding 和 AuthorizationDecision。

Subject 是授权主体，通常由 AuthN 的 Principal 映射而来；Resource 是被访问资源；Action 是动作，比如 read、write、delete、export；Scope 是授权域，比如家庭、机构、项目或租户；Permission 表示资源动作访问声明；RoleBinding 表示某个 Subject 在某个 Scope 下绑定了某个 Role。

这里 Casbin 可以作为 infra 层的 runtime engine，但不是 AuthZ 的领域模型。领域层仍然使用 Subject、Role、Permission、RoleBinding 这些业务语言，infra/authz adapter 再映射成 Casbin 的 p/g/r rules。
```

---

### 8.3 补一句 PolicyVersion / Outbox

```text
授权事实变化后，还需要让 runtime 感知变化。所以写入 RoleBinding 或 Permission 时，会 bump PolicyVersion，并通过 Transactional Outbox 发布版本变化事件，RuntimeReload 再刷新 Casbin runtime snapshot。这里选择的是本地事务强一致、跨系统最终一致，消费者要幂等。
```

## 9. 15-17 分钟：IDP 与第三方登录讲法

### 9.1 目标

IDP 这一段要讲清：

```text
IDP 解析外部身份事实，AuthN 生成内部登录态。
```

---

### 9.2 可直接讲

```text
第四个模块是 IDP，也就是外部身份源基础设施。

它负责接入微信小程序、公众号、企业微信等 provider，管理 provider app、credentials、provider access token，并把 provider 返回的 openid、unionid、wecom userid 等信息解析成 ExternalIdentity。

这里最容易混淆的是 provider 侧概念和 IAM 内部概念。openid 不是 IAM UserID，provider access_token 不是 IAM AccessToken，ExternalIdentity 也不是 Principal。

完整第三方登录链路应该是：客户端拿到微信 code；IDP 解析出 ExternalIdentity；AuthN 根据 ExternalIdentity 匹配或绑定 LoginIdentity；再生成 Principal、Session、AccessToken 和 RefreshToken。
```

## 10. 17-19 分钟：Suggest 读模型讲法

### 10.1 目标

Suggest 这一段要讲清：

```text
Suggest 是 Profile 搜索读模型，不是 Identity 主数据，也不是授权结果。
```

---

### 10.2 可直接讲

```text
第五个模块是 Suggest，它是 Profile 联想搜索读模型。

Identity 负责 Profile 主数据，Suggest 只是从这些 Profile facts 派生搜索 token 和 SuggestSnapshot。查询时先 normalize keyword，再从 Snapshot 命中候选，然后必须做 ProfileAccessScope 和可见性过滤，最后排序、截断、脱敏返回 SuggestResult。

这里最重要的边界是：索引命中不等于可见，可见候选也不等于有详情读取权限。比如手机号搜索只能扩大匹配方式，不能扩大可见范围；响应只能返回 mobile_mask，不能返回明文手机号；用户点击候选进入详情后，仍然要重新走 AuthZ Check。
```

## 11. 19-23 分钟：REST / gRPC / Go SDK 接入

### 11.1 目标

这一段要讲清：

```text
IAM 不是内部自用代码，而是面向业务系统的可接入服务。
```

---

### 11.2 可直接讲

```text
接入层上，IAM 提供三类方式。

REST 面向 Web、App、管理端和跨语言调用，OpenAPI 是 REST 的机器契约。

gRPC 面向内部可信服务间调用，proto 是 gRPC 的机器契约。

Go SDK 面向 Go 业务服务，用来封装 REST/gRPC 调用、TokenSource、错误模型和常用 request/response。

这里我比较强调契约事实源：REST 看 OpenAPI，gRPC 看 proto，SDK 看 pkg/sdk public API，文档只解释语义和边界，不能反向定义机器契约。
```

---

### 11.3 业务系统接入顺序

```text
业务系统接入 IAM 的标准顺序是：
先接 AuthN，拿到或校验 Principal；
再接 AuthZ，做 Resource / Action / Scope 的 Check；
再按需读取 Identity 身份事实；
如果涉及微信等第三方登录，再接 IDP；
如果需要 Profile 联想搜索，再接 Suggest。
```

## 12. 23-27 分钟：专题设计与架构护栏

### 12.1 目标

这一段要把“项目深度”讲出来：

```text
不是只做功能，而是对安全、一致性、读模型和工程质量做了取舍。
```

---

### 12.2 专题设计可以这么讲

```text
这个项目里有几个设计点我会重点讲。

第一是 JWT/JWKS 和 Key Rotation：JWT/JWS 解决 Token 可信表达，JWKS 解决公钥发布和本地验签，但验签不等于授权。

第二是 Session、AccessToken、RefreshToken 的边界：Session 是服务端会话状态，AccessToken 是短期访问凭证，RefreshToken 只用于续期。

第三是 Transactional Outbox：授权事实写入和 PolicyVersion 事件发布需要一致性，所以用本地事务写 Outbox，再由 Relay 异步发布，消费者幂等处理。

第四是 Casbin 定位：Casbin 是 infra runtime，不是 AuthZ domain。

第五是 ProfileLink 与 Permission 的边界：身份关系不是资源权限。

第六是 Suggest 读模型：搜索索引可以最终一致和降级，但不能牺牲可见性和脱敏安全边界。
```

---

### 12.3 架构护栏可以这么讲

```text
为了防止项目长期演进后边界变乱，我设计了四类工程护栏。

architecture tests 保护 import 依赖方向，比如 domain 不依赖 infra，transport 不绕过 application，SDK 不 import internal。

contract tests 保护 OpenAPI、proto、SDK 和 transport 实现一致。

SDK compile test 保护 Go SDK public API 和示例代码可编译。

docs hygiene 保护 README 链接、active/archive 边界和文档事实源。

这部分体现的是：工程质量不是只靠 code review 或自觉，而是把关键边界变成测试和 CI 门禁。
```
