# 00-项目一句话定位

## 1. 本文定位

本文是 `07-宣讲/` 的第一篇。

它不讲源码细节，也不替代 `00～06` 的事实层文档。

它只解决一个问题：

```text
IAM 项目到底是什么？
```

本文服务于：

```text
简历项目描述；
面试项目开场；
技术分享开场；
架构答辩开场；
朋友/同事快速说明。
```

目标是让你可以用：

```text
10 秒；
30 秒；
1 分钟；
3 分钟；
```

把 IAM 项目的定位讲清楚。

一句话：

> 本文负责把 IAM 从“用户系统 / 登录系统 / 权限系统”中区分出来，定位为面向业务系统接入的身份与访问管理服务。

## 2. 最推荐的一句话

```text
IAM 是一个面向业务系统接入的身份与访问管理服务，统一提供登录认证、Session 与 Token 管理、资源授权判定、User/Profile/ProfileLink 身份关系、第三方身份源集成，以及 REST/gRPC/SDK 接入能力。
```

这是最推荐的项目定位。

它覆盖了 IAM 的六个关键面：

```text
认证：AuthN；
授权：AuthZ；
身份：Identity；
第三方身份源：IDP；
接入：REST / gRPC / SDK；
治理：架构护栏与契约防漂移。
```

它避免把 IAM 误讲成：

```text
普通用户中心；
登录系统；
权限系统；
JWT 系统；
微信登录系统。
```

## 3. 10 秒版

```text
IAM 不是普通用户中心，而是统一处理认证、授权、身份关系和业务系统接入的基础服务。
```

适合场景：


这句话的重点是：


## 4. 30 秒版

```text
IAM 是一个面向业务系统接入的身份与访问管理服务。它不是简单的用户中心，而是把登录认证、Session 与 Token 管理、资源授权判定、User/Profile/ProfileLink 身份关系、第三方身份源，以及 REST/gRPC/SDK 接入能力统一起来。内部按 AuthN、AuthZ、Identity、IDP 拆分边界：AuthN 管登录态，AuthZ 管访问权，Identity 管用户与业务档案关系，IDP 管外部身份源配置和适配。
```

```text

```

这版要讲清三个点：

```text
1. IAM 的系统定位；
2. 它和普通用户中心的区别；
3. 四个核心模块边界。
```

## 5. 1 分钟版

```text
这个 IAM 项目定位是方寸系统的身份与访问管理基础服务，核心不是单纯做用户资料管理，而是解决业务系统统一接入认证和授权的问题。

在认证侧，AuthN 负责登录、Session、AccessToken、RefreshToken、Token Verify、JWKS 和 KeyRotation；在授权侧，AuthZ 通过 Subject、Role、Resource、Permission、RoleBinding、Scope 建模访问权，并通过 Check 给业务系统提供资源级判定；在身份侧，Identity 把 User 和业务档案 Profile 分开，通过 ProfileLink 表达本人、父母、祖辈等关系；在第三方身份源侧，IDP 管微信、企微等外部身份源配置与适配，真正的登录态仍由 AuthN 统一处理。

对外，IAM 提供 REST、gRPC 和 Go SDK 三种接入方式，让前端、管理后台、qs-server、worker 等系统按场景接入。同时通过架构测试、契约测试和文档事实源检查，保护系统长期演进中的边界稳定性。
```

适合场景：

```text
面试项目介绍；
技术分享开场；
项目复盘；
架构答辩。
```

这版已经可以自然引出后续追问：

```text
AuthN 为什么不只发 JWT？
AuthZ 为什么不是 user.role？
ProfileLink 为什么不能只是 User 字段？
REST/gRPC/SDK 如何划分？
架构护栏具体怎么做？
```

## 6. 3 分钟版

```text
IAM 是方寸系统里的身份与访问管理服务。它最重要的定位是：不是普通用户中心，不只是维护 users 表，也不只是登录后发一个 JWT，而是统一解决业务系统接入时的认证、授权、身份关系和第三方身份源问题。

我把它拆成四个核心边界。

第一是 AuthN，也就是认证模块。它回答“你是谁，以及你如何证明你是谁”。这里不是简单查用户表发 JWT，而是把登录身份、认证凭证、登录流程、Principal、Session、AccessToken、RefreshToken、JWKS、KeyRotation 和在线 Verify 拆清楚。Session 是服务端可控的登录态锚点，AccessToken 是短期访问凭证，RefreshToken 是续期凭证，JWKS 支持离线验签，在线 Verify 支持更强的状态校验。

第二是 AuthZ，也就是授权模块。它回答“你能不能访问某个资源”。这里不是 user.role 字段，而是通过 Subject、Role、Resource、Permission、RoleBinding、Action、Scope 建模访问权。业务系统在访问资源前构造 Resource / Action / Scope，调用 IAM Check，IAM 返回 AuthorizationDecision。授权写入也不是普通 CRUD，而是通过 PolicyChange、PolicyChangeCommitter、PolicyVersion、Outbox 和 RuntimeReload 保证管理事实、运行时事实和多实例传播的一致性。

第三是 Identity，也就是身份关系模块。这里 User 是登录主体，Profile 是业务档案，两者不能直接合并。比如在儿童测评业务里，一个用户可能关联多个儿童档案，一个儿童档案也可能关联父母、祖辈或其他照护人。系统通过 ProfileLink 表达 User 与 Profile 的关系，但 ProfileLink 只是身份关系，不替代 AuthZ 权限判定。

第四是 IDP，也就是第三方身份源基础设施。IDP 负责微信、企微等外部身份源的应用配置、密钥管理和外部 API 适配，但它不直接签发 IAM Token。外部身份源解析之后，仍然回到 AuthN 的 LoginIdentity、Principal、Session 和 Token 链路。

对外，IAM 提供 REST、gRPC 和 Go SDK 三种接入方式：REST 面向前端和管理端，gRPC 面向服务间调用，SDK 面向 Go 服务端项目，例如 qs-server。qs-server 通过 SDK 或 gRPC 验证 Token、查询 User/Profile/ProfileLink、调用 AuthZ Check，而不是自己复制 IAM 的账号、角色、权限表。

最后，为了避免项目长期演进后边界腐烂，我还建立了架构护栏：domain 不依赖 infra，application 不依赖 transport，transport 不直接访问 repository 或 Casbin，SDK 不 import internal 包；同时用 OpenAPI、proto、SDK public API 测试和 docs-hygiene 来防止接口和文档漂移。
```

适合场景：

```text
项目主讲；
面试深聊前的完整铺垫；
技术分享前 3 分钟；
架构答辩开场。
```

注意：3 分钟版不是背诵稿。

它的作用是帮你建立稳定讲法，实际表达时可以根据面试官反应裁剪。

## 7. 一句话关键词拆解

标准一句话：

```text
IAM 是一个面向业务系统接入的身份与访问管理服务，统一提供登录认证、Session 与 Token 管理、资源授权判定、User/Profile/ProfileLink 身份关系、第三方身份源集成，以及 REST/gRPC/SDK 接入能力。
```

关键词解释：

| 关键词 | 解释 |
| --- | --- |
| `面向业务系统接入` | IAM 不是孤立服务，而是给 qs-server 等业务系统使用 |
| `身份与访问管理` | Identity and Access Management，不只是用户资料 |
| `登录认证` | AuthN，回答“你是谁，如何证明” |
| `Session 与 Token` | 登录态锚点、访问凭证、续期凭证、验证与撤销边界 |
| `资源授权判定` | AuthZ，回答“你能不能访问某个资源” |
| `User/Profile/ProfileLink` | 登录主体、业务档案、二者关系 |
| `第三方身份源` | IDP，微信/企微等外部身份源配置与适配 |
| `REST/gRPC/SDK` | 前端、服务间、Go 服务端的三种接入投影 |

```text

```

```text
这是一个身份与访问管理服务，User 只是其中一部分。
```

```text
这是一个登录认证系统。
```

```text
只讲了 AuthN，漏掉 AuthZ、Identity、IDP 和接入契约。
```

更好的说法：

```text
登录认证只是 IAM 的 AuthN 边界，系统还包括授权、身份关系和接入能力。
```

---

### 8.3 不要说成“权限系统”

```text
这是一个权限系统。
```

问题：

```text
只讲了 AuthZ，漏掉登录态、Token、身份关系和第三方身份源。
```

更好的说法：

```text
权限判定是 IAM 的 AuthZ 边界，IAM 还统一处理认证和身份关系。
```

### 8.4 不要说成“JWT 系统”

## 10. 项目价值主张

对外讲项目时，不要只讲“我实现了哪些接口”。

要讲它解决了什么系统问题。

### 10.1 统一认证

```text
把密码、短信、微信、企微、Service Token 等认证方式统一到 AuthN 登录态模型。
```

价值：

```text
不同登录方式最终都进入同一套 Principal、Session、Token、Verify、Refresh、Revoke 边界。
```

---

### 10.2 统一授权

```text
把角色、资源、权限、角色绑定统一建模，通过 AuthZ Check 给业务服务提供资源访问判定。
```

价值：

```text
业务系统不需要各自实现一套权限系统，也不需要直接理解 Casbin facts。
```

---

### 10.3 统一身份关系

```text
把登录主体 User 和业务档案 Profile 分开，通过 ProfileLink 表达本人、父母、祖辈等关系。
```

价值：

```text
支持儿童档案、家庭协作、当前用户档案访问边界。
```

---

### 10.4 统一第三方身份源

```text
IDP 只负责外部身份源配置、密钥和外部 API 适配，登录态由 AuthN 统一管理。
```

价值：

```text
避免微信登录、企微登录、密码登录各自签发一套 Token。
```

---

### 10.5 统一接入

```text
通过 REST、gRPC、SDK 让不同调用方按场景接入 IAM。
```

价值：

```text
前端和管理端走 REST，后端服务走 gRPC，Go 服务通过 SDK 降低接入成本。
```

---

### 10.6 统一治理

```text
通过架构测试、契约测试、SDK public API compile test 和 docs-hygiene 防止系统长期演进后边界漂移。
```

价值：

```text
项目不是只做出来，还要能长期维护。
```

## 11. 和普通用户中心的区别

| 维度 | 普通用户中心 | IAM |
| --- | --- | --- |
| 核心对象 | User | Identity + Access |
| 登录 | 简单账号密码 | 多认证方式 + Session + Token |
| Token | 通常只发 JWT | AccessToken + RefreshToken + Verify + Revoke + JWKS |
| 授权 | user.role 或简单角色表 | Role / Resource / Permission / RoleBinding / Scope / Check |
| 用户资料 | User profile 字段 | User 与 Profile 分离 |
| 档案关系 | 通常没有 | ProfileLink |
| 第三方登录 | 写进登录逻辑 | IDP 基础设施 + AuthN 统一登录 |
| 接入方式 | HTTP API | REST + gRPC + SDK |
| 策略传播 | 通常没有 | PolicyVersion + Transactional Outbox |
| 架构护栏 | 通常靠约定 | architecture tests + contract tests |

一句话总结区别：

```text
用户中心管理用户资料；IAM 管理身份、认证、授权、会话、凭证、身份源、档案关系和系统接入。
```

## 12. 和 AuthN-only 服务的区别

AuthN-only 服务主要回答：

```text
你是谁？
你如何证明？
登录后如何发 Token？
```

IAM 还要回答：

```text
你能不能访问某个资源？
你和业务档案是什么关系？
业务系统如何接入？
权限变化如何传播？
SDK 和契约如何维护？
```

所以不要把 IAM 讲成单独认证服务。

---

## 13. 和 AuthZ-only 服务的区别

AuthZ-only 服务主要回答：

```text
某个 subject 能不能访问某个 resource？
```

IAM 还包括：

```text
登录认证；
Session / Token；
User / Profile / ProfileLink；
IDP 外部身份源；
REST / gRPC / SDK 接入；
```

所以不要把 IAM 讲成单独权限系统。

## 15. 推荐回答模板

### 15.1 面试官问：“这个项目是做什么的？”

```text
这是一个 IAM 身份与访问管理服务，不是普通用户中心。它统一处理业务系统接入时的登录认证、Session 与 Token 管理、资源授权判定、User/Profile/ProfileLink 身份关系、第三方身份源，以及 REST/gRPC/SDK 接入。内部拆成 AuthN、AuthZ、Identity、IDP 四个边界，分别处理认证态、访问权、身份档案关系和外部身份源。
```

---

### 15.2 面试官问：“你负责了哪些部分？”

```text
我主要围绕 IAM 的核心认证授权链路和架构文档体系做设计与实现：一是 AuthN 登录链路，包括 Session、AccessToken、RefreshToken、JWKS 和在线 Verify；二是 AuthZ 授权模型，包括 Role、Resource、Permission、RoleBinding、Check、PolicyVersion 和 Outbox；三是 Identity 里的 User、Profile、ProfileLink 模型；四是 REST/gRPC/SDK 接入契约和架构护栏。
```

这句话要按真实代码贡献调整。

不要把未完成能力说成已完成。

---

### 15.3 面试官问：“这个项目的难点是什么？”

```text
难点不在于写几个 CRUD 接口，而在于边界拆分和一致性治理。比如 AuthN 不能只发 JWT，还要处理 Session、Refresh、Revoke、JWKS 和在线 Verify；AuthZ 写入不是简单 insert/delete，而是要同时写授权 facts、递增 PolicyVersion、stage Outbox 事件，并在提交后 reload runtime policy；Identity 里 User 和 Profile 不能合并，要通过 ProfileLink 表达关系；另外 REST/gRPC/SDK 三种接入方式还要和源码事实保持一致。
```

---

### 15.4 面试官问：“这个项目有什么亮点？”

```text
亮点有三个。第一，模型边界清晰，把 AuthN、AuthZ、Identity、IDP 拆开，避免大 UserService。第二，关键链路有工程治理，比如 AuthZ 写入使用 PolicyChangeCommitter、UoW、PolicyVersion 和 Transactional Outbox，Token 使用 Session、RefreshToken、JWKS 和在线 Verify。第三，项目有可维护性护栏，包含架构测试、OpenAPI/proto 契约测试、SDK public API compile test 和文档事实源检查，防止长期演进中边界漂移。
```

---

### 15.5 面试官问：“它和普通用户系统区别在哪？”

```text
普通用户系统核心是 User CRUD 和简单登录。IAM 的核心是身份与访问管理：AuthN 负责认证态，AuthZ 负责访问权，Identity 负责 User/Profile/ProfileLink，IDP 负责外部身份源，接入层通过 REST/gRPC/SDK 给业务服务使用。普通用户系统通常不会完整处理 Session、RefreshToken、JWKS、资源级授权判定、授权版本传播、ProfileLink 关系和 SDK 接入这些问题。
```

```text
AuthN：认证态；
AuthZ：访问权；
Identity：身份与档案关系；
IDP：外部身份源；
Access：REST / gRPC / SDK 接入；
Guard：架构与契约护栏。
```

如果只记住一句话：

```text
IAM 是一个面向业务系统接入的身份与访问管理服务，统一提供登录认证、Session 与 Token 管理、资源授权判定、User/Profile/ProfileLink 身份关系、第三方身份源集成，以及 REST/gRPC/SDK 接入能力。
```
