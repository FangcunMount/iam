# 13-面试追问证据索引

## 1. 本文定位

本文是 `07-宣讲/` 的最后一篇，用于面试前准备和面试中快速回链证据。

它不是正文讲稿，而是一张 **追问作战地图**。

它回答：

```text
面试官可能怎么追问？
每个问题应该怎么答？
回答时应该回链哪些源码、契约、测试或文档？
哪些问题容易答偏？
如果继续深挖，应该往哪里展开？
Suggest 这类辅助读模型被追问时，如何讲清边界？
```

使用方式：

```text
1. 面试前按模块扫一遍；
2. 每个问题先记 30 秒回答；
3. 再记 2～3 个证据路径；
4. 最后准备一个可继续展开的技术点。
```

不要死背全文。

核心是训练：

```text
问题 -> 回答 -> 证据 -> 追问展开
```

## 2. 追问准备总原则

### 2.1 先答结论，再讲链路

不要一上来解释所有细节。

推荐结构：

```text
结论
  -> 为什么
  -> 怎么做
  -> 证据在哪里
  -> 代价和边界
```

示例：

```text
为什么 AuthZ 写入不是 CRUD？

结论：因为授权写入改变的是运行时授权事实，而不是单表记录。
为什么：它影响管理记录、runtime facts、PolicyVersion、Outbox 和 runtime reload。
怎么做：通过 PolicyChangeCommitter 在 UoW 里统一提交。
证据：docs/03-授权AuthZ/03-*、application/authz/policy/committer.go。
边界：reload 在事务后，是 best-effort，不回滚 DB facts。
```

---

### 2.2 不要只说“我用了某技术”

错误：

```text
我用了 JWT。
我用了 Casbin。
我用了 Outbox。
我用了 gRPC。
我用了 Trie。
```

正确：

```text
JWT 只是 AccessToken 的一种实现，完整登录态由 Session + RefreshToken + Verify 管。
Casbin 是 runtime policy engine，领域模型仍是 Role / Resource / Permission / RoleBinding。
Outbox 解决 DB facts 和事件传播的一致性。
gRPC 面向可信服务间调用，REST 和 SDK 有各自场景。
Trie / Hash 是 Suggest 高性能候选召回的数据结构，不能替代 ProfileAccessScope 过滤。
```

---

### 2.4 遇到不会的问题，承认边界

推荐说法：

```text
这个点当前项目里还没有完整实现，我当前的设计倾向是……
```

不要硬编。

例如：

```text
复杂 ABAC / OPA 当前不是第一阶段重点，当前采用 RBAC + Scope，后续如业务需要再演进。
```

如果问到 Suggest 独立服务：

```text
从领域边界看，Suggest 独立服务有合理性；但当前规模下独立部署、鉴权、同步和运维成本偏高，所以暂时作为 iam-apiserver 内置辅助读模型，后续流量和组织复杂度上来后再拆。
```

## B. 业务背景类追问

### B1. 为什么业务系统需要 IAM？

#### 30 秒回答

```text
当业务系统出现 Web、App、微信、管理后台、内部服务等多种入口时，认证、授权、第三方登录和档案关系就不能继续散落在各个业务模块中。否则会出现 token 语义不一致、权限判断分散、用户禁用后旧 token 仍可用、微信 AppSecret 分散、档案关系无法统一表达、管理后台 Profile 查询绕过权限等问题。IAM 把这些能力统一成基础服务。
```

#### 证据链


### B2. 项目最大的业务痛点是什么？

#### 30 秒回答

```text
最大的痛点是认证授权和身份关系分散。没有 IAM 时，每个业务系统会自己做登录、JWT、权限判断、微信登录和用户档案关系维护。短期快，长期会导致安全语义不一致、权限变更难同步、档案关系难表达、接入方式重复和边界腐烂。管理后台的 Profile 快速搜索如果没有统一边界，也容易出现 A 能查到不该看的档案、手机号泄露等问题。
```

### C3. Container 是不是 Service Locator？

#### 30 秒回答

```text
不是。这里的 container 更接近 composition root，它只在启动阶段负责初始化模块和组装依赖，并把能力投影成 REST deps、gRPC registrations 和 runtime deps。请求处理过程中，业务代码不会到 container 里随便取对象，而是通过显式依赖调用 application capabilities。Suggest 的 Runtime、Refresher、RateLimiter、Metrics 也是通过组合根装配，而不是在 handler 中临时创建。
```

## D. AuthN 认证类追问

### D1. 登录流程怎么设计？

#### 30 秒回答

```text
登录不是直接查用户发 JWT，而是先根据登录方式构造认证 proof，再交给 Authenticator 做领域认证。认证成功后得到 Principal，Principal 是认证链路的核心边界对象。之后 Token 链路基于 Principal 创建 Session，签发短期 AccessToken，并保存或管理 RefreshToken。这样后续 Verify、Refresh、Revoke 都能围绕同一个 Session 做状态控制。
```

### D2. 为什么不只用 JWT？

#### 30 秒回答

```text
JWT 只能证明 token 是 IAM 签发且未过期，不能证明登录态当前仍然有效。比如用户登出、被 block、账号 disabled，旧 JWT 在过期前本地验签仍可能通过。所以 IAM 用 Session 做在线登录态锚点，在线 Verify 会检查 revoked marker、Session active 和 User/Account 状态。
```

### D3. AccessToken 和 RefreshToken 怎么分工？

#### 30 秒回答

```text
AccessToken 是短期访问凭证，适合请求携带和 JWKS 本地验签；RefreshToken 是长期续期凭证，但必须服务端保存、可撤销、可轮换，并且绑定 Session。Refresh 时要检查 refresh token、Session 和 User/Account 状态，成功后轮换或失效旧 RefreshToken。
```

### D4. JWKS 和在线 Verify 有什么区别？

#### 30 秒回答

```text
JWKS 是公钥分发机制，用于本地验证 JWT 签名、kid、exp、issuer、audience；在线 Verify 是状态判定，会在验签之外检查 token 是否撤销、Session 是否 active、User/Account 是否仍可用。所以 JWKS 证明签名可信，在线 Verify 证明当前可用。
```

### D5. KeyRotation 怎么做？

#### 30 秒回答

```text
JWT header 中带 kid，验签时根据 kid 找 verification key。Key 有 active、grace、retired 三种状态：active 用于签新 token 并发布到 JWKS，grace 不签新 token 但继续发布用于验旧 token，retired 不再发布。这样可以平滑轮换签名密钥。
```

### D6. Service Token 和用户 Token 有什么区别？

#### 30 秒回答

```text
用户 Token 绑定 User、LoginIdentity 和 Session，Verify 时要检查 Session 与 User/Account 状态。Service Token 表达服务身份，不应该伪装成某个管理员用户登录，也不走用户 Session / RefreshToken 语义。它应该通过 audience、TTL、service identity、mTLS、ACL 和审计来约束。
```

### J5. 手机号搜索为什么要额外授权、限流和脱敏？

#### 30 秒回答

```text
手机号是高敏感标识，直接支持手机号搜索会带来枚举、存在性探测和隐私泄露风险。所以手机号形态关键词需要 AllowMobileSearch；查询仍然要经过 ProfileAccessScope 过滤；响应只返回 mobile_mask，不返回明文 mobile；接口还需要限流、日志脱敏和指标观测。无权限或降级时返回空结果比暴露拒绝细节更安全。
```

### J6. Trie / Hash / Runtime 怎么组织索引？

#### 30 秒回答

```text
ProfileSearchTerm 是 Suggest 的搜索读模型投影，不是 Profile 聚合本体。Trie 或 TST 负责姓名、拼音、简拼等前缀匹配，Hash 负责 ProfileID 和手机号这类精确匹配，ProfileSuggestionRuntime 持有当前活动 Store。查询时 Runtime 只读当前 Store，刷新时通过 Full/Delta refresh 构建或更新 Store。
```

### J7. Full refresh 和 Delta refresh 有什么区别？

#### 30 秒回答

```text
Full refresh 是全量构建新的 Search Store，再通过 Runtime.Replace 原子替换当前活动索引，适合启动、定期兜底和修复漂移。Delta refresh 是导入变化的 ProfileSearchTerm 或 tombstone，适合低成本处理增量变化。旧姓名、旧手机号、旧拼音等 key 的残留需要 Delta tombstone 协议和 Full refresh 兜底。
```

### J8. Suggest 挂了为什么可以降级为空结果？

#### 30 秒回答

```text
Suggest 是管理端辅助查询能力，不是 AuthN/AuthZ/Identity 主链路。如果索引未初始化或依赖异常，在 Required=false 的场景下降级为空结果，比绕过权限直接查全局 MySQL 更安全。这样牺牲 autocomplete 体验，但不扩大数据泄露风险，也不阻断登录和授权主流程。
```

### L2. 项目中最复杂的设计点是什么？

#### 推荐回答方向一：AuthZ 写入

```text
最复杂的是 AuthZ 写入，因为它不是单表 CRUD。一次授权变更会影响管理记录、runtime facts、PolicyVersion、Outbox event 和 runtime reload。这里需要 UoW 保证 DB facts、version 和 event 同事务提交，同时 runtime reload 和 outbox relay 又是事务后的异步动作。
```

#### 推荐回答方向二：AuthN 登录态

```text
另一个复杂点是 AuthN 登录态，不能只靠 JWT。需要区分 Session、AccessToken、RefreshToken、JWKS 和在线 Verify，才能同时支持性能、撤销、续期和安全状态一致性。
```

#### 推荐回答方向三：Suggest 辅助读模型

```text
Suggest 的复杂点在于它不是简单 autocomplete。它既要低延迟召回中文名、拼音、简拼、ProfileID、手机号，又要保证 ProfileAccessScope 过滤、手机号脱敏、限流、指标和降级。它还要通过 Full/Delta refresh 保持索引更新，避免旧 key 残留。
```

### L3. 项目中最能体现 DDD/领域建模的点是什么？

#### 30 秒回答

```text
最能体现领域建模的是把 User、Profile、ProfileLink 分开，以及 AuthZ 的 Role/Resource/Permission/RoleBinding 模型。User 是登录主体，Profile 是业务档案，ProfileLink 是关系事实；AuthZ 里 Permission 回答角色能做什么，RoleBinding 回答谁持有什么角色。这些模型不是从表结构倒推，而是从业务概念和变化原因拆出来的。Suggest 里 ProfileSearchTerm 和 ProfileAccessScope 也体现了读模型和核心身份模型分离。
```

## M. 面试前最后背诵版

### M1. 项目定位

```text
IAM 是一个面向业务系统接入的身份与访问管理服务，不是普通用户中心。它统一处理登录认证、Session/Token、资源授权、用户档案关系、第三方身份源、REST/gRPC/SDK 接入，并内置 Suggest 辅助读模型服务管理后台 Profile autocomplete。
```

### M2. 架构

```text
整体采用分层 + 六边形架构：Transport 做协议适配，Application 编排用例和事务，Domain 承载业务规则，Infra 适配 MySQL、Redis、Casbin、JWT、Outbox、第三方身份源和 Suggest Search，process 管生命周期，container 管组合装配。
```

### M3. AuthN

```text
AuthN 不是简单发 JWT，而是 Login -> Principal -> Session -> AccessToken -> RefreshToken。JWKS 做本地验签，在线 Verify 检查 revoked marker、Session 和 User/Account 状态。
```

### M4. AuthZ

```text
AuthZ 不是 user.role，而是 Subject、Role、Resource、Permission、RoleBinding、Action、Scope。Check 输入 subject、tenantDomain、resource、action、scope。写入通过 PolicyChangeCommitter/UoW 写 facts、递增 version、stage outbox，并 reload runtime policy。
```

### M5. Identity

```text
User 是登录主体，Profile 是业务档案，ProfileLink 是关系事实。ProfileLink 支持 self/parent/grandparent/other 和 active/revoked，用于当前用户档案访问 guard，但不是 AuthZ permission，也不是 Suggest ProfileAccessScope。
```

### M6. IDP

```text
IDP 只做第三方身份源基础设施，管理微信/企微应用、SecretVault 和平台 access_token；真正登录态、账号绑定、Session 和 IAM token 由 AuthN 统一处理。
```

### M7. 接入

```text
REST 面向 Web/App/Admin 和 Suggest autocomplete，gRPC 面向可信服务间调用，SDK 面向 Go 业务服务低成本接入。SDK 是接入产品层，不是业务层。
```

### M8. Suggest

```text
Suggest 是 iam-apiserver 内置的 Profile 联想搜索辅助读模型，不是核心身份域、完整搜索服务或 AuthZ 权限中心。它通过 ProfileSearchTerm、Trie/Hash、ProfileAccessScope、Full/Delta refresh、mobile_mask、限流、指标和降级解决后台 autocomplete 的性能与安全边界。
```

### M9. 工程质量

```text
工程质量靠多层护栏：architecture tests 保护依赖边界，REST/gRPC contract tests 保护机器契约，SDK compile test 保护公开面，Suggest tests 保护 ProfileAccessScope/mobile_mask/降级语义，docs-hygiene 保护文档事实源。
```
