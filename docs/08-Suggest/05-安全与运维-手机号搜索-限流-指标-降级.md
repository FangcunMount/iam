# 05-安全与运维：手机号搜索 / 限流 / 指标 / 降级

> 本文回答：Suggest 为什么必须把手机号搜索当作高敏感能力处理；`AllowMobileSearch`、`mobile_mask`、限流、审计日志如何协作；Suggest 指标如何观测查询链路和索引质量；`Required=false`、`DegradedService`、健康检查如何保护 IAM 核心链路；生产环境应该如何配置和排障。

---

## 30 秒结论

| 问题 | 结论 |
| ---- | ---- |
| 手机号搜索为什么特殊？ | 手机号可用于用户枚举和存在性探测，敏感度高于姓名 / 拼音搜索 |
| 没有手机号权限怎么办？ | 手机号形态关键词直接返回空数组，不继续查 Hash |
| 有手机号权限就能查全局吗？ | 不能。仍然必须经过 `ProfileAccessScope` 过滤 |
| 返回手机号吗？ | 生产只返回 `mobile_mask`，不返回明文 mobile |
| `DisableMobileMask` 能开吗？ | 生产环境禁止开启；仅允许特殊排障环境使用 |
| 限流怎么做？ | 按 operator 区分普通关键词和手机号形态关键词，手机号使用更严格 quota |
| 指标看什么？ | 查询量、手机号形态查询、返回结果数、过滤前后候选数、索引规模、刷新耗时 |
| Suggest 挂了怎么办？ | `Required=false` 时降级为空结果，不阻断 IAM 核心能力 |
| Snapshot 是恢复机制吗？ | 不是。Snapshot 主要用于排障观察，不是权威数据源 |
| 生产最重要的护栏是什么？ | 不返回明文手机号、不绕过 scope、不让 Suggest 故障拖垮 AuthN/AuthZ/Identity |

一句话：

> **Suggest 是高频读接口，安全上要防手机号枚举和越权，运维上要能限流、观测、降级，故障时宁可返回空结果，也不能返回不该看的数据。**

---

## 1. 安全与运维边界

Suggest 不是核心写链路，但它是高频查询入口。

高频查询入口的风险不是“写坏数据”，而是：

```text
读到不该读的数据；
通过返回差异探测数据存在；
高频调用压垮服务；
日志泄露敏感信息；
索引漂移导致权限收缩不及时；
故障降级时错误返回全局数据。
```

因此 Suggest 的安全与运维目标是：

```text
1. 认证后才能调用；
2. 接口级权限先拦截；
3. 数据结果必须经过 scope filter；
4. 手机号搜索额外授权；
5. 手机号输出必须脱敏；
6. 高频调用必须限流；
7. 查询和刷新必须可观测；
8. 失败时降级为空结果；
9. 生产禁止危险配置；
10. 排障路径必须清晰。
```

---

## 2. 手机号搜索为什么是高敏感能力

普通姓名搜索的问题主要是：

```text
是否能看到不属于自己范围的 Profile。
```

手机号搜索额外多了几类风险：

```text
手机号枚举；
手机号存在性探测；
跨组织查询；
日志泄露；
前端返回明文手机号；
撞库辅助信息泄露。
```

例如攻击者可以不断尝试：

```text
13800138000
13800138001
13800138002
...
```

如果系统返回结果差异明显，就可能被用来判断：

```text
这个手机号是否存在；
是否绑定了某个 Profile；
是否在当前系统内。
```

因此手机号搜索必须比姓名 / 拼音搜索更严格。

---

## 3. 手机号形态判断

当前逻辑不是识别“合法手机号”，而是识别“手机号形态关键词”。

典型判断：

```text
keyword.IsDigits() && LooksLikeMobile(keyword.String())
```

`LooksLikeMobile` 是宽松识别。

它的目的不是校验手机号格式，而是安全收紧：

```text
只要看起来像手机号，就进入更严格路径。
```

这样可以避免攻击者利用边界格式绕过手机号权限。

---

## 4. 手机号搜索权限：AllowMobileSearch

手机号搜索权限由 `ProfileAccessScope.AllowMobileSearch` 表达。

查询策略：

```text
keyword 看起来像手机号
  ↓
AllowMobileSearch=false
  ↓
返回空数组
```

注意：

```text
返回空数组，不是返回全局结果；
不继续查 Hash；
不暴露是否存在该手机号；
不把该情况当作服务异常。
```

---

## 5. 有手机号权限仍要经过 scope filter

`AllowMobileSearch=true` 只表示：

```text
当前用户允许使用手机号形态关键词发起搜索。
```

它不表示：

```text
当前用户可以看到所有手机号命中的 Profile。
```

正确链路是：

```text
手机号关键词
  ↓
AllowMobileSearch=true
  ↓
Hash 精确匹配 profileIDs
  ↓
ProfileAccessScope filter
  ↓
RankingPolicy
  ↓
mobile_mask DTO
```

结果矩阵：

| AllowMobileSearch | ProfileAccessScope 可见 | 返回 |
| ----------------- | ----------------------- | ---- |
| false | 不判断 | `[]` |
| true | false | `[]` |
| true | true | 脱敏候选 |

---

## 6. 为什么手机号无权限返回空数组

手机号无权限时可以有两种设计：

```text
返回 403；
返回空数组。
```

当前建议返回空数组。

原因：

1. 接口级 search 权限已经在 route middleware 判断。
2. 手机号搜索是更细粒度策略权限。
3. 返回 403 可能暴露“这是手机号形态且触发了权限拒绝”。
4. 对 autocomplete 来说，空数组是自然结果。
5. 减少存在性探测侧信道。

所以：

```text
接口权限不足 -> 403；
手机号形态无权限 -> 200 + []。
```

---

## 7. 手机号输出：mobile_mask

Suggest 返回 DTO 中应使用：

```text
mobile_mask
```

而不是：

```text
mobile
```

典型返回：

```json
{
  "id": "10001",
  "name": "张三",
  "mobile_mask": "138****0000",
  "weight": 1
}
```

脱敏原则：

```text
默认只取第一个手机号；
只返回脱敏结果；
异常手机号返回空 mask；
不返回完整手机号数组。
```

## 8. DisableMobileMask 生产禁用

配置中存在：

```text
DisableMobileMask
```

它只能用于特殊排障。

生产环境必须禁止：

```text
production && DisableMobileMask=true -> 启动失败
```

原因：

1. Suggest 是高频查询接口。
2. 手机号是敏感信息。
3. 前端和日志链路容易扩散明文数据。
4. 一旦被误开，风险很大。
5. 排障不能依赖关闭脱敏。

正确排障方式是：

```text
使用安全审计日志；
使用 request_id；
查看 masked result；
查看指标和索引快照；
必要时在受控环境复现。
```

## 9. 手机号搜索日志

手机号形态关键词可以记录安全日志，但不能记录明文关键词。

推荐记录：

```text
operator_id
tenant_domain
allow_mobile_search
keyword_len
request_id
client_ip_hash
result_count
rate_limited
```

禁止记录：

```text
明文手机号；
完整 keyword；
返回的 profile_ids；
完整 mobiles；
未脱敏 DTO。
```

当前基础日志至少应包含：

```text
operator_id
tenant_domain
allow_mobile_search
keyword_len
```

这已经能帮助判断：

```text
谁在发起手机号形态查询；
是否有权限；
是否存在异常频率；
是否触发了限流。
```

---

## 10. 限流设计

Suggest 是 autocomplete 接口。

用户输入时可能会触发：

```text
z
zh
zha
zhan
zhang
```

因此没有限流会带来：

```text
高频请求；
索引查询压力；
手机号枚举风险；
日志和指标膨胀；
服务资源被辅助接口消耗。
```

当前限流建议按 operator 分桶：

```text
operatorID + standard search
operatorID + mobile-shaped search
```

手机号形态关键词使用更严格 quota。

---

## 11. RateLimiter 接口语义

application 层通过端口描述限流能力。

核心语义：

```text
Allow(operatorID, mobileKeyword) bool
```

其中：

| 参数 | 说明 |
| ---- | ---- |
| operatorID | 当前操作员 ID |
| mobileKeyword | 是否手机号形态关键词 |

行为：

```text
true  -> 允许继续进入 Service；
false -> Handler 返回 429。
```

限流放在 Handler 层，而不是 Store 层。

原因：

```text
限流是接口保护；
应在 scope provider / index 访问前生效；
Store 不应该知道 operator 访问频率。
```

---

## 12. 本地限流与分布式限流

当前可使用本地内存限流。

优点：

```text
简单；
无外部依赖；
性能好；
适合单实例或早期部署。
```

限制：

```text
多实例下每个实例都有独立 quota；
无法全局限制同一 operator；
实例重启后状态丢失；
limiter map 需要考虑清理。
```

生产多实例建议引入：

```text
Redis 限流；
API Gateway 限流；
Nginx / Ingress 限流；
或本地 + Redis 双层限流。
```

推荐策略：

```text
本地限流保护单进程；
Redis / Gateway 限流保护整体系统。
```

---

## 13. 限流返回语义

如果触发限流：

```text
429 Too Many Requests
```

不应该继续进入：

```text
ProfileAccessScopeProvider；
Runtime.Current；
Trie / Hash 查询。
```

限流日志建议记录：

```text
operator_id
mobile_keyword
route
request_id
```

同样不要记录明文手机号。

## 14. 指标体系

Suggest 指标分为四类：

```text
查询指标；
手机号安全指标；
索引过滤指标；
刷新指标。
```

指标目的：

1. 观察查询量。
2. 观察手机号形态搜索是否异常。
3. 观察 scope filter 是否过滤掉大量候选。
4. 观察索引刷新是否稳定。
5. 观察返回结果数量是否异常。
6. 发现索引规模突变。

---

## 15. 查询指标

建议指标：

```text
iam_suggest_queries_total
```

可按 strategy 维度区分：

```text
mobile_denied
numeric_exact
prefix_text
unknown
```

用途：

```text
看总查询量；
看不同策略占比；
判断是否存在异常请求模式。
```

注意：

```text
不要把 operator_id / keyword / profile_id 作为 label。
```

这些都是高基数或敏感信息。

---

## 16. 手机号形态查询指标

建议指标：

```text
iam_suggest_mobile_shaped_queries_total
```

用途：

```text
观察手机号形态关键词查询量；
判断是否存在枚举行为；
配合限流日志定位异常 operator。
```

仍然不能记录明文 keyword。

---

## 17. 返回结果指标

建议指标：

```text
iam_suggest_results_returned
```

用途：

```text
观察平均返回结果数；
判断是否大量返回空；
判断 limit 是否设置过小或过大；
观察前端 autocomplete 体验。
```

如果结果长期为 0，可能原因：

```text
索引为空；
scopeProvider 过严；
PlaceholderOrgID 与 scope 不匹配；
keyword 归一化错误；
Trie/Hash 未正确导入。
```

---

## 18. 索引过滤指标

建议指标：

```text
iam_suggest_matched_candidates
iam_suggest_visible_after_scope
```

它们分别表示：

| 指标 | 说明 |
| ---- | ---- |
| matched_candidates | keyword 在索引中召回的候选数 |
| visible_after_scope | scope filter 后剩余候选数 |

这组指标非常重要。

例如：

```text
matched=200
visible=0
```

可能说明：

```text
scope 太窄；
用户没有可见 Profile；
OrgID 不匹配；
InternalLimit 召回的是其他组织数据；
搜索词确实无可见结果。
```

如果长期：

```text
matched=0
```

可能说明：

```text
索引未构建；
Trie key 未写入；
Hash key 未写入；
Loader 返回空；
keyword 格式不匹配。
```

---

## 19. 索引规模指标

建议指标：

```text
iam_suggest_index_terms
```

表示当前索引中的 ProfileSearchTerm 数量。

用途：

```text
启动后是否成功加载索引；
Full refresh 后索引规模是否异常下降；
Delta 删除是否过量；
数据源 SQL 是否返回异常。
```

如果突然从 10000 变成 0，需要立即排查：

```text
FullSQL；
数据库连接；
Loader 扫描；
PlaceholderOrgID；
Runtime.Replace；
刷新错误日志。
```

---

## 20. 刷新耗时指标

建议指标：

```text
iam_suggest_refresh_duration_seconds
```

维度可包含：

```text
refresh_type = full / delta
status = success / error
```

用途：

```text
观察 Full 是否越来越慢；
观察 Delta 是否异常频繁或异常慢；
发现 SQL 性能问题；
发现索引构建性能问题。
```

不要把 SQL 文本、operator、keyword 放入 label。

---

## 21. DegradedService

Suggest 支持降级服务。

当模块初始化失败且：

```text
Required=false
```

可以进入 degraded 状态。

降级行为：

```text
SuggestProfile 返回空数组。
```

它不应该：

```text
返回全局数据；
临时直接查 MySQL；
绕过 ProfileAccessScope；
返回内部错误详情给前端。
```

降级是安全优先策略。

---

## 22. 为什么降级返回空数组

Suggest 是辅助读能力。

当它不可用时，最安全行为是：

```text
查不到候选
```

而不是：

```text
查到不该看的候选
```

返回空数组的好处：

1. 不阻断 IAM 核心能力。
2. 不泄露内部错误。
3. 不绕过 scope。
4. 前端 autocomplete 可以自然处理。
5. 便于灰度和恢复。

## 23. Required 配置

`Required` 控制 Suggest 是否为 apiserver 启动必需能力。

| Required | 初始化失败行为 |
| -------- | -------------- |
| false | 进入 DegradedService，主服务继续启动 |
| true | 返回错误，阻断启动 |

建议：

```text
默认 false；
只有当业务强依赖 Suggest 时才设为 true。
```

如果设为 true，需要确保：

```text
DB 可用；
FullSQL 正确；
索引刷新耗时可接受；
生产配置经过验证；
故障告警明确。
```

---

## 24. 健康检查

Suggest 健康状态应至少关注：

```text
模块是否启用；
当前是否 degraded；
索引是否初始化；
最近一次 full refresh 是否成功；
最近一次 delta refresh 是否成功；
index terms 数量；
最近刷新错误。
```

健康检查不应该暴露：

```text
明文手机号；
完整索引内容；
profileIDs 列表；
SQL 文本中的敏感信息。
```

## 25. 常见故障：接口一直返回空数组

排查顺序：

```text
1. Suggest 是否 enabled；
2. 是否处于 degraded；
3. Runtime.Current 是否为空；
4. index_terms 是否为 0；
5. Loader.Full 是否返回数据；
6. PlaceholderOrgID 是否与 scope.OrgIDs 匹配；
7. ScopeProvider 是否返回空 scope；
8. keyword 是否进入正确策略；
9. matched_candidates 是否为 0；
10. visible_after_scope 是否为 0。
```

典型判断：

```text
matched=0 -> 索引/keyword 问题；
matched>0 visible=0 -> scope/权限范围问题；
visible>0 result=0 -> ranking/limit/DTO 问题。
```

---

## 26. 常见故障：手机号搜索无结果

排查：

```text
1. keyword 是否 LooksLikeMobile；
2. AllowMobileSearch 是否 true；
3. Hash 中是否写入该手机号；
4. 手机号是否被标准化为相同 string；
5. ProfileAccessScope 是否可见；
6. RateLimiter 是否拒绝；
7. 返回是否只是 mobile_mask 为空。
```

注意：

```text
手机号无权限时返回空是预期行为。
```

不要把它当作索引错误。

---

## 27. 常见故障：旧手机号仍能搜到

可能原因：

```text
DeltaSQL 未返回手机号变化后的 term；
DeltaSQL 未返回 tombstone；
profileKeys 未记录旧 hash key；
Hash RemoveProfileID 未生效；
Full refresh 未执行兜底。
```

排查：

```text
1. 检查 DeltaSQL 是否覆盖手机号更新；
2. 检查 Store.ImportTerms 是否先 removeOldKeys；
3. 检查 profileKeys 中是否有旧手机号 key；
4. 触发 Full refresh 验证是否恢复；
5. 检查 Snapshot 或 Loader 输出。
```

---

## 28. 常见故障：旧姓名 / 拼音仍能搜到

可能原因：

```text
Delta 没有返回姓名变更；
Trie RemoveProfileID 未执行；
profileKeys 没记录旧 Trie key；
拼音 key 生成规则变化；
Full refresh 未兜底。
```

排查同旧手机号问题。

重点看：

```text
profileKeys
Trie RemoveProfileID
Full refresh 后是否消失
```

---

## 29. 常见故障：Scope 过滤过宽

表现：

```text
用户看到不属于自己范围的 Profile。
```

排查：

```text
1. ScopeProvider 是否错误返回 AllProfile；
2. 普通用户是否被授予 TenantIDs；
3. OrgIDs 是否过宽；
4. ProfileIDs 是否缓存过期；
5. OwnerOperatorIDs 是否错误；
6. PlaceholderOrgID 是否导致所有 Profile 落入同一 org；
7. FullSQL 是否把 org_id 写错。
```

重点：

```text
TenantIDs 当前不应作为普通数据权限主路径。
```

---

## 30. 常见故障：Scope 过滤过窄

表现：

```text
用户明明应该能看到 Profile，但 suggest 返回空。
```

排查：

```text
1. ScopeProvider 是否未返回 OrgIDs / OperatorID / ProfileIDs；
2. PlaceholderOrgID 是否与请求 org 不一致；
3. owner_operator_ids 是否为空；
4. ProfileVisibilityIDsResolver 是否缓存过期；
5. Store 中 term.OrgID 是否为 0；
6. matched_candidates 是否足够大；
7. InternalMaxResults 是否过小。
```

---

## 31. 安全配置清单

生产环境建议：

```text
Enable=true
Required=false 或按业务依赖谨慎设置
DisableMobileMask=false
RateLimit enabled
MobileRateLimit stricter than StandardRateLimit
FullSyncCron enabled
DeltaSyncCron 仅在 tombstone 协议可靠后启用
PlaceholderOrgID 不作为长期权限模型
Metrics enabled
Snapshot optional
```

必须避免：

```text
DisableMobileMask=true
普通用户默认 AllProfile
普通用户默认 TenantIDs
手机号搜索不经 AllowMobileSearch
手机号搜索不经 scope filter
限流关闭且无网关保护
Delta 不完整但 Full refresh 周期很长
```

## 32. 安全不变量

1. 未认证不能调用 Suggest。
2. 没有接口级 search 权限不能调用 Suggest。
3. 手机号形态关键词必须检查 AllowMobileSearch。
4. 有手机号权限仍必须 scope filter。
5. 返回结果只能有 mobile_mask。
6. 生产不能关闭手机号脱敏。
7. 限流不能记录明文手机号。
8. 指标 label 不能包含 keyword / mobile / profile_id / operator_id。
9. DegradedService 只能返回空数组。
10. Suggest 不得绕过 ScopeProvider 返回全局索引结果。
11. TenantDomain 不得被当成 OrgID。
12. TenantIDs 不得成为普通用户默认数据权限路径。

## 34. 常见错误设计

### 34.1 手机号搜索和普通搜索共用 quota

错误。

手机号搜索应该更严格。

---

### 34.2 指标 label 放 operator_id

错误。

operator_id 高基数，且可能涉及隐私和审计边界。

应放在日志或审计事件中，不应放 Prometheus label。

---

### 34.3 降级时直接查 MySQL

错误。

这可能绕过索引层 scope filter，也可能压垮数据库。

降级应返回空数组。

---

### 34.4 Snapshot 当恢复源

错误。

当前 Snapshot 没有 reader / version / checksum，不是恢复机制。

---

### 34.5 排障时打开明文手机号

错误。

生产环境不能关闭脱敏。

应通过 request_id、指标、审计日志、Snapshot、测试环境复现排障。

## 35. 测试建议

建议覆盖：

```text
1. 手机号形态 + AllowMobileSearch=false 返回空；
2. 手机号形态 + AllowMobileSearch=true + scope 不可见返回空；
3. 手机号形态 + AllowMobileSearch=true + scope 可见返回 mobile_mask；

7. RateLimiter 拒绝时返回 429；
8. index nil 时返回空数组；
9. degraded service 返回空数组；
10. metrics 记录查询、返回数、过滤前后候选数；
11. metrics label 不包含 keyword/mobile/profileID；
12. scope 过宽/过窄场景可被测试捕获。
```

## 38. 文档总结

Suggest 的安全与运维可以归纳为三句话：

```text
手机号搜索必须更严格：额外授权、限流、脱敏、不记录明文。
索引查询必须更安全：先 scope filter，再排序返回。
模块故障必须可降级：返回空结果，不拖垮 IAM 核心能力。
```

至此，Suggest 模块的核心文档已经覆盖：

```text
00 模块总览
01 查询链路
02 权限范围
03 索引模型
04 刷新链路
05 安全与运维
```
