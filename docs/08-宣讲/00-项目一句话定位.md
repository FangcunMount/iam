# 项目一句话定位

## 本文用途

本文是 `08-宣讲` 模块的开篇，不是技术细节文档。

它的目标是帮助你在以下场景中，用一句话、三十秒、一分钟、三分钟，把 IAM 项目讲清楚：

```text
面试自我介绍
项目经历开场
技术分享开场
简历项目介绍
朋友/同事快速说明
架构答辩开场
```

本文只解决一个问题：

> **这个 IAM 项目到底是什么？**

后续文档会分别展开：

```text
业务背景
系统架构
AuthN
AuthZ
Identity
IDP
JWKS / Token 安全
Outbox
REST / gRPC / SDK
工程质量与架构护栏
```

## 1. 一句话定位

### 标准版

```text
IAM 是一个面向业务系统接入的身份与访问管理服务，统一提供登录认证、会话与 Token 管理、资源授权判定、用户与业务档案关系、第三方身份源集成，以及 REST/gRPC/SDK 接入能力。
```

这是最推荐的版本。

它覆盖了：

```text
身份
认证
授权
档案关系
第三方身份源
系统接入
```

不会把 IAM 误讲成普通用户中心。

```text
IAM 不是普通用户中心，而是一个统一处理登录、Token、授权、用户档案关系和业务系统接入的身份与访问管理服务。
```

## 3. 面试开场版

```text
我做的 IAM 项目是方寸系统里的身份与访问管理服务，不只是用户 CRUD。它把认证、授权、身份档案、第三方身份源拆成 AuthN、AuthZ、Identity、IDP 四个边界：AuthN 管登录、Session、Token、JWKS；AuthZ 管角色、资源、权限和授权判定；Identity 管 User、Profile、ProfileLink；IDP 管微信/企微应用配置和外部身份源。对外通过 REST、gRPC 和 Go SDK 给业务系统接入，并用架构测试和契约测试保护边界。
```

## 4. 30 秒版本

```text
IAM 是一个面向业务系统接入的身份与访问管理服务。它不是简单的用户中心，而是把登录认证、会话管理、Token/JWKS、资源授权、用户档案关系和第三方身份源统一起来。系统内部按 AuthN、AuthZ、Identity、IDP 拆分边界：AuthN 负责登录和 Token 生命周期；AuthZ 负责 Role、Resource、Permission、RoleBinding 和 Check；Identity 负责 User、Profile、ProfileLink；IDP 负责微信/企微应用配置和外部身份源。对外提供 REST、gRPC 和 SDK 三种接入方式。
```

这个版本适合第一次完整讲项目。

## 5. 1 分钟版本

```text
这个 IAM 项目定位是方寸系统的身份与访问管理基础服务。它解决的不是单纯“用户资料管理”，而是业务系统统一接入认证和授权的问题。

在认证侧，系统支持显式登录、Session、Access Token、Refresh Token、Token 撤销、在线 Verify、JWKS 发布和 KeyRotation；在授权侧，系统通过 Role、Resource、Permission、RoleBinding 建模权限，并通过 Casbin 做运行时判定，同时使用 PolicyVersion 和 Transactional Outbox 传播授权版本变化；在身份侧，系统把 User 和业务档案 Profile 分开，通过 ProfileLink 表达本人、父母、祖辈等关系；在第三方身份源侧，IDP 管微信/企微应用配置、SecretVault 和外部 API，真正的登录态仍由 AuthN 统一签发。

对外系统提供 REST、gRPC 和 Go SDK，让业务服务能稳定接入 IAM。为了防止项目长期演进中边界腐烂，还加入了架构测试、OpenAPI/proto 契约测试、SDK public API compile test 和文档事实源检查。
```

这个版本适合：

```text
面试项目介绍
技术分享开场
项目复盘开场
```

## 6. 3 分钟版本

```text
IAM 是方寸系统中的身份与访问管理服务。这个项目最重要的定位是：它不是普通用户中心，不只是维护 users 表，也不只是登录后发一个 JWT。它要统一解决业务系统接入时的认证、授权、身份关系和第三方身份源问题。

我把它拆成四个核心边界。

第一是 AuthN，也就是认证模块。它负责用户如何登录，以及登录态如何管理。这里不是简单查用户表发 JWT，而是包含显式登录、Session、Access Token、Refresh Token、Token 撤销、在线 Verify、JWKS 发布、KeyRotation 和 Service Token。Session 是在线登录态锚点，Access Token 是短期访问凭证，Refresh Token 是服务端可控的续期凭证。

第二是 AuthZ，也就是授权模块。它负责用户能不能访问某个资源。这里不是 user.role 字段，而是通过 Role、Resource、Permission、RoleBinding 建模，再通过 Casbin 做运行时判定。权限写入也不是简单 CRUD，而是通过 PolicyChangeCommitter 和 UoW 同时写授权 facts、递增 PolicyVersion、stage Outbox 事件，并在提交后 reload runtime policy。

第三是 Identity，也就是身份与档案关系模块。这里 User 是登录主体，Profile 是业务档案，两者不能直接合并。系统通过 ProfileLink 表达 User 和 Profile 之间的 self、parent、grandparent、other 等关系，并用 MyProfiles / MyProfileLinks 保护当前用户视角的访问边界。

第四是 IDP，也就是第三方身份源基础设施。IDP 负责微信/企微应用配置、AppSecret 加密、SecretVault、微信 access_token 和外部 API 适配，但不直接签发 IAM token。真正的登录判定、账号绑定、Session 和 Token 都由 AuthN 统一处理。

对外，IAM 提供 REST、gRPC 和 Go SDK 三种接入方式。REST 更适合 Web、移动端和管理后台，gRPC 更适合服务间调用，SDK 则把 REST/gRPC/JWKS/Verify/AuthZ Check 封装成业务服务更容易使用的接入产品层。

最后，为了保证系统长期演进不变成大泥球，我还做了架构护栏：domain 不能依赖 infra，application 不能依赖 transport，AuthZ 内部不能退回 assignment 包，Casbin facts 不能进入 domain，REST/gRPC/SDK 契约也都有对应测试保护。
```

这个版本适合：

```text
项目主讲
面试深聊前的完整铺垫
技术分享开场 3 分钟
```

## 7. 一句话里的关键词解释

标准一句话：

```text
IAM 是一个面向业务系统接入的身份与访问管理服务，统一提供登录认证、会话与 Token 管理、资源授权判定、用户与业务档案关系、第三方身份源集成，以及 REST/gRPC/SDK 接入能力。
```

逐词拆解：

| 关键词 | 解释 |
|---|---|
| `面向业务系统接入` | 它不是只给自己用的 user-service，而是让 QS、后端服务、管理后台等系统接入 |
| `身份与访问管理服务` | 对应 IAM：Identity and Access Management |
| `登录认证` | AuthN，负责用户如何证明自己是谁 |
| `会话与 Token 管理` | Session、Access Token、Refresh Token、Verify、Revoke、JWKS |
| `资源授权判定` | AuthZ，回答 subject 能不能访问 resource/action/scope |
| `用户与业务档案关系` | User、Profile、ProfileLink，不只是用户资料 |
| `第三方身份源集成` | IDP，微信/企微应用配置、SecretVault、外部 API |
| `REST/gRPC/SDK 接入` | 作为基础服务对外提供稳定契约和客户端封装 |

## 8. 不推荐的定位说法

### 8.1 不要说成“用户中心”

```text
这是一个用户中心项目。
```

问题：

```text
太窄。
```

它会让面试官以为只是：

```text
用户表 CRUD
登录注册
资料管理
```

但 IAM 当前明显包含 AuthN、AuthZ、Identity、IDP、SDK、Outbox 和架构护栏。

---

### 8.2 不要说成“登录系统”

```text
这是一个登录认证系统。
```

问题：

```text
只讲了 AuthN，漏掉 AuthZ、Identity、IDP 和接入契约。
```

如果这样讲，后面再说 Role、Permission、ProfileLink、SDK，会显得主题散。

---

### 8.3 不要说成“权限系统”

```text
这是一个权限系统。
```

问题：

```text
只讲了 AuthZ，漏掉登录态和身份源。
```

IAM 不是单独的 RBAC 服务，它还包括认证、会话、Token、用户档案关系和第三方登录。

---

### 8.4 不要说成“JWT 系统”

```text
这是一个 JWT 登录系统。
```

问题：

```text
严重低估。
```

JWT 只是 Access Token 的实现方式之一。IAM 的核心是：

```text
Session + Token + JWKS + Verify + AuthZ + Identity + IDP + SDK
```

---

### 8.5 不要说成“微信登录系统”

```text
这是一个微信登录系统。
```

问题：

```text
把 IDP 特例当成系统整体。
```

微信/企微只是第三方身份源之一。系统真正抽象是 IAM。

## 10. 项目价值主张

对外讲项目时，不要只讲“我实现了哪些接口”。  
要讲它解决了什么系统问题。

### 10.1 统一认证

```text
把密码、手机 OTP、微信、企微、Service Token 等登录方式统一到 AuthN 登录态模型。
```

价值：

```text
所有登录方式最终都走同一套 Session、Token、Verify、Refresh、Revoke。
```

---

### 10.2 统一授权

```text
把角色、资源、权限、角色绑定统一建模，通过 AuthZ Check 给业务服务提供资源访问判定。
```

价值：

```text
业务系统不需要各自实现一套权限系统。
```

---

### 10.3 统一身份关系

```text
把登录主体 User 和业务档案 Profile 分开，通过 ProfileLink 表达本人、父母、祖辈等关系。
```

价值：

```text
支持儿童档案、家庭协作、当前用户档案访问 guard。
```

---

### 10.4 统一第三方身份源

```text
IDP 只负责微信/企微应用配置、密钥和外部 API，登录态由 AuthN 统一管理。
```

价值：

```text
避免微信登录、企微登录、密码登录各自签发一套 token。
```

---

### 10.5 统一接入

```text
通过 REST、gRPC、SDK 让不同调用方按场景接入。
```

价值：

```text
Web/移动端走 REST，后端服务走 gRPC，Go 服务通过 SDK 降低接入成本。
```

---

### 10.6 统一治理

```text
通过架构测试、契约测试、docs-hygiene 和 public API compile test 防止系统长期演进后边界漂移。
```

价值：

```text
项目不是只做出来，还要能长期维护。
```

## 11. 与普通用户中心的区别

| 维度 | 普通用户中心 | IAM |
|---|---|---|
| 核心对象 | User | Identity + Access |
| 登录 | 简单账号密码 | 多认证方式 + Session + Token |
| Token | 通常只发 JWT | Access Token + Refresh Token + Verify + Revoke + JWKS |
| 授权 | user.role 或简单角色表 | Role / Resource / Permission / RoleBinding / Scope / Check |
| 用户资料 | User profile 字段 | User 与 Profile 分离 |
| 档案关系 | 通常没有 | ProfileLink |
| 第三方登录 | 写进登录逻辑 | IDP 基础设施 + AuthN 统一登录 |
| 接入方式 | HTTP API | REST + gRPC + SDK |
| 策略传播 | 通常没有 | PolicyVersion + Transactional Outbox |
| 架构护栏 | 通常靠约定 | architecture tests + contract tests |

一句话总结区别：

```text
用户中心管理用户资料；IAM 管理身份、认证、授权、会话、凭证、身份源、档案关系和系统接入。
```

## 12. 与单独认证服务的区别

| 维度 | AuthN-only 服务 | IAM |
|---|---|---|
| 登录 | 有 | 有 |
| Session | 有或没有 | 有 |
| Token | 有 | 有 |
| JWKS | 可能有 | 有 |
| AuthZ Check | 没有或很弱 | 有 |
| Role/Permission | 不负责 | 负责 |
| User/ProfileLink | 不负责 | 负责 |
| IDP 管理 | 可能内嵌 | 独立边界 |
| SDK 接入 | 不一定 | 有 |

所以不能把 IAM 讲成 AuthN-only。

## 15. 推荐回答模板

### 15.1 面试官问：“这个项目是做什么的？”

```text
这是一个 IAM 身份与访问管理服务，不是普通用户中心。它统一处理业务系统接入时的登录认证、Token 和 Session 管理、资源授权判定、用户与业务档案关系、第三方身份源，以及 REST/gRPC/SDK 接入。内部拆成 AuthN、AuthZ、Identity、IDP 四个边界，分别处理认证态、访问权、身份档案关系和外部身份源。
```

---

### 15.2 面试官问：“你负责了哪些部分？”

```text
我主要围绕 IAM 的核心认证授权链路和架构文档体系做设计与实现：一是 AuthN 登录链路，包括 Session、Access Token、Refresh Token、JWKS 和在线 Verify；二是 AuthZ 授权模型，包括 Role、Resource、Permission、RoleBinding、Check、PolicyVersion 和 Outbox；三是 Identity 里的 User、Profile、ProfileLink 模型；四是 REST/gRPC/SDK 接入契约和架构护栏。
```

如果你实际代码贡献有不同，可以按真实情况调整。

---

### 15.3 面试官问：“这个项目的难点是什么？”

```text
难点不在于写几个 CRUD 接口，而在于边界拆分和一致性治理。比如 AuthN 不能只发 JWT，还要处理 Session、Refresh、Revoke、JWKS 和在线 Verify；AuthZ 写入不是简单 insert/delete，而是要同时写授权 facts、递增 PolicyVersion、stage Outbox 事件，并在提交后 reload runtime policy；Identity 里 User 和 Profile 不能合并，要通过 ProfileLink 表达关系；另外 REST/gRPC/SDK 三种接入方式还要和源码事实保持一致。
```

---

### 15.4 面试官问：“这个项目有什么亮点？”

```text
亮点有三个。第一，模型边界清晰，把 AuthN、AuthZ、Identity、IDP 拆开，避免大 UserService。第二，关键链路有工程治理，比如 AuthZ 写入使用 UoW + PolicyVersion + Transactional Outbox，Token 使用 Session + Refresh + JWKS + 在线 Verify。第三，项目有可维护性护栏，包含架构测试、OpenAPI/proto 契约测试、SDK public API compile test 和文档事实源检查，防止长期演进中边界漂移。
```

---

### 15.5 面试官问：“它和普通用户系统区别在哪？”

```text
普通用户系统核心是 User CRUD 和简单登录。IAM 的核心是身份与访问管理：AuthN 负责认证态，AuthZ 负责访问权，Identity 负责 User/Profile/ProfileLink，IDP 负责外部身份源，接入层通过 REST/gRPC/SDK 给业务服务使用。普通用户系统通常不会处理 Session/Refresh/JWKS、资源级授权判定、授权版本传播、ProfileLink 关系和 SDK 接入这些问题。
```
