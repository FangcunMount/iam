# 业务背景与问题

## 本文用途

本文是 `08-宣讲` 模块的第二篇。

上一篇《00-项目一句话定位.md》回答：

```text
IAM 是什么？
```

本文回答：

```text
为什么需要 IAM？
它解决了什么业务问题？
如果没有 IAM，业务系统会遇到哪些具体痛点？
```

这篇不是技术实现说明，而是对外讲项目时的“背景铺垫”。  
它要帮助你在面试或技术分享中，从业务问题自然过渡到系统设计。

---

## 1. 一句话背景

```text
随着方寸业务系统出现 Web、App、微信、内部服务等多种接入方，认证、授权、用户档案关系和第三方身份源不能继续散落在各个业务系统里，因此需要一个统一的 IAM 服务来管理身份、登录态、访问权限和接入契约。
```

更短版本：

```text
当业务系统从单一应用演进到多入口、多服务、多身份源时，就需要 IAM 统一处理认证、授权、身份关系和系统接入。
```

---

## 2. 业务背景

IAM 所处的背景不是一个单体后台里的“用户管理页面”，而是一个逐步平台化的业务系统环境。

外部会有多类调用方：

```text
Web
App
微信小程序
第三方服务
内部后端服务
管理后台
worker / batch job
```

这些调用方会共同面对几类问题：

```text
用户如何登录？
登录态如何验证？
token 如何刷新和撤销？
用户是否被禁用？
某个用户有没有访问某个资源的权限？
用户和儿童档案/业务档案是什么关系？
微信/企微身份如何接入？
业务服务如何稳定调用认证授权能力？
```

如果每个业务系统自己解决，就会产生重复实现和边界混乱。

所以 IAM 的建设背景可以概括为：

> **业务系统需要一个统一的身份与访问管理基础服务，而不是让每个业务模块各自实现登录、权限、档案关系和第三方登录。**

---

## 3. 业务系统没有 IAM 时会怎样

如果没有 IAM，常见做法是：

```text
每个业务系统自己维护 user 表
每个业务系统自己做登录
每个业务系统自己签 JWT
每个业务系统自己判断权限
每个业务系统自己接微信/企微
每个业务系统自己维护用户和档案关系
```

短期看，开发很快。

长期会出现六类问题。

---

## 4. 问题一：认证能力分散

### 4.1 典型现象

业务系统自己写登录逻辑：

```text
用户名密码登录
手机号验证码登录
微信小程序登录
企业微信登录
后台运营账号登录
服务间 token
```

如果这些逻辑分散在不同服务里，就会出现：

```text
登录方式实现不一致
密码策略不一致
token claims 不一致
refresh 机制不一致
logout 语义不一致
用户禁用后旧 token 是否可用不确定
```

### 4.2 业务风险

认证分散会带来直接风险：

```text
用户在 A 系统已被禁用，但 B 系统旧 token 仍然可用
一个服务支持 refresh token，另一个服务不支持
微信登录和密码登录产生两套 user identity
不同服务对 token 过期、撤销、刷新理解不同
```

### 4.3 IAM 的解决方式

IAM 把认证统一到 AuthN：

```text
Login
Session
Access Token
Refresh Token
Verify
Revoke
JWKS
KeyRotation
ServiceToken
```

这样所有登录方式最终统一成：

```text
Principal
  -> Session
  -> Access Token
  -> Refresh Token
```

对外统一通过 REST/gRPC/SDK 接入。

---

## 5. 问题二：授权能力分散

### 5.1 典型现象

业务系统自己写权限判断：

```text
if user.role == "admin"
if userID == ownerID
if tenantID == xxx
if profile.UserID == currentUserID
```

一开始没问题。  
但业务增长后，会出现：

```text
角色越来越多
资源越来越多
权限判断散落在 handler/usecase 中
权限逻辑无法复用
权限变更无法审计
跨服务权限不一致
```

### 5.2 业务风险

授权分散会导致：

```text
同一个角色在不同服务含义不同
新增一个资源要改多个系统
某个权限撤销后部分服务仍然允许访问
管理员不知道用户到底有哪些权限
业务服务无法判断本地缓存是否过期
```

### 5.3 IAM 的解决方式

IAM 把授权统一到 AuthZ：

```text
Role
Resource
Permission
RoleBinding
Scope
Check
AuthorizationSnapshot
PolicyVersion
Transactional Outbox
```

业务服务不需要自己解释权限规则，而是调用：

```text
AuthZ Check
```

或者拉取：

```text
AuthorizationSnapshot
```

授权变更通过：

```text
PolicyVersion + Outbox event
```

传播给下游。

---

## 6. 问题三：用户与业务档案关系复杂

### 6.1 典型现象

在普通用户系统中，常见设计是：

```text
User.profile_id
Profile.user_id
```

但方寸业务中存在业务档案关系，例如：

```text
用户本人档案
儿童档案
父母与儿童档案关系
祖辈与儿童档案关系
其他监护/协作关系
```

这不是一个简单字段能表达的。

### 6.2 业务风险

如果把档案关系塞进 User 字段，会遇到：

```text
一个用户无法关联多个档案
一个儿童档案无法被多个用户关联
无法区分 self / parent / grandparent / other
无法撤销关系并保留历史
无法保护当前用户只能访问自己的关联档案
```

### 6.3 IAM 的解决方式

IAM 把身份关系放在 Identity 模块：

```text
User
Profile
ProfileLink
```

其中：

```text
User = 登录主体
Profile = 业务档案
ProfileLink = User 与 Profile 的关系事实
```

这样可以表达：

```text
self
parent
grandparent
other
active / revoked
```

并通过 MyProfiles / MyProfileLinks 保护当前用户访问边界。

---

## 7. 问题四：第三方身份源容易污染登录逻辑

### 7.1 典型现象

如果业务系统自己接微信/企微，常见写法是：

```text
LoginService 里直接写 code2Session
LoginService 里直接保存 AppSecret
LoginService 里直接刷新微信 access_token
LoginService 里直接创建用户并签 token
```

短期方便，长期会把登录逻辑、外部平台配置、secret 管理、token 签发全部混在一起。

### 7.2 业务风险

会出现：

```text
AppSecret 散落在多个服务
微信 access_token 和 IAM access token 混淆
微信登录和密码登录签发不同 token
企微和小程序逻辑无法复用
IDP 配置无法独立管理和审计
```

### 7.3 IAM 的解决方式

IAM 拆出 IDP 模块：

```text
WechatApp
SecretVault
微信 access_token
微信/企微 API 适配
```

但真正登录态仍由 AuthN 统一处理：

```text
IDP 只提供外部身份源基础设施
AuthN 统一完成账号绑定、Principal、Session、Token
```

这样能保证：

```text
所有登录方式最终走同一套 Session/Token/Verify/Revoke
```

---

## 8. 问题五：服务间接入缺少统一契约

### 8.1 典型现象

业务服务接入认证授权时，如果没有统一契约，可能会：

```text
直接读 IAM 数据库
复制 JWT 公钥配置
手写 HTTP client
手写 gRPC client
各自实现 token verify
各自处理错误码
各自写权限缓存
```

### 8.2 业务风险

这样会导致：

```text
接入方式不一致
错误处理不一致
token 校验策略不一致
服务间鉴权不一致
后续 IAM API 变更影响范围不可控
```

### 8.3 IAM 的解决方式

IAM 提供三层接入：

```text
REST
gRPC
Go SDK
```

推荐分工：

| 接入方式 | 适合场景 |
|---|---|
| REST | Web、App、管理后台、登录 |
| gRPC | 后端服务间调用、AuthZ Check、Identity 查询 |
| SDK | Go 业务服务接入 IAM 的标准客户端封装 |

这样业务系统不需要自己散落实现：

```text
JWT verify
AuthZ Check
JWKS 拉取
ServiceToken
ProfileLink query
IDP internal call
```

---

## 9. 问题六：权限变更无法可靠传播

### 9.1 典型现象

授权系统里常见操作：

```text
给用户绑定角色
撤销用户角色
给角色授予权限
撤销角色权限
```

如果只是改数据库，其他服务可能不知道。

如果直接发 MQ，又会遇到：

```text
DB 成功，MQ 失败
MQ 成功，DB 回滚
进程在 DB commit 后 publish 前崩溃
```

### 9.2 业务风险

授权缓存会不一致：

```text
IAM 数据库已经变了
当前实例 runtime policy 可能没刷新
其他业务系统本地缓存仍然是旧权限
用户权限被撤销后仍然能访问
```

### 9.3 IAM 的解决方式

IAM 在 AuthZ 写入中引入：

```text
PolicyVersion
Transactional Outbox
RuntimePolicyReload
```

一次授权变更会：

```text
写授权 facts
递增 PolicyVersion
同事务 stage version_changed event
提交后 reload 当前 runtime policy
后台 relay 可靠发布 outbox event
```

这样下游可以按：

```text
tenant_id + version
```

判断缓存是否过期。

---

## 10. 问题七：长期演进中边界容易腐烂

### 10.1 典型现象

系统复杂后，最常见的问题不是“没有功能”，而是：

```text
domain 开始 import infra
application 开始 import transport
REST router 开始直接读 container
AuthZ domain 里出现 Casbin p/g/r
IDP 开始直接签 IAM token
SDK 开始复制权限规则
文档继续引用旧路由和旧目录
```

### 10.2 业务风险

这些问题短期不会马上爆炸，但会让系统逐步变成大泥球：

```text
模块边界消失
测试困难
文档不可信
接口漂移
面试讲不清楚
后续重构成本越来越高
```

### 10.3 IAM 的解决方式

IAM 引入架构和契约护栏：

```text
architecture tests
REST router matrix test
gRPC proto contract test
SDK public API compile test
docs-hygiene
```

这说明项目不是只关注“功能能跑”，也关注：

```text
系统能不能长期维护
```

## 11. 业务问题总览

| 业务问题 | 如果没有 IAM | IAM 的解决方式 |
|---|---|---|
| 多登录方式 | 各系统各写一套登录 | AuthN 统一登录、Session、Token |
| token 生命周期 | JWT 策略分散 | Access/Refresh/Verify/Revoke/JWKS |
| 资源权限 | user.role 散落判断 | AuthZ Check / Snapshot |
| 权限传播 | 缓存失效不可控 | PolicyVersion + Outbox |
| 用户档案关系 | User 字段无法表达 | User/Profile/ProfileLink |
| 第三方身份源 | 微信/企微逻辑污染登录 | IDP 基础设施 + AuthN 统一登录 |
| 服务间接入 | 各自手写 client | REST/gRPC/SDK |
| 架构演进 | 边界靠约定 | architecture/contract/docs guard |

## 12. 业务价值表达

对外讲项目时，建议用“价值”而不是“功能堆叠”。

### 12.1 对业务系统

```text
业务系统不用重复实现登录、权限和身份关系，统一接入 IAM 即可。
```

### 12.2 对用户

```text
用户可以通过统一登录态访问不同业务能力，账号状态、会话状态和权限变化能被统一控制。
```

### 12.3 对管理员

```text
管理员可以统一管理角色、资源、权限、用户状态、第三方身份源和档案关系。
```

### 12.4 对后端服务

```text
后端服务可以通过 REST/gRPC/SDK 统一 Verify Token、Check Permission、查询用户和档案关系。
```

### 12.5 对系统长期演进

```text
系统通过架构测试、契约测试和文档事实源机制，降低长期演进中的边界漂移风险。
```

## 13. 宣讲时的业务背景开场

### 13.1 30 秒开场

```text
这个项目的背景是：方寸业务系统不再只是一个单体应用，它会有 Web、App、微信、内部后端服务等多个入口。只要系统出现多入口、多登录方式、多服务调用，就不能让每个业务系统各自实现登录、JWT、权限和用户档案关系，否则认证授权逻辑会分散，权限变化无法统一传播，第三方登录也会污染业务代码。所以我设计了 IAM 服务，统一处理认证、授权、身份关系、第三方身份源和业务系统接入。
```

### 13.2 1 分钟开场

```text
IAM 的业务背景可以理解为：当业务系统从单一应用演进到多个入口和多个后端服务时，认证授权会变成基础能力，而不是某个业务模块的附属功能。

如果没有统一 IAM，每个系统都会自己做用户登录、JWT 签发、权限判断、微信登录、用户和档案关系维护。短期开发快，但长期会出现 token 语义不一致、用户禁用后旧 token 仍可用、权限变更无法同步、档案关系无法表达、第三方 AppSecret 散落等问题。

所以 IAM 的目标是把这些能力统一起来：AuthN 管登录态和 token，AuthZ 管资源访问判定，Identity 管 User/Profile/ProfileLink，IDP 管微信/企微身份源，REST/gRPC/SDK 负责让业务系统稳定接入。
```

## 14. 面试常见问题回答

### Q1：为什么需要单独做 IAM？业务系统自己做登录不行吗？

```text
如果只是一个小系统，自己做登录可以。但当业务系统开始有多个客户端、多个后端服务、第三方登录和资源级权限时，登录和权限就变成基础能力。每个系统自己做，会导致 token、session、权限、用户状态和第三方身份源逻辑分散。IAM 的价值是把这些能力统一起来，让业务系统通过 REST/gRPC/SDK 接入。
```

---

### Q2：这个项目的业务痛点是什么？

```text
核心痛点是认证授权分散。具体包括多种登录方式难统一、token 刷新和撤销难统一、用户禁用后旧 token 是否生效不一致、资源权限判断散落在业务代码里、用户和儿童档案关系无法用简单 User 字段表达、微信/企微 AppSecret 和登录逻辑混在一起，以及业务服务之间缺少统一接入契约。
```

---

### Q3：为什么不直接用现成的 Keycloak？

可以回答得诚实一点：

```text
Keycloak 这类成熟产品很强，但我这个项目的目标不是简单部署一个现成 IAM，而是结合方寸业务系统，把认证、授权、用户档案关系、微信/企微身份源和 Go 服务端 SDK 接入做成可理解、可裁剪、可演进的内部基础服务。这个项目也承载了我对 AuthN/AuthZ/Identity/IDP 分层、Session/Token/JWKS、PolicyVersion/Outbox、ProfileLink 等工程问题的设计实践。
```

注意：不要贬低 Keycloak。  
成熟产品有成熟产品的价值。你讲的是“为什么自己做这个项目”。

---

### Q4：这个项目最核心的业务价值是什么？

```text
最核心的价值是把认证、授权和身份关系从业务系统里抽出来，变成统一基础服务。业务系统不需要自己维护登录态、权限模型和第三方身份源，只需要通过 REST/gRPC/SDK 接入 IAM，就能完成 token 校验、权限判定、用户与档案关系查询。
```

---

### Q5：业务背景和技术亮点怎么衔接？

可以这样衔接：

```text
业务背景是认证授权分散，所以技术上我首先拆了 AuthN、AuthZ、Identity、IDP 四个边界。认证侧用 Session + Access Token + Refresh Token + JWKS 解决登录态和 token 生命周期；授权侧用 Role/Resource/Permission/RoleBinding + Casbin + PolicyVersion + Outbox 解决资源级授权和版本传播；身份侧用 ProfileLink 解决用户和业务档案关系；接入侧用 REST/gRPC/SDK 解决业务系统接入。
```

## 16. 业务背景到技术设计的过渡句

你可以背这一段：

```text
因为问题不是单纯“能不能登录”，而是多系统下认证、授权、身份关系和第三方身份源如何统一，所以我没有把它做成一个 UserService，而是拆成 AuthN、AuthZ、Identity、IDP 四个边界。AuthN 解决登录态，AuthZ 解决访问权，Identity 解决用户和业务档案关系，IDP 解决外部身份源接入。再通过 REST、gRPC、SDK 提供给业务系统使用。
```

这个过渡句非常关键。  
它能自然引出后面所有技术设计。

## 18. 本文总结

IAM 的业务背景不是：

```text
我要做一个用户登录系统
```

而是：

```text
业务系统出现多入口、多服务、多登录方式、多权限场景后，需要一个统一的身份与访问管理基础服务。
```

没有 IAM，问题会分散在业务代码中：

```text
认证分散
授权分散
Token 语义分散
第三方身份源分散
用户档案关系分散
服务接入方式分散
权限版本传播不可控
架构边界长期腐烂
```

IAM 的价值是把这些问题收敛到统一边界中：

```text
AuthN：登录态和 Token
AuthZ：资源访问判定
Identity：User/Profile/ProfileLink
IDP：第三方身份源
Access：REST/gRPC/SDK
Guard：架构与契约护栏
```

面试或宣讲时，先讲业务背景，再讲技术设计。  
不要一上来堆 JWT、Casbin、Redis、Outbox。  
真正好的讲法是：

```text
业务复杂度为什么出现
如果不抽象会怎样
IAM 如何把问题拆成边界
每个边界如何解决问题
```
