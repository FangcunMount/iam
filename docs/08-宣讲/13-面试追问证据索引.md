# 面试追问证据索引

## 本文用途

本文是 `08-宣讲` 模块的最后一篇，用于面试前准备和面试中快速回链证据。

它不是正文讲稿，而是一个 **追问作战地图**。

它回答：

```text
面试官可能怎么追问？
每个问题应该怎么答？
回答时应该回链哪些源码、契约、测试或文档？
哪些问题容易答偏？
如果继续深挖，应该往哪里展开？
```

使用方式：

```text
1. 面试前按模块扫一遍；
2. 每个问题先记 30 秒回答；
3. 再记 2-3 个证据路径；
4. 最后准备一个可继续展开的技术点。
```

不要死背全文。  
核心是训练：

```text
问题 -> 回答 -> 证据 -> 追问展开
```

## 1. 追问准备总原则

### 1.1 先答结论，再讲链路

不要一上来解释所有细节。  
推荐结构：

```text
结论
  -> 为什么
  -> 怎么做
  -> 证据在哪里
  -> 代价和边界
```

示例：

```text
为什么 AuthZ 写入不是 CRUD？

结论：因为授权写入改变的是运行时授权事实，而不是单表记录。
为什么：它影响管理记录、Casbin facts、PolicyVersion、Outbox 和 runtime reload。
怎么做：通过 PolicyChangeCommitter 在 UoW 里统一提交。
证据：application/authz/policy/committer.go。
边界：reload 在事务后，是 best-effort，不回滚 DB facts。
```

---

### 1.2 不要只说“我用了某技术”

错误：

```text
我用了 JWT。
我用了 Casbin。
我用了 Outbox。
我用了 gRPC。
```

正确：

```text
JWT 只是 Access Token 实现，完整登录态由 Session + RefreshToken + Verify 管。
Casbin 是 runtime policy engine，领域模型仍是 Role/Resource/Permission/RoleBinding。
Outbox 解决 DB facts 和事件传播的一致性。
gRPC 面向可信服务间调用，REST 和 SDK 有各自场景。
```

---

### 1.3 所有亮点都要能回链事实

每个亮点至少能回链一种证据：

```text
源码路径
OpenAPI
proto
SDK public API
测试
文档事实层
```

没有证据的亮点，不要主动讲。

---

### 1.4 遇到不会的问题，承认边界

推荐说法：

```text
这个点当前项目里还没有完整实现，我当前的设计倾向是……
```

不要硬编。

例如：

```text
复杂 ABAC / OPA 当前不是第一阶段重点，当前采用 RBAC + Scope，后续如业务需要再演进。
```

# B. 业务背景类追问

## B1. 为什么业务系统需要 IAM？

### 30 秒回答

```text
当业务系统出现 Web、App、微信、管理后台、内部服务等多种入口时，认证、授权、第三方登录和档案关系就不能继续散落在各个业务模块中。否则会出现 token 语义不一致、权限判断分散、用户禁用后旧 token 仍可用、微信 AppSecret 分散、档案关系无法统一表达等问题。IAM 把这些能力统一成基础服务。
```

### 证据链

```text
docs/08-宣讲/01-业务背景与问题.md
README.md
```

### 可展开

```text
认证分散
授权分散
Profile 关系复杂
第三方身份源污染登录逻辑
服务间接入重复
授权版本传播不可控
```

---

## B2. 项目最大的业务痛点是什么？

### 30 秒回答

```text
最大的痛点是认证授权和身份关系分散。没有 IAM 时，每个业务系统会自己做登录、JWT、权限判断、微信登录和用户档案关系维护。短期快，长期会导致安全语义不一致、权限变更难同步、档案关系难表达、接入方式重复和边界腐烂。
```

# D. AuthN 认证类追问

## D1. 登录流程怎么设计？

### 30 秒回答

```text
登录不是直接查用户发 JWT，而是先根据 auth_method 选择 SignInAdapter，把不同 payload 转成领域 proof，再交给 Authenticator 认证。认证成功后得到 Principal，TokenIssuer 先创建 Session，再签发 Access Token，并保存 Refresh Token。这样后续 Verify、Refresh、Revoke 都围绕同一个 Session 做状态控制。
```

## D2. 为什么不只用 JWT？

### 30 秒回答

```text
JWT 只能证明 token 是 IAM 签发且未过期，不能证明登录态当前仍然有效。比如用户登出、被 block、账号 disabled，旧 JWT 在过期前本地验签仍可能通过。所以 IAM 用 Session 做在线登录态锚点，在线 Verify 会检查 revoked marker、Session active 和 User/Account 状态。
```

## D3. Access Token 和 Refresh Token 怎么分工？

### 30 秒回答

```text
Access Token 是短期访问凭证，适合请求携带和 JWKS 本地验签；Refresh Token 是长期续期凭证，但必须服务端保存、可撤销、可轮换，并且绑定 Session。Refresh 时要检查 refresh token、Session 和 User/Account 状态，成功后轮换旧 refresh token。
```

## D4. JWKS 和在线 Verify 有什么区别？

### 30 秒回答

```text
JWKS 是公钥分发机制，用于本地验证 JWT 签名、kid、exp、issuer、audience；在线 Verify 是状态判定，会在验签之外检查 token 是否撤销、Session 是否 active、User/Account 是否仍可用。所以 JWKS 证明签名可信，在线 Verify 证明当前可用。
```

## D5. KeyRotation 怎么做？

### 30 秒回答

```text
JWT header 中带 kid，验签时根据 kid 找 verification key。Key 有 active、grace、retired 三种状态：active 用于签新 token 并发布到 JWKS，grace 不签新 token 但继续发布用于验旧 token，retired 不再发布。这样可以平滑轮换签名密钥。
```

```text

```

# F. Outbox 与授权版本传播类追问

## F1. 为什么需要 PolicyVersion？

### 30 秒回答

```text
PolicyVersion 表示某个 tenant 的授权事实版本。每次授权 facts 改变后 version 递增。业务服务或 SDK 可以用 authz_version 判断本地授权快照是否过期，避免一直使用旧权限缓存。
```

## F2. 为什么需要 Transactional Outbox？

### 30 秒回答

```text
因为授权变更既要写 DB facts，又要通知其他系统。如果直接 DB commit 后 publish MQ，会有 DB 成功但 MQ 失败的窗口，通知可能丢失。Transactional Outbox 把 facts、PolicyVersion 和 outbox row 放在同一个数据库事务里提交，之后由 relay 异步投递，保证事件不丢。
```

```text

```

## F3. Outbox 是 exactly-once 吗？

### 30 秒回答

```text
不是，是 at-least-once。比如 publish 成功但 mark published 失败，或者 relay 在 publish 后崩溃，事件可能重复投递。所以消费者必须按 event_id 或 tenant_id + version 做幂等。
```

# G. Identity / ProfileLink 类追问

## G1. User 和 Profile 为什么分开？

## G2. ProfileLink 为什么不能只是 user.profile_id？

## H2. 为什么 IDP 不直接签发 IAM token？

## K2. 项目中最复杂的设计点是什么？

### 推荐回答方向一：AuthZ 写入

```text
最复杂的是 AuthZ 写入，因为它不是单表 CRUD。一次授权变更会影响管理记录、Casbin facts、PolicyVersion、Outbox event 和 runtime reload。这里需要 UoW 保证 DB facts、version 和 event 同事务提交，同时 runtime reload 和 outbox relay 又是事务后的异步动作。
```

### 推荐回答方向二：AuthN 登录态

```text
另一个复杂点是 AuthN 登录态，不能只靠 JWT。需要区分 Session、Access Token、Refresh Token、JWKS 和在线 Verify，才能同时支持性能、撤销、续期和安全状态一致性。
```

## K3. 项目中最能体现 DDD/领域建模的点是什么？

### 30 秒回答

# L. 面试前最后背诵版

## L1. 项目定位

```text
IAM 是一个面向业务系统接入的身份与访问管理服务，不是普通用户中心。它统一处理登录认证、Session/Token、资源授权、用户档案关系、第三方身份源和 REST/gRPC/SDK 接入。
```

## L2. 架构

```text
整体采用分层 + 六边形架构：Transport 做协议适配，Application 编排用例和事务，Domain 承载业务规则，Infra 适配 MySQL、Redis、Casbin、JWT、Outbox 和微信 API，process 管生命周期，container 管组合装配。
```

## L3. AuthN

```text
AuthN 不是简单发 JWT，而是 SignInAdapter -> Authenticator -> Principal -> Session -> Access Token -> Refresh Token。JWKS 做本地验签，在线 Verify 检查 revoked marker、Session 和 User/Account 状态。
```

## L4. AuthZ

```text
AuthZ 不是 user.role，而是 Role、Resource、Permission、RoleBinding。Check 输入 subject、tenant、resource、action、scope。写入通过 PolicyChangeCommitter/UoW 写 facts、递增 version、stage outbox，并 reload runtime policy。
```

## L5. Identity

```text
User 是登录主体，Profile 是业务档案，ProfileLink 是关系事实。ProfileLink 支持 self/parent/grandparent/other 和 active/revoked，用于当前用户档案访问 guard，但不是 AuthZ permission。
```

## L6. IDP

```text
IDP 只做第三方身份源基础设施，管理微信/企微应用、SecretVault 和微信 access_token；真正登录态、账号绑定、Session 和 IAM token 由 AuthN 统一处理。
```

## L7. 接入

```text
REST 面向 Web/App/Admin，gRPC 面向可信服务间调用，SDK 面向 Go 业务服务低成本接入。SDK 是接入产品层，不是业务层。
```

## L8. 工程质量

```text
工程质量靠多层护栏：architecture tests 保护依赖边界，REST/gRPC contract tests 保护机器契约，SDK compile test 保护公开面，docs-hygiene 保护文档事实源。
```
