# IAM 文档维护约定

> 状态：已实现 · 与当前文档目录、事实门禁和 CI 维护规则核对。

本文只保留长期有效的写作和验证规则。文档迁移过程、阶段计划和一次性盘点结果不放在这里。

## 1. 基本原则

IAM 文档负责解释和导航，不替代机器事实。

当信息冲突时，按以下顺序核对：

1. 源码与实际运行行为；
2. OpenAPI、proto、配置、迁移等机器可读事实；
3. 模块测试、契约测试和架构测试；
4. 当前 `docs/`；
5. `_archive/` 历史材料。

不要用“合理推测”填补代码中不存在的类型、目录、接口、协议或运行能力。

## 2. 文档分区

| 目录 | 职责 |
| --- | --- |
| `00-概览/` | 项目定位、模块关系、术语和阅读路径 |
| `01-运行时/` | 启动、装配、传输层、配置和后台任务 |
| `02-业务模块/` | Identity、AuthN、AuthZ、IDP、Suggest 的业务事实和边界 |
| `03-接入与契约/` | REST、gRPC、Go SDK 和接入约束 |
| `04-架构护栏/` | 分层、契约、SDK、文档的可执行检查 |
| `05-专题设计/` | 跨模块机制和设计取舍 |
| `06-宣讲/` | 从事实层派生的评审、分享和讲解材料 |
| `_archive/` | 已退出当前体系的历史材料，不是当前事实源 |

每个目录必须有 `README.md` 作为入口。新文档应从所属入口可达，不创建孤立文件。

## 3. 文档状态

每篇现行文档在标题后标明一个状态：

| 状态 | 使用条件 |
| --- | --- |
| `已实现` | 主要结论已经由当前代码、契约或测试核对 |
| `规划改造` | 描述目标设计、待实现能力或尚未收敛的方案 |

规则：

- 代码中不存在的能力必须标为 `规划改造`，并明确写出当前状态。
- `设计目标` 只允许存在于开发草稿或 `_archive/`，不得作为主分支 active docs 的文首状态。
- 文档同时包含现状和方案时，使用“当前实现”和“规划改造”两个小节隔离。
- “若已实现”“若已存在”“具体以代码为准”不能代替实际核对。
- 文档标题或概念名与 Go 类型不同，要明确说明它是通用概念还是现行符号。

### 3.1 正文内容标记

文首状态表示整篇文档的成熟度，不能代替正文中的内容分层。模块设计文档同时包含实现事实、设计理由和未来方案时，使用下列小节名称或显式标记：

| 标记 | 用途 |
| --- | --- |
| `当前实现` | 代码、契约、配置或数据库今天真实执行的行为 |
| `设计决策` | 已经明确采用的模型、边界、事务或协作选择 |
| `已知缺口` | 当前实现没有完全满足设计目标，或契约与代码尚未对齐 |
| `规划改造` | 已提出但尚未实现的目标方案 |
| `待确认决策` | 理由可以从代码或历史材料推导，但缺少明确团队决策证据 |

规则：

- 代码事实可以由当前源码、契约和测试证明；设计意图不能只根据代码反向编造。
- 旧文档、提交历史或评审记录可以证明历史决策，但进入现行正文前仍需核对当前实现是否延续该决策。
- 无法确认“为什么这样设计”时，写成 `待确认决策`，不要用合理化叙事填空。
- 一篇 `已实现` 文档可以包含 `已知缺口` 或 `规划改造`，前提是边界清楚，且主要现状已经完成核对。

## 4. 事实引用

引用代码事实时，优先链接或写出仓库内的精确路径：

```text
internal/apiserver/application/authn
api/grpc/iam/authn/v2/authn.proto
pkg/sdk/auth/client
```

不要写不存在的候选路径，也不要把多个目录压缩成类似 `a/b/c/d` 的伪路径。路径变更时，在同一提交中更新对应文档。

机器契约的职责：

- REST path、schema、status code：以 `api/rest/` 为准；
- gRPC service、RPC、message：以 `api/grpc/` 中的 proto 为准；
- Go SDK public API：以 `pkg/sdk/` 为准；
- 分层依赖：以 `internal/pkg/architecture/` 的测试为准。

文档解释契约语义，不复制大段可从机器契约生成的字段表。

## 5. 业务模块设计文档

业务模块文档不是接口清单，也不是代码目录的文字转写。它必须同时承担三类职责：

1. **解释设计**：模块为什么存在，解决什么问题，受哪些业务和技术约束影响；
2. **描述实现**：当前代码、契约、存储和运行时如何落实该设计；
3. **记录决策**：考虑过哪些替代方案，为什么选择当前方案，接受了哪些代价。

代码事实准确只是底线。只有事实而没有问题、约束和取舍的文档，只能作为实现手册，不能替代模块设计文档。

### 5.1 模块文档必须回答的问题

除纯 README 和纯代码索引外，每篇领域模型、关键链路或模块边界文档至少回答以下问题：

1. 要解决什么问题？
2. 设计目标和现实约束是什么？
3. 当前选择了什么方案？
4. 为什么采用这个方案？
5. 有哪些有意义的替代方案，为什么没有采用？
6. 当前代码、契约和存储如何实现这个方案？
7. 当前实现与设计目标之间还有什么缺口？

替代方案必须与真实问题相关。不要为了凑结构虚构从未存在、也没有分析价值的候选方案。

### 5.2 推荐结构

长篇模块设计文档优先使用以下顺序：

```text
本文回答
30 秒结论

问题背景
设计目标与约束
当前设计
核心设计决策
替代方案与取舍
当前实现映射
已知缺口与规划改造
代码证据与验证
```

这不是要求每篇文档机械复制同一套标题，而是要求阅读顺序完整：先知道问题和结论，再理解设计推理，最后核对实现和证据。

主图或主表放在结论之后。图只在能澄清模型关系、状态变化、多层调用或跨模块依赖时使用。

### 5.3 设计决策卡

一个文档包含多个重要选择时，使用简短的“设计决策卡”，避免把问题、方案和实现混成一段长文：

```text
决策：<选择了什么>

解决的问题：
<这个决策具体解决什么问题>

主要约束：
<业务基数、兼容性、一致性、安全性、性能或组织边界>

选择：
<当前采用的模型、协议、事务或依赖方向>

替代方案：
1. <方案 A>
2. <方案 B>

未采用原因：
<为什么这些方案不满足约束，或代价更高>

代价与后果：
<当前选择增加了什么复杂度，限制了什么能力，留下什么风险>

当前实现：
<domain/application/transport/infra/contract/test 证据入口>
```

设计决策卡不等于 ADR 编号体系。只有需要独立审批、长期追踪或跨多个模块生效的决策，才另建专题设计或 ADR 类文档。

### 5.4 模块目录内的文档职责

模块目录至少提供一个 `README.md`。当模块确有独立设计内容时，可拆出总览、领域模型、关键链路、模块边界和代码索引，但每篇必须有唯一职责：

| 文档类型 | 主要职责 | 不应该承担 |
| --- | --- | --- |
| `README.md` | 阅读导航、文档地图、事实源、按任务入口 | 完整重复模型和关键链路设计 |
| 模块总览 | 模块为什么存在、总体目标、宏观边界和关键决策 | 枚举所有字段、文件和接口 |
| 领域模型 | 建模问题、对象职责、聚合/关系、不变量和模型替代方案 | 重复完整 transport 链路 |
| 关键链路 | 用例目标、时序、事务、失败边界、幂等和替代流程 | 重复模块整体定位 |
| 模块边界 | 上下文映射、依赖方向、同步/异步协作和边界取舍 | 重复各模型全部字段 |
| 代码索引 | 设计到代码/契约/测试的映射和修改影响 | 再写一遍设计正文 |

不是每个模块都必须拥有同样数量的文件。只有内容有独立维护价值时才拆分，不为了目录对称制造空文档。

### 5.5 设计理由的证据

设计理由的证据可以来自：

- 当前领域模型、应用编排、约束和测试共同体现的稳定选择；
- 仍有效的专题设计、ADR、评审记录或提交历史；
- 明确的业务规则和数据基数；
- 当前契约兼容性、运行环境或存储能力形成的现实约束。

证据不足时要区分：

```text
代码事实：当前实现确实如此；
可推导理由：从实现和约束看，这样设计可能是为了……；
已确认决策：团队或有效设计记录明确选择了该方案。
```

“代码长这样”不能自动证明“当初就是为了这个理由”。可推导理由使用 `待确认决策`，确认后再升级为 `设计决策`。

### 5.6 去重与压缩规则

文档重构不以目标行数、压缩比例或文件数量为完成标准。压缩只用于消除重复和无效表达，不得删除设计推理。

可以删除或回链：

- 同一结论在多篇文档中的完整重复解释；
- 没有项目约束或决策价值的通用架构套话；
- “若已实现”“具体以代码为准”等未完成核对的占位表达；
- 每篇文档机械复制的 Verify 命令；
- OpenAPI、proto 或 SDK 已能生成的大段字段清单。

必须保留：

- 问题背景和设计目标；
- 业务、兼容性、一致性、安全性和运行约束；
- 核心设计决策及其理由；
- 有意义的替代方案和未采用原因；
- 当前选择的代价、副作用和能力限制；
- 失败边界、事务、幂等和一致性语义；
- 当前实现缺口、规划改造和验收条件；
- 能把设计回链到代码、契约、存储和测试的证据。

去重原则是“一处讲透，其他回链”。被保留为 canonical 的章节必须完整，不能只剩结论。

### 5.7 模块文档完成标准

模块文档完成时，应同时满足：

- 新读者能说明模块解决的问题，而不只是列出类型名；
- 维护者能说明当前方案为什么成立，以及什么条件变化会导致重新决策；
- 评审者能看到替代方案、取舍和已知缺口；
- 开发者能从设计回链到真实代码、契约、存储和测试；
- 同一设计理由只有一个 canonical 解释位置；
- 没有把推测、规划或理想架构写成当前事实。

## 6. 当前事实与设计方案

设计文档可以同时记录设计决策、当前实现和未来方案，但必须分层：

```text
问题背景：为什么需要解决这个问题；
设计目标与约束：方案必须满足什么；
设计决策：最终选择了什么，为什么；
当前实现：代码今天如何落实该决策；
已知缺口：实现与目标之间还差什么；
规划改造：准备改变什么；
验收条件：用什么代码、契约或测试证明完成。
```

禁止把目标架构图、建议错误码、候选 RPC、候选 SDK 或理想健康检查写成当前能力。

设计决策与当前实现不一致时，不要偷偷改写设计理由来迁就代码。应明确记录：

- 设计已经改变，需要形成新的决策；
- 实现发生偏移，需要修复代码；
- 旧决策已经失效，应移入历史背景或 archive；
- 证据不足，暂时标为 `待确认决策`。

## 7. 归档规则

文档不再维护但仍有历史价值时，移动到 `_archive/`；不要复制一份继续留在 active docs。

归档时：

1. 在文件开头标明归档日期和原因；
2. 从 active 入口移除链接；
3. 在 `_archive/README.md` 登记；
4. 确认 active docs 不依赖归档结论。

归档索引受链接检查保护，归档正文不要求持续追随当前代码。

## 8. 修改同步范围

| 变更 | 至少同步检查 |
| --- | --- |
| REST 路由或 schema | OpenAPI、handler/DTO、SDK、契约文档和测试 |
| gRPC service 或 message | proto、生成物、service/mapper、SDK、契约文档和测试 |
| public SDK API | SDK README、迁移说明、compile test |
| 模块边界或调用链 | 模块 README、专题设计、架构测试 |
| 配置或运行模式 | 配置样例、运行时文档、部署/健康检查说明 |
| 文件或目录重命名 | 入口、跨文档链接、代码路径和 Verify 命令 |

## 9. 最小验证

所有文档修改至少执行：

```bash
make docs-hygiene
```

这个命令检查：

- Markdown 本地链接；
- 反引号中的可验证仓库路径；
- 已退役路径、路由和术语是否回流；
- 归档索引是否指向真实材料。

涉及业务或契约时，再执行对应验证：

```bash
make api-validate
make proto-gen
go test ./internal/pkg/architecture
go test ./pkg/sdk/...
go test ./internal/apiserver/<相关模块>/...
```

不要为了让命令通过而写不存在的测试路径。若本机缺少某个外部工具，应明确记录未执行项。

## 10. 提交前检查

- 文档入口能找到新增或移动的文件；
- 状态标签符合真实证据，不用 `设计目标` 包装已知设计稿；
- 当前事实和规划方案已经隔离；
- 模块设计文档说明了问题、目标、约束、方案、理由和实现映射；
- 重要选择记录了替代方案、未采用原因、代价与后果；
- 设计理由有证据，无法确认的理由已标为 `待确认决策`；
- 去重没有删除 canonical 章节中的设计推理；
- 代码路径、类型名、接口名和 Verify 命令真实存在；
- 没有重复复制 OpenAPI/proto/SDK 的机器事实；
- 没有为了形式对称新增低价值文档；
- `make docs-hygiene` 已通过。
