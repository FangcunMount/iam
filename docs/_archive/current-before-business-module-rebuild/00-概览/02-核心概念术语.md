# 02-核心概念术语

## 1. 本文定位

本文是 IAM 项目的核心术语表，用于统一文档、代码阅读和技术表达中的基本语言。

本文不展开每个模块的完整设计细节，只回答三个问题：

```text

```

详细设计请进入对应模块文档：

```text

```

## 2. IAM 总体术语

IAM（Identity and Access Management）是身份与访问管理系统。

在本项目中，IAM 面向业务系统提供统一的身份、认证、授权和接入能力。

可以用一句话概括：

> Identity 负责“用户与档案关系”，AuthN 负责“如何证明用户身份”，AuthZ 负责“用户能否访问资源”，IDP 负责“第三方身份源接入”，Suggest 负责“Profile 联想搜索辅助读模型”。

核心协作主线如下：

```text
外部请求
  -> AuthN 通过 LoginIdentity / Credential / Challenge 完成认证
  -> AuthN 产出 Principal / Session / Token
  -> Principal.UserID 指向 Identity.User
  -> Identity 维护 User / Profile / ProfileLink 身份事实
  -> AuthZ 将 User 映射为 Subject 并执行资源访问判定
  -> REST / gRPC / SDK 对外提供接入能力
```

## 3. 系统级核心术语

| 术语      | 所属范围       | 含义                                               | 边界说明                                                                                |
| --------- | -------------- | -------------------------------------------------- | --------------------------------------------------------------------------------------- |
| IAM       | 系统整体       | Identity and Access Management，身份与访问管理系统 | 统一提供身份、认证、授权、IDP、Suggest、REST/gRPC/SDK 接入能力                          |
| Identity  | 核心模块       | 用户身份与档案关系模块                             | 负责 User、Profile、ProfileLink；不负责登录认证和资源授权                               |
| AuthN     | 核心模块       | Authentication，认证模块                           | 负责证明调用者身份，产出 Principal、Session、Token                                      |
| AuthZ     | 核心模块       | Authorization，授权模块                            | 负责判断 Subject 是否可以对 Resource 执行 Action                                        |
| IDP       | 辅助模块       | Identity Provider，第三方身份源接入模块            | 负责外部身份源适配，不直接决定 IAM 内部登录态                                           |
| Suggest   | 辅助模块       | Profile 联想搜索辅助读模型                         | 用于 autocomplete 场景，不替代 Identity 或 AuthZ                                        |
| User      | 跨模块身份锚点 | IAM 内部稳定身份主体                               | Identity 管理 User；AuthN 的 Principal.UserID 指向 User；AuthZ 可将 User 映射为 Subject |
| Principal | AuthN 运行时   | 认证成功后的运行时主体表达                         | 不是 User 本身，而是一次认证结果                                                        |
| Subject   | AuthZ 运行时   | 授权判定中的主体引用                               | 可表达为 `user:<userID>`、`group:<groupID>`、`service:<serviceID>`                      |

## 4. AuthN 认证术语

AuthN 回答：

```text
你是谁？
你如何证明你是这个主体？
认证成功后系统如何表达你？
```

| 术语          | 含义                                                              | 关键边界                                                                  |
| ------------- | ----------------------------------------------------------------- | ------------------------------------------------------------------------- |
| LoginIdentity | User 绑定的登录身份，表示系统可以通过什么登录标识找到 User        | 本项目中不要恢复旧 Account 中心模型                                       |
| Credential    | 长期认证材料；当前实现为 `password` hash | 可重复校验，有生命周期；不同于一次性 Challenge；passkey/TOTP 等为扩展方向 |
| Challenge     | 短期认证挑战，例如短信验证码、OAuth state、重置密码 code          | 短期有效，通常有 TTL 和一次性消费语义                                     |
| Principal     | 认证成功后的运行时主体表达                                        | 通常包含 UserID、LoginIdentityID、AuthMethod、SessionID、claims context   |
| Session       | 服务端认证上下文                                                  | 支持注销、续期、撤销、在线 Verify、设备管理、风险控制                     |
| Access Token  | 短期访问凭证                                                      | 当前通常以 JWT/JWS 表达，适合放在 `Authorization: Bearer` 中传递          |
| Refresh Token | 用于换取新 Access Token 的续期凭证                                | 生命周期更长，必须服务端可控，不能作为资源访问凭证                        |
| JWT           | JSON Web Token，用于表达 claims                                   | 是 Token 表达格式，不等于 Principal                                       |
| JWS           | JSON Web Signature，用于签名保护 JWT claims                       | 保证 Token 未被篡改                                                       |
| JWK           | JSON Web Key，用于表达密钥                                        | 可表达公钥或私钥；私钥不能通过 JWKS 发布                                  |
| JWKS          | JSON Web Key Set，用于发布一组公钥                                | 资源服务可通过 `kid` 查找公钥并验签                                       |
| KeyRotation   | 签名密钥轮换机制                                                  | 常见状态为 active -> grace -> retired；属于安全基础设施，不是业务身份模型 |

## 5. Identity 身份术语

Identity 回答：

```text
系统内部这个人是谁？
这个人和哪些业务档案有关？
这些关系是否仍然有效？
```

| 术语           | 含义                                      | 关键边界                                                               |
| -------------- | ----------------------------------------- | ---------------------------------------------------------------------- |
| User           | IAM 内部稳定身份主体                      | 不是 Profile；不直接保存认证凭据和资源权限                             |
| Profile        | 业务身份资料、业务档案或被服务对象        | 可以表示本人资料、儿童档案、被测评者档案等；不是登录主体               |
| ProfileLink    | User 与 Profile 之间的身份关系事实        | 表达 self、guardian、parent、viewer、operator 等关系；不是 Permission  |
| RelationType   | User 与 Profile 的关系类型                | 描述身份关系，不直接表示资源权限                                       |
| LinkStatus     | ProfileLink 当前状态                      | 表达关系生命周期，例如 active、revoked、pending；不替代 AuthZ Decision |
| MyProfiles     | 当前认证用户视角下可见的 Profile 列表     | 是有上下文的查询能力，不是全局 Profile 查询                            |
| MyProfileLinks | 当前认证用户视角下可见的 ProfileLink 列表 | 强调当前用户视角和身份关系边界，不等于 Permission 列表                 |

## 6. AuthZ 授权术语

AuthZ 回答：

```text
谁在什么授权域内，能否对什么资源执行什么动作，并满足什么范围约束？
```

可以抽象为：

```text
Subject + Tenant + Resource + Action + Scope -> AuthorizationDecision
```

| 术语                  | 含义                                         | 关键边界                                                                        |
| --------------------- | -------------------------------------------- | ------------------------------------------------------------------------------- |
| Subject               | 授权主体                                     | 表示谁在请求访问资源，例如 user、group、service                                 |
| Tenant                | 授权域边界                                   | RoleBinding、Permission、PolicyVersion 等授权事实都在 Tenant 内理解             |
| Role                  | 权限聚合点                                   | Role 是一组 Permission 的命名集合，不等于 `user.role` 字段                      |
| Resource              | 受保护资源目录项                             | 约束可授权的动作和 scope 类型                                                   |
| ResourceKey           | 资源目录标识                                 | 当前采用 `<app>:<domain>:<type>:<name-or-pattern>` 四段结构                     |
| ResourcePattern       | 授权事实或请求中的资源匹配模式               | 与 ResourceKey 格式相近，但语义偏匹配                                           |
| Action                | 对资源执行的动作                             | 例如 read、create、update、delete、manage、check                                |
| ActionPattern         | 动作匹配模式                                 | 用于授权事实侧表达可匹配动作，例如 read、manage、\*                             |
| Scope                 | 权限作用范围                                 | ResourceKey 表达资源类型或资源族；Scope 表达对象范围或上下文范围                |
| Permission            | Role 对 Resource / Action / Scope 的能力声明 | 不直接授予给 User，而是挂在 Role 下                                             |
| RoleBinding           | Subject 在 Tenant 下持有 Role 的授权事实     | 内部 application/domain 统一使用 RoleBinding                                    |
| Assignment            | 对外 wire term                               | REST/proto/SDK 可使用 Assignment；内部不恢复 assignment 包                      |
| AuthorizationRequest  | 一次授权判定请求                             | 是领域层 Check 输入，不等同于 REST/gRPC DTO                                     |
| AuthorizationDecision | 授权判定结果                                 | 表达 allow/deny 及原因，不等同于 HTTP status code                               |
| Check                 | 权威实时授权判定                             | 用于 API 准入和资源操作前置校验                                                 |
| Snapshot              | 授权事实快照                                 | 可用于菜单展示、能力提示、SDK 缓存；不能替代权威 Check                          |
| PolicyChange          | 授权变更计划                                 | 授权写入不应只是 CRUD，应形成可提交的变更计划                                   |
| PolicyChangeCommitter | 授权变更统一提交器                           | 负责统一提交管理记录、runtime facts、PolicyVersion、Outbox Event、RuntimeReload |
| PolicyVersion         | Tenant 级授权事实版本                        | 用于缓存失效、runtime reload、跨实例传播和下游感知                              |
| PolicyLinter          | 授权事实治理工具                             | 只读诊断，不自动修复；修复应进入显式变更链路                                    |

## 7. IDP 外部身份源术语

IDP 回答：

```text
如何接入外部身份源？
如何把外部身份源结果交给 AuthN 继续完成 IAM 内部认证？
```

| 术语                       | 含义                                     | 关键边界                                                                    |
| -------------------------- | ---------------------------------------- | --------------------------------------------------------------------------- |
| IDP                        | Identity Provider，身份提供方            | 在本项目中主要指微信、小程序、公众号、企业微信、OAuth Provider 等外部身份源 |
| WeChat                     | 微信身份源                               | 外部身份源，不是 IAM 内部 User                                              |
| WeCom                      | 企业微信身份源                           | 外部身份源，不是 IAM 内部 User                                              |
| ProviderApp                | 第三方身份源应用配置                     | 例如 AppID、CorpID、应用配置等                                              |
| ProviderIdentity           | 外部身份源返回的身份结果                 | 例如 openid、unionid、corp_id + userid；不等于 User                         |
| ExternalCredential         | 外部身份源证明材料                       | 需要经 AuthN 映射为 LoginIdentity 后才进入 IAM 登录态                       |
| ProviderToken              | 调用外部身份源 API 使用的 provider token | 不等于 IAM Access Token                                                     |
| AppID / CorpID             | 外部身份源命名空间标识                   | 同一个 openid 在不同 AppID 下不能简单视为同一登录身份                       |
| AppSecret                  | 第三方应用密钥                           | 属于应用级密钥材料，不是 IAM 用户 Credential                                |
| session_key / access_token | 微信或企业微信协议材料                   | 外部 access_token 不等于 IAM Access Token                                   |

正确关系是：

```text
ProviderIdentity / ExternalCredential
  -> LoginIdentity
  -> User
  -> Principal / Session / Token
```

## 8. Suggest 联想搜索术语

Suggest 回答：

```text
当前操作员输入关键词时，如何快速返回他有权看到的 Profile 候选？
```

| 术语                  | 含义                       | 关键边界                                      |
| --------------------- | -------------------------- | --------------------------------------------- |
| Suggest               | Profile 联想搜索辅助读模型 | 服务 autocomplete，不是完整搜索系统           |
| ProfileSearchTerm     | Profile 可搜索词条         | 是读模型数据，不是 Profile 聚合本体           |
| ProfileAccessScope    | Profile 搜索访问范围       | 用于过滤候选结果，不等于 ProfileLink          |
| Suggest Runtime       | 联想搜索运行时索引         | 可使用 Trie / Hash 等结构；属于 infra runtime |
| Suggest Index Refresh | 索引刷新任务               | 负责从持久化事实刷新读模型索引                |
| mobile_mask           | 脱敏手机号展示字段         | 响应不应返回明文 mobile                       |

关键规则：

```text
Suggest 查询必须经过 ProfileAccessScope 过滤；
手机号形态关键词需要显式授权；
响应只返回 mobile_mask，不返回明文 mobile；
索引不可用时可以降级为空结果，但不能绕过权限直接查全局 MySQL。
```

## 9. 接入与契约术语

| 术语     | 含义                                                | 关键边界                                                               |
| -------- | --------------------------------------------------- | ---------------------------------------------------------------------- |
| REST API | 面向 Web、App、管理后台和普通 HTTP 客户端的接入方式 | REST 层负责路由、DTO、参数校验、响应映射；不写领域规则                 |
| gRPC API | 面向可信服务间调用的接入方式                        | 适合 Online Verify、AuthZ Check、Identity 查询等低延迟调用             |
| SDK      | IAM 的接入产品层                                    | 封装 REST/gRPC/JWKS/ServiceAuth/AuthZ Check 等接入复杂度，不成为业务层 |
| OpenAPI  | REST 契约事实源                                     | REST 路径、字段、schema、错误响应以 OpenAPI 和测试为准                 |
| Proto    | gRPC 契约事实源                                     | service、message、RPC 方法以 proto 和生成代码为准                      |
| DTO      | 协议层数据结构                                      | 用于 transport 层，不应泄露到 domain 作为领域对象                      |
| Mapper   | 协议模型与应用/领域模型之间的转换器                 | 用于隔离 wire model 和 domain model                                    |

## 10. 运行时与分层架构术语

| 术语                 | 含义                               | 关键边界                                                                                |
| -------------------- | ---------------------------------- | --------------------------------------------------------------------------------------- |
| process              | 生命周期编排层                     | 负责启动阶段、资源准备、后台任务、优雅关闭、健康诊断                                    |
| container            | 组合根                             | 负责装配 application service、repository adapter、token/cache/idp/casbin/outbox adapter |
| transport            | 协议适配层                         | 包括 REST handler、gRPC service、DTO/proto mapping、错误响应转换                        |
| application          | 用例编排层                         | 负责 command/query、事务边界、端口调用、结果组装                                        |
| domain               | 领域规则层                         | 负责 entity、value object、domain service、policy、不变量、领域错误                     |
| infra                | 基础设施适配层                     | 负责 MySQL、Redis、JWT、Casbin、IDP API、Outbox、SMS 等技术适配                         |
| port                 | application/domain 期望的能力接口  | 例如 TokenSigner、RoleRepository、DecisionEngine、IDPClient                             |
| adapter              | infra 对 port 的具体实现           | 例如 JWT adapter、MySQL repository、Casbin runtime adapter、WeChat adapter              |
| UoW                  | Unit of Work，事务工作单元         | 用于控制跨多个 repository/adapter 的一致性提交边界                                      |
| Transactional Outbox | 业务事实和事件记录同事务提交的模式 | 解决数据库写入与消息发布之间的一致性问题；下游需要幂等                                  |

## 11. 基础设施术语

| 术语                | 含义                        | 关键边界                                                                                                              |
| ------------------- | --------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| MySQL               | 主要管理事实持久化存储      | 可保存 User、LoginIdentity、Credential、Role、Resource、RoleBinding、PolicyVersion、IDP app config、Outbox records 等 |
| Redis               | 运行时状态和缓存设施        | 可用于 Challenge、Session、Refresh Token、缓存、限流、临时状态等                                                      |
| Casbin              | AuthZ runtime policy engine | 是 infra runtime engine，不是 AuthZ 领域模型                                                                          |
| Authorization Facts | 运行时授权事实              | 在 Casbin 中通常表现为 p fact、g fact；不是对外业务契约                                                               |
| RuntimeReload       | 运行时授权策略刷新          | 与 PolicyChange、PolicyVersion、Outbox Event、Casbin runtime adapter 协作                                             |
| KeyStore            | 签名密钥材料管理能力        | 管理私钥、公钥、kid、active/grace/retired 状态等                                                                      |
| JWKS Endpoint       | 公钥发布接口                | 只发布公钥，不发布私钥                                                                                                |
| Message Broker      | 消息投递基础设施            | 只有当前实现明确接入 MQ 时才作为部署事实描述；否则应只描述 Outbox table                                               |

## 12. 易混淆术语对照

| 容易混淆                          | 正确边界                                                                             |
| --------------------------------- | ------------------------------------------------------------------------------------ |
| User vs Principal                 | User 是 Identity 的稳定身份主体；Principal 是 AuthN 认证成功后的运行时主体表达       |
| User vs Subject                   | User 是身份事实；Subject 是 AuthZ 的授权主体引用                                     |
| Principal vs Subject              | Principal 来自认证结果；Subject 用于授权判定                                         |
| LoginIdentity vs Credential       | LoginIdentity 解决“通过什么标识找到 User”；Credential 解决“用什么长期材料证明控制权” |
| Credential vs Challenge           | Credential 是长期认证材料；Challenge 是短期、可过期、可消费的认证挑战                |
| Access Token vs Session           | Access Token 是短期访问凭证；Session 是服务端认证上下文                              |
| Access Token vs Refresh Token     | Access Token 用于访问；Refresh Token 用于续期                                        |
| JWT vs Principal                  | JWT 是 claims 的安全表达；Principal 是认证成功后的运行时主体                         |
| JWKS vs KeyStore                  | JWKS 发布公钥；KeyStore 管理签名密钥材料                                             |
| Profile vs User                   | User 是稳定身份主体；Profile 是业务身份资料或业务档案                                |
| ProfileLink vs Permission         | ProfileLink 是身份关系；Permission 是资源访问能力                                    |
| ProfileLink vs RoleBinding        | ProfileLink 连接 User 与 Profile；RoleBinding 连接 Subject 与 Role                   |
| Role vs Permission                | Role 是权限聚合点；Permission 是资源/动作/范围能力声明                               |
| RoleBinding vs Assignment         | RoleBinding 是内部领域术语；Assignment 是 REST/proto/SDK 对外 wire term              |
| ResourceKey vs ResourcePattern    | ResourceKey 偏资源目录标识；ResourcePattern 偏授权匹配表达                           |
| ResourceKey vs Scope              | ResourceKey 表达资源类型或资源族；Scope 表达对象范围                                 |
| Action vs ActionPattern           | Action 是请求侧具体动作；ActionPattern 是授权事实侧匹配表达                          |
| Check vs Snapshot                 | Check 是权威实时判定；Snapshot 是授权事实投影                                        |
| PolicyChange vs CRUD              | PolicyChange 是授权变更计划；CRUD 是简单数据操作模型                                 |
| Casbin vs AuthZ Domain            | Casbin 是 infra runtime engine；AuthZ Domain 是业务授权模型                          |
| IDP vs AuthN                      | IDP 提供外部身份源证明；AuthN 决定如何认证并签发 IAM 登录态                          |
| Suggest vs Identity               | Suggest 是 Profile 搜索读模型；Identity 才是身份事实源                               |
| ProfileAccessScope vs ProfileLink | ProfileAccessScope 是搜索过滤上下文；ProfileLink 是身份关系事实                      |
| container vs application          | container 负责装配；application 负责用例编排                                         |
| transport vs application          | transport 负责协议适配；application 负责业务用例                                     |
| infra vs domain                   | infra 负责技术适配；domain 负责领域不变量                                            |

## 13. 术语使用规则

| 规则                            | 说明                                                                                         |
| ------------------------------- | -------------------------------------------------------------------------------------------- |
| AuthN 不恢复 Account 中心模型   | 文档和架构图中优先使用 User、LoginIdentity、Credential、Challenge、Principal、Session、Token |
| AuthZ 内部使用 RoleBinding      | Assignment 只作为 REST/proto/SDK 对外 wire term                                              |
| 不把 ProfileLink 写成权限       | ProfileLink 是 Identity 关系事实；资源访问能力必须进入 AuthZ                                 |
| 不把 ResourceKey 当对象 ID 容器 | ResourceKey 表达资源类型或资源族；具体对象范围通过 Scope 表达                                |
| 不把 Casbin 语言污染领域语言    | p/g/sub/dom/obj/act 等术语应限制在 infra/casbin 边界内                                       |
| 不把 SDK 当业务层               | SDK 是接入产品层，封装协议调用，不定义 IAM 业务规则                                          |
| 不把 docs 当机器契约            | 字段、路径、RPC、SDK API 以 api/rest、api/grpc、pkg/sdk、configs、migrations 为准            |

## 14. 本文总结

IAM 的术语体系可以压缩成以下主线：

```text
AuthN 通过 LoginIdentity / Credential / Challenge 证明调用者身份，产出 Principal、Session、Token。
Identity 以 User 为稳定身份主体，维护 Profile 与 ProfileLink 身份事实。
AuthZ 将 User 映射为 Subject，通过 RoleBinding、Role、Permission、Resource、Action、Scope 完成授权判定。
IDP 提供外部身份源证明，但不直接决定 IAM 登录态。
Suggest 提供 Profile 联想搜索读模型，但不替代 Identity 或 AuthZ。
REST / gRPC / SDK 是接入形态，不是业务模型本身。
process / container / transport / application / domain / infra 分别承担生命周期、装配、协议、用例、领域和基础设施职责。
```

如果只记一句话：

> User 是身份锚点，Principal 是认证结果，Subject 是授权主体；LoginIdentity 找人，Credential / Challenge 证明控制权，ProfileLink 表达身份关系，Permission 表达资源访问能力。
