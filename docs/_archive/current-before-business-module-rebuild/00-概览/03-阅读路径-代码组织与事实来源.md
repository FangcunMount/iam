# 03-阅读路径-代码组织与事实来源

## 1. 本文定位

本文是 IAM 项目的阅读导航与事实源说明。

它回答三个问题：

```text
不同读者应该按什么顺序阅读文档？
想理解某条链路时应该进入哪些代码目录？
当文档、源码、契约、测试发生冲突时，应该相信谁？
```

本文不展开每个模块的完整设计细节。

模块细节应进入：

```text
01-运行时/
02-认证AuthN/
03-授权AuthZ/
04-身份Identity/
05-接入与契约/
06-架构护栏/
07-宣讲/
08-Suggest/
```

本文的作用是提供路线图。

---

## 2. 阅读 IAM 的基本原则

阅读 IAM 时，不建议从数据库表或接口列表开始。

更合适的顺序是：

```text
先看系统边界
再看运行时装配
再看核心模块模型
再看用例链路
再看接口契约
最后看 infra 和测试护栏
```

原因是：

```text
IAM 不是若干 CRUD 接口的集合；
它是围绕身份、认证、授权、身份关系和接入契约组织起来的系统；
如果先看表和接口，很容易把 AuthN、AuthZ、Identity、IDP 的职责混在一起。
```

推荐的全局阅读主线是：

```text
00-概览
  -> 01-运行时
  -> 02-认证AuthN
  -> 03-授权AuthZ
  -> 04-身份Identity
  -> 05-接入与契约
  -> 06-架构护栏
  -> 07-宣讲
  -> 08-Suggest
```


```text

```

## 4. 代码组织总览

IAM 主要代码组织如下：

```text
cmd/
└── apiserver/                       # 进程入口

internal/
├── apiserver/
│   ├── app.go                       # 应用启动入口
│   ├── process/                     # 生命周期编排
│   ├── container/                   # 组合根与能力装配
│   ├── transport/                   # REST/gRPC 协议适配
│   ├── application/                 # 用例编排
│   ├── domain/                      # 领域模型与领域规则
│   ├── infra/                       # 外部资源适配
│   └── options/                     # 配置选项
│
└── pkg/
    ├── architecture/                # 架构测试
    ├── code/                        # 错误码
    ├── migration/                   # 数据库迁移
    └── middleware/                  # 通用中间件

api/
├── rest/                            # REST/OpenAPI 契约
└── grpc/                            # gRPC/proto 契约

pkg/
└── sdk/                             # Go SDK public API

configs/                             # 配置、Casbin model、运行配置
scripts/                             # 文档、契约、工程检查脚本
docs/                                # 当前解释层文档
```

阅读代码时要区分两种维度：

```text
layer 维度：process / container / transport / application / domain / infra
module 维度：authn / authz / identity / idp
```

例如：

```text
internal/apiserver/application/authz/policy
```

表示：

```text
application 层
AuthZ 模块
policy 写入用例
```

## 5. 分层阅读方法

### 5.1 从运行时进入

适合理解服务如何启动：

```text
cmd/apiserver
  -> internal/apiserver/app.go
  -> internal/apiserver/process
  -> internal/apiserver/container
  -> internal/apiserver/transport/rest 或 transport/grpc
```

这种读法适合回答：

```text
服务如何启动？
依赖如何装配？
REST/gRPC 在哪里注册？
后台任务在哪里启动？
优雅关闭如何处理？
```

---

### 5.2 从接口进入

适合理解一个 API 请求如何执行：

```text
api/rest 或 api/grpc
  -> internal/apiserver/transport/rest 或 transport/grpc
  -> internal/apiserver/application/<module>/<usecase>
  -> internal/apiserver/domain/<module>
  -> internal/apiserver/infra/<adapter>
```

这种读法适合回答：

```text
一个请求从协议入口到业务用例如何流动？
DTO 如何转换为 command/query？
application 如何调用 domain 和 repository？
错误如何映射成协议响应？
```

---

### 5.3 从领域模型进入

适合理解业务设计：

```text
docs/<module>/00-模型总览
  -> internal/apiserver/domain/<module>
  -> internal/apiserver/domain/<module>/<semantic-subpackage>
  -> domain tests
  -> application use case
```

这种读法适合回答：

```text
核心概念是什么？
不变量在哪里？
值对象如何校验？
哪些规则不能下沉到 transport/infra？
```

---

### 5.4 从测试进入

适合理解边界和已锁定行为：

```text
internal/pkg/architecture
internal/apiserver/domain/<module>/...
internal/apiserver/application/<module>/...
internal/apiserver/transport/rest/<module>/...
internal/apiserver/transport/grpc/service/<module>/...
pkg/sdk/...
```

这种读法适合回答：

```text
哪些行为已经被测试锁定？
哪些架构边界不能破坏？
哪些契约变更会影响接入方？
```

## 7. 事实源分类

IAM 项目中有多类事实源。

阅读时必须区分：

```text
源码事实源
机器契约事实源
测试事实源
配置与迁移事实源
文档事实源
历史归档材料
```

---

### 7.1 源码事实源

源码事实源用于判断实际运行行为。

主要包括：

```text
cmd/
internal/apiserver/
internal/pkg/
pkg/
```

其中：

| 目录 | 事实含义 |
| --- | --- |
| `cmd/apiserver` | 进程入口事实源 |
| `internal/apiserver/process` | 生命周期事实源 |
| `internal/apiserver/container` | 组合根和依赖装配事实源 |
| `internal/apiserver/transport` | REST/gRPC 协议适配事实源 |
| `internal/apiserver/application` | 用例编排事实源 |
| `internal/apiserver/domain` | 领域模型和不变量事实源 |
| `internal/apiserver/infra` | 外部资源适配事实源 |
| `pkg/sdk` | SDK public API 事实源 |

---

### 7.2 机器契约事实源

机器契约事实源用于判断外部接入兼容性。

主要包括：

```text
api/rest
api/grpc
pkg/sdk
```

规则：

```text
REST 路径、字段、schema、错误响应以 OpenAPI 为准。
gRPC service、message、RPC 以 proto 为准。
SDK public API 以 pkg/sdk 为准。
```

`docs/` 不应该复制机器契约的全部字段清单。

`docs/` 应该解释：

```text
为什么这样设计接口；
什么时候用 REST/gRPC/SDK；
字段背后的业务语义是什么；
契约变化会影响哪些接入方。
```

---

### 7.3 测试事实源

测试事实源用于判断哪些行为和边界已经被锁定。

主要包括：

```text
internal/pkg/architecture
internal/apiserver/domain/**/**_test.go
internal/apiserver/application/**/**_test.go
internal/apiserver/transport/rest/**/**_test.go
internal/apiserver/transport/grpc/**/**_test.go
pkg/sdk/**/**_test.go
```

测试比文档更接近代码事实。

如果文档说某个边界存在，但测试没有覆盖，应考虑补测试。

---

### 7.4 配置与迁移事实源

配置和迁移用于判断运行参数、数据库结构、Casbin 模型等事实。

主要包括：

```text
configs
configs/casbin_model.conf
internal/pkg/migration/migrations
```

规则：

```text
表结构以 migration 为准。
Casbin matcher 以 casbin_model.conf 为准。
运行默认值以 configs 和 options 为准。
```

---

### 7.5 文档事实源

当前 active docs 是解释层事实源。

范围是：

```text
docs/00-概览
docs/01-运行时
docs/02-认证AuthN
docs/03-授权AuthZ
docs/04-身份Identity
docs/05-接入与契约
docs/06-架构护栏
docs/07-宣讲
docs/08-Suggest
```

文档负责解释：

```text
系统边界
设计取舍
模块关系
源码阅读路径
事实源索引
架构护栏
对外讲法
```

文档不替代源码、契约、测试、migration。

---

### 7.6 历史归档材料

`docs/_archive` 是历史材料。

它只能用于：

```text
追溯设计演进
查看旧方案
理解为什么废弃某些结构
```

它不能作为当前事实源。

不要从 `_archive` 复制当前架构描述。

---

## 8. 事实源优先级

当事实冲突时，按以下优先级判断：

```text
1. 源码与运行时行为
2. 机器契约、配置、migration
3. 测试与架构护栏
4. 当前 active docs
5. _archive 历史材料
```

表格版：

| 优先级 | 事实源 | 用途 |
| --- | --- | --- |
| 1 | 源码与运行时行为 | 判断系统实际如何运行 |
| 2 | REST/gRPC/SDK 契约、配置、migration | 判断外部接入、运行配置、数据库和 Casbin 模型 |
| 3 | 测试与架构护栏 | 判断哪些行为和边界已被锁定 |
| 4 | 当前 active docs | 解释设计、边界、路径和取舍 |
| 5 | `_archive` | 历史追溯，不作为当前事实源 |

例如：

```text
如果 docs 说接口字段是 A，但 OpenAPI/proto 是 B，应以 OpenAPI/proto 为准，并修正文档。
如果 docs 说 AuthZ 内部使用 assignment，但源码已使用 rolebinding，应以源码为准，并修正文档。
如果 docs 说 ResourceKey 是三段，但 domain/authz/resource/key.go 已要求四段，应以源码为准，并修正文档。
如果 _archive 说用户中心包含 child/guardian，但当前 Identity 已使用 Profile/ProfileLink，应以当前 Identity 文档和源码为准。
```

## 11. 常见误读路径

### 11.1 从数据库表开始读

问题：

```text
容易把数据结构当作领域模型。
```

例如：

```text
看到 casbin_rule，就以为 AuthZ = Casbin CRUD；
看到 users，就以为 Identity = 用户资料表；
看到 credentials，就以为 AuthN = Account。
```

更好的路径：

```text
先读模型文档，再看 domain，再看 repository 和 migration。
```

---

### 11.2 从 REST handler 开始读

问题：

```text
容易把协议 DTO 当作业务模型。
```

更好的路径：

```text
REST handler
  -> application command/query
  -> domain model
  -> infra adapter
```

不要停留在 DTO 层理解业务。

---

### 11.3 从 Casbin 开始读 AuthZ

问题：

```text
容易把 p/g/sub/dom/obj/act 当成业务语言。
```

更好的路径：

```text
AuthZ 模型总览
  -> Role / Resource / Permission / RoleBinding
  -> Check / Snapshot
  -> Casbin runtime 映射
```

Casbin 是 runtime engine，不是领域模型。

---

### 11.4 从旧文档或 _archive 开始读

问题：

```text
容易读到已退役的业务域、接口目录和旧术语。
```

更好的路径：

```text
只把 _archive 当历史材料；
当前事实从 docs/00 到 docs/08 active docs 开始；
最终以源码、契约、测试为准。
```

## 13. 本文总结

阅读 IAM 的关键不是“从哪个文件随便开始”，而是按事实层级和模块边界阅读：

```text
先系统地图，后模块模型；
先运行时装配，后请求链路；
先 domain/application，后 infra 细节；
先机器契约，后接入解释；
先 active docs，后 _archive 历史材料。
```

如果只记一条规则：

> 读 IAM 时，先按 AuthN/AuthZ/Identity/IDP 分清业务责任，再按 transport/application/domain/infra 分清代码层次；出现冲突时，以源码、契约、测试为准，文档跟随事实源更新。
