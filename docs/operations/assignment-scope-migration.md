# Assignment Scope 迁移维护手册

> 状态：已实现 · 工具与契约已实现，生产 Scope 迁移及业务验收尚未完成。

当前工具用于显式配置旧后台角色分配的公司与门店范围。上线前仍需完成隔离 MySQL 专项、三端版本核对、生产逐人映射复核和回滚演练；本手册不是上线完成记录。

## 输入与边界

`iam-maintenance scope-migrate` 提供 `status`、`preflight`、`apply`、`verify`、`rollback`。沿用维护工具数据库环境变量：IAM 使用 `MYSQL_*`，QS 使用 `QS_MYSQL_*`。凭据从受限运行环境注入，不放在命令参数或报告里。

所有命令同时读取 IAM 和 QS。QS 读取有效和停用但未删除的 Operator，以及门店状态。只有唯一的有效公司 Operator 身份允许成为映射目标；不从医生关系推断范围。

映射文件示例仅说明结构，编号不能直接用于生产：

```json
{
  "version": 1,
  "mappings": [
    {
      "assignment_id": "101",
      "subject_id": "201",
      "role_id": "301",
      "targets": [
        {"org_id": "1", "kind": "stores", "store_ids": ["401", "402"]}
      ]
    }
  ]
}
```

每条有效旧 QS 或平台管理员分配必须有明确目标；`all_stores` 必须显式填写且 `store_ids` 为空数组。同一旧分配跨公司时逐公司列出目标，每个目标都必须有有效 Operator 身份。缺失映射不表示全公司。已经配置 Scope 的分配不会被覆盖，目标冲突必须人工核对。

首个规范排序后的公司目标保留原 Assignment ID，增加版本及更新审计；其他公司目标新增分配。角色、Grant、资源、业务关系及旧迁移清单不改写。没有门店归属的受试者不因 `all_stores` 获得可见性。

## 运行顺序

先创建权限为 `0700` 的受限报告目录。每次运行使用新的绝对报告路径；文件以 `0600` 创建且禁止覆盖。stdout 只输出结构化摘要，完整报告和错误保存在文件中。

```sh
iam-maintenance scope-migrate status --migration-id scope-cutover-001 --report /private/scope/status-001.json
iam-maintenance scope-migrate preflight --migration-id scope-cutover-001 --mapping /private/scope/mapping.json --report /private/scope/preflight-001.json
```

审核报告中的完整映射及指纹。维护窗口暂停 IAM 授权写入和 QS 运营身份、门店配置写入，并保持受影响后台业务维护。重新预演，再使用最新审核指纹：

```sh
iam-maintenance scope-migrate apply --migration-id scope-cutover-001 --mapping /private/scope/mapping.json --actor-id REVIEWED_IAM_USER_ID --fingerprint REVIEWED_FINGERPRINT --writes-stopped --report /private/scope/apply-001.json
iam-maintenance scope-migrate verify --migration-id scope-cutover-001 --report /private/scope/verify-001.json
```

Apply 要求先安装迁移 000036、000037 及有效事件目录，使用现有事务 Outbox。数据库间不构成原子事务；工具前后复核不能替代暂停写入。

| 状态 | 含义与后续动作 |
|---|---|
| pending | 需要完整映射和预演 |
| applied_unchanged | 原迁移已完成且当前指纹一致；Apply 重跑不再写入 |
| applied_drifted | 历史完成，当前事实变化；只核对差异，不自动覆盖 |
| rolled_back | 已完成补偿；不复用原标识重新迁移 |
| invalid | 归档、转换关系或数据读取无效；停止 |

`status` 成功分类不等于业务验收通过；`verify` 只接受 `applied_unchanged`。检查命令退出码及报告，不用正则提取日志来决定自动迁移。请求结果不明时先查询状态，不重新分配角色。

## 回滚与验收

在维护窗口协调 IAM、QS、运营端版本与数据边界，使用原预演指纹执行 `rollback`（参数同 Apply，省略 `--mapping`）。回滚恢复原范围，保留审计并软删除本次新增分配；策略版本和分配版本递增。后续授权或 QS 配置变化阻止自动回滚。新增清单表保留原 before/after/input/plan 和独立回滚证据，不能通过 schema down 丢弃审计。

恢复访问前必须另外验证普通角色的正反业务场景、转店历史访问权交接、医生及监护人独立入口、策略与 Outbox/缓存/投影收敛。数据库校验和本地测试不能代替这些证据。

### 逐人目标权限汇总

预演的 `effective_permissions` 按用户、公司、当前 QS 资源目录及具体动作汇总目标范围，同时保留贡献该权限的 AssignmentID 和 GrantID。相同动作的门店范围取并集；不同动作和公司分别计算。`all_stores` 保留其动态含义，不转换成当前门店 ID 快照。已有 Scope 分配与本次拟迁移分配共同参与汇总。

该汇总仅展开当前有效目录。通配授权对未来新增资源的覆盖仍以原 Grant 为准。报告不将旧体系的数据可见范围推断为全公司，也不替代逐用户真实记录访问对比；未配置受试者、业务状态限制和独立自服务规则须在 QS 验收中单独核对。

## 三端发布与验收清单

Scope 发布必须将代码检查、授权事实、运行版本和业务验收分别记录。下列步骤都完成后才能认定本轮上线完成；本地测试通过不能自动关闭生产项。

| 顺序 | 交付与检查 | 放行证据 |
|---|---|---|
| 1 | 确认每条存量分配的公司和范围，核对有效 Operator 与门店；异常身份单独处理 | 受限映射文件、逐人确认及可执行预演，无未解释问题 |
| 2 | 用生产事实副本在隔离 MySQL 执行迁移、重跑、校验、补偿回滚 | 原始副本校验和、Apply/Verify/Rollback 报告；策略版本递增，既有授权未被覆盖 |
| 3 | 发布包含 Scope 契约的 IAM SDK，更新 QS 的正式版本依赖 | 已发布标签可拉取，QS 无本地 replace/GOWORK 依赖，三端 CI 成功 |
| 4 | 准备协调版本、兼容结构迁移和恢复包，进入后台维护窗口并暂停授权及相关配置写入 | 备份、旧/新二进制版本、消费者清单、维护生效证据 |
| 5 | 安装 IAM 000036/000037，重新读取两端事实、复核指纹并执行一次正式 Apply | 最新预演与清单一致；Verify 为 applied_unchanged；迁移写入及 Outbox 原子完成 |
| 6 | 切换支持 Scope 的 IAM、QS 所有实例和运营端，保持后台维护 | 实际运行 SHA、数据库版本/dirty、SDK 版本及范围契约版本一致 |
| 7 | 核对逐用户变化和真实业务正反场景，确认策略、Outbox、缓存及投影收敛 | 下表完整证据；没有未解释的权限扩大或业务拒绝 |
| 8 | 恢复后台访问，归档发布与验收记录 | 放行记录、告警检查和受限证据位置 |

构建时的本地工作区替换只用于开发验证，不能成为发布依赖。新版 IAM 数据库 `status` 门禁接受 `37/clean`，要求 Scope 清单表存在；该结果证明结构符合预期，不证明任何人员已经分配范围。历史 RoleBinding 清理入口的旧版本限制不应作为新 Scope 状态判断。

### 业务验收矩阵

仅使用专用身份和专用业务数据执行变更型验收。每项记录身份、角色分配、公司/门店、动作、资源 ID、请求结果及策略版本；敏感标识和完整响应保存在受限目录，工作流日志仅留摘要。

| 场景 | 应观察的结果 |
|---|---|
| 普通运营员只管理 A 店 | 可访问 A 店授权动作的数据；拒绝 B 店、其他公司及未归属受试者的数据 |
| 单人多角色、不同动作范围 | 同一动作的范围取并集；另一动作的范围不会被借用，例如 A 店结果读取权不能因 B 店运营权限扩大到 B 店结果 |
| 同一动作被分配多家门店 | 列表、详情、统计和写入均在明确门店并集内工作 |
| 公司全部门店 | 包含本公司当前有效授权对象及后续门店；不跨公司，不将未归属受试者当作已归属 |
| 受试者 A 店转 B 店 | B 店可读取该受试者完整历史；A 店失去业务读取权，列表计数、缓存命中和聚合结果一致收敛 |
| 仅有运营执行权限 | 可执行允许的进度操作；无专业结果动作时，报告、评分和答卷仍拒绝，重试响应不夹带结果 |
| 更新范围发生并发冲突 | 旧策略版本写入被拒绝；重读后核对，不覆盖他人配置；不重复增加策略事件 |
| 无有效 Operator、旧会话或旧范围契约 | 后台数据拒绝访问；医生档案本身不产生运营身份或范围 |
| 医生、参与者、监护人的独立路径 | 原有身份和业务关系规则继续生效，不因后台范围变化获得额外访问，也不被错误套用 Operator 门槛 |
| 医生首次配置/真正调店 | 初配保留二维码；真实调店旧码永久失效，新码按原流程生成；不自动移动受试者 |

受试者转店前后的权限交接必须使用真实应用入口验证，仓储锁测试不能替代该项。28,220 位无有效医生关系的历史未决受试者按已确认决定暂缓处理，维持未归属；此数量是历史基线，执行时仍记录实际未归属数量和差异。

### 当前证据边界

本地已分别执行 Go 测试、lint/分层检查、隔离 MySQL 并发与迁移专项，以及生产授权事实子集的备份恢复。真实完整迁移链后的状态检查覆盖正常版本、缺少清单表、dirty 状态和可选历史审计表。具体日志及执行清单存放于维护人员的受限目录，不提交生产数据到代码库。

生产事实副本的结构升级不等于按审核映射完成授权迁移；测试夹具的回滚也不等于生产映射的回滚演练。人员范围、异常身份处置、正式 SDK 发布、远端 CI、部署及真实业务验收仍须逐项补证。文档中的历史生产版本不能替代切换时重新读取的版本。

### 回滚配套

Scope 回滚先暂停后台访问与授权/配置写入，再检查完整事实是否仍与本次清单一致。回滚授权事实时使用工具补偿并发布更高 PolicyVersion；保留清单和历史记录，不通过删表或回退版本号清除证据。存在后续变更时停止自动补偿。

IAM 授权事实、QS 数据范围执行和运营端入口必须协调恢复。不能在旧消费者尚未执行范围限制时直接开放后台，也不能单独恢复旧宽松读取行为。恢复访问前重做关键拒绝场景及策略收敛核对。医生调店造成的二维码永久失效不因 Scope 回滚而撤销。

## 新建门店登录身份的准备

`iam-maintenance account-provision preflight|apply --input <private.json> --report <new-private-report.json>` 复用 IAM 的 Signup 应用事务，只创建 User、用户名 LoginIdentity 和密码 Credential，不创建角色、Operator 或 Scope。Apply 另需 `--fingerprint <预演指纹>`。调用人须为当前有效的平台根管理员，事务中锁定策略版本行以保持授权检查稳定。

受限输入包含 `request_id`、`actor_id`、`username`、`name`、`reason`、`password`，密码由执行方随机生成并妥善保存。文件必须为私有普通文件；报告目录必须为 `0700`，报告以 `0600` 新建。报告与日志不包含密码或密码摘要，不将凭据放入命令参数。

同名登录身份仅在本次执行标识、非秘密输入指纹、用户状态及保留密码均匹配时报告 `historical_completed`。其他用户名冲突、后续改密或状态变化停止执行，不接管账号、不自动重置密码。原始审计操作人和执行标识保存在新身份中。该状态仅证明登录身份开通历史，不能代替 Operator、角色 Scope 或实际业务验收。

当前 QS 旧 OperationAccountService 适配器已停用，本次不恢复已删除的 AccountOnboarding RPC。账号开通后，按已确认映射独立建立 Operator 并配置角色范围；在范围配置完成前保持无后台权限。

## 维护窗口跨部署保留

IAM 发布会同步配置目录。为避免临时授权写入禁令被发布包覆盖，在目标机使用由 root 管理、权限为 `0700` 的 `/opt/iam/maintenance/authz-write-freeze` 目录，放置以下三个普通文件（`0600`）：

- `grpc_acl.yaml`：基于目标版本配置生成、已验证的维护 ACL，保留快照查询和必要的维护工具调用，禁止其他管理客户端赋权。
- `sha256`：上述 ACL 文件的 SHA-256 十六进制校验和。
- `release_sha`：本次部署的精确 `IMAGE_TAG`，通常为完整提交 SHA。

发布在同步配置前校验三者，并将维护 ACL 放入发布配置。目录不存在时沿用正常配置；目录存在但不完整、校验不符、版本不符或使用符号链接时，发布失败，不能静默回到正常授权写入状态。更换发布版本前必须重新核对维护 ACL 与目标版本的服务权限清单，再更新发布绑定。

这只是部署配置保留机制，不会自行暂停业务写入。进入窗口前仍须关闭后台 REST 写入、确认其他 gRPC 消费者及后台任务的写入边界，并使当前 IAM 实例加载维护 ACL；Nginx 暂停页面或暂停 CD 不能替代这些步骤。

切换验证通过后，将维护目录移入受限审计归档，显式恢复目标版本的正常 ACL 并重载服务；确认授权策略和消费者收敛后再开放后台。移走维护目录不会自动修改已经运行的 ACL，也不会回滚授权数据。
