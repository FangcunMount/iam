# 跨部署保留授权写入冻结

> 状态：已实现 · 2026-10-06 整理既有发布配置保留机制；此机制不自行冻结全部业务写入。

## 作用与边界

IAM 发布会同步配置目录。临时禁写 ACL 若只放在普通配置中，可能被下一次发布覆盖。本机制将维护 ACL 与目标发布 SHA、校验和一起保留，发布时严格核对，避免部署意外恢复 gRPC 授权写入。后台 REST、其他消费者/任务以及 QS 配置写入仍由操作方独立暂停。

## 私有目录和发布绑定

在目标机使用由 root 管理、权限为 `0700` 的 `/opt/iam/maintenance/authz-write-freeze` 目录，放置以下三个普通文件（`0600`）：

- `grpc_acl.yaml`：基于目标版本配置生成、已验证的维护 ACL，保留快照查询和必要的维护工具调用，禁止其他管理客户端赋权。
- `sha256`：上述 ACL 文件的 SHA-256 十六进制校验和。
- `release_sha`：本次部署的精确 `IMAGE_TAG`，通常为完整提交 SHA。

发布在同步配置前校验三者，并将维护 ACL 放入发布配置。目录不存在时沿用正常配置；目录存在但不完整、校验不符、版本不符或使用符号链接时，发布失败，不能静默回到正常授权写入状态。更换发布版本前必须重新核对维护 ACL 与目标版本的服务权限清单，再更新发布绑定。

部署账号需具有已有的 `test`、`rsync`、`chown` 提权权限。脚本仅将三个文件同步到发布包内的临时受限目录，交回部署账号后以普通权限读取、校验和复制，结束后清理临时目录；不要求允许 `sudo cat`、`sudo sha256sum` 或 `sudo cp`，也不扩大服务器权限。

这只是部署配置保留机制，不会自行暂停业务写入。进入窗口前仍须关闭后台 REST 写入、确认其他 gRPC 消费者及后台任务的写入边界，并使当前 IAM 实例加载维护 ACL；Nginx 暂停页面或暂停 CD 不能替代这些步骤。

切换验证通过后，将维护目录移入受限审计归档，显式恢复目标版本的正常 ACL 并重载服务；确认授权策略和消费者收敛后再开放后台。移走维护目录不会自动修改已经运行的 ACL，也不会回滚授权数据。

## 验证与协作

生效实例须加载维护 ACL，不能只检查静态文件。核对完整服务清单、快照/必要查询仍可用、管理写入被拒绝，以及新部署没有恢复禁写方法。运行证据与配置校验分开，writes-stopped 声明不能代替这些检查。

事实入口为 `scripts/cd/maintenance-acl.sh` 的严格核对，以及 `scripts/cd/remote-deploy.sh` 同步前调用。`maintenance_acl_test.go` 覆盖缺文件、校验失败、版本漂移和符号链接拒绝。迁移中还须遵循 [Scope 维护](assignment-scope-migration.md) 的两端事实冻结和 [AuthZ 发布验收](../02-业务模块/03-AuthZ/09-安全加固与发布验收.md) 的恢复边界。
